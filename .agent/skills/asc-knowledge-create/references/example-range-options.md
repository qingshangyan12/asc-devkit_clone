# examples 标注范围改进方案

本文收集三个候选方案，供后续选择，尚未实施。当前仍按
[源码标注契约](source-annotation-contract.md)执行“每源文件一个连续范围”的规则；
本文不改变现有契约、脚本或样例标签。

## 1. 问题与实际样例

当前用两行相同的 `//! [id1, id2, ...]`，包住一个源文件中所有重点 API 的共同范围。
遇到多个函数分别完成数据搬运、配置、计算和结果输出时，从首个调用到最后一个调用的连续范围
会包含大量中间代码，接近整个设备侧实现。不同 API 也会得到同一个展示范围。

以仓内原有的
[`mmad_mx.asc`](../../../../examples/02_simd_c_api/03_c_api/03_matrix_compute/mmad_mx/mmad_mx.asc)
为例，调研时标签位于第 70、245 行，内部共 174 行：

- 开始位置在 `copy_matrix_a_to_l1` 函数内部。
- 范围跨越数据搬运、补零、计算、结果搬出等多个函数。
- 结束位置在 `mmad_mx_custom` 的条件分支内部。
- 后面的 `compute_mmad_mx(...)`、结果搬出调用和部分同步操作仍在范围之外。

因此，连续范围大并不意味着展示了完整调用流程。改进时既要缩小阅读范围，也要保留必要上下文。

## 2. 方案对比

| 方案 | 标注方式 | 优点 | 代价 |
| --- | --- | --- | --- |
| 1. 按函数分组 | 每个相关函数使用一对标签，列出该函数涉及的重点 API 重载 ID | 沿用现有标签格式，函数边界清晰 | 重载 ID 可能重复；调用入口需要额外关联 |
| 2. 集中管理重载 ID，按片段引用 | 一处维护重载 ID 与片段的对应关系，代码中用简短片段名成对标注 | 保留集中管理，支持不连续片段和共享上下文 | 需要扩展标注格式、写入器和解析逻辑 |
| 3. 保留现有标签，检索时缩小范围 | 保留文件共同范围，工具按目标 API 提取函数及必要上下文 | 保留现有标注形式，减少标签维护 | 函数识别、调用关联和上下文选择更复杂 |

## 3. 方案 1：按函数分组

将“每源文件一个范围”改为“每个相关函数一个范围”。一对标签包住完整函数，
其中集中列出该函数涉及的重点 API 的具体重载 ID；不退回每个 API 调用各打一对标签的方式。
同一重载出现在多个函数时，可以对应多个范围。各范围不交叉、不嵌套。

在 `mmad_mx` 中：

- `compute_mmad_mx` 单独作为计算范围，保留三个场景以及第三个场景的两次计算。
- `copy_result_to_gm` 单独作为结果搬出范围，保留参数配置和实际拷贝。
- `mmad_mx_custom` 作为调用入口，展示数据准备、同步、计算和结果搬出的顺序。
- 共享的类型别名、维度常量通过附加上下文关联，避免只展示函数后无法理解参数类型。

需要调整生成器的分组和范围选择规则，并让索引保留同文件多个范围。
如果调用入口没有直接调用目标 API，还需要关联该入口与被调用的辅助函数，不能只靠直接调用匹配。

适合优先沿用现有格式、降低改造成本的情况。局限是同一个重载 ID 仍可能写在多个标签对中，
集中管理程度弱于方案 2。

## 4. 方案 2：集中管理重载 ID，按片段引用

将“哪些重载使用这个样例”和“展示哪几段代码”分开表达：

- 重载 ID 与片段的对应关系在一处维护，不在每个代码片段中重复长 ID 列表。
- 原有代码中只用简短片段名成对标注，每个片段具有完整的函数或逻辑块边界。
- 一个重载可以对应多个不连续片段；一个片段也可以被多个重载共享。
- 对片段记录用途和展示顺序，例如类型与配置、计算、结果搬出、调用流程。

集中声明可以放在源文件注释中，也可以使用独立的样例映射文件；具体格式留待选型后确定。
下面仅展示关联思路，不是当前解析器已支持的格式：

```text
asc_mmad_mx 的具体重载 ID
  → 类型与配置
  → 计算
  → 调用流程

asc_copy_l0c2gm 的具体重载 ID
  → 结果搬出
  → 调用流程
```

在 `mmad_mx` 中，可以划分四类片段：

| 片段 | 原有代码范围或内容 | 用途 |
| --- | --- | --- |
| 类型与配置 | `SCENARIO_NUM` 对应的 `AType`、`BType` 及必要维度常量 | 解释具体重载和参数来源 |
| 计算 | 完整的 `compute_mmad_mx` 函数 | 展示三种场景和累加用法 |
| 结果搬出 | 完整的 `copy_result_to_gm` 函数 | 展示配置与拷贝的配套使用 |
| 调用流程 | `mmad_mx_custom` 中的数据准备、同步、计算和输出流程 | 展示执行顺序与配套接口 |

问具体参数用法时，优先展示“计算”和必要配置；问配套接口时，再展开“调用流程”
及相关数据准备函数。各片段保持源文件原文，不拼接成伪造的可运行样例。

需要扩展声明格式、片段解析、标注写入和索引记录，并校验片段引用存在、边界配对、重载关联有效。
这最符合“重载 ID 集中管理，同时缩小展示范围”的需求，是本次调研的推荐方向，尚未选定实施。

## 5. 方案 3：保留现有标签，检索时缩小范围

保留现有文件级共同范围，将它作为 API 与样例的关联依据；代码展示范围由工具另行推导。
检索具体重载时定位对应调用，提取所在函数，并按问题补充配置、类型定义和调用入口。

在 `mmad_mx` 中，查询 `asc_mmad_mx` 时优先展示 `compute_mmad_mx`；
查询 `asc_copy_l0c2gm` 时优先展示 `copy_result_to_gm`；询问配套流程时展开 `mmad_mx_custom`。
由于当前标签没有覆盖完整调用入口，上下文查找需要允许读取同一源文件的范围外代码。

需要识别函数边界、条件分支、类型别名和调用关系，尤其要区分不同场景下的具体重载。
不能直接按固定行数截断，避免遗漏配置和同步。无法可靠提取时，应保留原范围或源文件位置，
明确自动提取的局限。

该方案适合希望维持标注方式、将展示精度交给工具的情况。它不解决标签本身跨度大的问题，
只是让查询结果不必展示整个标签范围。

## 6. 现有工具的适配点

调研时确认了以下行为：

- [example_snippet_markers.py](../scripts/example_snippet_markers.py) 按源文件汇总调用，
  取共同起止位置并合并旧标签，最终写入一个标签对。方案 1、2 都需要调整该规则。
- [examples_db.py](../../asc-search/scripts/derive/examples_db.py) 已能读取同文件内多个顺序排列、
  不嵌套的标签对，同一个重载 ID 可以对应多个范围；尚不支持方案 2 的片段引用关系。
- [build_index.py](../../asc-search/scripts/build_index.py) 当前按 `(path, file)` 对样例去重，
  同文件的多个范围会被后面的记录覆盖。采用多个片段时，需要保留范围及其重载关联，
  不能继续只按文件去重。

选定方案后再同步修订契约、生成器和消费端。所有方案都只对仓内已有样例增加或调整注释，
不创建替代 `.asc` 样例，也不修改原有代码逻辑。

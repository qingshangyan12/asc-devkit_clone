# C API 废弃文档迁移模式

本文总结仓库中 `asc_abs_sync` 和 `asc_set_atomic_add_int` 的文档整理方式。它描述的是文档信息架构，不代表已经完成源码废弃或最终删除。

## 两种迁移起点

| 起点 | 处理方式 | 示例形态 |
|---|---|---|
| 废弃接口已有独立文档 | 将文档移动到 `c_api/deprecated_interface/`，保持 `_deprecated.md` 后缀 | 原子操作类接口 |
| 废弃接口只是正常接口文档中的一个重载 | 从原文档删除该原型，新建独立的 `_deprecated.md` 文档 | 同步封装接口 |

## 导航迁移矩阵

迁移一个 C API 废弃文档时检查以下位置：

| 位置 | 动作 |
|---|---|
| `docs/zh/api/README.md` | 从正常分类删除入口，在“废弃接口”分类增加入口 |
| `docs/zh/api/SIMD-API/c_api/c_api.md` | 从正常 API 表删除，在废弃接口表增加 |
| 原分类目录页 | 删除旧条目 |
| `deprecated_interface/deprecated_interface.md` | 按功能领域增加条目 |
| `docs/zh/api/appendix/deprecated_interface.md` | 增加或修正迁移说明与链接 |
| 其他引用页面 | 将旧相对路径更新为新路径 |

不要只移动文件。漏改任何一个入口都会留下断链或重复分类。

## 单接口文档模板

~~~md
# <api>（废弃）

## 产品支持情况

<保持废弃前的真实支持矩阵>

## 功能说明

**该接口已废弃，请使用[<replacement>](<relative-link>)替代。**

<保留原接口行为说明；组合替代时说明调用顺序和语义差异。>

## 函数原型

```cpp
[[deprecated("NOTICE: <api> is deprecated. Please use <replacement> instead.")]]
<prototype>
```

## 参数说明

<保留完整参数表>

## 返回值说明

<保留真实返回值>

## 流水类型

<保留真实流水类型>

## 约束说明

<保留原约束并补充迁移约束>

## 调用示例

<优先展示替代写法；若保留旧调用，明确它仅用于兼容说明。>
~~~

文档中的 `[[deprecated]]` 必须与当前公开声明一致。若代码尚未添加属性，函数原型只展示真实声明，并在报告中指出“仅完成文档归档”。

## 组合替代

一个同步封装接口可能没有单一等价替代。例如旧接口同时完成计算和同步，新方案可能是：

```cpp
replacement_compute(...);
replacement_sync(...);
```

此时不要只写“使用计算接口替代”。同时说明同步点、流水依赖和性能调优责任，否则迁移后的行为可能不等价。

## 案例边界

这类目录迁移通常只改变文档：

- 不删除公开声明。
- 不删除架构实现。
- 不改变产品支持矩阵。
- 不自动产生编译告警。
- 不替代兼容性测试和删除版本策略。

因此评审结论应写成“废弃文档已集中归档”，而不是“接口已经废弃完成”或“接口已经删除”。

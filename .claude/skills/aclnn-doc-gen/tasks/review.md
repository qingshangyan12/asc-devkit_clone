# 一致性校验与修正任务

## 任务目标

对生成的文档进行一致性校验和修正，输出已审校底稿 `5_review.md`。
不新增未证实信息，只修正不一致和格式问题。

## 输入输出约定

### 输入

**阶段产出（按顺序读取）**：
1. 算子信息提取报告：`{算子目录}/outputs/{目标接口名}/1_extract.md`
2. 公式分析报告：`{算子目录}/outputs/{目标接口名}/2_formula.md`
3. 文档草稿：`{算子目录}/outputs/{目标接口名}/4_generate.md`

**参考资源**：
- references/common_terminology.yml — 完整术语规范
- references/terminology_dict.yml — 术语字典

### 输出

**review 产出**：
- 写入位置：`{算子目录}/outputs/{目标接口名}/5_review.md`
- 内容要求：输出修正后的完整文档底稿，不包含 `## 调用示例` 章节

## 校验规则

### 1. 参数说明表与函数原型一致性
- **【强制检查】函数原型开头文本**：`## 函数原型` 章节的第一行必须是固定的两段式接口说明文本：`每个算子分为[两段式接口](../../../docs/zh/context/两段式接口.md)，必须先调用"aclnn{OperatorName}GetWorkspaceSize"接口获取计算所需workspace大小以及包含了算子计算流程的执行器，再调用"aclnn{OperatorName}"接口执行计算。`。若发现被改写为"第一段接口：xxx""第二段接口：xxx"或其他变体，必须修正为固定文本。两个函数签名之间也不得插入额外的分隔说明文字
- **【强制检查】函数原型完整性**：`## 函数原型` 章节必须包含**两个**函数签名——`aclnn{OperatorName}GetWorkspaceSize` 和 `aclnn{OperatorName}`（或对应的 Inplace 变体）。若只有一个函数原型，必须从代码中补全另一个
- 第一段接口参数说明表中的参数名、参数类型、参数顺序必须与函数原型完全一致；第二段接口参数说明表中的参数名、参数顺序必须与函数原型完全一致，但"参数名"列只填写参数名本身，禁止附带参数类型
- 不得遗漏函数原型中的参数，不得新增函数原型中不存在的参数
- 若参数类型属于 C 原生类型或普通指针类型（如 `char*`、`bool`、`uint64_t`、`float`、`double`、`int64_t`、`int32_t`、`uint32_t`、`const char*` 等），则"数据类型"列必须为 `-` 或留空，不得填写 `FLOAT16`、`BFLOAT16`、`INT8` 等对象 dtype 描述
- 若参数为 `workspaceSize（uint64_t*）`，则该行必须固定为：输入/输出=`输出`，描述=`返回需要在Device侧申请的workspace大小。`，使用说明/数据类型/数据格式/维度(shape)/非连续Tensor 全部为 `-`
- 若参数为 `executor（aclOpExecutor**）`，则该行必须固定为：输入/输出=`输出`，描述=`返回op执行器，包含了算子计算流程。`，使用说明/数据类型/数据格式/维度(shape)/非连续Tensor 全部为 `-`

### 2. 参数说明表与功能说明一致性
- **【强制检查】公式块级格式**：所有 `$$` 必须单独占一行，公式内容在中间行。若发现 `$$` 和公式写在同一行（如 `$$<公式>$$`），必须拆成三行格式（`$$` / 公式内容 / `$$`）
- 功能说明中的计算公式、逐公式`说明：`、统一变量映射、局部变量解释必须与公式分析报告一致；若不一致，以公式分析报告为准修正
- 功能说明计算公式变量声明行中的每个符号，必须在参数说明表中有对应参数行
- 参数说明表"描述"列引用的公式变量，必须在计算公式中存在
- 非参数局部变量不得出现在参数说明表中
- 同一章节内，统一变量映射（`其中，$符号$ 表示参数名...`）只能保留一组；同一参数符号不得在多个公式后重复映射
- 同一章节内，同名局部变量/中间变量（如 `A`、`\tilde{S}`、`\hat{X}_{cq}`）只能解释一次；若在多个公式后重复出现，必须合并到整组公式末尾统一保留
- 每条公式后的 `说明：` 必须保留，但其内容应突出功能语义与作用，不得写成底层计算实现流程，也不得重复抄写变量定义
- 若公式分析报告已采用"步骤公式"结构，最终文档必须保持相同的步骤拆分与顺序，禁止合并成单一大公式块，也禁止擅自新增或删除步骤
- 若公式分析报告判定为简单算子并只给出 1 条公式，最终文档允许保留单条公式结构；若公式分析报告已采用步骤公式结构，则必须保持步骤化结构
- 若只有 1 条公式，前面必须保留总引导语；若有多条公式，则每条步骤公式前必须保留一句介绍语。若出现多个公式块连续堆叠且中间没有介绍语，必须补回与公式分析报告一致的介绍语

### 3. 返回值表与参数说明表一致性
- 返回值表中的拦截场景必须与参数说明表"使用说明"列一一对应
- 参数说明表"使用说明"列未出现的约束，返回值表不得出现
- **【强制检查】返回值章节严禁出现任何芯片/产品差异内容**：返回值表不区分芯片，不按芯片拆分行；若发现返回值表或返回值描述中包含"仅xxx产品""xxx产品不支持"或按产品区分的描述，必须移除产品相关内容，保留通用描述；芯片差异约束只能出现在约束说明章节
- **【强制检查】161001 固定话术**：当错误码为 `161001` 时，对应描述只能写成 `传入的xx参数是空指针`；其中 `xx` 必须是当前算子的真实参数名。若出现"为空""未传入""空值不合法"等其他说法，必须修正为固定句式
- **【强制检查】161002 固定话术**：当错误码为 `161002` 时，对应描述只能写成以下三种形式之一：`xx参数的xx属性不在支持的范围内`、`xx参数的xx属性不满足上述要求`、`xx参数的取值或取值范围不满足上述要求`
- **【强制检查】161002 参数名替换**：`161002` 三种固定句式中的第一个 `xx` 必须替换为当前算子的真实参数名，禁止保留字面量 `xx`
- **【强制检查】161002 属性范围**：若 `161002` 描述使用"xx属性"句式，属性名只能是字面量 `dtype`、`format`、`shape` 之一；不得写成"数据类型""格式""维度"等同义改写。若是参数自身取值或取值范围校验，必须改写为 `xx参数的取值或取值范围不满足上述要求`
- **【强制检查】同类行合并**：同一错误码下，句式相同、仅参数名不同的多行必须合并为一行，用顿号连接参数名，最后一个参数前用"或"。例如 `161001` 的多个空指针行合并为 `传入的a、b或c参数是空指针。`；`161002` 的多个 dtype 行合并为 `a、b或c参数的dtype属性不在支持的范围内。`。合并后不同句式的行仍然分行（dtype 一行、format 一行、shape 一行、取值范围一行）

### 4. 约束说明与参数说明表一致性
- 若提取报告中某参数存在 `broadcast关系` 结论，则最终文档该参数的"使用说明"列必须保留对应的 broadcast 约束，禁止缺失、弱化或改写成泛泛的 shape 描述
- 参数说明表中已写的**纯单参数取值范围约束**（仅涉及一个参数自身的 dtype/取值枚举/范围），约束说明不重复；但涉及两个及以上参数的关联约束（如"A 必须与 B 相同""A 的 head 数必须能被 B 的 head 数整除""A 与 B 必须同时存在"等）、跨场景组合条件约束、以及全局行为约束（如推理/训练场景限制）必须保留在约束说明公共约束区域，即使参数说明表使用说明列中有部分提及
- 参数说明表中 dtype/format/shape/非连续必须是并集结果
- 若提取报告明确表明某参数只支持空指针、或该参数仅在空指针/省略场景下生效，则最终参数说明表中该参数只允许保留"输入/输出""描述""使用说明"三列的有效内容；"数据类型""数据格式""维度(shape)""非连续Tensor"必须全部为 `-`
- **【强制检查】参数说明表严禁出现任何芯片/产品差异内容**：若发现参数说明表的"数据类型""数据格式""shape""非连续Tensor""描述""使用说明"列中包含"仅xxx产品支持""xxx产品不支持"或按产品区分的描述，必须将差异部分移除，表中只保留所有产品的并集结果，差异描述移至约束说明章节按产品分组呈现
- 参数的 dtype/format/shape/非连续/空Tensor 等维度需与提取报告中对应参数的结论一致，若冲突以提取报告为准修正；若提取报告中的空Tensor结论为 `<span style="color:#dc2626;">【需用户补齐】</span>`，最终文档必须保留该标记，禁止改写成"支持"或"不支持"
- 若返回值/shape 说明中涉及 broadcast 后的结果 shape、后两维 shape 或 batch 维关系，则必须与参数"使用说明"中的 broadcast 约束保持一致
- 若提取报告已根据部分证据提炼出某参数的维度值/范围（如 `4`、`2-4`、`1, 3, 4`），最终文档必须直接保留该维度结果，不得改写成"存在 4 维处理证据"等描述；若提取报告该项为默认 `1-8`，最终文档也必须保持 `1-8`
- **【强制检查】维度格式规范**：参数说明表"维度(shape)"列中，连续的维度值必须写成范围区间格式，禁止逐个列举。例如 `3, 4, 5` 必须修正为 `3-5`，`2, 3, 4` 必须修正为 `2-4`。仅当维度值不连续时才允许逗号枚举（如 `1, 3, 4`）。约束说明正文中的维度描述同理
- 约束说明中的场景标题必须保留用户确认标记，格式为 `<summary><span style="color:#d97706;">【需用户确认】</span> 场景名</summary>`；场景名以可读性优先，禁止直接使用底层条件表达式作为标题
- 场景顺序必须可复现：按对应场景证据在代码中的首次出现位置排序；无内容场景可省略
- 同一约束不得在多个场景重复出现
- 同一产品块内，`<summary>` 文本相同的场景块只能出现一次；若重复必须合并
- 若两个场景块的数据类型表与约束说明完全一致，必须合并为一个场景块
- 若文档中出现"无跨产品完全通用且区别于参数表单参数约束的附加公共约束"或同类空洞占位描述，必须删除，不得保留；但已列出具体约束条目的公共约束区域不属于空洞占位，必须保留
- 若某产品块不存在实际公共约束，则不得保留 `- **公共约束**` 标题、`<a id="公共约束"></a>` 锚点及相关空说明

### 4.1 版本差异作用域一致性（强制）
- 版本迭代差异、接口间差异仅允许出现在 `## 功能说明` 章节中的 `- 接口功能：` 这一项
- `## 函数原型`、参数说明、返回值、`## 约束说明`、`## 调用示例` 中禁止出现版本对比描述（如"相比V2""V3新增/删除参数"等）

### 5. 格式校验
- 所有产品名必须有 `<term>` 标记
- 描述相同的多个产品必须合并为一个列表项
- HTML 表格单元格内禁止 Markdown 语法
- **rowspan 校验**：返回值表中使用 `rowspan` 的单元格，其值必须等于实际合并的行数；若不一致必须修正为正确值
- `<details>`/`<summary>` 缩进规则：第2层顶格，第3层缩进两格
- 固定链接使用正确的相对路径
- 审阅提示颜色仅使用橙色（#d97706）和红色（#dc2626）

### 5.1 内部实现细节泄漏检查（强制）
- 最终文档是对外 ACLNN 接口文档，只能描述用户可感知的接口行为、参数约束、产品差异、错误场景和调用方式；源码证据、内部实现流程和分析痕迹不得出现在最终文档中
- 若文档中出现内部代码块、源码片段、源码路径、行号、内部函数名、内部类名、内部变量名、内部宏名、内部枚举名、内部算子注册名，必须在不改变技术事实的前提下删除或改写为对外语义
- 最终文档禁止出现以下内部实现标识或同类表述：`op_kernel`、`op_host`、`op_tiling`、`kernel`、`tiling`、`AddConfig`、`OP_TYPE_REGISTER`、`#include`、`SocVersion`、`NpuArch`、`__NPU_ARCH__`、`__CCE_AICORE__`、`DAV_`、`ascend910`、`ASCEND910`、`.cpp`、`.cc`、`.c`、`.h`、`.hpp`、源码绝对路径、`代码中`、`源码中`、`实现中`、`分支中`、`命中`、`证据`、`调用内部函数`
- 允许保留公开接口和公开文档概念：目标 ACLNN 接口名、函数原型中的公开参数名、公开 ACL 类型（如 `aclTensor`、`aclScalar`、`aclIntArray`、`aclOpExecutor`）、公开错误码、公开数据类型、公开数据格式、`workspace` 与 `executor`
- 改写时遵循“证据到结论”的规则：`代码中判断 x 维度为 4` 改为 `x 的维度必须为 4`；`op_kernel 中 A8W8 分支` 改为 `当使用 A8W8 量化场景时`；`AddConfig 注册某内部芯片` 改为对应 `<term>` 产品支持结论；`调用内部校验函数检查 shape` 改为 `参数 shape 必须满足以下要求`
- 若某段内容只是在说明内部实现过程，且无法转换为用户需要遵守的接口行为或约束，必须删除，不得保留为“实现说明”

### 6. 术语与规范用语校验

从 references/common_terminology.yml 读取完整术语规范，逐字扫描文档，按规范替换不规范用语。发现即替换，无需标注。

从 references/terminology_dict.yml 读取术语字典，确保术语使用正确。

**注意事项**：
- 术语替换不得破坏 HTML 标签结构（如 `<span style="color:#d97706;">【需用户确认】</span>` 和 `<span style="color:#dc2626;">【需用户补齐】</span>` 中的文本不得被替换）
- 术语替换不得破坏 Markdown 链接语法（如 `[两段式接口](../../../docs/zh/context/两段式接口.md)` 中的链接文本不得被替换）
- 术语替换不得破坏 `<term>` 标签内的产品名称

### 7. 内容完整性
- **【强制检查】标记说明块完整性**：标题 `# aclnn{OperatorName}` 之后、`## 产品支持情况` 之前，必须存在完整的两行标记说明。若缺少任何一行或缺少描述文字，必须补全为以下固定文本：
  ```
  <span style="color:#d97706;">【需用户确认】</span>：表示文档可从代码逻辑推断生成，需用户确认最终表述是否正确
  <span style="color:#dc2626;">【需用户补齐】</span>：表示文档无法从代码提取足够信息，需用户手动补齐描述
  ```
- 必须包含所有必选章节：产品支持情况、功能说明、函数原型、接口章节、约束说明
- 若当前文档的目标接口为普通接口或 Inplace 接口中的一种，则接口章节只能保留该目标接口对应的 `GetWorkspaceSize` 与执行接口两节；不得同时保留 `aclnnXxx` 与 `aclnnInplaceXxx` 两组章节
- 约束说明第一条必须是固定占位：`确定性说明：<span style="color:#dc2626;">【需用户补齐】</span>`
- **调用示例章节不得出现**：review 阶段输出的文档中不应包含 `## 调用示例` 章节——该章节在 review 完成后才由脚本输出拼接而来。若文档中已存在 `## 调用示例`（可能是 generate 阶段误生成），必须删除

## 修正要求

- 发现不一致时直接修正，不要标注"已修正"
- 不新增任何未在提取报告、差异分析报告或代码中出现的信息
- 保持技术事实不变
- 仅允许最小必要内容修改，禁止重写整篇文档
- **保形规则（强制）**：必须保留原文档的章节顺序、标题层级、列表层级、缩进、空行、代码块、HTML 表格结构和标签结构
- **审阅标记保留（强制）**：文档中已存在的 `<span style="color:#d97706;">【需用户确认】...` 与 `<span style="color:#dc2626;">【需用户补齐】...` 不得删除或降级为普通文本；仅可在原标签内改正文字
- **功能说明保护（强制）**：`## 功能说明` 中的无序列表样式必须保持不变；统一局部变量解释条目必须保留颜色标记
- **返回值段落保护（强制）**：`- 返回值` 下的固定两段文字、以及返回值 HTML 表格结构（含 rowspan/colspan）不得被改成其他写法
- **确定性说明保护（强制）**：`确定性说明：<span style="color:#dc2626;">【需用户补齐】</span>` 必须原样保留
- **文风校正（强制）**：若文档中出现"部分场景""某些场景""相关场景""等场景"等模糊量词，必须改写为明确的参数条件、取值范围、维度范围、layout 名称或具体场景名
- **表述校正（强制）**：若文档中出现"代码路径中出现……""存在……证据""代码中取值为 ……"这类证据口吻，必须在不改变事实的前提下改写为面向用户的自然中文条件句
- 如某项修正会导致格式变化，则放弃该修正，保留原格式
- 输出完整的最终文档（不是 diff）

## 失败处理

若本阶段无法完成正常产出，**不写** `5_review.md`，改为写入失败标志文件；最终交付物也不得继续生成。

**文件路径**：`{算子目录}/outputs/{目标接口名}/5_review_FAILED.md`

**触发条件**（满足任一即触发）：
- `4_generate.md` 缺失且存在 `4_generate_FAILED.md`（上游阶段失败）
- `1_extract.md` 或 `2_formula.md` 缺失且存在对应 `_FAILED.md`（校验依据不可用）

**文件结构**（照此格式逐字段填写）：

- 标题：`# 一致性校验（review）失败`

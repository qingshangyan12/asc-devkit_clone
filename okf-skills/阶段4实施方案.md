# 阶段4实施方案：okf-index 索引建设（调研稿）

## 1. 目标与输入

按[后续实施计划](后续实施计划.md)阶段 4：把阶段 3 生成的 140 篇 OKF YAML 头组织成**可复用的持久化检索索引**，支撑阶段 5 `okf-retrieve` 的五类真实查询，满足"关系有依据、日常使用无需重建"。

**输入资产（全部已存在，零新增采集）**：
- 140 篇文档 front matter（9 字段：okftype/description/tag×9 ns/signature/dependencies/examples）
- `okf-yaml-generate/taxonomy/core-v8-frozen.json`（含每个标签值的中文定义，可作查询扩展词表）
- `okf-evaluate/testset/tasks.yaml`（20 题定义了索引必须支撑的查询形态与缺口形态）
- include/ 头文件与样例 marker 的反向链接（prototype_id ↔ 文档）

**查询需求映射**（来自测试集，索引设计的验收基准）：

| 类别 | 查询形态 | 索引支撑 |
| --- | --- | --- |
| A 完整算子（8 题） | 算子需求 → 搬入/计算/搬出分阶段候选 | roles + operations + objects + dtype 多维过滤 |
| B 单项能力（5 题） | 能力词 → 文档；家族 → 架构变体页；类型转换对；归约模式 | description 关键词 + family 分组 + dtype pair + operations |
| C 关联查找（2 题） | API → 配套配置 API | dependencies 图（configures/requires 边）一跳遍历 |
| D 条件不完整（2 题） | 同能力多分支候选 | operation 族内按 traits/description 区分并列出 |
| E 范围外缺口（3 题） | 能力 → "范围内无文档"+范围外线索 | 完整 scope 清单 + gaps 缺口登记表 |

## 2. 技术选型（轻量可复用优先）

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **静态 JSON 索引 + 标准库查询 CLI** | **采用** | 纯派生数据（front matter → 索引），140 篇构建 <1s；JSON 可 diff、可 review、随 git 版本化满足"无需重建"；查询端零依赖（Python stdlib + 已在用的 PyYAML）；阶段 6 维护 = 改 front matter 后重跑构建 |
| SQLite 单文件库 | 否决 | 二进制不可 diff、git 不友好；140 篇规模用不到 SQL 能力，多一套方言 |
| Markdown 索引页 | 否决（主形态） | 多维组合查询（role×operation×dtype）与图遍历不可编程；可作为构建副产物生成 1 页人读概览 |
| 不建索引、检索时直查 front matter | 否决（主形态） | C 类多跳遍历、B2 家族展开、E 类缺口判定每次临场拼装，检索步数不可控；但**重建成本极低**这一事实恰好保证索引可随时再生成，无一致性风险 |

**复用原则**：`build_index.py` 直接 `import` 复用 `okf-yaml-generate/scripts/controller.py` 的 `split_front_matter / taxonomy / sha256`（sys.path 注入，无新依赖、不复制规则）；校验失败即拒绝出索引（沿用"YAML 头检查通过后再纳入索引"的推进原则）。

## 3. 交付物结构

```
okf-skills/okf-index/
  SKILL.md                    # 构建/查询/维护三段流程说明
  scripts/
    build_index.py            # front matter → 索引；内联全量合规校验（字段/词表/依赖目标存在/无环）
    query.py                  # 查询 CLI（唯一检索入口，阶段5/7 复用）
  index/
    index.json                # 主索引（提交 git）
    gaps.json                 # 范围外能力登记表（提交 git）
    build-meta.json           # 源 commit、140 个文件 sha256、词表版本（陈旧检测）
  tests/test_index.py         # 构建确定性 + 查询正确性单测
```

### index.json 结构（草案）

```
meta:      {built_at, source_commit, taxonomy_version, doc_count}
documents: {path → {okftype, title, description, tags, signatures[prototype_id/dtypes/archs/headers],
                   deps_out[{path,kind,condition}], examples[], family, arch_variants[]}}
views:     {by_role, by_operation, by_tag["ns:value"], by_dtype_pair["half→float"],
           by_prototype_id, by_header, by_family}        # 全部倒排到 path
graph:     {edges[{from,to,kind,condition}], reverse[configures_of, requires_of]}
scope:     {all_docs[140], navigation_pages[17], arch_pages[8]}   # 与 tasks.yaml 口径对齐
```

### gaps.json（E 类支撑）

条目 = 能力关键词组 + 结论（"范围内无文档"）+ 范围外线索（如 `include/c_api/sync/sync.h`、`c_api/reg_compute/` 目录）+ 证据路径。**登记规则**：只收录有结构化证据的条目（范围内文档正文/依赖指向范围外，或源码声明存在而文档不在 scope），禁止为凑查询结果编造；每条可追溯到证据文件。初始 3 条（同步、寄存器 load/store、floor 取整）均来自阶段 1-3 已固化的发现，另将阶段 3 记录的 `report_unresolved` 5 条复核后纳入。

## 4. query.py 查询接口（对应五类任务）

```
query.py --stage in|compute|out            # roles 过滤（A 类阶段拆解）
query.py --operation divide [--dtype f32]  # operations+objects 多维过滤（A/B 类）
query.py --kw 非对齐                        # description/title 关键词（B1）
query.py --api asc_copy_gm2ub              # 主页+架构变体+配套依赖展开（B2/C 类）
query.py --deps-of <path> [--kind configures]   # 图遍历（C 类）
query.py --convert half float              # dtype pair（B4）
query.py --gap 同步                         # 缺口登记表（E 类）
```

输出统一为：path + API 名 + 一句话用途（description）+ 选择依据（命中的视图/边），直接对齐评测答案格式"候选 + 未覆盖说明"。

## 5. 实施步骤与验收

| 步骤 | 内容 | 验证 |
| --- | --- | --- |
| 1 | build_index.py：解析+校验+倒排+图+scope，产 index.json/build-meta.json | 重建确定性（两次构建字节一致）；校验 0 错误 |
| 2 | gaps.json：3+N 条登记 | 每条有证据路径；E1-E3 dry-run 命中 |
| 3 | query.py 七个接口 | 单测：20 题的 required 均可 ≤2 次查询定位（dry-run 清单逐题核对）；C 类一跳可达 |
| 4 | SKILL.md + 概览页 | 与基线对照口径可复述（读文档数是核心效率观测量） |

**完成条件**（对照阶段 4 门）：能定位相关分类与文档（B2/A 类 dry-run 全过）；关系有依据（每条图边即 front matter dependencies，有正文证据留痕）；日常使用无需重建（索引提交 git，构建脚本仅维护时运行）。

## 6. 风险与回流项

- **families 覆盖 33/140**（阶段 3 词表缺口）：索引以 operations（101/140）+ roles 为主通道，families 仅作辅助视图；缺口清单已回流阶段 2 调研，扩值后重跑构建即可（<1s）。
- **索引与文档漂移**：build-meta 记录 sha256，query 启动时可选校验；阶段 6 维护 skill 以此定位需重建的范围。
- **评测公平性**：gaps.json 内容源自结构化证据而非测试题面；阶段 7 报告中单列"索引缺口登记对 E 类的贡献"以便复核是否存在过拟合。
- **跨 skill import 路径耦合**：controller.py 位置变更会破坏构建；在 SKILL.md 标注依赖，或后续阶段 6 收敛为 okf-common 共享模块。

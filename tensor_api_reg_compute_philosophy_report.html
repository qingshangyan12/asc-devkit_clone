basic_api/reg_compute 的问题本质
与 TensorAPI 接口设计如何回应

本文从软件设计理念（非单纯 bug 列表）出发，解释旧 reg_compute 为何难以学习、扩展与组合； 再用概念 + 真实代码说明新 TensorAPI（AscendC::Te）如何用 Tag × Trait × Verb × Operand 重构这一领域。

22 intf headers 39 load/store APIs Tag × Trait × Verb CuTe-inspired

0两种 API 范式：指令投影 vs 形式化 DSL

旧 reg_compute — 指令投影型 API

把硬件指令手册直接投影到 C++ 命名空间：每个变体一个顶层函数，配置塞进模板参数。

namespace Reg {
  Add<T, ZEROING>(dst, s0, s1, mask);
  LoadAlign<T, DIST_NORM>(dst, ub);
  LoadAlign(mask, ub, offset); // 同名异义!
}

本质：扁平符号表，无统一代数结构。

新 TensorAPI — 嵌入式 DSL

操作 = Tag（做什么）× Trait（怎么做）× Verb（执行）× Operand（对谁），四层可组合。

namespace Te {
  Compute(MakeVec(vec::Add{}), dst, s0, s1, mask);
  Load(MakeLoad(load::UbAlign{}), dst, ub);
}

本质：可推理、可扩展的形式系统。

1TensorAPI 的六条设计公理

Operand
MakeRegTensor / MakeMaskReg — 操作数工厂（对称 MakeTensor）
Verb
Compute / Load / Store / Copy — 固定动词表
Factory
MakeVec / MakeLoad — 构造可复用策略对象（Atom）
Trait
VecTrait / RegLoadTrait — 正交编译期配置
Tag
vec::Add / load::UbAlign — 空 struct，指令族标识
Inst
Inst::Add::Run → asc_add — 硬件绑定，arch 可替换

①正交性：维度纠缠 vs 维度分离

理念：独立设计维度应自由组合。若每个组合对应一个符号，API 空间按笛卡尔积爆炸，且无法证明完备性。

旧 API：LoadAlign 把 5 个维度绑在一个名字上

// kernel_reg_compute_datacopy_intf.h — 39 个重载，节选
template <typename T, LoadDist dist, typename U>
void LoadAlign(U& dstReg, __ubuf__ T* srcAddr);                    // vld

template <typename T, PostLiteral postMode, LoadDist dist, typename U>
void LoadAlign(U& dstReg, __ubuf__ T*& srcAddr, int32_t stride);  // vld+post

template <MaskDist dist, typename T>
void LoadAlign(MaskReg& mask, __ubuf__ T* srcAddr);             // pld — 完全不同语义!

维度：指令族 × LoadDist × PostMode × 单/双寄存器 × 操作数类型 —— 全部折叠进 LoadAlign。

新 API：维度外置到 Tag 与 Trait

// load_trait.h — 正交维度各自独立
struct RegLoadTrait {
    Reg::LoadDist dist = Reg::LoadDist::DIST_NORM;  // 维度 1
    PostMode post = PostMode::NORMAL;               // 维度 2
    RegWidth width = RegWidth::SINGLE;              // 维度 3
    AddrMode addr = AddrMode::DIRECT;               // 维度 4
};

// 动词固定，变体由 tag + trait 表达
Load(MakeLoad(load::UbAlign{}, trait), dst, ubPtr);
LoadMask(MakeLoad(load::MaskAlign{}, trait), mask, ubPtr); // 规划：拆分异义

向量计算：N 个算子 → 1 个动词

// 每个算子一个顶层函数
Reg::Add(dst, s0, s1, mask);
Reg::Sub(dst, s0, s1, mask);
Reg::Mul(dst, s0, s1, mask);
// ... 50+ 同类函数
// 一个消除器 + N 个 tag
Compute(MakeVec(vec::Add{}), dst, s0, s1, mask);
Compute(MakeVec(vec::Sub{}), dst, s0, s1, mask);
Compute(MakeVec(vec::Mul{}), dst, s0, s1, mask);

②统一访问原则：动词碎裂 vs 三段式

理念（Bertrand Meyer · UAP）：同一抽象层级的同类操作，应有且仅有一种访问路径。

旧 API 中「UB ↔ 寄存器」至少有四套入口，语义相近但名字不同：

旧符号实际含义问题
LoadAlign对齐 UB → Regintf 声明名
DataCopy对齐 UB ↔ Reg测试/impl 实际用名，intf 未声明
Load通用 load与 LoadAlign 并存
LoadUnAlign非对齐 load又一套动词
旧 — 多入口、无统一形状
Reg::LoadAlign<half>(vA, ubPtr);
Reg::DataCopy(vA, ubPtr);       // 影子 API
Reg::Add<half, ZEROING>(dst, a, b, m);
Reg::Move<half, MERGING>(dst, src, m);
新 — 全栈同一形状
Load(MakeLoad(load::UbAlign{}), vA, ubPtr);
Compute(MakeVec(vec::Add{}), dst, a, b, m);
Store(MakeStore(load::UbStoreAlign{}), ubPtr, dst, m);
// 全局侧同样：Copy(MakeCopy(...), dst, src)

管道 Load → Compute → Store 可读，与全局 Copy → Mmad → Copy 同构。

③标签分发：同名异义 vs 编译期类型路由

理念：一个符号应只有一个指称（denotation）。用参数类型猜语义是 ad-hoc 多态，不可形式化。

旧 API 的 LoadAlign 同名异义

// 第一参数是 RegTensor → 向量寄存器加载 (vld)
LoadAlign(dstReg, srcAddr);

// 第一参数是 MaskReg → 掩码寄存器加载 (pld) — 动词相同，语义跃迁
LoadAlign(mask, srcAddr, offset);

新 API：动词按操作数类型拆分 + Tag 路由

// arch/vector/load_op.h — 空 struct 作 phantom type
namespace load { struct UbAlign {}; struct MaskAlign {}; }

// 编译期链：MakeLoad(tag) → LoadAtom<tag> → Inst::UbAlign::Run → asc_loadalign
Load(MakeLoad(load::UbAlign{}),  regDst, ub);   // RegTensor 路径
LoadMask(MakeLoad(load::MaskAlign{}), mask, ub); // MaskReg 路径（规划）

向量域：flat 命名空间中的 And 歧义

旧 Reg::And出现位置实际操作对象
And(dst, s0, s1, mask)vec_binary_intfRegTensor 位运算
And(dst, s0, s1, mask)maskreg_intfMaskReg 位运算
 
// 新：分域命名空间，同名绝不跨域
Te::vec::And{}    → Compute(MakeVec(vec::And{}), ...)
Te::mask::And{}   → mask 子域独立动词（规划）

④策略对象：匿名调用 vs 可复用 Atom

理念（Strategy / Command 模式）：将「请求」封装为对象，使发送者与执行者解耦；配置应可独立于执行存在。
旧 — 每次调用重新「解析」模板实例
for (...) {
  Reg::Add<half, ZEROING>(dst, a, b, mask);
  // 无法提取可复用配置
  // 无法 template<class Op> 泛型
}
新 — Atom 是编译期策略对象
constexpr auto addAtom =
    MakeVec(vec::Add{});
for (...) {
  Compute(addAtom, dst, a, b, mask);
}

// 泛型 kernel
template<typename Op>
void Elt(...) {
  Compute(MakeVec(Op{}), dst, a, b, mask);
}

Trait 收敛：消灭 4 种 mode 写法

// 旧 — 同一概念 4 种表达（binary_intf）
Add<T, MaskMergeMode mode, U>(...)     // MaskMergeMode mode
Div<T, auto mode, U>(...)             // auto mode（可扩 SpecificMode*）
Cast<..., const CastTrait&, ...>(...) // CastTrait

// 新 — 统一 VecTrait 对象
MakeVec(vec::Add{});
MakeVec(vec::Add{}, VecTrait{MaskMergeMode::MERGING});

⑤分层解耦与开闭原则

理念（OCP）：对扩展开放、对修改关闭。架构差异应隔离在 Inst 层，不应污染公开 intf。

旧 API：层次坍塌

// struct_intf.h — 类型定义层直接 #include arch 实现
#if (__NPU_ARCH__ == 3510)
  #include "dav_3510/kernel_reg_compute_datatype_impl.h"
#elif (__NPU_ARCH__ == 5102)
  #include "dav_m510/..."
// ... 6 套 arch 复制，105+ impl 文件

// vec_binary_intf_impl.h — 路由又一层 #if
#if __NPU_ARCH__ == 3003
  #include "dav_l300/.../vec_binary_impl.h"
#else
  #include "dav_3510/.../vec_binary_impl.h"

新 API：四层 + 注册宏扩展

// 扩展新算子 = 2 步，不改 Compute 签名
// 1) vec_op.h 声明
struct Relu;

// 2) vec_atom_impl.h 一行注册
ASCENDC_TE_REGISTER_VEC_OP(Relu, Relu, 1);

// Inst 层 arch 路由（if constexpr CURRENT_ARCH_VERSION）
if constexpr (CURRENT_ARCH_VERSION == ArchVersion::V3510) {
    asc_add(...);
}

友好 static_assert 替代晦涩模板报错

template <typename Op> struct VecInstOf {
    static_assert(sizeof(Op)==0,

static_assert(sizeof...(Rest) == arity + 1,

⑥形式契约：零文档 vs 文档即 API

理念：API 不仅是签名，还应包含前置/后置条件、操作数约定、扩展配方——否则是 tacit knowledge，不可教、不可验证。
旧 — 22 个 intf，@brief 几乎全部为空
/* !
 * \file kernel_reg_compute_vec_binary_intf.h
 * \brief          ← 空
 */

// Move 默认 MERGING，Add 默认 ZEROING — 无注释
Move<T, MaskMergeMode::MERGING>(dst, src, mask);
Add<T, MaskMergeMode::ZEROING>(dst, s0, s1, mask);
新 — vector_compute.h 自说明
// Operand convention:
//   dst first, then source register(s),
//   then the predicate mask register.
//
// Three ways to use:
//   1) Compute(MakeVec(vec::Add{}), ...)
//   2) template<typename Op> Elt(...)
//   3) Add(dst, s0, s1, mask)  // sugar

// MERGING 显式传入，默认 ZEROING 写在 VecTrait
VecTrait{mrg: MaskMergeMode::MERGING}

3完整流水线：概念 + 代码对照

任务：dst = a + b - c（256B 寄存器 tile，带尾块 mask）

旧 reg_compute 写法

using namespace AscendC::Reg;
RegTensor<half> vA, vB, vC, vDst;
MaskReg mask = UpdateMask<half>(elemCount);

DataCopy(vA, ubA);              // 影子 API，intf 未声明
DataCopy(vB, ubB);
DataCopy(vC, ubC);

Add<half, MaskMergeMode::ZEROING>(vDst, vA, vB, mask);
Sub<half, MaskMergeMode::ZEROING>(vDst, vDst, vC, mask);

DataCopy(ubDst, vDst, mask);

新 TensorAPI 写法

using namespace AscendC::Te;

auto vA   = MakeRegTensor<half>();     // 操作数工厂
auto vB   = MakeRegTensor<half>();
auto vC   = MakeRegTensor<half>();
auto vDst = MakeRegTensor<half>();
auto mask = MakeMaskReg<half>(elemCount);

Load(MakeLoad(load::UbAlign{}), vA, ubA);   // 动词 + tag
Load(MakeLoad(load::UbAlign{}), vB, ubB);
Load(MakeLoad(load::UbAlign{}), vC, ubC);

Compute(MakeVec(vec::Add{}), vDst, vA, vB, mask);
Compute(MakeVec(vec::Sub{}), vDst, vDst, vC, mask);

Store(MakeStore(load::UbStoreAlign{}), ubDst, vDst, mask);

兼容层：旧代码零改动

// kernel_reg_compute_te_intf.h — 薄适配
template<...> void Add(Dst& dst, Src0& s0, Src1& s1, MaskT& mask) {
    Te::Compute(Te::MakeVec(Te::vec::Add{}), dst, s0, s1, mask);
}
template<...> void DataCopy(Dst& dst, __ubuf__ T* src) {
    Te::Load(Te::MakeLoad(Te::load::UbAlign{}), dst, src);
}
迁移哲学：旧符号保留为语法糖适配器，语义统一走 Te 层——避免双轨永久并存，但允许渐进替换。

5诚实边界：理念正确 ≠ 全面替换

TensorAPI 给出了正确的形式系统公理，但当前实现仍是 MVP： Compute 域 ~11 个 tag；Load/Store 仅 UbAlign 基本路径；Reduce/Cast/Fused/Mask 运算域尚未迁移。 旧 kernel_reg_compute_*_intf.h 仍是生产主路径。
层次结论
设计公理已建立，与 Copy/Mmad 全局侧一致
向量 Compute已验证范式，可扩展
Load/StoreTrait 契约 + MVP；39 接口中 ~5% 落地
RegTensor 抽象仍 alias 旧类型，长期需重建
全量替换需 P1–P6 分期完成

一句话：reg_compute 的问题是缺少可推理的代数结构；TensorAPI 用 Tag×Trait×Verb 给出了这个结构——接下来要做的是用结构覆盖全部领域，而非停在 MVP。

# C API上精度最大误差表

## 需求

为C API中涉及浮点近似计算的接口提供“最大精度误差”汇总表，使开发者能够按接口、数据类型、算法模式和NPU架构查询精度上界，并能从汇总表跳转到对应接口资料。

本任务当前只有名称，立项前需要确认以下范围：

- “C API”是否仅指`docs/zh/api/SIMD-API/c_api/reg_compute`下的Reg矢量计算接口，还是还包含标量、矩阵计算等接口。
- 误差数据是否已有芯片/编译器责任方发布的权威基线；若没有，生成基线和评审定标不能只由资料开发人员完成。
- 首期覆盖的NPU架构。当前SIMT/Regbase主入口涉及DAV 3510，但不能据此默认所有C API只需要一套精度数据。
- 精度口径是ULP、相对误差、绝对误差，还是按输入区间采用不同口径；是否需要区分FTZ、舍入模式、编译选项及特殊值。

## 背景简述

- 当前仓库已有[Reg矢量计算接口精度标准汇总](../docs/zh/api/appendix/reg_vector_compute_interface_precision_standard_summary.md)和[SIMT接口精度标准汇总](../docs/zh/api/appendix/SIMT_interface_precision_standard_summary.md)，可以复用其附录组织方式、索引接入方式和表格风格。
- C API目录当前约有852个Markdown文件，但其中包含概述、索引、数据搬运、同步、缓存控制等不产生数值近似误差的内容，不能将目录中的文件机械地全部纳入精度表。
- C API资料中尚无统一的“最大精度误差”章节或汇总表；目前仅在个别接口中零散说明，例如`asc_div`对`half`、`float`注明可能存在1 ULP精度差异。
- SIMT精度表已经体现出精度结论会受数据类型、硬件指令/软件仿真、Subnormal支持和编译选项影响。C API表也需要保留这些维度，否则“最大误差”容易被误读成无条件承诺。

## 涉及领域

- C API Reg矢量/标量/矩阵计算接口分类。
- 浮点数据类型、ULP/相对误差/绝对误差和特殊值语义。
- 硬件指令、软仿实现、FTZ与舍入模式。
- NPU架构差异和接口产品支持范围。
- API附录、接口资料、API总索引及链接维护。
- 精度测试、黄金值生成和边界输入设计。

## 方案详述

### 1. 冻结统计口径

先输出一份接口清单，不直接开始填表。按照如下规则分类：

| 分类 | 处理方式 |
|---|---|
| 浮点近似计算，如除法、开方、倒数、指数、对数、三角函数 | 纳入最大误差表 |
| 浮点到浮点/整数的转换 | 单独记录舍入模式和溢出/饱和规则，不与普通计算误差混为一列 |
| 加减乘、整数运算等结果可按标准精确定义的接口 | 标记“精确”或“不适用”，是否入表由评审决定 |
| 数据搬运、同步、缓存、系统变量、纯配置接口 | 不纳入，并在表前明确排除范围 |
| 废弃接口 | 默认不重复维护，只链接现有废弃说明；若仍需承诺精度则单独列出 |

清单至少包含：接口名、文档路径、声明路径、实现/指令映射、支持架构、dtype、重载/模式、是否软仿、当前资料是否已有精度描述、数据责任人。

### 2. 建立精度数据模型

建议汇总表至少使用以下列：

| 接口 | 数据类型 | 算法/舍入模式 | NPU架构 | 最大误差 | 有效输入范围 | Subnormal/特殊值 | 备注 |
|---|---|---|---|---|---|---|---|

表前统一定义ULP、相对误差和绝对误差；同一接口在不同输入区间使用不同指标时拆行，不写成含糊的单值。`NaN`、`Inf`、正负零、Subnormal、溢出和除零属于行为约束，不应被计入普通有限值的最大误差统计。

### 3. 精度术语解释

精度表不能只列缩写，需要在表前增加术语说明和读表示例。建议至少解释以下概念：

| 术语 | 含义 | 使用时需要注意的点 |
|---|---|---|
| 参考值/Golden | 用更高精度算法或权威参考实现算出的期望结果，用于和接口实际输出比较 | Golden本身必须比被测数据类型精度更高，并按目标接口的舍入规则转换后再比较 |
| ULP（Unit in the Last Place） | 目标浮点格式在某个数值附近相邻两个可表示数之间的间隔，也可以理解为“末位相差多少格” | ULP的实际数值随指数变化，不是固定的小数；因此1 ULP不等于固定的`1e-6` |
| 0 ULP | 实际输出与按约定规则得到的参考浮点结果一致 | 需要先明确参考实现、目标dtype和舍入模式；不能笼统理解为数学实数意义上的绝对零误差 |
| 1 ULP | 实际输出与参考浮点结果最多相差一个相邻浮点数间隔 | 适合衡量浮点结果的“可表示步数”，但仍需说明适用输入范围和特殊值规则 |
| 绝对误差 | `abs(actual - golden)` | Golden接近0时通常比相对误差更有意义；不同数量级的结果不便直接横向比较 |
| 相对误差 | `abs(actual - golden) / abs(golden)` | Golden为0时无定义，需要改用绝对误差或单独规定分母下限 |
| Normal（规格化数） | 浮点格式中处于正常指数范围的非零有限数，具有完整的有效数字精度 | 一般精度指标主要针对Normal有限值统计 |
| Subnormal/Denormal（次正规数/非规格化数） | 比最小Normal数更接近0的一组非零浮点数，用逐渐减少有效位数的方式表示极小值 | 有效精度低于Normal；接口、架构和编译选项可能选择支持、软仿或将其按0处理 |
| FTZ（Flush To Zero） | 将Subnormal输入或结果按0处理的一类模式 | `FTZ=true`和`FTZ=false`可能得到不同结果；具体影响输入、输出还是中间值，需要以对应接口和编译选项资料为准 |
| 舍入模式 | 精确实数无法直接表示时，选择哪个可表示值的规则 | 常见模式包括就近舍入、向零舍入、向正无穷舍入和向负无穷舍入；精度结论必须和模式绑定 |
| 硬件指令实现 | 接口主要由对应硬件指令直接完成 | 精度通常受指令规格和架构约束，不同架构不能直接复用结论 |
| 软仿实现 | 接口没有使用单条对应硬件指令，而是由若干已有指令或软件算法组合实现 | 此处“软仿”不是CPU调试器；其精度可能受算法版本和编译选项影响 |
| Full range | 精度结论适用于该接口已定义的整个有效输入范围 | 不包含文档明确排除的非法输入；`NaN`、`Inf`、溢出等仍按特殊值规则判断 |
| 特殊值 | `NaN`、正负`Inf`、正负零、Subnormal，以及接口定义的非法域输入 | 一般验证返回类别、符号和规定行为，不应简单并入普通有限值的ULP统计 |

ULP可以通过如下例子直观理解：在`float32`中，从`1.0`向上相邻的下一个可表示值是`1 + 2^-23`，两者间隔约为`1.1920929e-7`，这个位置的一个间隔就是1 ULP。如果参考结果为`1.0`，接口返回这个相邻值，则误差为1 ULP。数值变大或变小时，相邻浮点数的间隔会变化，所以不能用一套固定的绝对误差阈值代替ULP。

精度表中的一句话也需要给出读法。例如“`1-ulp (full range), Support denormalized numbers`”表示：在文档定义的全部有效输入范围内，接口结果与约定参考结果最多相差1个目标dtype的可表示间隔，并且Subnormal按接口规则参与计算，而不是直接按0处理。该结论仍需和具体dtype、架构、编译选项及舍入模式一起阅读。

测试报告建议同时输出Golden、实际值、绝对误差、相对误差和ULP差值。这样既能对照规格判定，也便于在Golden为0、数值跨数量级或结果位于Subnormal区间时定位问题。

### 4. 获取并核验权威数据

1. 从指令精度规格、编译器软仿规格或接口设计文档获取声明值，并记录来源版本。
2. 对照C API公开声明、实现和现有UT，确认每个重载最终映射的指令或软仿路径。
3. 编写或复用精度扫描用例，覆盖正常区间、分段边界、极值、零附近、Subnormal和特殊值。
4. 高精度黄金值优先使用MPFR等可信高精度实现；比较前明确目标dtype的舍入方式。
5. 测试结果用于发现规格/实现偏差，不能以有限采样观测值直接替代“最大误差”规格。
6. 若实测超过声明值，先形成问题单，由接口、编译器或芯片责任方定界，不能通过放宽资料数值规避问题。

### 5. 文档落地

- 在`docs/zh/api/appendix`新增C API精度标准汇总文档，命名与现有附录保持一致。
- 按接口族或dtype拆分子表，避免单张超宽表；接口名链接到具体API资料。
- 在`docs/zh/api/appendix/appendix.md`和`docs/zh/api/README.md`增加入口。
- 对已有精度描述的接口逐项核对；接口页保留必要约束，详细矩阵统一链接到附录，避免两处维护不同数值。
- 如果精度受编译选项影响，同时更新对应编译选项资料并在表头注明测试配置。
- 在汇总表开头加入上述术语、公式和读表示例，并链接到更完整的浮点数据类型或精度转换资料，确保没有精度背景的读者也能独立理解表格。

### 6. 验收方案

- 清单中的所有目标接口均有结论，不允许无说明的空单元格；未知项显式标记“待定标”。
- 表中接口、dtype、架构和模式与当前声明及产品支持表一致。
- 抽取每类至少一个接口执行精度用例，并对高风险近似函数执行完整边界测试。
- Markdown格式、产品标签、相对链接和总索引检查通过。
- 由一名没有精度背景的开发者试读，能够正确解释1 ULP、相对/绝对误差、Subnormal和FTZ，不把1 ULP误解为固定小数阈值。
- 由接口/编译器/芯片精度责任方确认表中数值，资料评审只能确认表达和一致性。

## 难点和容易出问题的点

- **最大值来源**：有限用例只能证明“已观测最大误差”，不能证明全定义域上界。缺少规格签字时不应对外写成“最大误差”。
- **统计维度膨胀**：同一接口可能因dtype、架构、FTZ、舍入模式或软仿路径不同而有多套结论，过度合并会形成错误承诺。
- **误差指标混用**：0 ULP、1 ULP、相对误差和绝对误差不可直接横向比较；零附近和大数区间尤其容易误判。
- **特殊值处理**：`NaN`、`Inf`、Subnormal、溢出/饱和与普通精度误差需要分开描述。
- **资料漂移**：汇总表、单接口页和实现三处都可能发生变化，必须建立逐项核对表并指定唯一数据源。
- **架构误用**：不能把DAV 3510上的结论无条件复制到DAV 2201等其他架构。

# Ascend C提供SIMT到SIMD算子迁移指导

## 需求

新增一份面向算子开发者的SIMT到SIMD迁移指导，回答以下问题：什么场景值得迁移、哪些场景不应强行迁移、线程级算法如何改写成分块/向量化算法、如何选择C API或C++ API、如何保证功能精度并验证性能收益。

完整交付不应只有概念对照表，需要包含一篇迁移指南，以及reduce、广播、elementwise三类各一个可编译运行的“迁移前/迁移后”样例。当前任务名称未指定目标API层级和目标NPU架构，立项时必须补齐。

## 背景简述

- 仓库已有SIMT编程、SIMD编程以及SIMD/SIMT混合编程资料，也分别有`examples/03_simt_api`、`examples/01_simd_cpp_api`、`examples/02_simd_c_api`和`examples/05_simd_simt_hybrid`样例，但缺少以“同一个算子从SIMT改写为SIMD”为主线的迁移方法。
- SIMT代码通常以Grid、Thread Block和Thread为视角；SIMD代码通常以逻辑核、数据分块、Local Memory和向量指令为视角。迁移是并行算法和存储流水的重构，不是API名称替换。
- 源SIMT能力主要面向DAV 3510。目标SIMD若只使用跨代兼容API，可能扩大产品范围；若使用Regbase/C API等架构相关能力，则仍可能只支持特定架构。最终范围必须以目标API资料和实际编译验证为准。
- 本地可用CANN路径为`/home/developer/Ascend/cann-9.2.0`，但目标SoC尚未指定，因此目前只能制定验证矩阵，不能承诺具体设备结果。

## 涉及领域

- SIMT与SIMD编程模型、核函数执行配置和多核切分。
- GM/UB/寄存器存储层次、数据对齐、搬运与流水并行。
- 线程索引、Warp协作、掩码、规约、Gather/Scatter和原子操作。
- Tiling、Host侧启动配置及工作空间。
- C API、基础C++ API、高阶API和混合编程的选型。
- 功能、精度、性能和多Shape泛化验证。

## 方案详述

### 1. 明确迁移决策边界

指南开篇提供决策树：

- 连续规整访存、低分支、同构逐元素或规约计算，优先评估完整迁移到SIMD。
- 离散访存、分支发散明显、线程间动态协作较多的部分，优先保留SIMT或采用SIMD/SIMT混合编程。
- 矩阵计算应迁往SIMD矩阵计算路径，不能继续用SIMT线程模拟矩阵单元。
- 如果SIMD版本没有性能收益、引入不可接受的UB占用或改变数值语义，应允许保留原实现。

### 2. 给出核心概念映射

| SIMT实现要素 | SIMD迁移思路 | 重点检查 |
|---|---|---|
| `gridDim`/`blockDim`/线程索引 | Host Tiling决定核数和每核数据量，Device侧按Block和Tile循环 | 尾核、尾块和空核 |
| 每线程处理一个或少量元素 | 每条向量指令处理一段连续数据 | 向量宽度、对齐和mask尾处理 |
| 线程直接访问GM | GM→UB→计算→GM分阶段处理 | 搬运粒度、地址空间和越界 |
| Warp shuffle/vote/reduce | Reg矢量指令、基础/高阶规约API或分级规约 | 计算顺序变化导致的浮点误差 |
| 分支控制 | mask、Select、分段计算或保留SIMT子任务 | 两侧是否都有副作用、分支稀疏度 |
| 线程/块同步 | `TQue`、事件同步、流水屏障或核间同步 | 不漏同步，也不重复同步 |
| 原子更新 | 按核局部聚合后再原子写回，或改为分级规约 | 冲突率、确定性和数据类型支持 |
| 动态局部变量/寄存器 | UB Buffer、LocalTensor或Reg Tensor | UB容量、生命周期和复用 |
| SIMT Launch配置 | SIMD核数、Tiling参数、必要的workspace | 架构核数和小Shape调度开销 |

每类映射都应引用当前仓库中对应的API资料；不存在一对一能力时明确给出“重构算法”或“保留混合编程”，不能制造虚假的API对应关系。

### 3. 设计端到端迁移步骤

1. **建立基线**：记录源SIMT算子的支持dtype/Shape、精度标准、设备耗时、编译选项、Grid/Block配置和资源占用。
2. **识别并行语义**：标出线程独占数据、线程间共享数据、同步点、原子冲突和分支区域。
3. **重新切分数据**：设计多核切分和单核Tile，计算对齐块、尾块以及UB预算。
4. **选择SIMD接口层**：规则张量优先评估C++基础/高阶API；需要直接控制Reg指令时选C API。选择后逐个核对目标架构、dtype、地址空间、对齐和同步约束。
5. **构造搬运计算流水**：实现CopyIn、Compute、CopyOut，按依赖关系使用队列或事件；存在收益时再加入Double Buffer。
6. **重写不规则逻辑**：将可向量化的分支改为mask；无法高效向量化的片段拆为SIMT VF或保留原SIMT实现。
7. **处理尾块**：分别验证数据量小于一个向量、非对齐尾块、尾核无数据以及极端Shape。
8. **对齐数值语义**：规约顺序、FTZ、舍入模式和近似函数改变时，重新定义合理阈值并记录差异原因。
9. **性能迭代**：从正确的单Buffer版本开始，再优化核数、Tile、搬运合并、流水重叠、Reg使用和同步开销。

### 4. 配套样例设计

样例固定覆盖以下三类，三者使用相同的工程骨架、数据生成方式、计时口径和目标SIMD API层级，形成从简单到复杂的迁移路径：

| 类别 | 建议样例 | SIMT侧典型实现 | SIMD侧迁移重点 | 关键测试Shape |
|---|---|---|---|---|
| Elementwise | Add：`z[i] = x[i] + y[i]` | 每个线程按全局索引处理一个或多个元素 | 多核切分、GM/UB搬运、向量Add、尾块mask和Double Buffer | 小于一个向量、对齐长度、非对齐长度、不能被核数整除的长度 |
| 广播 | Broadcast Add：`z[m,n] = x[m,n] + b[n]` | 线程按`m,n`计算输入和广播索引 | 广播轴映射、`b`数据的搬运/复用、Tile选择、跨行尾块以及避免重复GM读取 | `M=1`、`N=1`、`N`非对齐、单个Tile内多行、跨Tile/跨核 |
| Reduce | 按行ReduceSum：`y[m] = sum(x[m,:])` | 每线程累加部分数据，再用Warp/Block协作规约 | 向量局部规约、跨Tile部分和、必要时的多级规约、同步及浮点累加顺序变化 | 归约轴小于/等于/大于一个Tile、非2的幂、非对齐、多行及单行大Shape |

选择这三个样例的原因是：Elementwise用于讲清最基础的线程到向量映射；广播增加输入复用和二维索引；Reduce进一步引入线程协作到分级向量规约的转换、同步和精度变化。三个样例不能合并成一个复合算子，否则读者难以区分每类迁移的关键点。

每个样例都需要提供：

- 原始SIMT Kernel、Grid/Thread Block配置和资源使用基线。
- 功能等价的SIMD实现及Host侧核数/Tiling配置。默认优先用C++基础API；若需求方明确面向C API，则三个样例统一改用C API，避免同一指南混用接口层级。
- 数据生成、Golden校验、边界Shape集合和性能测量脚本。
- 独立README或指南小节，逐段解释索引映射、内存布局、同步变化和性能数据，不只展示最终代码。
- SIMT与SIMD正常路径的输出对比；Reduce样例单独说明并行累加顺序变化及精度阈值。

样例应复用现有examples工程结构，并加入对应中文指南索引。若涉及新的Kernel API、重载、dtype或地址空间组合，实施前必须从`docs/zh/api/README.md`和API列表开始核对文档、声明、实现和现有样例。

### 5. 验收方案

- 指南覆盖迁移决策、模型映射、代码步骤、同步、尾块、精度、性能和常见问题。
- Elementwise、广播和Reduce三组样例均在指定NPU架构上完成SIMT/SIMD两版编译和运行，不能用其中一类替代另一类。
- 三组样例分别覆盖表中规定的关键Shape；公共用例还需覆盖对齐/非对齐、小Shape、大Shape和多核尾块。
- SIMD输出满足已评审的精度标准；对规约顺序等造成的合理差异有明确说明。
- 三组样例分别输出性能对比，固定环境、编译参数和Shape，同时报告设备耗时及关键资源；若某类未获得收益，需要给出瓶颈分析而不是隐藏结果。
- 新增文档接入`docs/zh/guide/index.md`及相关章节索引，链接检查通过。

## 难点和容易出问题的点

- **不是语法迁移**：把线程循环直接包进SIMD Kernel通常只能得到功能近似代码，无法形成正确高效的向量流水。
- **索引和尾块**：线程索引改为Block/Tile偏移后，最容易出现尾核重复处理、尾块越界和mask错误。
- **地址空间差异**：SIMT指针、GM、UB、LocalTensor/Reg Tensor的语义不同，错误转换可能编译通过但运行结果异常。
- **同步错误**：漏掉MTE/Vector依赖会产生偶现错误；在`TQue`自动同步之外重复加事件则可能死锁或降低性能。
- **精度变化**：规约树、运算顺序、融合方式及FTZ策略改变会导致结果不逐bit一致。
- **三类样例不能套用同一切分**：Elementwise按元素切分最直接，广播需要兼顾被广播数据复用，Reduce则要保证一行的部分和能够正确汇总；强行复用同一Tiling会造成额外搬运或错误结果。
- **Reduce验证最复杂**：归约轴跨Tile或跨核时需要二次规约或原子汇总，还会改变浮点累加顺序，功能、精度和性能都要单独验收。
- **广播索引易错**：`M=1`、`N=1`、尾行和跨Tile场景容易出现广播维度判断错误、重复搬运或越界访问。
- **性能倒退**：小Shape、分支密集、离散访存或UB占用过大的算子可能不适合纯SIMD，必须用数据而不是预期判断迁移成功。
- **架构范围扩大错误**：从SIMT迁出不代表自动支持旧架构，目标接口及dtype仍可能是架构相关能力。

# C API接口资料的调用示例，Host侧代码增加对nullptr的校验

## 需求

系统排查C API接口资料中的完整调用示例，对Host侧动态分配得到的指针增加空指针校验，确保分配失败时不会继续执行Host-to-Device拷贝、Kernel Launch、Device-to-Host拷贝或释放无效资源，并统一失败路径的清理行为。

本任务只处理示例代码的健壮性，不顺带重构所有Runtime返回码检查，也不改变Device侧接口行为。立项前需要确认是否覆盖废弃接口、实验接口、英文资料，以及“只有片段、没有Host代码”的调用示例。

## 背景简述

- 当前`docs/zh/api/SIMD-API/c_api`约有852个Markdown文件，其中约694个含“调用示例”，约340个文件出现`aclrtMalloc`。这说明任务是批量整改，不能按少量接口估算。
- 现有示例风格不统一：部分使用`ACL_CHECK`或`check`包装Runtime返回值，部分直接调用`aclrtMalloc`后继续使用指针；仅按`nullptr`关键字检索也会混入`aclInit(nullptr)`、Kernel启动参数和接口本身允许空指针的语义。
- `aclrtMalloc`失败时既需要检查返回码，也需要确认输出指针；只补`if (ptr == nullptr)`能避免解引用，但会丢失具体错误信息。建议统一同时校验返回码和指针。
- 文档代码块可能包含多个独立示例、架构标签和不同资源组合，无法安全地使用全局文本替换完成。

## 涉及领域

- C API Markdown调用示例和Host侧C/C++代码。
- CANN Runtime资源创建、内存分配、拷贝、Kernel启动及清理。

## 方案详述

### 1. 定义检查对象和排除规则

需要校验的是“由可能失败的分配/创建操作写出的、后续会被使用的Host侧指针或句柄”，首期至少覆盖：

- `aclrtMalloc`返回的Device指针。
- 示例中使用`malloc`/`new (std::nothrow)`等方式创建的Host缓冲区。
- 如果样例含workspace查询和分配，覆盖workspace指针。

明确排除：

- `aclInit(nullptr)`中的可选配置参数。
- Kernel Launch中的共享内存大小`0`，以及接口规范明确允许传空的可选参数。
- 仅作为初始值的`T* ptr = nullptr`，应检查其后续赋值点，而不是声明本身。
- Device侧API参数的空指针语义；这属于接口行为，不是Host示例健壮性整改。

### 2. 建立可审计清单

编写只读扫描脚本，提取Markdown中的C/C++代码块，并为每个文件记录：

- 调用示例数量及是否包含`main`。
- 分配/创建调用、接收变量和后续首次使用位置。
- 是否检查Runtime返回码、是否检查`nullptr`、失败分支是否清理已成功创建的资源。
- 文档所属接口族、产品标签和是否废弃/实验。

扫描结果人工复核后形成“需修改/无需修改/接口允许空指针/待确认”四类清单。脚本不能直接依据`aclrtMalloc`字符串批量插入代码，因为调用可能跨行、被宏包装或处于注释中。

### 3. 统一Host错误处理模板

优先复用文件内已有的错误检查宏或函数，避免同一示例出现两套风格。对于没有公共辅助函数的独立示例，建议遵循以下语义：

1. 保存Runtime API返回码。
2. 当返回码非成功或输出指针为`nullptr`时，打印可定位的错误信息。
3. 跳转到统一清理路径或通过RAII退出，清理此前已经成功申请的资源。
4. 只有检查成功后才执行拷贝和Kernel Launch。
5. 清理函数应允许处理未初始化资源，并避免重复释放。

示意逻辑如下，实际代码需服从各文档现有风格：

```cpp
aclError ret = aclrtMalloc(reinterpret_cast<void**>(&inputDevice), bytes,
                           ACL_MEM_MALLOC_HUGE_FIRST);
if (ret != ACL_SUCCESS || inputDevice == nullptr) {
    std::cerr << "aclrtMalloc inputDevice failed, ret = " << ret << std::endl;
    // 清理此前已经成功创建的资源后返回失败。
}
```

不建议仅使用`assert(ptr != nullptr)`：Release构建可能关闭断言，而且示例需要可理解的运行时错误信息和清理路径。

### 4. 分批整改

按目录分批提交，建议顺序为：

1. 先整改一组具有单输入/单输出的Reg计算示例并评审模板。
2. 再处理多输入、多输出、workspace和流对象的复杂示例。
3. 最后处理矩阵、同步、原子、缓存控制等带特殊资源或执行顺序的示例。
4. 每批更新扫描清单，确保没有新增遗漏，也没有误改合法`nullptr`。

如果变更文件过多，应拆成多个逻辑提交，但仍可放在同一任务分支；不建议生成一个无法审查的超大提交。

### 5. 验证方案

- **静态复扫**：所有目标分配点均同时满足返回码和空指针检查，检查发生在第一次使用之前。
- **失败路径审查**：模拟第1、2、N次分配失败，确认只释放已成功申请的资源，不继续Launch、不泄漏、不重复释放。
- **编译验证**：提取受影响的完整示例，按资料给出的`bisheng`命令在其支持架构上编译；不能只做Markdown语法检查。
- **运行抽测**：每种错误处理模板至少选择一个示例在设备上正常运行；具备注入条件时增加分配失败测试。
- **文档检查**：执行Markdown格式、产品标签、链接和索引检查，确保批量编辑没有破坏代码围栏或条件标签。
- **回归检查**：对比整改前后的Kernel、输入、期望输出和正常路径日志，确保本任务只改变失败路径。

## 难点和容易出问题的点

- **范围误判**：`nullptr`在`aclInit`、可选workspace、Kernel参数和API语义中可能完全合法，简单搜索替换会制造错误示例。
- **只查指针不查返回码**：能阻止崩溃但丢失Runtime错误；反过来只用宏检查返回码，也未必满足本任务明确要求的空指针防御。
- **部分分配失败**：多输入示例在第二或第三次分配失败时容易泄漏前面已分配的内存。
- **清理顺序**：Stream、Device内存、Device和ACL运行时需要按已有范式逆序释放；失败分支与正常分支必须一致且不可重复释放。
- **宏的控制流**：部分检查宏可能直接`return`或`exit`，插入前必须理解其行为，否则清理代码永远无法执行。
- **示例不可编译**：Markdown中的调用片段不一定是完整程序，需区分“可编译完整示例”和“语法片段”，避免不现实的全量运行承诺。
- **批量改动审查困难**：约340个含分配调用的文件可能产生大量重复diff，应先统一模板、按目录分批并保留扫描清单。

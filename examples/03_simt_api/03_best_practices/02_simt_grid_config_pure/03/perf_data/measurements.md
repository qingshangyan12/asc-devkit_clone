# 中-shape 核数扫描实测数据

> 环境：Ascend 950PR（物理 AIV 核数 64），strided gather kernel，每 block 线程数固定 **2048**。
> 计时：`msprof op` 的 Task Duration(us)，每点 5 次取平均（131072 那组为初测）。
> input 张量 [1100000] float，index/output 为对应 shape 的 gather 结果。

## 结论速览

- **数据量越大，最优核数越靠近 64**：在较大 shape（65536、131072）下，Task Duration 随核数下降到 64 物理核为止；131072 实测到 128 核时越过物理核，超出的逻辑核排队等待，反而比 64 核慢约 27%，最优核数顶在物理核上限 64。
- **数据量足够小（8192、16384）时最低点落在非满核**：每核工作量小到一定程度后，"启动更多核 → 更多调度头开销"开始反客为主，最优核数落在 **32 核（物理核数一半）**，打满 64 核反而更慢约 10%。
- 因此中-小 shape 场景**必须实测**最优核数，不能盲目打满物理核；最优核数（最低点位置）随 shape 变化，shape 越大越靠近物理核上限。

## shape [8,1024] = 8192（曲线呈 U 形，最优 = 32 核）

仅取 16 / 32 / 64 三点（折线图用），5 次取平均：

| cores | rows/core | mean(us) | min | max | std |
| ----: | --------: | -------: | --: | --: | --: |
| 16 | 512 | 3.622 | 3.408 | 3.755 | 0.124 |
| **32** | 256 | **3.315** | 3.267 | 3.384 | 0.044 |
| 64 | 128 | 3.669 | 3.409 | 3.864 | 0.167 |

- 最低点在 **32 核（3.315us）**，16 核与 64 核都更慢；32 → 64 **变慢约 10.7%**。
- 32 整除 8192（256 rows/core，无尾巴不均衡），噪声最小（std 0.044）。
- 与 16384 档一样，最低点都落在 32 核（物理核数一半），三点即可清晰呈现这条 U 形曲线的最低点。

### 旁证：[8,2048] = 16384，小核数段（1/2/4/8）

同为 16384 个元素，但 shape 写成 [8,2048]，扫描小核数：

| cores | rows/core | mean(us) | min | max | std |
| ----: | --------: | -------: | --: | --: | --: |
| 1 | 16384 | 34.230 | 33.763 | 34.924 | 0.408 |
| 2 | 8192  | 19.152 | 18.874 | 19.363 | 0.174 |
| 4 | 4096  | 10.792 | 10.598 | 10.991 | 0.143 |
| 8 | 2048  | 6.676  | 6.542  | 6.768  | 0.080 |

- 小核数段单调下降，最低点不在此处（最低点在 32 核，见上表）。
- 与上面 [128,128]=16384 的同核数点几乎一致（1核 34.2 vs 34.5、8核 6.68 vs 6.79），说明 **Task Duration 只取决于元素总数与核数，与 shape 的行列写法无关**。

## shape [32,2048] = 65536（单调下降，64 核最快）

| cores | rows/core | mean(us) | min | max | std |
| ----: | --------: | -------: | --: | --: | --: |
| 16 | 4096 | 9.963 | 9.824 | 10.242 | 0.152 |
| 32 | 2048 | 6.736 | 6.575 | 6.873  | 0.099 |
| **64** | 1024 | **5.912** | 5.835 | 5.997 | 0.070 |

- 曲线无回升，64 核最快。每核工作量（1024 rows）仍足够大，加核继续受益。

## shape [64,2048] = 131072（最优 = 64 物理核，128 核越过物理核反而变慢）

| cores | rows/core | mean(us) | min | max | std |
| ----: | --------: | -------: | --: | --: | --: |
| 16 | 8192 | 16.753 | 16.516 | 17.085 | 0.196 |
| 32 | 4096 | 10.127 | 9.998  | 10.193 | 0.067 |
| **64** | 2048 | **7.753** | 7.670 | 7.870 | 0.083 |
| 128 | 1024 | 9.857 | 9.707 | 10.012 | 0.116 |

- 16 → 32 → 64 单调下降，**最优落在 64 物理核（7.753us）**；数据量大，每核工作量（2048 rows）仍足够大，加核到物理核上限持续受益。
- 64 → 128：核数翻倍越过 64 物理核，超出的 64 个逻辑核须排队等物理核空闲，Task Duration 从 7.753 升到 **9.857us，反而变慢约 27.1%**。
- 与 16384/8192 最低点落在物理核以内不同：131072 数据量足够大，最优核数已顶到物理核上限，再加核只剩排队等待的代价。

## 复现方法

参数化探针 kernel（`TOTAL` 与 `NB` 为编译宏，每 block 2048 线程，strided gather）：

```bash
# 对每个 (TOTAL, NB) 组合：
cmake -DTOTAL=<元素总数> -DNB=<核数> <probe_dir>
make -j
msprof op --application=./g --output=<out>
# 从 <out>/OPPROF_*/OpBasicInfo.csv 读取 Task Duration(us)，多次取平均
```

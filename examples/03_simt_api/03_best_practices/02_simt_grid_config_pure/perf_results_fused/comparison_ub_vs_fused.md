# UB 两阶段版 vs 融合无 UB 版 — msprof op 性能对比

- 采集命令：`msprof op --application=./grid_config`
- 采集时间：2026-05-28
- 目标平台：Ascend 950PR / 950DT（AIV 物理核数 = 64）
- 数据规模：`input[1100000]`, `index/output[1024,1024]`（`INDEX_WIDTH=1024`）

## 两版 kernel 的差异

只有 `gather_adds_kernel` 体不同；`empty_kernel` 与 host launch 的其他部分完全一致。

| 项目 | UB 版（`grid_config.asc`） | fused 版（`grid_config_fused.asc`） |
|------|---------------------------|------------------------------------|
| UB 中间缓冲 | `extern __ubuf__ float ub_scratch[]` | 删除 |
| 循环结构 | 阶段 1：GM→UB；阶段 2：UB→GM（两轮 stride loop） | 单轮 fuse：GM→寄存器→GM |
| host `dyn_ubuf_size` | `(rows_per_block) * sizeof(float)` | `0` |

> **Case 5/6 才是 UB 是否有用的真实信号**，结论：去掉 UB 微弱占优。

## 结论

1. 在这个 sample 的访问模式下，**UB 中间层是纯粹冗余**：每条线程只读写自己的格子，无跨线程共享 / 散点→连续重排 / 多次复用，UB 三大杠杆全空。
2. 去掉 UB 的实测收益：Case 5 -1.77%、Case 6 -3.02%。方向正确，幅度有限。
3. UB 真正能压性能的场景（仍以这个 kernel 为框架举例）：
   - 多线程协作 gather **同一段** index → 共享 UB 实现"读一次用 N 次"；
   - 散点 gather 结果先在 UB 中按 cache line 重排，再 vector store coalesce 写回 GM；
   - 中间张量在 UB 内被多次累加 / 读写。
4. 教学示例的取舍：保留 UB 版作为 `dyn_ubuf_size` 与 `extern __ubuf__` launch 语法演示是合理的；如果重点在"性能"，需要换一个真正能展现 UB 收益的 pattern。

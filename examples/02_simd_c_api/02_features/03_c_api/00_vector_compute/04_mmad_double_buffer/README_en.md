# Matmul C-API High-Performance Sample

## Overview

This sample implements half matrix multiplication with the Ascend C C-API and compares four configurations: single buffering, L1-only double buffering, L0-only double buffering, and L1/L0 double buffering. Ping/Pong buffers allow MTE2 transfer, MTE1 loading, and Cube computation to overlap across different K iterations.

## Sample Description

The sample computes `C = A x B`. A and B are generated with a fixed random seed. B is transposed before it is written so that the K dimension is contiguous in GM and can be transferred in K tiles. Table2 lists the data specifications.

**Table2**  Input and Output Data Specifications

| Data | Input/Output | Data file | Data type | Logical shape | File and GM layout | Description |
| --- | --- | --- | --- | --- | --- | --- |
| A | Input | `input/x1_gm.bin` | half | `[M, K] = [1024, 1024]` | ND, stored as `[M, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| B | Input | `input/x2_gm.bin` | half | `[K, N] = [1024, 1024]` | Transposed ND, stored as `[N, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| C | Output | `output/output.bin` | float | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Result computed by the Kernel |
| golden | Golden data | `output/golden.bin` | float | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Generated by running `np.matmul` on inputs cast to float. |

The sample computes `C = A x B`, where `M`, `N`, and `K` are all 1024. The matrices use `[128, 128, 64]` tiles and 64 logical Cube blocks, with each block computing one `[128, 128]` output tile. `block_idx` assigns the output tile, and each block accumulates it over 16 MMAD iterations along K.

Data moves from GM through L1 Buffer, L0A Buffer/L0B Buffer, and L0C Buffer before being written back to GM. Table4 lists the layouts and APIs used at each stage.

The `SCENARIO_NUM` build option selects the A/B buffer configuration in L1 and L0. All four scenarios use the same matrix dimensions, tiles, K iterations, Block count, and MMAD parameters; only the A/B buffer count in L1 and L0A/L0B differs.

**Table5**  Scenario Configuration

| `SCENARIO_NUM` | Kernel | Scenario | L1 Buffer | L0A Buffer/L0B Buffer | L0C Buffer | Pipeline behavior |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | `mmad_baseline` | Single-buffer baseline | One A/B group | One A/B group | One group for result accumulation | Completes load, L0 Buffer transfer, MMAD, and full synchronization before processing the next K tile. |
| 1 | `mmad_l1_double_buffer` | L1-only double buffering | Ping/Pong A/B groups | One A/B group | One group for result accumulation | MTE2 can prepare a later K tile; MTE1 still waits to reuse the single L0 group. |
| 2 | `mmad_l0_double_buffer` | L0-only double buffering | One A/B group | Ping/Pong A/B groups | One group for result accumulation | MTE1 can load a later K tile into an idle L0 group while MMAD uses the other group. |
| 3 | `mmad_double_buffer` | L1/L0 double buffering | Ping/Pong A/B groups | Ping/Pong A/B groups | One group for result accumulation | MTE2, MTE1, and M can process different K tiles. |

### Scenario 0: Single-Buffer Baseline

`mmad_baseline` allocates one A/B buffer group in L1 Buffer, L0A Buffer, and L0B Buffer. All 16 K iterations reuse the same addresses. Table6 lists the buffer sizes and purposes.

**Table6**  Single-Buffer Configuration

| Buffer | Array | Elements | Bytes | Purpose |
| --- | --- | --- | --- | --- |
| L1 Buffer A | `a_l1` | 8192 half elements | 16384 | Stores the current A tile loaded from GM and converted to Nz. |
| L1 Buffer B | `b_l1` | 8192 half elements | 16384 | Stores the current B tile loaded from GM and converted to Nz. |
| L0A Buffer | `a_l0` | 8192 half elements | 16384 | Stores the current A tile used by MMAD. |
| L0B Buffer | `b_l0` | 8192 half elements | 16384 | Stores the current B tile used by MMAD. |
| L0C Buffer | `c_l0` | 16384 float elements | 65536 | Accumulates the C output tile over 16 MMAD iterations. |

Each K iteration runs in the following order:

1. MTE2 calls `copy_a_to_l1` and `copy_b_to_l1` to move the current A/B tiles from GM to L1 Buffer and convert them from ND to Nz.
2. After MTE2 releases the Mutex, MTE1 acquires it and loads A/B into L0A Buffer and L0B Buffer.
3. After MTE1 releases the Mutex, M calls `asc_mmad` to compute `[128, 64] x [64, 128]`. Iteration 0 initializes L0C Buffer, and subsequent iterations accumulate into it.
4. `asc_sync_pipe(PIPE_ALL)` runs at the end of each iteration. The next iteration cannot reuse the L1 Buffer and L0 Buffer addresses until the current iteration has finished.

Because every iteration ends with a full pipeline synchronization, MTE2, MTE1, and M process the same K tile in sequence and cannot overlap across iterations. This implementation serves as the performance baseline.

### Scenario 1: L1-Only Double Buffering

`mmad_l1_double_buffer` allocates Ping/Pong A/B groups only in L1. L0A and L0B still use one group. Even iterations use L1 Ping and Mutex 0, odd iterations use L1 Pong and Mutex 1, and the single L0 group uses Mutex 2.

Once MTE1 has read an L1 group, MTE2 can write a later K tile to that group without waiting for MMAD. Because L0 has only one group, MTE1 must still wait for MMAD to finish reading it before loading the next tile.

### Scenario 2: L0-Only Double Buffering

`mmad_l0_double_buffer` allocates Ping/Pong A/B groups only in L0A and L0B. L1 still uses one A/B group. The single L1 group uses Mutex 0; even iterations use L0 Ping and Mutex 2, and odd iterations use L0 Pong and Mutex 3.

Once MTE1 has read L1, MTE2 can reuse the single L1 group. While MMAD uses one L0 group, MTE1 can load a later K tile into the other L0 group.

### Scenario 3: L1/L0 Double Buffering

`mmad_double_buffer` allocates Ping/Pong A/B groups in both L1 and L0. Even iterations use Ping with Mutexes 0/2, while odd iterations use Pong with Mutexes 1/3. L0C is not switched; all 16 MMAD iterations accumulate into the same `c_l0` tile.

All scenarios use [asc_lock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_lock.md) and [asc_unlock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_unlock.md) to control buffer-reuse dependencies. These Mutexes ensure that data is written before it is read and read before it is overwritten; they are not a separate performance optimization.

**Table7**  Buffer-Reuse Dependencies

| Dependency direction | Mutex IDs | Purpose |
| --- | --- | --- |
| `MTE2 -> MTE1` and `MTE1 -> MTE2` | L1: `0` for one group and `0/1` for Ping/Pong | Controls L1 writes, MTE1 reads, and L1 reuse. |
| `MTE1 -> M` and `M -> MTE1` | L0: `2` for one group and `2/3` for Ping/Pong | Controls L0 loads, MMAD reads, and L0 reuse. |

For example, Scenario 3 uses Ping in iteration 0, Pong in iteration 1, and Ping again in iteration 2. While M computes iteration 0, MTE1 can load the Pong data for iteration 1 and MTE2 can transfer iteration 2 into the Ping L1 group after MTE1 releases it. After the K loop, FIX waits on the final L0 Mutex before storing the result to GM.

The four scenarios are single buffering, L1-only double buffering, L0-only double buffering, and L1/L0 double buffering, respectively; they compare the pipeline-overlap benefit of Ping/Pong buffering at each level and at both levels.

Keep the matrix, MMAD parameters, and input data unchanged during performance testing. Mutexes express the required read, write, and reuse dependencies. For a valid comparison, use the same hardware, CANN version, and system load, and verify accuracy before collecting performance data.

#### Performance Analysis

Using Scenario 0 as the baseline, the speedup of Scenario 3 with L1/L0 double buffering is

$$
S = \frac{T_{\text{baseline}}}{T_{\text{double-buffer}}}
  = \frac{37.684}{20.792}
  \approx 1.812
$$

The end-to-end duration reduction is

$$
R = \frac{T_{\text{baseline}} - T_{\text{double-buffer}}}{T_{\text{baseline}}} \times 100\%
  = \frac{37.684 - 20.792}{37.684} \times 100\%
  \approx 44.83\%
$$

`Task Duration` decreases from 37.684μs to 20.792μs, a reduction of 16.892μs or 44.83%, corresponding to a 1.812x speedup. `aicore_time` follows the same trend, decreasing from 36.470μs to 19.900μs.

The `aic_mac_time` values of Scenarios 0 and 3 differ by only 0.153μs, so the Cube workload is essentially unchanged. The gain comes from overlapping MTE2 transfers, MTE1 loads, and Cube computation across K iterations. `aic_mte2_time` decreases from 21.169μs to 14.863μs, the largest change among the pipeline metrics.

In Scenario 3, `aic_mte2_ratio` rises from 58.0% to 74.7% and remains the largest ratio. The higher ratio results from the shorter total `aicore_time`; it does not mean MTE2 became slower. Profiler pipeline durations include execution and wait time, so they cannot be added directly or treated as the duration of one transfer.

The benefits of L1 and L0 double buffering can interact. When data for Scenarios 1 and 2 is available, compare both their result relative to Scenario 0 and their incremental benefit after double buffering is enabled at the other level.

**Table13**  L1 and L0 Double-Buffer Contribution Analysis

| Comparison | Interpretation |
| --- | --- |
| Scenario 0 -> Scenario 1 | Benefit of L1 double buffering with one L0 group. |
| Scenario 0 -> Scenario 2 | Benefit of L0 double buffering with one L1 group. |
| Scenario 1 -> Scenario 3 | Additional benefit of L0 double buffering when L1 double buffering is enabled. |
| Scenario 2 -> Scenario 3 | Additional benefit of L1 double buffering when L0 double buffering is enabled. |

#### Conclusion

- **Optimization method**: With Ping/Pong Buffers in both L1 and L0, MTE2 can transfer the next K tile, MTE1 can load the current K tile, and Cube can compute the previous K tile at the same time. Double buffering changes waiting relationships between stages; it does not reduce the Cube workload.
- **Measured gain**: In the Scenario 0 to Scenario 3 comparison in Table12, `Task Duration` decreases from 37.684μs to 20.792μs, a reduction of 16.892μs or 44.83%, for a 1.812x speedup. The nearly unchanged `aic_mac_time` shows that the gain mainly comes from pipeline overlap.
- **Per-level contribution**: Scenarios 1 and 2 isolate the L1-only and L0-only configurations. The Scenario 1 to Scenario 3 and Scenario 2 to Scenario 3 comparisons then show the incremental benefit of the other buffer level. The two levels can interact, so their isolated gains cannot be added directly.
- **Next steps**: MTE2 remains the largest-ratio stage in Scenario 3. Further work should use measured Memory and L2 Cache metrics to examine input-transfer volume, L2 reuse, and tile size rather than infer bandwidth from one pipeline duration alone.

## Build and Run

Configure the CANN environment:

```bash
source ${install_path}/cann/set_env.sh
```

Build and run one scenario from this sample directory:

```bash
SCENARIO_NUM=0
mkdir -p build && cd build
cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 -DSCENARIO_NUM=${SCENARIO_NUM} ..
make -j
python3 ../scripts/gen_data.py
./c_api_mmad_double_buffer_example
python3 ../scripts/verify_result.py output/output.bin output/golden.bin
```

Set `SCENARIO_NUM` to `1`, `2`, or `3`, then rerun CMake, build, execution, and verification to test the corresponding scenario. Clear the CMake cache before switching scenarios.

**Table14**  Build Options

| Build option | Values | Description |
| --- | --- | --- |
| `CMAKE_ASC_ARCHITECTURES` | `dav-3510` | NPU architecture |
| `CMAKE_ASC_RUN_MODE` | `npu` (default), `cpu`, `sim` | Run mode |
| `SCENARIO_NUM` | `0`, `1`, `2`, `3` (default) | Single buffer, L1-only double buffer, L0-only double buffer, or L1/L0 double buffer. |

A successful verification prints:

```text
test pass!
```

# Matmul C-API High-Performance Sample

## Overview

This sample implements half matrix multiplication with the Ascend C C-API and compares four configurations: single buffering, L1-only double buffering, L0-only double buffering, and L1/L0 double buffering. Ping/Pong buffers allow MTE2 transfer, MTE1 loading, and Cube computation to overlap across different K iterations.

## Sample Description

The sample computes `C = A x B`. A and B are generated with a fixed random seed. B is transposed before it is written so that the K dimension is contiguous in GM and can be transferred in K tiles. Table2 lists the data specifications.

**Table2**  Input and Output Data Specifications

| Data | Input/Output | Data file | Data type | Logical shape | File and GM layout | Description |
| --- | --- | --- | --- | --- | --- | --- |
| A | Input | `input/x1_gm.bin` | half | `[M, K] = [1024, 1024]` | ND, stored as `[M, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| B | Input | `input/x2_gm.bin` | half | `[K, N] = [1024, 1024]` | Transposed ND, stored as `[N, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| C | Output | `output/output.bin` | float | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Result computed by the Kernel |
| golden | Golden data | `output/golden.bin` | float | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Generated by running `np.matmul` on inputs cast to float. |

The matrices are tiled along the M, N, and K axes. Table3 lists the tiling parameters.

**Table3**  Matrix Tiling and Multicore Parameters

| Parameter | Value | Description |
| --- | --- | --- |
| Matrix dimensions | `[M, N, K] = [1024, 1024, 1024]` | `C[M, N] = A[M, K] x B[K, N]` |
| Base tile | `[TILE_M, TILE_N, TILE_K] = [128, 128, 64]` | M, N, and K ranges of each MMAD iteration |
| Number of M tiles | 8 | `MATRIX_M / TILE_M` |
| Number of N tiles | 8 | `MATRIX_N / TILE_N` |
| Logical Cube blocks | 64 | `8 * 8`; each block computes one output tile. |
| Output tile per block | `[128, 128]` float | 16384 elements, occupying 65536 bytes in L0C Buffer. |
| K iterations | 16 | `MATRIX_K / TILE_K` |
| A tile per iteration | `[128, 64]` half | 8192 elements, occupying 16384 bytes. |
| B tile per iteration | `[128, 64]` half | A tile of transposed `[N, K]` data, with 8192 elements occupying 16384 bytes. |

`block_idx` determines the output tile assigned to each logical Cube block: `m_tile_idx = block_idx % 8` and `n_tile_idx = block_idx / 8`. Each block computes one `[128, 128]` C tile over 16 MMAD iterations along K. The first iteration initializes L0C Buffer, and the remaining 15 accumulate into it.

Data moves from GM through L1 Buffer, L0A Buffer/L0B Buffer, and L0C Buffer before being written back to GM. Table4 lists the layouts and APIs used at each stage.

**Table4**  Data Movement Path and Layouts

| Storage unit | Data | Layout | Data movement or compute API |
| --- | --- | --- | --- |
| GM | A and transposed B | ND | - |
| L1 Buffer | A and B tiles | Nz | `asc_set_gm2l1_nz_para`, `asc_copy_gm2l1_nd2nz` |
| L0A Buffer | A tile | Nz | `asc_copy_l12l0a` |
| L0B Buffer | B tile | Zn | `asc_copy_l12l0b` |
| L0C Buffer | C output tile | Nz, float | `asc_mmad` |
| GM | C | ND, float | `asc_set_l0c2gm_nz2nd`, `asc_copy_l0c2gm` |

The `SCENARIO_NUM` build option selects the A/B buffer configuration in L1 and L0. All four scenarios use the same matrix dimensions, tiles, K iterations, Block count, and MMAD parameters; only the A/B buffer count in L1 and L0A/L0B differs.

**Table5**  Scenario Configuration

| `SCENARIO_NUM` | Kernel | Scenario | L1 Buffer | L0A Buffer/L0B Buffer | L0C Buffer | Pipeline behavior |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | `mmad_baseline` | Single-buffer baseline | One A and one B tile, 32768 bytes total | One A and one B tile, 32768 bytes total | One tile, 65536 bytes | Completes load, L0 Buffer transfer, MMAD, and full synchronization before processing the next K tile. |
| 1 | `mmad_l1_double_buffer` | L1-only double buffering | Ping/Pong A and B tiles, 65536 bytes total | One A and one B tile, 32768 bytes total | One tile, 65536 bytes | MTE2 can prepare a later K tile; MTE1 still waits to reuse the single L0 group. |
| 2 | `mmad_l0_double_buffer` | L0-only double buffering | One A and one B tile, 32768 bytes total | Ping/Pong A and B tiles, 65536 bytes total | One tile, 65536 bytes | MTE1 can load a later K tile into an idle L0 group while MMAD uses the other group. |
| 3 | `mmad_double_buffer` | L1/L0 double buffering | Ping/Pong A and B tiles, 65536 bytes total | Ping/Pong A and B tiles, 65536 bytes total | One tile, 65536 bytes | MTE2, MTE1, and M can process different K tiles. |

### Scenario 0: Single-Buffer Baseline

`mmad_baseline` allocates one A/B buffer group in L1 Buffer, L0A Buffer, and L0B Buffer. All 16 K iterations reuse the same addresses. Table6 lists the buffer sizes and purposes.

**Table6**  Single-Buffer Configuration

| Buffer | Array | Elements | Bytes | Purpose |
| --- | --- | --- | --- | --- |
| L1 Buffer A | `a_l1` | 8192 half elements | 16384 | Stores the current A tile loaded from GM and converted to Nz. |
| L1 Buffer B | `b_l1` | 8192 half elements | 16384 | Stores the current B tile loaded from GM and converted to Nz. |
| L0A Buffer | `a_l0` | 8192 half elements | 16384 | Stores the current A tile used by MMAD. |
| L0B Buffer | `b_l0` | 8192 half elements | 16384 | Stores the current B tile used by MMAD. |
| L0C Buffer | `c_l0` | 16384 float elements | 65536 | Accumulates the C output tile over 16 MMAD iterations. |

Each K iteration runs in the following order:

1. MTE2 calls `copy_a_to_l1` and `copy_b_to_l1` to move the current A/B tiles from GM to L1 Buffer and convert them from ND to Nz.
2. After MTE2 releases the Mutex, MTE1 acquires it and loads A/B into L0A Buffer and L0B Buffer.
3. After MTE1 releases the Mutex, M calls `asc_mmad` to compute `[128, 64] x [64, 128]`. Iteration 0 initializes L0C Buffer, and subsequent iterations accumulate into it.
4. `asc_sync_pipe(PIPE_ALL)` runs at the end of each iteration. The next iteration cannot reuse the L1 Buffer and L0 Buffer addresses until the current iteration has finished.

Because every iteration ends with a full pipeline synchronization, MTE2, MTE1, and M process the same K tile in sequence and cannot overlap across iterations. This implementation serves as the performance baseline.

### Scenario 1: L1-Only Double Buffering

`mmad_l1_double_buffer` allocates Ping/Pong A/B groups only in L1. L0A and L0B still use one group. Even iterations use L1 Ping and Mutex 0, odd iterations use L1 Pong and Mutex 1, and the single L0 group uses Mutex 2.

Once MTE1 has read an L1 group, MTE2 can write a later K tile to that group without waiting for MMAD. Because L0 has only one group, MTE1 must still wait for MMAD to finish reading it before loading the next tile.

### Scenario 2: L0-Only Double Buffering

`mmad_l0_double_buffer` allocates Ping/Pong A/B groups only in L0A and L0B. L1 still uses one A/B group. The single L1 group uses Mutex 0; even iterations use L0 Ping and Mutex 2, and odd iterations use L0 Pong and Mutex 3.

Once MTE1 has read L1, MTE2 can reuse the single L1 group. While MMAD uses one L0 group, MTE1 can load a later K tile into the other L0 group.

### Scenario 3: L1/L0 Double Buffering

`mmad_double_buffer` allocates Ping/Pong A/B groups in both L1 and L0. Even iterations use Ping with Mutexes 0/2, while odd iterations use Pong with Mutexes 1/3. L0C is not switched; all 16 MMAD iterations accumulate into the same `c_l0` tile.

All scenarios use [asc_lock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_lock.md) and [asc_unlock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_unlock.md) to control buffer-reuse dependencies. These Mutexes ensure that data is written before it is read and read before it is overwritten; they are not a separate performance optimization.

**Table7**  Buffer-Reuse Dependencies

| Dependency direction | Mutex IDs | Purpose |
| --- | --- | --- |
| `MTE2 -> MTE1` and `MTE1 -> MTE2` | L1: `0` for one group and `0/1` for Ping/Pong | Controls L1 writes, MTE1 reads, and L1 reuse. |
| `MTE1 -> M` and `M -> MTE1` | L0: `2` for one group and `2/3` for Ping/Pong | Controls L0 loads, MMAD reads, and L0 reuse. |

For example, Scenario 3 uses Ping in iteration 0, Pong in iteration 1, and Ping again in iteration 2. While M computes iteration 0, MTE1 can load the Pong data for iteration 1 and MTE2 can transfer iteration 2 into the Ping L1 group after MTE1 releases it. After the K loop, FIX waits on the final L0 Mutex before storing the result to GM.

**Table8**  Four-Scenario Comparison

| Comparison | Scenario 0 | Scenario 1 | Scenario 2 | Scenario 3 |
| --- | --- | --- | --- | --- |
| L1 A/B Buffer | One group, 32768 bytes | Two groups, 65536 bytes | One group, 32768 bytes | Two groups, 65536 bytes |
| L0A/L0B Buffer | One group, 32768 bytes | One group, 32768 bytes | Two groups, 65536 bytes | Two groups, 65536 bytes |
| L0C Buffer | One group, 65536 bytes | One group, 65536 bytes | One group, 65536 bytes | One group, 65536 bytes |
| Main overlap | None | MTE2 and later stages | MTE1 and MMAD | MTE2, MTE1, and MMAD |
| Additional A/B storage | None | L1: 32768 bytes | L0: 32768 bytes | L1 and L0: 32768 bytes each |

## Performance Comparison

The four scenarios change only the A/B buffer count in L1 and L0. Mutexes express the required read, write, and reuse dependencies. For a valid comparison, use the same hardware, CANN version, input data, and system load, and verify accuracy before collecting performance data.

Use msOpProf to collect performance data and inspect the following fields in `PipeUtilization.csv`.

**Table11**  Performance Metric Descriptions

| Metric | Description |
| --- | --- |

**End-to-End Result**:

Using Scenario 0 as the baseline, the full double-buffer speedup of Scenario 3 is

$$
S = \frac{T_{\text{baseline}}}{T_{\text{double-buffer}}}
  = \frac{37.684}{20.792}
  \approx 1.812
$$

The end-to-end duration reduction is

$$
R = \frac{T_{\text{baseline}} - T_{\text{double-buffer}}}{T_{\text{baseline}}} \times 100\%
  = \frac{37.684 - 20.792}{37.684} \times 100\%
  \approx 44.83\%
$$

`Task Duration` decreases from 37.684μs to 20.792μs, a reduction of 16.892μs or 44.83%, corresponding to a 1.812x speedup. `aicore_time` also decreases by 45.43%, following the same trend as the end-to-end duration.

The `aic_mac_time` values of Scenarios 0 and 3 differ by 0.153μs, so Cube compute time is essentially unchanged. Among the pipeline metrics, `aic_mte2_time` changes most noticeably, decreasing from 21.169μs to 14.863μs. `aic_mte1_time` and `aic_scalar_time` increase, but each absolute increase is below 1μs. Profiler pipeline durations include both execution and wait time, so these values do not show that an individual load or Scalar instruction became slower. `aic_fixpipe_time` differs by only 0.038μs, indicating similar result-store overhead.

After collecting the data for Scenarios 1 and 2, use Table13 to assess the effect of each buffer level. The benefits may interact, so compare both the results relative to Scenario 0 and the incremental benefit after enabling double buffering at the other level.

**Table13**  L1 and L0 Double-Buffer Contribution Analysis

| Comparison | Interpretation |
| --- | --- |
| Scenario 0 -> Scenario 1 | Benefit of L1 double buffering with one L0 group. |
| Scenario 0 -> Scenario 2 | Benefit of L0 double buffering with one L1 group. |
| Scenario 1 -> Scenario 3 | Additional benefit of L0 double buffering when L1 double buffering is enabled. |
| Scenario 2 -> Scenario 3 | Additional benefit of L1 double buffering when L0 double buffering is enabled. |

**Theoretical Performance Analysis**:

For $M=N=K=1024$, 64 AI Cores, a Cube frequency of 1.65GHz, and $16\times16\times16$ multiply-accumulate operations per AI Core per cycle, the ideal Cube duration is

$$
T_{\text{cube,theory}}
= \frac{M \times N \times K}
       {16 \times 16 \times 16 \times \text{core count} \times \text{Cube frequency}}
= \frac{1024 \times 1024 \times 1024}
       {16 \times 16 \times 16 \times 64 \times 1.65 \times 10^9}
\approx 2.482\ \mu s
$$

The measured `aic_mac_time` values for Scenarios 0 and 3 are 7.06μs and 7.213μs, approximately 2.84 and 2.91 times the theoretical value. The theoretical value includes only Cube instructions and excludes K-loop control, address calculation, synchronization, and scheduling. The similar MAC durations show that double buffering does not change the Cube workload; the performance difference comes from overlapping transfer, loading, and computation across iterations.

Each output tile reads its corresponding A and B tiles. A is read by eight N-direction tiles, and B is read by eight M-direction tiles. Without considering cache hits, the theoretical input traffic is

$$
D_{\text{read}}
= \left(\frac{N}{TILE_N} \times M \times K
+ \frac{M}{TILE_M} \times K \times N\right) \times sizeof(half)
= 32\ \text{MiB}
$$

The float output traffic is

$$
D_{\text{write}} = M \times N \times sizeof(float) = 4\ \text{MiB}
$$

**Pipeline and Bandwidth Analysis**:

Using the 32MiB theoretical input traffic and `aic_mte2_time`, the estimated aggregate read bandwidth of Scenario 0 is

$$
BW_{\text{read,baseline}}
= \frac{32\ \text{MiB}}{21.169\ \mu s}
\approx 1.585\ \text{TB/s}
$$

For Scenario 3, it is

$$
BW_{\text{read,double-buffer}}
= \frac{32\ \text{MiB}}{14.863\ \mu s}
\approx 2.258\ \text{TB/s}
$$

The Scenario 3 estimate is 42.43% higher. This calculation uses the total volume repeatedly read by all cores and is affected by both L2 Cache hits and ND-to-Nz conversion. It does not represent physical HBM bandwidth.

In Scenario 0, the MAC, MTE1, MTE2, and FIX ratios sum to 89.5%, so the stages run mostly serially. In Scenario 3, they sum to 138.2%, showing that transfer, loading, and computation overlap across K iterations.

`aic_mte2_ratio` rises from 58.0% to 74.7%, while `aic_mte2_time` decreases by 29.79%. The ratio rises because total `aicore_time` is shorter, not because MTE2 became slower. MTE2 still has the highest ratio, so further optimization should focus on input transfer and data reuse.

#### Conclusion

Full L1/L0 Ping/Pong double buffering allows MTE2, MTE1, and M to process different K tiles. In the Scenario 0 to Scenario 3 comparison, `Task Duration` decreases by 16.892μs, or 44.83%. Scenarios 1 and 2 isolate the L1-only and L0-only configurations; their contributions must be determined from measurements. A/B usage increases by 32768 bytes in each of L1 and L0.

MTE2 still accounts for the largest share of execution time. Further work can evaluate tile size, UnitFlag, L2 Cache reuse, and transfer granularity, with Memory and L2 Cache metrics used to separate the effects of HBM access and cache reuse.

## Build and Run

Configure the CANN environment:

```bash
source ${install_path}/cann/set_env.sh
```

Build and run one scenario from this sample directory:

```bash
SCENARIO_NUM=0
mkdir -p build && cd build
cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 -DSCENARIO_NUM=${SCENARIO_NUM} ..
make -j
python3 ../scripts/gen_data.py
./c_api_mmad_double_buffer_example
python3 ../scripts/verify_result.py output/output.bin output/golden.bin
```

Set `SCENARIO_NUM` to `1`, `2`, or `3`, then rerun CMake, build, execution, and verification to test the corresponding scenario. Clear the CMake cache before switching scenarios.

**Table14**  Build Options

| Build option | Values | Description |
| --- | --- | --- |
| `CMAKE_ASC_ARCHITECTURES` | `dav-3510` | NPU architecture |
| `CMAKE_ASC_RUN_MODE` | `npu` (default), `cpu`, `sim` | Run mode |
| `SCENARIO_NUM` | `0`, `1`, `2`, `3` (default) | Single buffer, L1-only double buffer, L0-only double buffer, or L1/L0 double buffer. |

```text
test pass!
```

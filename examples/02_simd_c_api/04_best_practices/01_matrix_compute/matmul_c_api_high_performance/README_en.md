# Matmul C-API High-Performance Sample

## Overview

This sample implements float16 matrix multiplication with the Ascend C C-API and compares single buffering with Ping/Pong double buffering. The double-buffer implementation alternates between two L1 Buffer and L0 Buffer groups so that MTE2 transfer, MTE1 loading, and Cube computation can overlap across K iterations.

## Sample Description

The sample computes `C = A x B`. A and B are generated with a fixed random seed. B is transposed before it is written so that the K dimension is contiguous in GM and can be transferred in K tiles. Table2 lists the data specifications.

**Table2**  Input and Output Data Specifications

| Data | Input/Output | Data file | Data type | Logical shape | File and GM layout | Description |
| --- | --- | --- | --- | --- | --- | --- |
| A | Input | `input/x1_gm.bin` | float16 | `[M, K] = [1024, 1024]` | ND, stored as `[M, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| B | Input | `input/x2_gm.bin` | float16 | `[K, N] = [1024, 1024]` | Transposed ND, stored as `[N, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| C | Output | `output/output.bin` | float32 | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Result computed by the Kernel |
| golden | Golden data | `output/golden.bin` | float32 | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Generated by running `np.matmul` on inputs cast to float32. |

The matrices are tiled along the M, N, and K axes. Table3 lists the tiling parameters.

**Table3**  Matrix Tiling and Multicore Parameters

| Parameter | Value | Description |
| --- | --- | --- |
| Matrix dimensions | `[M, N, K] = [1024, 1024, 1024]` | `C[M, N] = A[M, K] x B[K, N]` |
| Base tile | `[TILE_M, TILE_N, TILE_K] = [128, 128, 64]` | M, N, and K ranges of each MMAD iteration |
| Number of M tiles | 8 | `MATRIX_M / TILE_M` |
| Number of N tiles | 8 | `MATRIX_N / TILE_N` |
| Logical Cube blocks | 64 | `8 * 8`; each block computes one output tile. |
| Output tile per block | `[128, 128]` float32 | 16384 elements, occupying 65536 bytes in L0C Buffer. |
| K iterations | 16 | `MATRIX_K / TILE_K` |
| A tile per iteration | `[128, 64]` float16 | 8192 elements, occupying 16384 bytes. |
| B tile per iteration | `[128, 64]` float16 | A tile of transposed `[N, K]` data, with 8192 elements occupying 16384 bytes. |

`block_idx` determines the output tile assigned to each logical Cube block: `m_tile_idx = block_idx % 8` and `n_tile_idx = block_idx / 8`. Each block computes one `[128, 128]` C tile over 16 MMAD iterations along K. The first iteration initializes L0C Buffer, and the remaining 15 accumulate into it.

Data moves from GM through L1 Buffer, L0A Buffer/L0B Buffer, and L0C Buffer before being written back to GM. Table4 lists the layouts and APIs used at each stage.

**Table4**  Data Movement Path and Layouts

| Storage unit | Data | Layout | Data movement or compute API |
| --- | --- | --- | --- |
| GM | A and transposed B | ND | - |
| L1 Buffer | A and B tiles | Nz | `asc_set_gm2l1_nz_para`, `asc_copy_gm2l1_nd2nz` |
| L0A Buffer | A tile | Nz | `asc_copy_l12l0a` |
| L0B Buffer | B tile | Zn | `asc_copy_l12l0b` |
| L0C Buffer | C output tile | Nz, float32 | `asc_mmad` |
| GM | C | ND, float32 | `asc_set_l0c2gm_nz2nd`, `asc_copy_l0c2gm` |

The `SCENARIO_NUM` build option selects single buffering or double buffering. The two implementations differ only in the number of A/B buffers and their synchronization; all other compute parameters are the same.

**Table5**  Scenario Configuration

| `SCENARIO_NUM` | Kernel | Scenario | L1 Buffer | L0A Buffer/L0B Buffer | L0C Buffer | Pipeline behavior |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | `mmad_baseline` | Single-buffer baseline | One A and one B tile, 32768 bytes total | One A and one B tile, 32768 bytes total | One tile, 65536 bytes | Completes load, L0 Buffer transfer, MMAD, and full synchronization before processing the next K tile. |
| 1 | `mmad_double_buffer` | Double-buffer optimization | Ping/Pong A and B tiles, 65536 bytes total | Ping/Pong A and B tiles, 65536 bytes total | One tile, 65536 bytes | MTE2, MTE1, and M process different K tiles with cross-iteration overlap. |

### Scenario 0: Single-Buffer Baseline

`mmad_baseline` allocates one A/B buffer group in L1 Buffer, L0A Buffer, and L0B Buffer. All 16 K iterations reuse the same addresses. Table6 lists the buffer sizes and purposes.

**Table6**  Single-Buffer Configuration

| Buffer | Array | Elements | Bytes | Purpose |
| --- | --- | --- | --- | --- |
| L1 Buffer A | `a_l1` | 8192 float16 elements | 16384 | Stores the current A tile loaded from GM and converted to Nz. |
| L1 Buffer B | `b_l1` | 8192 float16 elements | 16384 | Stores the current B tile loaded from GM and converted to Nz. |
| L0A Buffer | `a_l0` | 8192 float16 elements | 16384 | Stores the current A tile used by MMAD. |
| L0B Buffer | `b_l0` | 8192 float16 elements | 16384 | Stores the current B tile used by MMAD. |
| L0C Buffer | `c_l0` | 16384 float32 elements | 65536 | Accumulates the C output tile over 16 MMAD iterations. |

Each K iteration runs in the following order:

1. MTE2 calls `copy_a_to_l1` and `copy_b_to_l1` to move the current A/B tiles from GM to L1 Buffer and convert them from ND to Nz.
2. After MTE2 releases the Mutex, MTE1 acquires it and loads A/B into L0A Buffer and L0B Buffer.
3. After MTE1 releases the Mutex, M calls `asc_mmad` to compute `[128, 64] x [64, 128]`. Iteration 0 initializes L0C Buffer, and subsequent iterations accumulate into it.
4. `asc_sync_pipe(PIPE_ALL)` runs at the end of each iteration. The next iteration cannot reuse the L1 Buffer and L0 Buffer addresses until the current iteration has finished.

Because every iteration ends with a full pipeline synchronization, MTE2, MTE1, and M process the same K tile in sequence and cannot overlap across iterations. This implementation serves as the performance baseline.

### Scenario 1: L1 Buffer/L0 Buffer Double Buffering

`mmad_double_buffer` allocates Ping/Pong A/B groups in both L1 Buffer and L0 Buffer. Even iterations use Ping with Mutexes 0/2, and odd iterations use Pong with Mutexes 1/3. Adjacent K iterations use different A/B buffers. L0C Buffer is not switched; all 16 MMAD iterations accumulate into the same `c_l0` tile.

**Table7**  Ping/Pong Buffer Configuration

| K iteration | Buffer group | L1 Mutex ID | L0 Mutex ID | L1 Buffer | L0 Buffer |
| --- | --- | --- | --- | --- | --- |
| Even | Ping | `0` | `2` | `a_l1_ping`, `b_l1_ping` | `a_l0_ping`, `b_l0_ping` |
| Odd | Pong | `1` | `3` | `a_l1_pong`, `b_l1_pong` | `a_l0_pong`, `b_l0_pong` |

Within the K loop, [asc_lock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_lock.md) and [asc_unlock](../../../../../docs/zh/api/SIMD-API/c_api/sync/asc_unlock.md) manage L1 Buffer and L0 Buffer separately. Because the two levels use different Mutex IDs, MTE2 can reuse an L1 Buffer group as soon as MTE1 finishes reading it, without waiting for the current MMAD to finish.

**Table8**  Double-Buffer Synchronization Dependencies

| Synchronization direction | Mutex ID | Enforced dependency | Buffer reuse condition |
| --- | --- | --- | --- |
| `MTE2 -> MTE1` | L1 Mutex: `0/1` | MTE1 can acquire the same Mutex and read the current L1 Buffer group only after MTE2 has loaded A/B and released the Mutex. | Prevents MTE1 from reading incomplete data in L1 Buffer. |
| `MTE1 -> MTE2` | L1 Mutex: `0/1` | MTE2 can acquire the same Mutex to reuse the L1 Buffer group only after MTE1 has finished reading and released the Mutex. | Prevents MTE2 from overwriting L1 Buffer data still being loaded into L0 Buffer. |
| `MTE1 -> M` | L0 Mutex: `2/3` | M can acquire the same Mutex and execute MMAD only after MTE1 has loaded A/B and released the Mutex. | Prevents MMAD from reading incomplete data in L0 Buffer. |
| `M -> MTE1` | L0 Mutex: `2/3` | MTE1 can acquire the same Mutex to reuse the L0 Buffer group only after MMAD has finished reading and released the Mutex. | Prevents MTE1 from overwriting L0 Buffer data still being computed. |

For example, iteration 0 uses Ping, iteration 1 uses Pong, and iteration 2 returns to Ping. While M computes iteration 0, MTE1 can load the Pong data for iteration 1 and MTE2 can transfer iteration 2 into the released Ping L1 Buffer. In the steady state, the three stages process different K tiles, allowing computation to cover part of the transfer and loading time.

After all 16 K iterations, FIX uses the final L0 Mutex to wait for MMAD to finish. It then calls `asc_copy_l0c2gm` to convert the result from Nz to ND and store it in GM. A final `asc_sync_pipe(PIPE_ALL)` waits for all operations to complete.

Table9 summarizes the main differences between the two implementations.

**Table9**  Single-Buffer and Double-Buffer Comparison

| Comparison | Scenario 0: Single-buffer baseline | Scenario 1: L1 Buffer/L0 Buffer double buffering |
| --- | --- | --- |
| A/B buffers in L1 Buffer | One tile per matrix, 32768 bytes total | Two Ping/Pong tiles per matrix, 65536 bytes total |
| L0A Buffer/L0B Buffer | One tile per matrix, 32768 bytes total | Two Ping/Pong tiles per matrix, 65536 bytes total |
| L0C Buffer | One tile accumulating 16 MMAD iterations | One tile accumulating 16 MMAD iterations |
| A/B buffers used by adjacent K iterations | The same; reuse waits for the previous iteration to finish. | Different; alternates between Ping and Pong. |
| End-of-iteration synchronization | Calls `asc_sync_pipe(PIPE_ALL)` in every iteration. | Uses two L1 Mutexes and two L0 Mutexes for local dependencies and performs full-pipeline synchronization only after the K loop. |
| Cross-iteration pipeline overlap | Not supported | MTE2, MTE1, and M can process different K tiles. |
| Optimization cost | Lower L1 Buffer and L0 Buffer usage | Doubles the space occupied by A/B buffers in L1 Buffer and L0 Buffer. |

## Performance Comparison

The two scenarios change only the buffer count and synchronization. For a valid comparison, use the same hardware, CANN version, input data, and system load, and verify accuracy before collecting performance data.

### Test Conditions

**Table10**  Performance Test Configuration

| Configuration | Value |
| --- | --- |
| Chip version | Ascend 950PR |
| CANN version | CANN 9.1.0 |
| NPU architecture | `dav-3510` |

### Performance Metrics

Use msOpProf to collect performance data and inspect the following fields in `PipeUtilization.csv`.

**Table11**  Performance Metric Descriptions

| Metric | Description |
| --- | --- |
| `Task Duration(μs)` | Total Task execution time. Use this metric for the end-to-end comparison. |
| `Block Num` | Number of Blocks launched by the Kernel. This sample should report 64. |
| `aicore_time(μs)` | Average Task execution time on AI Core. |
| `aic_mac_time(μs)` / `aic_mac_ratio` | Duration and ratio of MMAD execution on the Cube compute unit. |
| `aic_scalar_time(μs)` / `aic_scalar_ratio` | Scalar instruction duration and ratio. |
| `aic_mte1_time(μs)` / `aic_mte1_ratio` | Duration and ratio of L1 Buffer-to-L0A Buffer/L0B Buffer loads on the MTE1 pipeline. |
| `aic_mte2_time(μs)` / `aic_mte2_ratio` | Duration and ratio of GM-to-L1 Buffer transfers on the MTE2 pipeline. |
| `aic_fixpipe_time(μs)` / `aic_fixpipe_ratio` | Duration and ratio of L0C Buffer-to-GM stores on the FIX pipeline. |

Double buffering overlaps MTE2, MTE1, and M, so their durations or ratios cannot be added directly. Use `Task Duration` for the end-to-end comparison and the other metrics to identify where time is spent.

**End-to-End Result**:

Using Scenario 0 as the baseline, the double-buffer speedup is

$$
S = \frac{T_{\text{baseline}}}{T_{\text{double-buffer}}}
  = \frac{37.684}{20.792}
  \approx 1.812
$$

The end-to-end duration reduction is

$$
R = \frac{T_{\text{baseline}} - T_{\text{double-buffer}}}{T_{\text{baseline}}} \times 100\%
  = \frac{37.684 - 20.792}{37.684} \times 100\%
  \approx 44.83\%
$$

`Task Duration` decreases from 37.684μs to 20.792μs, a reduction of 16.892μs or 44.83%, corresponding to a 1.812x speedup. `aicore_time` also decreases by 45.43%, following the same trend as the end-to-end duration.

The two `aic_mac_time` values differ by 0.153μs, so Cube compute time is essentially unchanged. Among the pipeline metrics, `aic_mte2_time` changes most noticeably, decreasing from 21.169μs to 14.863μs. `aic_mte1_time` and `aic_scalar_time` increase, but each absolute increase is below 1μs. Profiler pipeline durations include both execution and wait time, so these values do not show that an individual load or Scalar instruction became slower. `aic_fixpipe_time` differs by only 0.038μs, indicating similar result-store overhead.

**Theoretical Performance Analysis**:

For $M=N=K=1024$, 64 AI Cores, a Cube frequency of 1.65GHz, and $16\times16\times16$ multiply-accumulate operations per AI Core per cycle, the ideal Cube duration is

$$
T_{\text{cube,theory}}
= \frac{M \times N \times K}
       {16 \times 16 \times 16 \times \text{core count} \times \text{Cube frequency}}
= \frac{1024 \times 1024 \times 1024}
       {16 \times 16 \times 16 \times 64 \times 1.65 \times 10^9}
\approx 2.482\ \mu s
$$

The measured `aic_mac_time` values are 7.06μs and 7.213μs, approximately 2.84 and 2.91 times the theoretical value. The theoretical value includes only Cube instructions and excludes K-loop control, address calculation, synchronization, and scheduling. The similar MAC durations show that double buffering does not change the Cube workload; the performance difference comes from overlapping transfer, loading, and computation across iterations.

Each output tile reads its corresponding A and B tiles. A is read by eight N-direction tiles, and B is read by eight M-direction tiles. Without considering cache hits, the theoretical input traffic is

$$
D_{\text{read}}
= \left(\frac{N}{TILE_N} \times M \times K
+ \frac{M}{TILE_M} \times K \times N\right) \times sizeof(half)
= 32\ \text{MiB}
$$

The float32 output traffic is

$$
D_{\text{write}} = M \times N \times sizeof(float) = 4\ \text{MiB}
$$

**Pipeline and Bandwidth Analysis**:

Using the 32MiB theoretical input traffic and `aic_mte2_time`, the estimated aggregate read bandwidth of Scenario 0 is

$$
BW_{\text{read,baseline}}
= \frac{32\ \text{MiB}}{21.169\ \mu s}
\approx 1.585\ \text{TB/s}
$$

For Scenario 1, it is

$$
BW_{\text{read,double-buffer}}
= \frac{32\ \text{MiB}}{14.863\ \mu s}
\approx 2.258\ \text{TB/s}
$$

The Scenario 1 estimate is 42.43% higher. This calculation uses the total volume repeatedly read by all cores and is affected by both L2 Cache hits and ND-to-Nz conversion. It does not represent physical HBM bandwidth.

In Scenario 0, the MAC, MTE1, MTE2, and FIX ratios sum to 89.5%, so the stages run mostly serially. In Scenario 1, they sum to 138.2%, showing that transfer, loading, and computation overlap across K iterations.

`aic_mte2_ratio` rises from 58.0% to 74.7%, while `aic_mte2_time` decreases by 29.79%. The ratio rises because total `aicore_time` is shorter, not because MTE2 became slower. MTE2 still has the highest ratio, so further optimization should focus on input transfer and data reuse.

#### Conclusion

Ping/Pong double buffering allows MTE2, MTE1, and M to process different K tiles. In this test, `Task Duration` decreases by 16.892μs, or 44.83%. The tradeoff is that A/B usage doubles in both L1 Buffer and L0 Buffer, and Ping/Pong selection and Mutex synchronization add overhead.

MTE2 still accounts for the largest share of execution time. Further work can evaluate tile size, UnitFlag, L2 Cache reuse, and transfer granularity, with Memory and L2 Cache metrics used to separate the effects of HBM access and cache reuse.

## Build and Run

Configure the CANN environment:

```bash
source ${install_path}/cann/set_env.sh
```

Build and run one scenario from this sample directory:

```bash
SCENARIO_NUM=0
mkdir -p build && cd build
cmake -DCMAKE_ASC_ARCHITECTURES=dav-3510 -DSCENARIO_NUM=${SCENARIO_NUM} ..
make -j
python3 ../scripts/gen_data.py
./c_api_mmad_double_buffer_example
python3 ../scripts/verify_result.py output/output.bin output/golden.bin
```

Set `SCENARIO_NUM=1`, then rerun CMake, build, execution, and verification to test the double-buffer scenario. Clear the CMake cache before switching scenarios.

**Table13**  Build Options

| Build option | Values | Description |
| --- | --- | --- |

| `CMAKE_ASC_RUN_MODE` | `npu` (default), `cpu`, `sim` | Run mode |
| `SCENARIO_NUM` | `0`, `1` (default) | Single-buffer baseline or double-buffer optimization |

test pass!

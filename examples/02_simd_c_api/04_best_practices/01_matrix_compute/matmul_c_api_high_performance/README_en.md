# Matmul C-API High-Performance Sample

## Overview

This sample implements float16 matrix multiplication with the Ascend C C-API. It provides a single-buffer baseline and an L1 Buffer/L0 Buffer Ping/Pong double-buffer scenario. Both scenarios use the same matrix dimensions, Cube tiling, core count, and compute APIs so that the performance effect of the three-stage pipeline can be compared directly.

## Sample Description

The sample computes `C = A x B`. A and B are generated with a fixed random seed. B is transposed before being written to the input file so that the K dimension is contiguous in GM and can be transferred one K tile at a time. The input, output, and golden data are listed below.

**Table2**  Input and Output Data Specifications

| Data | Input/Output | Data file | Data type | Logical shape | File and GM layout | Description |
| --- | --- | --- | --- | --- | --- | --- |
| A | Input | `input/x1_gm.bin` | float16 | `[M, K] = [1024, 1024]` | ND, stored as `[M, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| B | Input | `input/x2_gm.bin` | float16 | `[K, N] = [1024, 1024]` | Transposed ND, stored as `[N, K]` | Randomly generated in the range `[-0.1, 0.1)`. |
| C | Output | `output/output.bin` | float32 | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Result computed by the Kernel |
| golden | Golden data | `output/golden.bin` | float32 | `[M, N] = [1024, 1024]` | ND, stored as `[M, N]` | Generated by running `np.matmul` on inputs cast to float32. |

The matrices are tiled along the M, N, and K axes. The tiling and multicore parameters are listed below.

**Table3**  Matrix Tiling and Multicore Parameters

| Parameter | Value | Description |
| --- | --- | --- |
| Matrix dimensions | `[M, N, K] = [1024, 1024, 1024]` | `C[M, N] = A[M, K] x B[K, N]` |
| Base tile | `[TILE_M, TILE_N, TILE_K] = [128, 128, 64]` | M, N, and K ranges of each MMAD iteration |
| Number of M tiles | 8 | `MATRIX_M / TILE_M` |
| Number of N tiles | 8 | `MATRIX_N / TILE_N` |
| Logical Cube blocks | 64 | `8 * 8`; each block computes one output tile. |
| Output tile per block | `[128, 128]` float32 | 16384 elements, occupying 65536 bytes in L0C Buffer. |
| K iterations | 16 | `MATRIX_K / TILE_K` |
| A tile per iteration | `[128, 64]` float16 | 8192 elements, occupying 16384 bytes. |
| B tile per iteration | `[128, 64]` float16 | A tile of transposed `[N, K]` data, with 8192 elements occupying 16384 bytes. |

`block_idx` determines the output tile assigned to each logical Cube block: `m_tile_idx = block_idx % 8` and `n_tile_idx = block_idx / 8`. Each block computes one fixed `[128, 128]` C tile and accumulates 16 A/B tiles along the K axis. The first `asc_mmad` iteration initializes L0C Buffer, and the remaining 15 iterations accumulate into the same L0C Buffer tile.

A complete matrix multiplication moves data through GM -> L1 Buffer -> L0A Buffer/L0B Buffer -> L0C Buffer -> GM. The layouts in each storage unit are listed below.

**Table4**  Data Movement Path and Layouts

| Storage unit | Data | Layout | Data movement or compute API |
| --- | --- | --- | --- |
| GM | A and transposed B | ND | - |
| L1 Buffer | A and B tiles | Nz | `asc_set_gm2l1_nz_para`, `asc_copy_gm2l1_nd2nz` |
| L0A Buffer | A tile | Nz | `asc_copy_l12l0a` |
| L0B Buffer | B tile | Zn | `asc_copy_l12l0b` |
| L0C Buffer | C output tile | Nz, float32 | `asc_mmad` |
| GM | C | ND, float32 | `asc_set_l0c2gm_nz2nd`, `asc_copy_l0c2gm` |

The `SCENARIO_NUM` build option selects the single-buffer baseline or the L1 Buffer/L0 Buffer double-buffer optimization. Both scenarios use identical inputs, matrix dimensions, tiling, block count, and MMAD workload. They differ only in the number of A/B buffers and pipeline synchronization.

**Table5**  Scenario Configuration

| `SCENARIO_NUM` | Kernel | Scenario | L1 Buffer | L0A Buffer/L0B Buffer | L0C Buffer | Pipeline behavior |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | `mmad_baseline` | Single-buffer baseline | One A and one B tile, 32768 bytes total | One A and one B tile, 32768 bytes total | One tile, 65536 bytes | Completes load, L0 Buffer transfer, MMAD, and full synchronization before processing the next K tile. |
| 1 | `mmad_double_buffer` | Double-buffer optimization | Ping/Pong A and B tiles, 65536 bytes total | Ping/Pong A and B tiles, 65536 bytes total | One tile, 65536 bytes | MTE2, MTE1, and M process different K tiles with cross-iteration overlap. |

### Scenario 0: Single-Buffer Baseline

The baseline Kernel, `mmad_baseline`, allocates only one A/B buffer group across L1 Buffer, L0A Buffer, and L0B Buffer. All 16 K iterations repeatedly use the same buffers. Their sizes and purposes are listed below.

**Table6**  Single-Buffer Configuration

| Buffer | Array | Elements | Bytes | Purpose |
| --- | --- | --- | --- | --- |
| L1 Buffer A | `a_l1` | 8192 float16 elements | 16384 | Stores the current A tile loaded from GM and converted to Nz. |
| L1 Buffer B | `b_l1` | 8192 float16 elements | 16384 | Stores the current B tile loaded from GM and converted to Nz. |
| L0A Buffer | `a_l0` | 8192 float16 elements | 16384 | Stores the current A tile used by MMAD. |
| L0B Buffer | `b_l0` | 8192 float16 elements | 16384 | Stores the current B tile used by MMAD. |
| L0C Buffer | `c_l0` | 16384 float32 elements | 65536 | Accumulates the C output tile over 16 MMAD iterations. |

Each K iteration runs in the following order:

1. The MTE2 pipeline calls `copy_a_to_l1` and `copy_b_to_l1`. `asc_copy_gm2l1_nd2nz` moves the current A/B tiles from GM to L1 Buffer and converts them from ND to Nz.
2. After MTE2 finishes loading and calls `asc_unlock` to release the Mutex, MTE1 acquires the same Mutex through `asc_lock` and calls `asc_copy_l12l0a` and `asc_copy_l12l0b` to load A and B into L0A Buffer and L0B Buffer.
3. After MTE1 finishes loading and releases the Mutex, the M pipeline acquires the same Mutex and calls `asc_mmad` to compute `[128, 64] x [64, 128]`. Iteration 0 initializes L0C Buffer, while subsequent iterations accumulate into L0C Buffer.
4. At the end of every iteration, `asc_sync_pipe(PIPE_ALL)` waits for MTE2, MTE1, and M to finish before the next iteration can overwrite the same buffers in L1 Buffer and L0 Buffer.

Therefore, while M is computing K tile n, MTE1 cannot load K tile n+1 and MTE2 cannot prefetch a later tile. The three stages advance sequentially within each iteration and cannot overlap across K iterations. This scenario provides the performance baseline for the L1 Buffer/L0 Buffer double-buffer optimization.

### Scenario 1: L1 Buffer/L0 Buffer Double Buffering

The optimized Kernel, `mmad_double_buffer`, allocates Ping/Pong A and B buffer groups in both L1 Buffer and L0 Buffer. Even-numbered K iterations use Ping with Mutex 0 for L1 Buffer synchronization and Mutex 2 for L0 Buffer synchronization. Odd-numbered iterations use Pong with Mutex 1 for L1 Buffer synchronization and Mutex 3 for L0 Buffer synchronization. Adjacent K iterations therefore do not access the same buffers in L1 Buffer or L0 Buffer. L0C Buffer is not double buffered: all 16 MMAD iterations accumulate into the same `c_l0` output tile.

**Table7**  Ping/Pong Buffer Configuration

| K iteration | Buffer group | L1 Mutex ID | L0 Mutex ID | L1 Buffer | L0 Buffer |
| --- | --- | --- | --- | --- | --- |
| Even | Ping | `0` | `2` | `a_l1_ping`, `b_l1_ping` | `a_l0_ping`, `b_l0_ping` |
| Odd | Pong | `1` | `3` | `a_l1_pong`, `b_l1_pong` | `a_l0_pong`, `b_l0_pong` |

Within the K loop, [asc_lock](../../../../../docs/zh/api/SIMD-API/C-API/sync/asc_lock.md) and [asc_unlock](../../../../../docs/zh/api/SIMD-API/C-API/sync/asc_unlock.md) establish independent Mutex chains for L1 Buffer and L0 Buffer to control buffer production, consumption, and reuse. L1 Buffer and L0 Buffer use different Mutex IDs, so MTE2 waits only for MTE1 to finish reading L1 Buffer instead of waiting for the current MMAD to finish.

**Table8**  Double-Buffer Synchronization Dependencies

| Synchronization direction | Mutex ID | Enforced dependency | Buffer reuse condition |
| --- | --- | --- | --- |
| `MTE2 -> MTE1` | L1 Mutex: `0/1` | MTE1 can acquire the same Mutex and read the current L1 Buffer group only after MTE2 has loaded A/B and released the Mutex. | Prevents MTE1 from reading incomplete data in L1 Buffer. |
| `MTE1 -> MTE2` | L1 Mutex: `0/1` | MTE2 can acquire the same Mutex to reuse the L1 Buffer group only after MTE1 has finished reading and released the Mutex. | Prevents MTE2 from overwriting L1 Buffer data still being loaded into L0 Buffer. |
| `MTE1 -> M` | L0 Mutex: `2/3` | M can acquire the same Mutex and execute MMAD only after MTE1 has loaded A/B and released the Mutex. | Prevents MMAD from reading incomplete data in L0 Buffer. |
| `M -> MTE1` | L0 Mutex: `2/3` | MTE1 can acquire the same Mutex to reuse the L0 Buffer group only after MMAD has finished reading and released the Mutex. | Prevents MTE1 from overwriting L0 Buffer data still being computed. |

For example, K iteration 0 uses Ping, iteration 1 uses Pong, and iteration 2 reuses Ping. While M computes iteration 0 with Ping, MTE1 can load the Pong data for iteration 1 from L1 Buffer to L0 Buffer, and MTE2 can prefetch iteration 2 into the released Ping buffers in L1 Buffer. In the steady state, MTE2, MTE1, and M can process adjacent K tiles concurrently, hiding part of the GM-to-L1 Buffer transfer and L1 Buffer-to-L0 Buffer load latency.

After all 16 K iterations, the FIX pipeline acquires the L0 Mutex used by the final iteration. Because the final MMAD releases this Mutex, acquiring it guarantees that L0C Buffer accumulation is complete. FIX then calls `asc_copy_l0c2gm` to convert the L0C Buffer result from Nz to ND and store it in GM, followed by `asc_sync_pipe(PIPE_ALL)` to wait for all pipelines to finish.

The main differences between the two scenarios are summarized below.

**Table9**  Single-Buffer and Double-Buffer Comparison

| Comparison | Scenario 0: Single-buffer baseline | Scenario 1: L1 Buffer/L0 Buffer double buffering |
| --- | --- | --- |
| A/B buffers in L1 Buffer | One tile per matrix, 32768 bytes total | Two Ping/Pong tiles per matrix, 65536 bytes total |
| L0A Buffer/L0B Buffer | One tile per matrix, 32768 bytes total | Two Ping/Pong tiles per matrix, 65536 bytes total |
| L0C Buffer | One tile accumulating 16 MMAD iterations | One tile accumulating 16 MMAD iterations |
| A/B buffers used by adjacent K iterations | The same; reuse waits for the previous iteration to finish. | Different; alternates between Ping and Pong. |
| End-of-iteration synchronization | Calls `asc_sync_pipe(PIPE_ALL)` in every iteration. | Uses two L1 Mutexes and two L0 Mutexes for local dependencies and performs full-pipeline synchronization only after the K loop. |
| Cross-iteration pipeline overlap | Not supported | MTE2, MTE1, and M can process different K tiles. |
| Optimization cost | Lower L1 Buffer and L0 Buffer usage | Doubles the space occupied by A/B buffers in L1 Buffer and L0 Buffer. |

```bash

cat ./OPPROF_*/PipeUtilization.csv
cd ..
```

Change `SCENARIO_NUM` to `1` and repeat the procedure. Collect at least five valid runs for each scenario, record the `Task Duration` of each run, and enter the median in the result table. Use the other pipeline metrics from the run corresponding to that median.

**Optimization Effect Analysis (To Be Completed After Measurement)**:

Let $T_{\text{baseline}}$ be the `Task Duration` of Scenario 0 and $T_{\text{double-buffer}}$ be that of Scenario 1. Using Scenario 0 as the baseline, the double-buffer speedup is

$$
S = \frac{T_{\text{baseline}}}{T_{\text{double-buffer}}}
$$

The end-to-end duration reduction is

$$
R = \frac{T_{\text{baseline}} - T_{\text{double-buffer}}}{T_{\text{baseline}}} \times 100\%
$$

After adding the measurements, analyze the following:

- Compare `Task Duration` and report the speedup and duration reduction.
- Compare `aic_mte2_time`, `aic_mte1_time`, and `aic_mac_time` to evaluate overlap among GM-to-L1 Buffer transfer, L1 Buffer-to-L0 Buffer load, and Cube computation.
- Compare the pipeline ratios to determine whether the bottleneck moves after optimization.
- If `Task Duration` changes little, analyze the Cube compute bottleneck, data movement bandwidth, and synchronization overhead. Double buffering can reduce end-to-end duration only when input transfer, data load, and computation provide useful overlap.

**Theoretical Performance Analysis**:

This sample uses $M=N=K=1024$ and 64 AI Cores. The Ascend 950PR Cube runs at 1.65GHz, and each AI Core performs $16\times16\times16$ multiply-accumulate operations per cycle. Considering only ideal Cube throughput and excluding data movement, format conversion, pipeline synchronization, instruction scheduling, and other overhead, the theoretical Cube duration is

$$
T_{\text{cube,theory}}
= \frac{M \times N \times K}
       {16 \times 16 \times 16 \times \text{core count} \times \text{Cube frequency}}
= \frac{1024 \times 1024 \times 1024}
       {16 \times 16 \times 16 \times 64 \times 1.65 \times 10^9}
\approx 2.482\ \mu s
$$

After collecting measurements, calculate the deviation of `aic_mac_time` from the theoretical Cube duration for both scenarios as follows:

$$
E_{\text{cube}}
= \frac{T_{\text{mac,measured}} - T_{\text{cube,theory}}}
       {T_{\text{cube,theory}}} \times 100\%
$$

Each output tile reads its corresponding A tile and B tile from GM. A is read repeatedly by eight N-direction tiles, and B is read repeatedly by eight M-direction tiles. Therefore, without considering cache hits, the theoretical total input traffic is

$$
D_{\text{read}}
= \left(\frac{N}{TILE_N} \times M \times K
+ \frac{M}{TILE_M} \times K \times N\right) \times sizeof(half)
= 32\ \text{MiB}
$$

The float32 output traffic is

$$
D_{\text{write}} = M \times N \times sizeof(float) = 4\ \text{MiB}
$$

The actual MTE2 duration also depends on L2 Cache hits, ND-to-Nz conversion, and transfer efficiency, so no theoretical end-to-end duration is given before measurement. After testing, use `aic_mte2_time` together with the Memory metrics to calculate effective read bandwidth and determine whether the sample is Cube-bound or transfer-bound. The theoretical Cube duration is only an ideal compute lower bound and is not the theoretical duration of the complete Kernel.

#### Double-Buffer Optimization Summary

- **Current implementation**: Scenario 1 uses two Ping/Pong groups in L1 Buffer and L0 Buffer so that MTE2 transfer, MTE1 loading, and Cube computation can process different K tiles. The end-to-end gain and degree of pipeline overlap remain to be measured on hardware.
- **Advantages**: Double buffering hides part of the data-transfer and loading wait time without changing the matrix workload or result. Independent L1 and L0 Mutexes allow MTE2 to prefetch subsequent data after MTE1 releases L1 Buffer, without waiting for the current MMAD to finish.
- **Limitations**: A/B usage increases from 32768 bytes to 65536 bytes in L1 Buffer and from 32768 bytes to 65536 bytes in L0A Buffer/L0B Buffer. Ping/Pong selection and Mutex synchronization also introduce overhead. If Cube computation is already the main bottleneck, or if transfer and loading durations per tile are short, the end-to-end gain from double buffering may be limited.
- **Future optimization**: After collecting both scenarios on hardware, use the MTE2, MTE1, Cube, and FIX metrics to identify the bottleneck. With identical workloads maintained between scenarios, further evaluations can cover different tile sizes, UnitFlag, L2 Cache reuse, and transfer granularity.

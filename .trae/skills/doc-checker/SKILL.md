# 文档写作规范检查技能

## 技能用途

根据 CANN 项目文档写作规范，检查用户提供的 Markdown 文档是否符合标准格式。

## 检查项目清单（一定要逐项检查，不能跳过或者忽略）

### 1. 标点符号规范
- [ ] 中文描述使用中文标点（，。：；？！""），不使用英文符号
- [ ] 句子末尾必须有句号，以下情况例外（不加句号）：
  - 表格单元格内的短语（如表头、参数名、简要描述）
  - 列表项为短语时（仅一个名词或简短说明）
  - 标题末尾
  - 代码块内的内容
- [ ] 中英文混用时英文前后不加空格
- [ ] 单位与数字之间不加空格（如：50m、10kg、64Kbit/s）

### 2. Markdown 格式规范
- [ ] 标题使用 `# [空格][标题名]` 格式
- [ ] 标题级别逐级递增，最多四级
- [ ] 标题末尾不加标点
- [ ] 标题中不能手工添加序号（如 "## 1. 安装" 应改为 "## 安装"）
- [ ] 标题与正文之间空一行

### 3. 列表规范
- [ ] 有序列表使用数字加 `.` 号
- [ ] 无序列表统一使用 `*`、`+` 或 `-`（同一列表保持一致）
- [ ] 列表嵌套缩进 2/4 个空格（不使用 Tab）
- [ ] 列表项为短语时不加标点，为句子时加句号
- [ ] 列表前后需要空行：列表与上下文的正文之间必须空一行分隔

  **正确示例：**
  ```
  文字描述如下：

  - 列表项一
  - 列表项二

  继续正文。
  ```

  **错误示例：**
  ```
  文字描述如下：
  - 列表项一
  - 列表项二
  继续正文。
  ```

### 4. 表格规范
- [ ] 使用标准 Markdown 表格语法，不使用 HTML 表格
- [ ] 表格格式：`| 表头 | 表头 |` 后跟 `| --- | --- |`
- [ ] 表格内换行使用 `<br>`
- [ ] 表格前后加换行：
反例：
**表 1**  模板参数说明
| 参数名 | 描述 |
|--------|------|
| T | 设定原子操作不同的数据类型。 |
正例：
**表 1**  模板参数说明

| 参数名 | 描述 |
|--------|------|
| T | 设定原子操作不同的数据类型。 |

### 5. 代码块规范
- [ ] 行内代码使用 1 对反引号：`` `code` ``
- [ ] 块级代码使用 3 个反引号，声明语言类型
- [ ] 代码块上下空一行
- [ ] 代码块内缩进 2/4 个空格

### 6. 注释符号规范
文档中会出现以下注释符号，代表提示的重要程度，须使用标准 GFM 警示块语法。正文中单独出现的"说明"、"注意"、"警告"等词语不在此检查项范围内，仅检查以 `>[!TYPE]` 开头的块级引用格式。

- [ ] 说明：提供辅助性提示或参考信息，格式为：

    ```text
    >[!NOTE]说明
    >正文
    ```

- [ ] 注意：如未按此操作，可能导致任务中断或结果异常（可恢复），格式为：

    ```text
    >[!CAUTION]注意
    >正文
    ```

- [ ] 警告：如不避免，可能导致轻微或中度伤害，格式为：

    ```text
    >[!WARNING]警告
    >正文
    ```

### 7. 图片规范
- [ ] 使用相对路径引用图片
- [ ] 路径使用正斜杠 `/`（不是反斜杠 `\`）
- [ ] 使用 `![](图片路径)` 格式
- [ ] 所有图片统一存放在 `docs/api/figures/` 目录下，引用时根据不同文档位置计算相对路径
- [ ] 所有图片的文件名必须是英文小写加下划线（如：atomic_operation_pipelined_data_movement_diagram.png、atomic_operation_3.png）
- [ ] 如果有图注（没有图注的话就忽略），图注（如"图 1"、"图 2"）必须写在图片上方，格式为 `**图 n**  图片标题`（注意 `**图 n**` 和标题之间是两个空格）
  **正确示例（在 `docs/api/SIMD-API/基础API/原子操作/原子操作概述.md` 中引用）：**
  ```
  **图 1**  数据搬运随路原子累加效果示意图
  ![](../../../figures/atomic_operation_pipelined_data_movement_diagram.png)
  ```
  **错误示例：**
  ❌ 路径使用了反斜杠
  ![](..\..\..\figures\atomic_operation_pipelined_data_movement_diagram.png)
  ```
### 8. 图和表编号规范
- [ ] 文中的图和表从1开始递增编号（如"图 1"、"图 2"；"表 1"、"表 2"），不允许中断或跳号
- [ ] 图注和表格标题严格区分，图上方为"**图 n**  标题"，表上方为"**表 n**  标题"
- [ ] 同一个文档中不同章节共享同一个图/表编号序列，不按章节重新编号

  **正确示例（依次出现时编号连续）：**
  ```
  **图 1**  xxx
  ![](../figures/xxx.png)

  **图 2**  xxx
  ![](../figures/xxx.png)

  **表 1**  xxx
  | a | b |
  ```

  **错误示例：**
  ```
  **图 1**  xxx        ← 正确
  **图 3**  xxx        ← ❌ 跳过了图2
  ```

### 9. 链接与锚点
- [ ] 链接目标有效，避免死链。
- [ ] 引用以下几个手册时使用书名号包裹并添加网址链接：Ascend C API参考、毕昇编译器手册、Ascend C 算子实践参考、Ascend C 编程指南，其余普通的网址不需要书名号。
- [ ] 图片/表格引用使用锚点

### 10. 接口引用路径跳转
- [ ] 正文中非本文档介绍的接口，**第一次出现**时需要加上相对路径跳转链接，后续出现不再需要重复添加
- [ ] 跳转链接使用相对路径，指向该接口对应的 Markdown 文档

  **正确示例（在 SetAtomicAdd.md 文档中引用其他接口）：**
  ```
  SetAtomicAdd内部已集成与[SetAtomicType](SetAtomicType.md)相同的功能。
  ```

  **错误示例：**
  ```
  SetAtomicAdd内部已集成与SetAtomicType相同的功能。  ← ❌ 第一次出现未加跳转链接
  ```

  **注意**：本文档自身介绍的接口名称无需添加跳转链接；仅被引用的其他接口才需要。

### 11. 芯片过滤标签（多芯片差异内容）
- [ ] 使用 `<cann-filter npu-type="xxx">` 标签
- [ ] 支持的芯片类型：950、910b、A3、910、310p、310b、x90、9030
- [ ] 标签内需显式说明芯片型号
- [ ] `npu-type` 的值与标签内描述的芯片产品名称必须一致，参照以下映射关系（来源：`references/芯片与标签映射关系.md`）：

  | `npu-type` | 对应的芯片产品名称 |
  |------------|-------------------|
  | 950 | `Ascend 950PR/Ascend 950DT` |
  | A3 | `Atlas A3 训练系列产品/Atlas A3 推理系列产品` |
  | 910b | `Atlas A2 训练系列产品/Atlas A2 推理系列产品` |
  | 910 | `Atlas 训练系列产品` |
  | 310p | `Atlas 推理系列产品 Vector Core` |
  | 310p | `Atlas 推理系列产品 AI Core` |
  | 310b | `Atlas 200I/500 A2 推理产品` |
  | x90 | `Kirin X90` |
  | 9030 | `Kirin 9030` |

  **反例**（标签值与描述不匹配）：
  ```
  <cann-filter npu-type="310b">
  Atlas 推理系列产品    ← ❌ 310b 对应的应是 "Atlas 200I/500 A2 推理产品"
  </cann-filter>
  ```

- [ ] 产品支持情况表格中，芯片的排列顺序应按照 950 → A3 → 910b → 310b → 310p → 910 的顺序排列（即支持的产品优先排列，不支持的产品排列在最后，同类产品中位宽越大越靠前）。当存在多个 `<cann-filter>` 块罗列时，块之间的顺序也应遵循此规则。

  **正确示例（芯片顺序）：**
  ```
  | 产品 | 是否支持 |
  |------|----------|
  | <cann-filter npu-type="950">... | √</cann-filter> |
  | <cann-filter npu-type="A3">... | √</cann-filter> |
  | <cann-filter npu-type="910b">... | √</cann-filter> |
  | <cann-filter npu-type="310b">... | x</cann-filter> |
  | <cann-filter npu-type="310p">... | x</cann-filter> |
  | <cann-filter npu-type="910">... | x</cann-filter> |
  ```

  **错误示例（芯片顺序混乱）：**
  ```
  | 产品 | 是否支持 |
  |------|----------|
  | <cann-filter npu-type="910b">... | √</cann-filter> |   ← ❌ 应为950在前
  | <cann-filter npu-type="A3">... | √</cann-filter> |
  | <cann-filter npu-type="950">... | √</cann-filter> |   ← ❌ 950应排在910b之前
  | <cann-filter npu-type="910">... | x</cann-filter> |
  | <cann-filter npu-type="310b">... | x</cann-filter> |
  | <cann-filter npu-type="310p">... | x</cann-filter> |
  ```

### 12. 数据类型规范
- [ ] 数据类型的写法与代码中保持一致，必须使用标准类型名（如 `int8_t`），不能简写或变体（如 ❌ `Int8` / `int8` / `S8`）
- [ ] 数据类型的写作顺序保持一致（原则：位宽从小到大、有符号数→无符号数→浮点数、浮点数按指数位大小排序）：bool、int4b_t、int8_t、uint8_t、fp4x2_e2m1_t、fp4x2_e1m2_t、hifloat8_t、fp8_e8m0_t、fp8_e5m2_t、fp8_e4m3fn_t、int16_t、uint16_t、half、bfloat16_t、int32_t、uint32_t、float、complex32、int64_t、uint64_t、double、complex64
- [ ] 接口支持的数据类型只和位宽有关时，可通过位宽表达：b8、b16、b32、b64，注意表示位宽时，字母b不能大写。

### 13. API 文档章节结构（API 文件必检）
检查 API 文档是否包含以下标准章节（按顺序，一个也不能缺）：
- [ ] 产品支持情况
- [ ] 功能说明
- [ ] 函数原型
- [ ] 参数说明
- [ ] 数据类型
- [ ] 返回值说明
- [ ] 流水类型
- [ ] 约束说明
- [ ] 调用示例

注：概述类索引文件除外，单个 API 文档应包含上述章节。

### 14. 术语规范
检查文档中是否使用了非标准术语，遇到可疑短语（与术语类似的缩写/简写）应提出警示。

**缓冲区术语**（必须带"Buffer"后缀）：
- ✅ L0A Buffer / ❌ L0A / ❌ L0A
- ✅ L0B Buffer / ❌ L0B / ❌ LOB
- ✅ L0C Buffer / ❌ L0C / ❌ LOC
- ✅ L1 Buffer / ❌ L1（当指代物理缓冲区时）
- ✅ Unified Buffer / ✅ UB（两者均可）
- ✅ BiasTable Buffer / ❌ BiasTable
- ✅ Fixpipe Buffer / ❌ Fixpipe

**常见缩写规范写法**：
- ✅ Global Memory / ✅ GM（两者均可）
- ✅ Unified Buffer / ✅ UB（两者均可）
- ✅ AI Core / ❌ AICore
- ✅ Cube Core / ✅ Vector Core / ✅ Scalar
- ✅ Cube Unit / ✅ Vector Unit / ✅ Scalar Unit

**芯片产品名称规范写法**：
- ✅ Atlas 训练系列产品 / ❌ Atlas训练系列产品
- ✅ Atlas A2 训练系列产品 / ❌ Atlas A2训练系列产品
- ✅ Atlas 推理系列产品 / ❌ Atlas推理系列产品
- ✅ Ascend 950PR / ❌ ascend 950PR
- ✅ Ascend 950DT / ❌ ascend 950DT

**数据通路写法**：
- ✅ VECOUT->GM / ✅ UB->GM
- ❌ VECOUT → GM（使用 `->` 而非 `→`）

**检查原则**：遇到可疑的短语（如单独出现的 L0C、L1、L0A 等不带 Buffer 后缀的缓冲区名称），应提出警示并建议修正为标准术语。代码块内的内容不检查术语。

术语标准参考来源：`references/terminology.md`（基于项目本地术语表整理，比网页版更全面，包含80+术语）

### 15. API 名称规范
- [ ] 正文中提及的 API 函数名/接口名需用反引号 `` ` `` 包裹
- [ ] 已作为链接文本的 API 名称除外（如 `[SetAtomicAdd](...)`）
- [ ] 代码块内的 API 名称不需额外处理

### 16. 错别字与语病检查
检查文档中是否存在错别字或语病，重点关注以下常见问题：

**常见错别字**：
- 的/得/地 混用（"正确的使用" → "正确地使用"）
- 其他/其它（统一用"其他"，不用"其它"）
- 示例/实例（"调用示例" / "代码示例"，注意不要写成"实例"）
- 即/既混淆（"即使" / "既然"）
- 与/于混淆、以/已混淆
- 重叠字（"的的"、"了了"等）
- 拼音遗留（如 ing → "进行"误写为"jinxing"）

**常见语病**：
- 谓语/宾语残缺（如"通过...，使..."缺少主语）
- 搭配不当（如"提高...水平"而不是"提高...质量"本身）
- 虚词滥用（多余的"的"、"了"、"进行"等）
- 语序混乱（修饰语位置错误导致歧义）
- 前后矛盾（如"必须...也可以不"）
- 结构杂糅（如"是由于...导致的" → "是由于..."或"是...导致的"）

**检查原则**：代码块内的内容不检查错别字与语病。

## 使用流程

1. **读取文件**：使用 `read_file` 工具读取用户指定的 Markdown 文件
2. **逐项检查**：按照上述检查清单逐项核对文档内容
3. **输出报告**：列出所有发现的问题，格式如下：
   ```
   ## 文档检查报告

   文件：xxx.md

   ### 发现的问题

   | # | 检查项 | 位置 | 问题描述 | 修改建议 |
   |---|--------|------|----------|----------|
   | 1 | **[标点符号]** | [第 XX 行](file:///绝对路径:XX) | 中文内容使用了英文逗号 | 将 `,` 改为 `，` |
   | 2 | **[表格格式]** | [第 XX 行](file:///绝对路径:XX) | 使用了 HTML 表格 | 改为 Markdown 表格 |
   ...

   ### 合格项

   - [x] 标题格式正确
   - [x] 代码块语法正确
   ...
   ```
4. **跳转功能**：报告中每个问题的"位置"列提供可点击链接，格式为 `[第 XX 行](file:///绝对路径:XX)`，用户点击后可直接跳转到文档对应行。绝对路径从读取文件时获取。
5. **修改建议与确认**：报告输出后，使用 `ask_followup_question` 工具将所有问题逐项（或分批）列出，每项包含：
   - 问题描述
   - 原文内容
   - 建议修改为的内容
   - 选项：`全部接受` / `全部拒绝` / `逐项确认`
   
   若用户选择"逐项确认"，则对每项单独询问"接受/拒绝"；若选择"全部接受"，则批量执行所有修改；若选择"全部拒绝"，则不修改。
   
   用户确认后，使用 `replace_in_file` 工具逐项执行修改。

# 中级性能优化<a name="ZH-CN_TOPIC_000000_GELU_REG_MID"></a>

本节以Gelu算子为例，介绍在基础API实现上启用RegBase API和VF融合能力的优化方法。通过寄存器级别的向量计算接口减少中间数据的Load/Store开销，显著降低向量指令耗时。

## 概述

本节在[入门功能落地](./入门功能落地.md)基础API实现的基础上，引入以下优化方法：

**优化路径**：
- Case 1: 启用RegBase API和VF融合能力

本章节性能数据在Ascend 950系列产品上运行得到，样例实现的是固定shape为8192×8192的Gelu计算，数据类型为float。

## Case 1: 启用RegBase API和VF融合能力

**实现方式**：参考 `KernelGelu::GeluVfBasic()` 函数实现

将基础API转换为RegBase API，使用寄存器级别的向量计算接口，减少数据在UB和Reg之间的交互。

**关键代码**：
```cpp
__simd_vf__ inline void GeluVfBasic(
    __ubuf__ float* xAddr, __ubuf__ float* yAddr, uint32_t n, uint32_t loopNum)
{
    constexpr uint32_t oneRepeatSize = AscendC::GetVecLen() / sizeof(float);
    AscendC::Reg::MaskReg mask;
    AscendC::Reg::RegTensor<float> xReg, yReg;

    for (uint16_t i = 0; i < loopNum; ++i) {
        mask = AscendC::Reg::UpdateMask<float>(n);
        AscendC::Reg::LoadAlign(xReg, xAddr + i * oneRepeatSize);
        AscendC::Reg::Mul(yReg, xReg, xReg, mask);
        AscendC::Reg::Mul(yReg, yReg, xReg, mask);
        AscendC::Reg::Muls(yReg, yReg, COEFF_A, mask);
        AscendC::Reg::Add(yReg, xReg, yReg, mask);
        AscendC::Reg::Muls(yReg, yReg, COEFF_B, mask);
        AscendC::Reg::Exp(yReg, yReg, mask);
        AscendC::Reg::Adds(yReg, yReg, 1.0f, mask);
        AscendC::Reg::Div(yReg, xReg, yReg, mask);
        AscendC::Reg::StoreAlign(yAddr + i * oneRepeatSize, yReg, mask);
    }
}
```

**VF函数调用**：
```cpp
__aicore__ inline void GeluRegBaseCompute(
    const AscendC::LocalTensor<float>& xLocal,
    const AscendC::LocalTensor<float>& yLocal, uint32_t n)
{
    constexpr uint32_t oneRepeatSize = AscendC::GetVecLen() / sizeof(float);
    uint32_t loopNum = AscendC::CeilDivision(n, oneRepeatSize);
    __ubuf__ float* xAddr = (__ubuf__ float*)xLocal.GetPhyAddr();
    __ubuf__ float* yAddr = (__ubuf__ float*)yLocal.GetPhyAddr();
    asc_vf_call<GeluVfBasic>(xAddr, yAddr, n, loopNum);
}
```

**样例配置**：
- 多核切分：M方向分2份，N方向32份，共计64份数据，分布到64core上计算
- `tileLen = 8192` 为每次搬运和计算的数据元素个数

**优化手段**：
- **RegBase API优势**：
  - 寄存器级别的数据访问，减少中间数据的Load/Store开销
  - 支持Hardware Loop优化，循环可被优化为硬件级向量循环
- **VF融合（Vector Function Fusion）**：
  - 将多条向量指令融合到一个VF函数中，数据在寄存器间直接传递
  - 基础API每次计算后数据需要写回UB，下一次计算再从UB读入Reg
  - VF融合后，数据在Reg内部流转，仅首尾各一次Load/Store

**基础API vs RegBase API对比**：

```
基础API（入门Case 1）：
Load(x) → Mul → Store(UB) → Load(UB) → Mul → Store(UB) → ... → Store(y)
          ↑ 每步都需要Load/Store交互

RegBase API（本Case）：
Load(x) → Mul → Mul → Muls → Add → Muls → Exp → Adds → Div → Store(y)
          ↑ 数据在寄存器间直接传递，仅首尾各一次Load/Store
```

**性能数据**：

| Task Duration(μs) | aiv_time(μs) | aiv_vec_time(μs) | aiv_vec_ratio | aiv_scalar_time(μs) | aiv_scalar_ratio | aiv_mte2_time(μs) | aiv_mte2_ratio | aiv_mte3_time(μs) | aiv_mte3_ratio |
|:---|:---|:---|:---|:---|:---|:---|:---|:---|:---|
| 348.868 | 347.99 | 66.277 | 0.19 | 3.03 | 0.009 | 320.543 | 0.921 | 314.547 | 0.904 |

**优化效果分析**：
- 端到端耗时：**348.868μs**，相比入门Case 1耗时减少 **0.76%**
- 向量指令耗时：66.277μs，相比入门Case 1耗时减少 **55.2%**
- 本样例为MTE2 bound，搬运占比超过90%，因此端到端收益不明显
- 向量指令耗时从147.895μs降至66.277μs，说明VF融合显著降低了计算耗时

**原理说明**：
- **基础API的瓶颈**：每次向量计算内部会进行Load → Compute → Store操作，计算数据均需要在UB和Reg之间交互。Gelu的8步计算会产生8次Load和8次Store（首尾可优化为1次Load + 1次Store + 7次中间Load/Store）
- **RegBase API的优化**：使用`AscendC::Reg::RegTensor`在寄存器级别操作数据，整个Gelu计算的8步运算仅需1次LoadAlign和1次StoreAlign，中间结果直接在寄存器间传递
- **VF融合的硬件支持**：`__simd_vf__`标记的函数会被编译器识别为VF函数，利用硬件的双发特性，常规计算指令（如Mul、Add）可以达到512 bytes/cycle的并行度

**性能优化建议**：
> 💡 **使用RegBase API + VF融合减少中间数据交互**
>
> 1. 对于多步向量计算链（如Gelu的8步运算），优先使用RegBase API
> 2. 通过`asc_vf_call`调用VF函数，利用硬件双发特性提升IPC
> 3. 计算链越长，RegBase API的收益越明显

**下一步优化方向**：
- VF融合已大幅降低向量指令耗时，但Gelu计算依赖路径较长
- 可通过循环展开优化提高指令级并行度，详见[高阶极限打磨](./高阶极限打磨.md)

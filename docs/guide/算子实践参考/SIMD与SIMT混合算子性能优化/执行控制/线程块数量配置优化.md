# 线程块数量配置优化<a name="ZH-CN_TOPIC_0000002284237124"></a>

>[!NOTE]说明 
>该性能优化建议适用于如下型号：
>-   Ascend 950PR/Ascend 950DT

【优先级】高

【描述】SIMT kernel启动时，通过内核调用符<<<>>>的第一个参数配置本次任务要启动的线程块数量，线程块数量即为逻辑核数量。逻辑核最终落到硬件实际存在的物理核（Vector Core）上执行，两者数量关系直接影响调度开销：当逻辑核数不超过物理核数时，所有逻辑核可以一次占满物理核并行执行；当逻辑核数超过物理核数时，超出部分的逻辑核必须等待物理核空闲后才能被调度，等待开销随超出的逻辑核数量近似线性增加。因此，线程块数量配置需要根据数据shape合理选择：大shape下线程块数量应等于物理核数，既避免过多（排队等待）又避免过少（并行度不足）；小shape下每核工作量较小，启动更多核带来的调度头开销会反超有效计算的收益，最优核数往往小于物理核数，需要实测确定。此外，线程数量也应按每核实际处理的元素数设置，避免空转线程浪费性能。物理核数可通过`aclrtGetDeviceInfo`在运行期查询获取（样例实测的物理核数为64）。

【样例介绍】以Gather算子为例，算子功能为根据索引张量从输入张量中采集对应位置的数据写入输出，计算公式为output\[i\]\[j\] = input\[index\[i\]\[j\]\]。完整样例请参考[线程块数量配置与vf调用优化样例](https://gitcode.com/cann/asc-devkit/tree/master/examples/01_simd_cpp_api/04_best_practices/03_fusion_compute_practices/simt_and_simd_grid_dim_config)。

SIMT线程层次结构为：

-   Kernel启动核数：64（大shape）/ 16（小shape实测最优）
-   单次SIMT VF调用线程数：2048（大shape）/ 1024（小shape按实际元素数分配）

【反例】

**反例1：大shape下线程块数量超过物理核数**

以Gather算子大shape（index和output形状为\[1024, 2048\]）为例，对应样例中的Case 2（SCENARIO\_NUM=9）。该场景通过<<<>>>启动1024个线程块，远超物理核数64，超出的960个逻辑核必须排队等待物理核空闲后才能被调度，代码如下。

```cpp
// 启动1024个线程块，远超物理核数64
gather_kernel<<<1024, 0, stream>>>(input_device, index_device, output_device, ...);

__global__ __vector__ void gather_kernel(...)
{
    uint32_t rows_per_block = index_total_length / gridDim.x;
    uint32_t index_start = blockIdx.x * rows_per_block;
    asc_vf_call<simt_gather>(dim3(2048), output, input, index, ...);
}
```

**反例2：大shape下线程块数量低于物理核数**

同一大shape下，对应样例中的Case 2（SCENARIO\_NUM=11）。该场景通过<<<>>>启动32个线程块，仅使用一半物理核，并行度不足，每核工作量翻倍（65536个元素），代码如下。

```cpp
// 启动32个线程块，仅使用一半物理核，并行度不足
gather_kernel<<<32, 0, stream>>>(input_device, index_device, output_device, ...);
```

**反例3：小shape下线程块数量打满物理核数**

以Gather算子小shape（index和output形状为\[8, 2048\]）为例，对应样例中的Case 3（SCENARIO\_NUM=16）。该场景通过<<<>>>启动64个线程块（物理核数），但每核仅处理256个元素，增加核数带来的调度开销反超并行收益，代码如下。

```cpp
// 启动64个线程块（打满物理核），每核仅256元素
// 小shape下调度开销反超并行收益
gather_kernel<<<64, 0, stream>>>(input_device, index_device, output_device, ...);
```

【正例】

**正例1：大shape下线程块数量等于物理核数**

大shape（SCENARIO\_NUM=10）通过<<<>>>启动64个线程块（物理核数），所有逻辑核一次占满物理核并行执行，无需排队等待，并行度充足。核函数通过`rows_per_block = index_total_length / gridDim.x`计算每核处理的数据量，保证数据均匀分配。物理核数通过`aclrtGetDeviceInfo`在运行期查询获取，代码如下。

```cpp
// 大shape: 启动64个线程块，每核处理32768个元素
gather_kernel<<<64, 0, stream>>>(input_device, index_device, output_device, ...);
```

**正例2：小shape下实测最优核数且线程数量按实际元素数分配**

小shape下最优核数为16（物理核数的1/4），对应样例中的Case 3（SCENARIO\_NUM=14）。同时将线程数量从固定2048调整为每核实际处理的元素数1024，消除空转线程，代码如下。

```cpp
// 小shape: 启动16个线程块（实测最优），而非打满64
gather_kernel<<<16, 0, stream>>>(input_device, index_device, output_device, ...);

// 线程数量按每核实际元素数设置，而非固定2048
// 16核时每核处理1024元素，线程数量设为1024
asc_vf_call<simt_gather>(dim3(1024), ...);
```

【性能对比】

**大shape（\[1024, 2048\]）线程块数量配置对比**

| SCENARIO\_NUM | 线程块数量 | 每核处理元素数 | Task Duration\(μs\) | 说明 |
|:---:|:---:|:---:|---:|:---|
| 9 | 1024 | 2048 | 78.533 | 1024核 ≫ 64核，排队等待 |
| 10 | 64 | 32768 | 62.649 | 64核 = 64（物理核数），最优 |
| 11 | 32 | 65536 | 113.609 | 32核 < 64核，并行度不足 |

大shape下线程块数量等于物理核数（64）时性能最优。线程块数量为1024时，超出物理核数的逻辑核排队等待，Task Duration为78.533μs；线程块数量为32时，仅使用一半物理核，并行度不足，每核工作量翻倍，Task Duration为113.609μs。线程块数量为64时，既避免了过多调度开销又保证了充足并行度，Task Duration为62.649μs，相比1024核下降约20.2%，相比32核下降约44.8%。

**小shape（\[8, 2048\]）线程块数量与线程数量配置对比**

| SCENARIO\_NUM | 线程块数量 | 线程数量 | 每核处理元素数 | Task Duration\(μs\) | 说明 |
|:---:|:---:|:---:|:---:|---:|:---|
| 12 | 4 | 2048 | 4096 | 9.989 | 核数太少，单核工作量重 |
| 13 | 8 | 2048 | 2048 | 8.755 | 继续加核仍明显收益 |
| 14 | 16 | 1024 | 1024 | 7.832 | 最优核数（物理核数的1/4） |
| 15 | 32 | 512 | 512 | 7.959 | 核数增加，耗时回升 |
| 16 | 64 | 256 | 256 | 8.820 | 打满64核，调度开销反超 |

小shape下最优配置为16核1024线程（SCENARIO\_NUM=14），Task Duration为7.832μs。4→8→16核数增加过程中耗时持续下降；16→32→64核数继续增加后耗时回升，折线呈"先降后升"的谷形。32核耗时增加约1.6%，64核耗时增加约10.8%，说明小shape下每核任务量较小，增加核数带来的调度开销反超并行收益。

【总结】

1. **大shape需优先匹配物理核数**：受硬件资源限制，实际可并行执行的物理核数量存在上限。线程块数量应尽量等于物理核数，避免线程块数量过多（排队等待、调度开销累积）或过少（并行度不足、单线程块工作量重）。
2. **小shape需实测线程块数量性能**：小shape下每核工作量较小，启动更多线程块带来的调度头开销会反超收益，最优线程块数量不一定是最大物理核数。可通过分档测试寻找最优线程块数量。

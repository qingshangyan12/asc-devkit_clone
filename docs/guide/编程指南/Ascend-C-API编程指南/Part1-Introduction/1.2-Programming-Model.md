# 1.2 Programming Model

This chapter introduces the Ascend C programming model at a high level and separate from any language. The terminology and concepts introduced here apply to Ascend C in any supported programming language. Later chapters will illustrate these concepts in C language using Ascend C API.

## 1.2.1 Heterogeneous Systems

The Ascend C programming model assumes a **heterogeneous computing system**, which means a system that includes both Ascend NPUs and CPUs. The CPU and the memory directly connected to it are called the *host* and *host memory*, respectively. An Ascend NPU and the memory directly connected to it are referred to as the *device* and *device memory*, respectively. In some system-on-chip (SoC) systems, these may be part of a single package. In larger systems, there may be multiple CPUs or Ascend NPUs.

Ascend C applications execute some part of their code on the Ascend NPU, but applications always start execution on the CPU. The host code, which is the code that runs on the CPU, can use Ascend C APIs to copy data between the host memory and device memory, start code executing on the Ascend NPU, and wait for data copies or Ascend NPU code to complete. The CPU and Ascend NPU can both be executing code simultaneously, and best performance is usually found by maximizing utilization of both CPUs and Ascend NPUs.

The code an application executes on the Ascend NPU is referred to as *device code*, and a function that is invoked for execution on the Ascend NPU is called a *kernel*. The act of starting a kernel running is called *launching* the kernel. A kernel launch can be thought of as starting many parallel execution units running the kernel code in parallel on the Ascend NPU. Unlike CUDA threads, Ascend C uses *blocks* as the basic execution unit, where each block executes the kernel code in a pipeline fashion.

## 1.2.2 AI Core Hardware Model

Like any programming model, Ascend C relies on a conceptual model of the underlying hardware. For the purposes of Ascend C programming, the Ascend NPU can be considered to be a collection of **AI Cores**. Each AI Core contains:

- **AI Vector**: A SIMD (Single-Instruction Multiple-Data) vector computation unit
- **AI Cube**: A matrix computation unit for matrix multiplication acceleration
- **Unified Buffer (UB)**: An on-chip memory for vector computation data
- **Local Memories (L0/L1/L2/L3)**: Hierarchical memory levels for different purposes
- **MTE (Memory Transfer Engine)**: Dedicated engines for data movement

The AI Vector unit performs SIMD parallel operations on data loaded into the Unified Buffer. The AI Cube unit performs high-performance matrix multiplication operations using data loaded into L0/L1 memories. The MTE engines handle data movement between Global Memory and local memories, enabling concurrent data transfer and computation.

> [!NOTE]
> The actual hardware layout of an Ascend NPU or the way it physically carries out the execution of the programming model may vary across different architecture versions (910B, 310P, 950PR, etc.). These differences do not affect correctness of software written using the Ascend C programming model.

### 1.2.2.2 Execution Units: Blocks

When an application launches a kernel, it does so with one or more **execution units called blocks**. A *block* is the fundamental execution unit in Ascend C, analogous to a thread block in CUDA. However, unlike CUDA threads, Ascend C blocks execute kernel code in a **pipeline fashion**, where different stages (data loading, computation, data storing) can overlap in execution.

All blocks executing a kernel have access to the same Global Memory (GM). Each block has its own local resources:

- **Unified Buffer (UB)**: Private on-chip memory for the block
- **L0/L1/L2/L3**: Private local memories for the block
- **AI Vector/Cube**: Computational units shared by pipeline stages

Multiple blocks can be executed concurrently on different AI Cores, or sequentially on the same AI Core, depending on system resources and scheduling.

> [!NOTE]
> Unlike CUDA's millions of threads, Ascend C typically uses a smaller number of blocks (e.g., 1-8 blocks per kernel launch). Each block handles a larger portion of work using pipeline execution and SIMD operations.

### 1.2.2.3 Pipeline Execution Model

A distinctive feature of Ascend C is the **pipeline execution model**. Within a block, execution is organized into pipeline stages:

- **Load Stage**: Data movement from Global Memory to UB or local memories
- **Compute Stage**: Vector or matrix computation on loaded data
- **Store Stage**: Data movement from UB or local memories to Global Memory

These stages can execute **concurrently** through pipeline optimization, overlapping data movement with computation. This is different from CUDA's thread execution model, where all threads execute the same code synchronously.

### 1.2.2.4 SIMD Execution on AI Vector

Within the AI Vector unit, computation follows a **SIMD (Single-Instruction Multiple-Data) execution model**. The AI Vector performs the same operation on multiple data elements simultaneously, similar to CUDA's warp execution but with explicit SIMD width control.

Key characteristics:

- **SIMD Width**: The number of elements processed simultaneously (e.g., 256 elements)
- **Vector Instructions**: Operations like `asc_add`, `asc_mul`, `asc_reduce` process multiple elements
- **Unified Buffer**: Data is loaded into UB before SIMD computation
- **Repeat Pattern**: Operations can repeat across multiple data blocks

This SIMD execution is explicit in Ascend C API - developers directly call vector functions that operate on multiple elements, unlike CUDA's implicit warp execution.

## 1.2.3 AI Core Memory Hierarchy

In modern computing systems, efficiently utilizing memory is just as important as maximizing the use of computational units. Ascend NPU has a rich memory hierarchy with multiple levels, each serving specific purposes.

### 1.2.3.1 Global Memory (GM)

From the perspective of device code, the DRAM attached to the Ascend NPU is called **Global Memory (GM)**. This is the largest memory space, analogous to CUDA's global memory:

- **Size**: Large capacity (several GB)
- **Access**: Accessible to all AI Cores in the Ascend NPU
- **Latency**: Higher latency than on-chip memories
- **Usage**: Primary storage for input/output data

All blocks executing a kernel share the same Global Memory space. Data must be explicitly moved from Global Memory to on-chip memories (UB, L0, L1) before computation.

### 1.2.3.2 Unified Buffer (UB)

The **Unified Buffer (UB)** is a fast on-chip memory attached to the AI Vector unit:

- **Size**: Limited capacity (typically ~1MB)
- **Access**: Very low latency, high bandwidth
- **Usage**: Intermediate storage for vector computation data
- **Sharing**: Private to each block, not shared across blocks

UB is analogous to CUDA's shared memory but optimized for SIMD vector operations. All vector computation functions (`asc_add`, `asc_mul`, `asc_reduce`, etc.) operate on data loaded into UB.

### 1.2.3.3 Local Memories (L0/L1/L2/L3)

Ascend NPU has a hierarchical local memory system:

- **L0**: Smallest, fastest memory for AI Cube operations
- **L1**: Intermediate memory for matrix data
- **L2**: Larger local memory for intermediate results
- **L3**: Largest on-chip memory, shared across AI Cores

Each level serves specific computational units:

| Memory Level | Attached Unit | Primary Usage |
|--------------|---------------|---------------|
| **L0** | AI Cube | Matrix multiplication operand storage |
| **L1** | AI Cube | Matrix data buffer |
| **UB** | AI Vector | Vector computation data |
| **L2/L3** | System | Intermediate results, shared data |

### 1.2.3.5 Memory Access Patterns

Efficient memory usage is critical for performance. Key principles:

1. **Minimize Global Memory Access**: Load data once, reuse multiple times in UB
2. **Use UB for Intermediate Results**: Perform vector computation in UB, not Global Memory
3. **Overlap Data Movement**: Use MTE for concurrent data transfer during computation
4. **Choose Appropriate Memory Level**: Use L0/L1 for matrix, UB for vector

Inefficient memory access patterns lead to performance bottlenecks. Part 2 will cover specific API usage for optimal memory management.

## 1.2.4 Computational Units

### 1.2.4.1 AI Vector Unit

The **AI Vector unit** performs SIMD parallel computation:

- **Operation Types**: Arithmetic (add, sub, mul, div), comparison (eq, gt, le), reduction (sum, max, min), type conversion
- **SIMD Width**: Processes multiple elements simultaneously (e.g., 256 elements per operation)
- **Data Location**: Operates on data in Unified Buffer (UB)
- **Programming Model**: Call vector API functions explicitly (e.g., `asc_add`, `asc_mul`)

Unlike CUDA's implicit SIMD execution through warp, Ascend C makes SIMD execution explicit through vector API calls.

### 1.2.4.2 AI Cube Unit

The **AI Cube unit** accelerates matrix multiplication:

- **Operation**: High-performance matrix-matrix multiplication (MMAD)
- **Data Location**: Operates on data in L0/L1 memories
- **Programming Model**: Call matrix API functions (e.g., `asc_mmad`, `asc_mmad_mx`)
- **Performance**: Specialized hardware for matrix operations, much faster than vector-based matrix computation

AI Cube is analogous to CUDA's Tensor Core but with explicit API control.

### 1.2.4.3 Computational Unit Comparison

| Unit | Computation Type | Memory | API Category | CUDA Analog |
|------|------------------|--------|--------------|-------------|
| **AI Vector** | SIMD vector operations | UB | `asc_add`, `asc_mul`, `asc_reduce` | CUDA cores |
| **AI Cube** | Matrix multiplication | L0/L1 | `asc_mmad`, `asc_mmad_mx` | Tensor Core |

## 1.2.5 Synchronization

### 1.2.5.1 Pipeline Synchronization

In Ascend C, synchronization is necessary to coordinate pipeline stages and ensure correct execution order:

- **Intra-Pipeline Sync**: Synchronize between Load → Compute → Store stages within a block
- **Inter-Pipeline Sync**: Synchronize between multiple pipeline iterations
- **Event-Based Sync**: Use event mechanisms to control execution flow

Key synchronization functions:

- `asc_sync_pipe`: Synchronize pipeline stages
- `asc_sync_vec`: Wait for AI Vector completion
- `asc_sync_mte2`: Wait for MTE load completion
- `asc_sync_mte3`: Wait for MTE store completion

### 1.2.5.2 Memory Synchronization

Memory operations require synchronization to ensure data consistency:

- **Load Completion**: Ensure data is fully loaded before computation
- **Store Completion**: Ensure computation completes before storing results
- **Atomic Operations**: Synchronize atomic memory access

Without proper synchronization, data races and incorrect results may occur.

> [!WARNING]
> Incorrect synchronization leads to undefined behavior. Always synchronize between dependent operations, especially between data movement and computation.

## 1.2.6 Comparison with CUDA Programming Model

For developers familiar with CUDA, here's a comparison:

| Concept | Ascend C | CUDA |
|---------|----------|------|
| **Execution Unit** | Block (pipeline execution) | Thread block (thread execution) |
| **Thread Model** | SIMD on AI Vector (explicit) | Threads in warp (implicit) |
| **Memory** | GM → UB → AI Vector | Global → Shared → Registers |
| **Matrix Unit** | AI Cube (explicit API) | Tensor Core (WMMA API) |
| **Synchronization** | Pipeline sync, event-based | `__syncthreads()`, events |
| **Programming Level** | Low-level C API | C++ extensions |

Key differences:

1. **Execution Model**: Ascend C uses pipeline execution within blocks, CUDA uses thread execution
2. **SIMD**: Ascend C makes SIMD explicit through API calls, CUDA makes it implicit through warp execution
3. **Memory Control**: Ascend C requires explicit data movement between memory levels, CUDA allows more flexible access
4. **Matrix Acceleration**: Both have specialized units, but Ascend C exposes them through lower-level C API

- **Heterogeneous Systems**: CPU (host) + Ascend NPU (device) architecture

- **Memory Hierarchy**: Global Memory → L3 → L2 → L1/L0/UB → Computational units
- **Computational Units**: AI Vector for SIMD, AI Cube for matrix acceleration

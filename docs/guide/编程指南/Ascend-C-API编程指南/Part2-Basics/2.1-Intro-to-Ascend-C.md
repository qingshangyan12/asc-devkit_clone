# 2. Programming AI Core in Ascend C

This chapter introduces the basic concepts of the Ascend C programming model by illustrating how they are exposed in C language through Ascend C API. This programming guide focuses on the **C API** (also called **Low-Level API** or **Pointer-Based API**), which provides direct hardware control through function calls.

Ascend C API is the lowest-level programming interface, analogous to CUDA's driver API in terms of control granularity, but with C-language function call syntax like CUDA's runtime API. It provides:

- **Direct Hardware Mapping**: API calls map directly to hardware instructions
- **Transparent Memory Control**: Explicit data movement between memory levels
- **Fine-Grained Synchronization**: Precise control over execution flow
- **Maximum Performance**: Optimized for custom operators and performance-critical applications

## 2.1 Intro to Ascend C

### 2.1.1 Ascend C Language Extensions

Ascend C extends standard C/C++ with special **type qualifiers** and **keywords** to support AI Core programming:

#### Function Type Qualifiers

- `__global__`: Marks a function as a kernel (entry function on AI Core)
- `__aicore__`: Marks a function to execute on AI Core device
- `__vector__`: Marks a kernel as vector-type operator (uses AI Vector unit)
- `__cube__`: Marks a kernel as matrix-type operator (uses AI Cube unit)
- `__mix__(cube, vec)`: Marks a kernel as fusion-type operator (uses both units)

#### Variable Type Qualifiers

- `__gm__`: Pointer to Global Memory (off-chip DRAM)
- `__ubuf__`: Pointer to Unified Buffer (on-chip memory for vector computation)
- `__l1__`: Pointer to L1 Memory (for matrix computation)
- `__l0__`: Pointer to L0 Memory (for matrix computation)
- `__cc__`: Pointer to L0C Memory (for matrix result)

#### Execution Configuration

- `<<<numBlocks>>>`: Kernel launch syntax, specifies number of AI Cores to execute

#### Comparison with CUDA

| CUDA | Ascend C | Purpose |
|------|----------|---------|
| `__global__` | `__global__ __aicore__` | Kernel function marker |
| `__device__` | `__aicore__` | Device-side function |
| No equivalent | `__vector__`, `__cube__` | Computational unit marker |
| `<<<grid, block>>>` | `<<<numBlocks>>>` | Execution configuration |
| `__global__` pointer | `__gm__` pointer | Global Memory pointer |
| `__shared__` pointer | `__ubuf__` pointer | On-chip memory pointer |

### 2.1.2 Kernel Function Definition

A **kernel function** is the entry function that executes on AI Core. All kernels must be defined with specific qualifiers:

```c
// Basic kernel definition syntax
__global__ __aicore__ void kernel_name(__gm__ type* parameter_list)
{
    // Kernel implementation
}
```

#### Kernel Definition Rules

1. **Return Type**: Must be `void`
2. **Qualifiers**: Must have `__global__` and `__aicore__`
3. **Parameters**: Global Memory pointers must use `__gm__` qualifier
4. **Syntax**: Standard C function syntax with Ascend C extensions

#### Kernel Types

Different kernel types for different computational units:

```c
// Vector-type kernel (uses AI Vector unit)
__vector__ __global__ __aicore__ void vector_kernel(__gm__ float* input, __gm__ float* output)
{
    // Vector computation logic
}

// Cube-type kernel (uses AI Cube unit)
__cube__ __global__ __aicore__ void matrix_kernel(__gm__ half* a, __gm__ half* b, __gm__ float* c)
{
    // Matrix multiplication logic
}

// Fusion-type kernel (uses both AI Vector and AI Cube)
__mix__(1, 1) __global__ __aicore__ void fusion_kernel(__gm__ half* a, __gm__ half* b, __gm__ float* c)
{
    // Matrix multiplication + vector computation logic
}
```

### 2.1.3 Kernel Launch

Kernels are launched using the `<<<numBlocks>>>` syntax:

```c
// Launch syntax
kernel_name<<<numBlocks>>>(argument_list);
```

- **numBlocks**: Number of AI Cores to execute the kernel (e.g., 8 means 8 AI Cores)
- **Argument List**: Kernel function parameters (Global Memory pointers)

#### Launch Example

```c
// Host-side code
extern "C" __global__ __aicore__ void add_kernel(__gm__ float* x, __gm__ float* y, __gm__ float* z);

int main()
{
    // Allocate Global Memory
    float* x_gm = ...;  // Allocate on Ascend NPU
    float* y_gm = ...;
    float* z_gm = ...;
    
    // Launch kernel on 8 AI Cores
    add_kernel<<<8>>>(x_gm, y_gm, z_gm);
    
    // Wait for completion (synchronization)
    aclrtSynchronizeStream(stream);
    
    return 0;
}
```

#### Kernel Execution Model

When a kernel is launched:

- Each AI Core executes the same kernel function with the same parameters
- Different AI Cores can process different data portions using `block_idx`
- Execution is asynchronous - host code continues immediately after launch
- Synchronization required to wait for kernel completion

### 2.1.4 Block Indexing

Each AI Core executing a kernel has a unique **block index** (`block_idx`), analogous to CUDA's `blockIdx`:

```c
__global__ __aicore__ void kernel_name(__gm__ float* input, __gm__ float* output)
{
    // Get block index (0 to numBlocks-1)
    uint32_t block_idx = asc_get_block_idx();
    
    // Each block processes different data portion
    uint32_t block_num = asc_get_block_num();  // Total number of blocks
    
    // Calculate data offset for this block
    uint32_t data_per_block = total_length / block_num;
    uint32_t offset = block_idx * data_per_block;
    
    // Process data[offset : offset + data_per_block]
}
```

System variable APIs for block identification:

- `asc_get_block_idx()`: Get current block's index (0-based)
- `asc_get_block_num()`: Get total number of blocks executing the kernel
- `asc_get_core_id()`: Get AI Core's physical ID

### 2.1.5 Memory Address Qualifiers

Ascend C uses different qualifiers for different memory types:

| Qualifier | Memory Type | Usage | Example |
|-----------|-------------|-------|---------|
| `__gm__` | Global Memory | Kernel parameters, large data | `__gm__ float* input` |
| `__ubuf__` | Unified Buffer | Vector computation operands | `__ubuf__ half* dst` |
| `__l1__` | L1 Memory | Matrix computation operands | `__l1__ half* matrix` |
| `__l0__` | L0 Memory | Matrix operands | `__l0__ half* operand` |
| `__cc__` | L0C Memory | Matrix result | `__cc__ float* result` |

#### Example

```c
__global__ __aicore__ void vector_kernel(__gm__ float* input, __gm__ float* output)
{
    // Allocate Unified Buffer (UB)
    __ubuf__ float* ub_buffer = ...;
    
    // Load data from Global Memory to UB
    asc_copy_gm2ub(ub_buffer, input, size);
    
    // Compute on UB data
    asc_add(ub_buffer, ub_buffer, ub_buffer, count);
    
    // Store result from UB to Global Memory
    asc_copy_ub2gm(output, ub_buffer, size);
}
```

### 2.1.6 Putting It All Together: First Kernel

Here's a complete vector addition kernel using Ascend C API:

```c
#include <ascendc_api.h>

// Kernel definition
extern "C" __vector__ __global__ __aicore__ void vecadd_kernel(
    __gm__ float* x, 
    __gm__ float* y, 
    __gm__ float* z, 
    uint32_t total_length)
{
    // Step 1: Get block information
    uint32_t block_idx = asc_get_block_idx();
    uint32_t block_num = asc_get_block_num();
    
    // Step 2: Calculate data portion for this block
    uint32_t length_per_block = total_length / block_num;
    uint32_t offset = block_idx * length_per_block;
    
    // Handle remainder for last block
    if (block_idx == block_num - 1) {
        length_per_block = total_length - offset;
    }
    
    // Step 3: Allocate Unified Buffer (UB)
    // Note: UB allocation is typically done through memory pool or static allocation
    // This is simplified for illustration
    constexpr uint32_t tile_length = 256;  // Process 256 elements at a time
    __ubuf__ float x_local[tile_length];
    __ubuf__ float y_local[tile_length];
    __ubuf__ float z_local[tile_length];
    
    // Step 4: Process data in tiles
    uint32_t tiles = length_per_block / tile_length;
    for (uint32_t i = 0; i < tiles; i++) {
        // Load data from Global Memory to UB
        asc_copy_gm2ub(x_local, x + offset + i * tile_length, tile_length * sizeof(float));
        asc_copy_gm2ub(y_local, y + offset + i * tile_length, tile_length * sizeof(float));
        
        // Wait for load completion (synchronization)
        asc_sync_mte2();
        
        // Perform vector addition on UB
        asc_add(z_local, x_local, y_local, tile_length);
        
        // Wait for computation completion
        asc_sync_vec();
        
        // Store result from UB to Global Memory
        asc_copy_ub2gm(z + offset + i * tile_length, z_local, tile_length * sizeof(float));
        
        // Wait for store completion
        asc_sync_mte3();
    }
}

// Host-side launch (simplified)
int main()
{
    uint32_t total_length = 1024;
    uint32_t num_blocks = 8;
    
    // Allocate Global Memory on Ascend NPU
    float* x_gm = allocate_global_memory(total_length * sizeof(float));
    float* y_gm = allocate_global_memory(total_length * sizeof(float));
    float* z_gm = allocate_global_memory(total_length * sizeof(float));
    
    // Initialize input data
    initialize_data(x_gm, y_gm, total_length);
    
    // Launch kernel
    vecadd_kernel<<<num_blocks>>>(x_gm, y_gm, z_gm, total_length);
    
    // Synchronize (wait for completion)
    aclrtSynchronizeStream(stream);
    
    // Verify result
    verify_result(z_gm, total_length);
    
    // Clean up
    free_global_memory(x_gm);
    free_global_memory(y_gm);
    free_global_memory(z_gm);
    
    return 0;
}
```

### 2.1.7 Compilation and Execution

Ascend C kernels are compiled using the **Ascend C Compiler**:

```bash
# Compile Ascend C kernel
ncc vecadd_kernel.cpp -o vecadd_kernel.o

# Link with host code
g++ main.cpp vecadd_kernel.o -lascend_runtime -o vecadd_example

# Run
./vecadd_example
```

> [!NOTE]
> The actual compilation process depends on the Ascend Toolkit version and project setup. This is a simplified example.

### 2.1.8 Key Differences from CUDA

| Aspect | CUDA | Ascend C API |
|--------|------|--------------|
| **Kernel Launch** | `<<<grid, block>>>` | `<<<numBlocks>>>` |
| **Thread Model** | Millions of threads per kernel | Fewer blocks with pipeline execution |
| **Memory Access** | Direct access to global memory | Must move data to UB before computation |
| **SIMD Execution** | Implicit (warp) | Explicit (vector API calls) |
| **Synchronization** | `__syncthreads()` | `asc_sync_*` APIs |
| **Programming Style** | Per-thread code | Data flow code (load → compute → store) |

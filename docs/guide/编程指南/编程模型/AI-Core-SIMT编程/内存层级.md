## Global Memory<a name="section8946131492119"></a>

Device侧的全局内存是整个Grid中所有线程均可访问的内存空间，其作用与CPU系统中的随机存取存储器（RAM）相似，运行在Device侧的核函数可直接访问全局内存，这种方式与CPU上代码访问系统内存的方式相同。

全局内存具有持久性：通过全局内存分配的空间、其中存储的数据将持续保留，直到该内存空间被释放或应用程序终止。用户通过Runtime API完成Device侧全局内存的管理。Host使用aclrtMalloc分配Device侧的全局内存，并通过aclrtMemcpy将数据从Host拷贝到Device侧的全局内存，或将数据从Device的全局内存拷贝回Host内存；通过aclrtMalloc分配的Device全局内存需使用aclrtFree接口释放。有关Runtime API的更多信息与细节，可以参考《应用开发指南 \(C&C++\)》中的“Runtime API参考 > 运行时管理 > 内存管理”章节。

在实际开发过程中，用户需在核函数启动前，通过Runtime API完成全局内存的分配与初始化；在核函数执行期间，SIMT每个线程均可读取和写入数据到全局内存；核函数执行完毕后，其写入全局内存的结果可拷贝回Host。由于全局内存对Grid内所有线程均开放访问，因此必须严格规避线程间的数据竞争。

下述代码为全局内存的使用提供了简易示例。数组 x、y、z 均存储于全局内存中，通过以下核函数实现每个线程对全局内存的访问和存储。

```
__global__ void add_custom(float* x, float* y, float* z, uint64_t total_length)
{
    // Calculate global thread ID
    int32_t idx = blockIdx.x * blockDim.x + threadIdx.x;
    // Maps to the row index of output tensor
    if (idx >= total_length) {
        return;
    }
    z[idx] = x[idx] + y[idx];
}
```

## Unified Buffer<a name="section66329146410"></a>

Unified Buffer位于每个Vector Core内部，是一块高速片上内存空间，总大小为256KB。相比Global Memory，Unified Buffer虽然容量较小，但具有更高的带宽和更低的访问延迟。Unified Buffer在SIMT编程模式下按功能划分为多个区域：
  - **Share Memory（共享内存）**：用于线程块内所有线程的数据交互和共享。
  - **Data Cache（数据缓存）**：用于SIMT线程访问Global Memory时的数据中转。
  - **预留空间**：编译器和Ascend C预留空间。

共享内存是可供同一个线程块内所有线程访问的内存空间，相比全局内存，共享内存虽然容量远小于全局内存，但带宽更高，访问延迟更低，视为内核执行期间由用户管理的高速缓存资源。由于共享内存可被线程块内的全部线程访问，因此必须注意避免同一线程块内线程间的数据竞争。可通过asc\_syncthreads接口实现同一线程块内的线程同步。该函数会阻塞线程块内的所有线程，直至所有线程均执行到接口调用位置。

用户可通过动态或者静态方式申请共享内存。

1.  静态申请：分配一段指定大小的内存空间，其大小在编译时确定，不可动态修改，开发者通过数组分配申请使用。

    ```
    __ubuf__ half staticBuf[1024];
    ```

2.  动态申请：用户需要通过<<<\>\>\>中参数[dynUBufSize](核函数.md#li12421238101815)指定动态内存的空间大小，其大小在运行期确定，SIMT核函数内可通过使用动态数组申请使用。

    ```
    extern __ubuf__ char dynamicBuf[];
    ```

由于Unified Buffer不仅作为共享内存，还有部分内存空间预留作内部使用，因此用户在申请共享内存时，应注意不能将所有共享内存用尽。如下图，Unified Buffer内存空间总大小为256KB，按功能划分为四个主要区域，从低地址到高地址依次为静态内存、动态内存、预留空间和Data Cache。

![](../../../figures/UB内存分配.png)

具体结构如下：

1.  静态内存和动态内存共同组成线程块内的共享内存。
2.  预留空间：编译器和Ascend C预留空间，大小固定为8KB。
3.  Data Cache：SIMT专有的Data Cache空间，用于SIMT线程访问全局内存时的数据缓存，DataCache的空间可配置范围在32KB到128KB。

 Data Cache实际内存大小受用户配置的静态和动态内存大小影响，简单计算公式为：
 ```
 DataCache =  UB总大小（256KB） - 静态内存 - 动态内存 - 预留空间（8KB）
 ```
 因此，用户需要合理配置静态和动态内存大小，以确保DataCache大于或等于32KB，否则将校验报错。

## 基于内存层级的SIMT编程建议

- **提高合并访问效率**<a name="section_cache_hit"></a>

    Global Memory作为容量最大但延迟最高的存储资源，其数据访问遵循以下路径：
    ```
    Global Memory ↔ Data Cache ↔ 寄存器
    ```
    Data Cache作为Global Memory的高速缓存，其命中率直接影响内存访问性能：
    - Cache命中（Cache Hit）：当线程访问的数据已存在于Data Cache中时，无需从Global Memory加载，直接从Data Cache读取到寄存器。此时读取路径简化为：`Data Cache → 寄存器`。
    - Cache未命中（Cache Miss）：当线程访问的数据不在Data Cache中时，需要从Global Memory加载数据到Data Cache，再传输到寄存器。
    提高Data Cache命中率是SIMT编程性能优化的关键方向，当同一Warp中的多个线程访问Global Memory时，硬件会尝试将这些访问请求合并为更少的内存事务，具体表现为：
    - 合并访问（Coalesced Access）：当线程访问连续且对齐的内存地址时，多个访问请求可合并为一个内存事务，显著提升带宽利用率；
    - 非合并访问：当线程访问分散或未对齐的地址时，每个访问请求可能需要单独的内存事务，降低性能。

    因此，SIMT编程中，提高Global Memory的访问效率有以下优化策略：
    - 内存合并访问：同一Warp中的线程应尽量访问相邻的内存地址，使得多个线程的内存访问请求可以合并为更少的内存事务；
    - 数据重用：尽量让同一Vector Core上的线程重复使用已加载到Data Cache中的数据；
    - 避免随机访问：非连续的内存访问模式会降低Cache利用率；
    - 可将频繁访问的数据从Global Memory加载到Share Memory，减少Global Memory访问次数；
    - 合理分配资源：由于Share Memory和Data Cache共用Unified Buffer内存空间，更多的Data Cache能增加Cache命中率，但使用Share Memory缓存频繁使用的数据，减少Global Memory访问次数，因此需要合理划分Share Memory和Data Cache空间，避免资源争用。

- **注意数据同步**<a name="section_write_back_policy"></a>

    由于数据从Data Cache写回到Global Memory默认采用非实时策略，Data Cache中的数据不一定会立即写回Global Memory，硬件会在适当时机（如Cache行替换时）进行写回。若用户需要确保数据实时更新到Global Memory（如与其他Vector Core同步时），可显式调用同步接口强制刷新。

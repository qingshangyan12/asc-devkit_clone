## 引言

AI Core采用「外部全局存储+片上分级存储+计算单元内部寄存器」的三级存储架构，是C指针编程实现高性能算子的物理根基。存储层次的设计直接决定数据搬运路径、内存分配策略、同步时机等关键技术决策，所有C指针算子的内存管理、数据流转逻辑均基于该存储架构实现。

本章旨在帮助开发者建立对AI Core存储体系的系统化认知，掌握合理的片上内存规划方法，充分理解各级存储单元的功能定位与协作机制，实现高性能算子的精细化内存管理。全文遵循「物理架构—内存管理—寄存器体系—数据流协作」的递进逻辑展开，完整覆盖存储架构全链路核心内容：阐述AI Core三级存储层次的物理布局与功能分工、拆解Local Memory的内存申请方式与地址限定符机制，并逐层讲解寄存器变量类型及其与Local Memory的Load-Compute-Store协作流程。

## 硬件底层支撑：AI Core三级存储架构

AI Core是昇腾NPU的基础核心计算单元，采用「外部全局存储+片上分级存储+计算单元内部寄存器」的经典三级架构，各层级分工明确、协同联动。硬件的存储能力边界直接决定算子的数据流转路径与内存管理方式，下文将详细介绍AI Core核心存储层级、以及基于存储架构的数据搬运机制。

### AI Core核心存储层级

AI Core包含多级内部存储、外部存储和计算单元内部的寄存器，形成完整的存储层次结构，支撑数据从全局内存到计算单元的全链路流转。

- **Global Memory（全局内存）**：AI Core外部大容量存储空间，用于存放算子输入/输出数据。所有计算单元通过总线访问，速度最慢但容量最大，是算子数据的源头与归宿。
- **Local Memory（片上存储）**：AI Core片内高速存储体系，用于缓存计算中间数据，规避频繁访问低速全局内存的性能损耗，降低访存延迟。根据配套计算单元的差异，分为以下子类型：
  - **[L1 Buffer](../../高级编程/硬件实现/基本架构.md)**：Cube数据中转区，MTE1、MTE2、FixPipe可访问
  - **[L0A Buffer](../../高级编程/硬件实现/基本架构.md)**：Cube左矩阵输入存储，Cube、MTE1可访问
  - **[L0B Buffer](../../高级编程/硬件实现/基本架构.md)**：Cube右矩阵输入存储，Cube、MTE1可访问
  - **[L0C Buffer](../../高级编程/硬件实现/基本架构.md)**：Cube输出结果存储，Cube、FixPipe可访问
  - **[UB（Unified Buffer）](../../高级编程/硬件实现/基本架构.md)**：Vector输入/输出统一缓存，Vector、MTE2、MTE3可访问
- **寄存器（Register）**：计算单元内部的高速存储，用于存储计算过程中的数据。根据功能差异，分为以下子类型：
  - **矢量数据寄存器**：Vector计算单元的工作存储，位宽为VL（Vector Length = 256B），直接参与向量运算
  - **掩码寄存器**：用于矢量计算中选择参与计算的元素，实现部分元素的条件计算
  - **地址寄存器**：用于存储地址偏移量，支持循环自增，简化循环访问内存的地址管理

> 📌 **提示**：Ascend 950PR/Ascend 950DT新一代架构在传统UB缓存体系的基础上，开放寄存器（Register）可编程能力，构建出「Global Memory → UB → Register」的三级内存层级，开发者可获得接近峰值的计算性能。

### 基于存储架构的数据搬运机制

与传统CPU串行编程、SIMT线程编程不同，AI Core SIMD编程的显著特征是**显式分层访存**：开发者需手动管控数据流转，将数据从Global Memory搬运至AI Core片内Local Memory完成计算，最终将运算结果写回全局内存。

数据搬运遵循存储层级逐级流转的基本原则：
- **Vector算子数据流**：Global Memory → UB → 寄存器（可选） → 计算 → UB → Global Memory
- **Cube算子数据流**：Global Memory → L1 → L0A/L0B → 计算 → L0C → Global Memory/L1

> 📌 **提示**：AI Core片内本地存储空间有限，无法一次性加载超大尺寸张量。实际开发中普遍采用「迭代分块搬运、分批计算、结果累加」的策略完成全域数据计算，同时搭配流水线技术屏蔽数据搬运耗时，提升整体运算效率。

## 内存管理核心机制：地址限定符与申请方式

### 地址限定符：内存层级标识机制

C指针编程通过地址限定符描述不同层级内存，编译器根据限定符将数据分配到对应的物理存储单元。地址限定符是实现内存精准分配的核心机制，每种限定符对应特定的存储层级与访问权限。

### Local Memory内存申请方式

C指针编程提供两种Local Memory申请方式：静态数组方式和偏移量方式。两种方式各有适用场景与技术约束，开发者可根据算子特性灵活选用。

#### 静态数组申请方式：编译期自动管理

使用数组方式申请片上内存，数组长度必须为编译期常量，编译器自动分配地址空间，避免地址重叠。

**语法规范**：
```cpp
constexpr uint32_t length = <编译期常量>;
__<地址限定符>__ <数据类型> buffer[length];
```

**代码示例**：
```cpp
// 申请UB内存（Vector算子）
constexpr uint32_t ub_size = 256;
__ubuf__ half ub_buffer[ub_size];

// 申请L1内存（Cube算子）
constexpr uint32_t l1_size = 4096;
__cbuf__ half l1_buffer[l1_size];

// 申请L0A/B/C内存（Cube算子）
constexpr uint32_t l0_size = 512;
__ca__ half a_l0a[l0_size];
__cb__ half b_l0b[l0_size];
__cc__ float c_l0c[l0_size];
```

**技术优势**：
- 语法简洁，易于理解
- 无需手动管理地址偏移，降低开发门槛
- 编译器自动分配，避免地址重叠，提升稳定性

**使用约束**：
- 数组长度必须为编译期常量（`constexpr`）
- 不支持动态数组（长度不能是运行时变量）
- 不支持多维数组和嵌套数组
- 不支持与偏移量方式混用

#### 偏移量申请方式：灵活布局管控

通过偏移量获取物理地址，需手动管理地址分配和对齐，适合需要精细控制内存布局的场景。

**语法规范**：
```cpp
__<地址限定符>__ <数据类型>* ptr = (__<地址限定符>__ <数据类型>*)asc_get_phy_buf_addr(offset);
```

**代码示例**：
```cpp
constexpr uint32_t buffer0_size = 1024;
constexpr uint32_t buffer1_size = 512;

// 通过偏移量申请UB内存，手动规划布局
__ubuf__ half* buffer0 = (__ubuf__ half*)asc_get_phy_buf_addr(0);
__ubuf__ half* buffer1 = (__ubuf__ half*)asc_get_phy_buf_addr(buffer0_size * sizeof(half));
__ubuf__ half* buffer2 = (__ubuf__ half*)asc_get_phy_buf_addr((buffer0_size + buffer1_size) * sizeof(half));
```

**技术优势**：
- 可以灵活控制内存布局，优化空间利用率
- 支持动态计算偏移量（偏移量可以是运行时变量）

**使用约束**：
- 不能与静态数组方式混用，否则可能导致地址重叠
- 需手动确保地址对齐（建议32字节对齐）
- 需手动计算偏移量，避免地址重叠
- 需要开发者自行管理内存空间规划

#### 申请方式选择决策

开发者可结合算子数据规模、分块策略、开发效率诉求，灵活选用对应申请方式：

| 场景 | 推荐方式 | 原因 |
|------|----------|------|
| **大多数情况** | 静态数组方式 | 编译器自动管理，不易出错 |
| **数组长度编译期确定** | 静态数组方式 | 语法简洁，自动对齐 |
| **需要灵活控制内存布局** | 偏移量方式 | 可以手动规划内存空间 |
| **偏移量需要运行时计算** | 偏移量方式 | 支持动态偏移量 |

> 📌 **提示**：静态数组方式与偏移量方式不能混用，否则会导致地址重叠，引发数据覆盖错误。建议单一算子内统一使用一种申请方式。

## 寄存器变量类型体系：计算单元工作存储

寄存器是计算单元内部的高速存储，直接参与计算过程。Ascend 950PR/Ascend 950DT新一代架构开放寄存器可编程能力，开发者可获得接近峰值的计算性能。根据功能差异，寄存器分为矢量数据寄存器、掩码寄存器、地址寄存器三类。

### 矢量数据寄存器

矢量数据寄存器用于存储矢量数据，位宽为VL（Vector Length = 256B），是Vector计算单元的工作存储空间，直接参与向量运算。

**表 3**  矢量数据寄存器类型

| 位宽 | 数据类型 | 元素数量 | 说明 |
|------|----------|----------|------|
| b8 | `vector_int8_t` / `vector_uint8_t` | 256个 | 8位整型 |
| b16 | `vector_half` / `vector_bfloat16_t` | 128个 | 16位浮点 |
| b32 | `vector_float` / `vector_int32_t` | 64个 | 32位数据 |
| b64 | `vector_int64_t` / `vector_uint64_t` | 32个 | 64位整型 |

**使用示例**：
```cpp
vector_half dst;
half index = 0;
asc_arange(dst, index);
```

### 掩码寄存器

掩码寄存器用于矢量计算中选择参与计算的元素，实现部分元素的条件计算，适配尾部数据处理、条件计算等场景。

**使用示例**：
```cpp
vector_bool mask = asc_create_mask_b16(PAT_ALL);  // 创建全True掩码
vector_bool mask = asc_update_mask_b16(length);   // 根据元素数量生成掩码
```

### 地址寄存器

地址寄存器用于存储地址偏移量，支持循环自增，简化循环访问内存的地址管理，适配循环加载/存储数据场景。

**使用示例**：
```cpp
iter_reg addr_reg = asc_create_iter_reg_b8(offset);
```

### 寄存器类型选择决策流程

开发者可结合计算场景特性，选择对应的寄存器类型：

```
你的计算场景是什么？
├─ 逐元素计算（加、减、乘、激活函数）
│   └─ 使用 vector_half / vector_float 等矢量寄存器
│       └─ 配合 mask：控制哪些元素参与计算
│
├─ 需要选择性处理元素（如尾部数据）
│   └─ 使用 vector_bool 掩码寄存器
│       └─ 通过 mask 控制计算范围
│
├─ 需要循环访问内存
│   └─ 使用 iter_reg 地址寄存器
│       └─ 自动管理地址偏移
```

**表 4**  寄存器类型使用场景

| 寄存器类型 | 使用时机 | 使用场景 |
|-----------|----------|----------|
| **矢量数据寄存器** | Vector计算时 | 存储计算输入/输出数据，例如向量加法、乘法、激活函数 |
| **掩码寄存器** | 需要选择性计算时 | 部分元素参与计算（如尾部数据处理、条件计算） |
| **地址寄存器** | 需要循环访问内存时 | 循环加载/存储数据，自动管理地址偏移 |

## Local Memory与寄存器协作模型：Load-Compute-Store数据流

### 核心协作关系

**Local Memory是数据存储空间，寄存器是计算单元的工作台。**

这是AI Core硬件架构的核心设计原则，所有Vector计算均遵循Load-Compute-Store数据流：
- **Vector计算单元只能访问寄存器**：硬件设计上，Vector单元不直接读取Local Memory，只能操作寄存器中的数据
- **寄存器是计算单元的"工作台"**：类似厨师的工作台，材料（数据）必须先放到工作台上才能加工
- **Local Memory是"仓库"**：类似仓库，存储大量数据，但计算单元不能直接使用仓库里的材料

类比理解：
```
传统CPU编程：可以直接操作内存中的数据
AI Core编程：必须先把数据从仓库搬运到工作台
```

### Vector计算数据流三阶段

Vector计算数据必须先从UB加载到寄存器，计算完成后写回UB，遵循标准的三阶段流程：

**图 2**  Local Memory与寄存器数据流

![Local Memory与寄存器数据流](../../../../figures/Local%20Memory与寄存器数据流.png)

#### 第一阶段：Load（数据加载）

从Local Memory（UB）加载数据到寄存器，为计算准备输入数据。

```cpp
constexpr uint32_t length = 128;
__ubuf__ half src_buffer[length];  // 数据存储在UB

vector_half src_reg;
asc_loadalign(src_reg, src_buffer);  // Load: UB → 寄存器
```

#### 第二阶段：Compute（数据计算）

寄存器数据参与计算，结果存储到寄存器，完成核心运算逻辑。

```cpp
vector_half dst_reg;
vector_bool mask = asc_create_mask_b16(PAT_ALL);
asc_add(dst_reg, src_reg, src_reg, mask);  // Compute: 寄存器 → 寄存器
```

#### 第三阶段：Store（结果存储）

从寄存器写回数据到Local Memory（UB），完成计算结果输出。

```cpp
__ubuf__ half dst_buffer[length];  // 结果存储在UB
asc_storealign(dst_buffer, dst_reg, mask);  // Store: 寄存器 → UB
```

### 完整Vector计算数据流示例

```cpp
// 1. 申请Local Memory（UB）
constexpr uint32_t length = 128;
__ubuf__ half src_buffer[length];  // 数据存储在UB
__ubuf__ half dst_buffer[length];  // 结果存储在UB

// 2. Load: Local Memory → 寄存器
vector_half src_reg;
asc_loadalign(src_reg, src_buffer);

// 3. Compute: 寄存器 → 寄存器
vector_half dst_reg;
vector_bool mask = asc_create_mask_b16(PAT_ALL);
asc_add(dst_reg, src_reg, src_reg, mask);

// 4. Store: 寄存器 → Local Memory
asc_storealign(dst_buffer, dst_reg, mask);
```

### Cube计算数据流示例

Cube计算单元只能访问L0寄存器，数据必须先从L1加载到L0A/B，遵循类似的Load-Compute-Store流程：

```cpp
// 1. 申请Local Memory（L1、L0A/B/C）
__cbuf__ half a_l1[4096];  // L1中转区
__ca__ half a_l0a[512];    // L0A输入
__cb__ half b_l0b[512];    // L0B输入
__cc__ float c_l0c[256];   // L0C输出

// 2. Load: L1 → L0A/L0B
asc_copy_l12l0a(a_l0a, a_l1, 0, 1, 1, 0);
asc_copy_l12l0b(b_l0b, b_l1, 0, 1, 1, 0);

// 3. Compute: L0A/B → L0C
asc_mmad(c_l0c, a_l0a, b_l0b, 128, 64, 64, 0, false, false, true);

// 4. Store: L0C → GM或L1
asc_copy_l0c2gm(output, c_l0c, size);
```

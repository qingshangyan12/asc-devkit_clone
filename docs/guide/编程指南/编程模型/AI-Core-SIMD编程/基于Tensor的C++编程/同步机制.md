## 引言

AI Core采用多条流水线异步并行架构，数据搬入、计算、数据搬出分别由MTE2、Vector/Cube、MTE3流水线承载。流水线异步执行带来天然并行优势，但也引入数据依赖风险。同步机制是协调流水线协作、确保数据依赖关系得到满足的关键技术。

> 📌 通常情况下，开发者基于编程模型进行编程时不需要关注同步，编程模型帮助开发者完成了同步控制。自行同步控制可能带来一定编程复杂度。

---

## 为什么需要同步：异步执行的数据依赖风险

### 流水线异步执行的优势与风险

AI Core包含多条独立流水线（MTE2/MTE3搬运、Vector计算、Cube计算），异步并行执行，各自独立推进，无需等待其他流水线。
- **并行优势**：数据搬入与计算可同时进行，MTE2搬运下一块数据时Vector正在处理上一块，流水线重叠使吞吐率大幅提升。
- **潜在风险**：流水线缺乏自动协调，若计算在搬运完成前启动，会读取未就绪数据导致错误。需开发者通过显式同步指令控制执行顺序，确保数据搬运与计算的严格时序。

> 💡 **类比理解**：传统串行程序像"一个人依次洗菜→切菜→炒菜"，每一步自动等待前一步完成；异步并行程序像"三个人各自独立工作：洗菜人、切菜人、炒菜人"，各自按自己的节奏推进。同步机制就像"洗菜人洗完后喊'菜洗好了'，切菜人听到后才开始切"，通过明确的信号传递协调各环节的执行时机。

### 数据依赖关系：同步的本质需求

流水线之间存在明确的数据依赖关系，本质是"生产者-消费者"协作：
- **搬入→计算依赖**：MTE2搬运数据完成后，Vector/Cube才能开始计算。数据未就绪时计算会读取错误数据。
- **计算→搬出依赖**：Vector/Cube计算完成后，MTE3才能开始搬出。计算未完成时搬出会输出不完整数据。

> 💡 **类比理解**：餐厅后厨的协作流程——采购员买菜回来（数据搬入），厨师才能开始做饭（计算），做完饭后服务员才能端菜上桌（数据搬出）。若厨师在采购员还没回来就开始做饭，会发现"没菜可做"；若服务员在厨师还没做完就端菜，会端上"半成品"。

## 同步机制概述

Ascend C同步机制按同步范围分为两大类：**核内同步**、**核间同步**。
## 一、核内同步
AI Core内部的异步并行计算过程如下：Scalar计算单元读取指令序列，并把向量计算、矩阵计算、数据搬运指令发射给对应单元的指令队列。向量计算单元、矩阵计算单元、数据搬运单元异步并行执行接收到的指令。该过程可以参考图1中蓝色箭头所示的指令流。
不同的指令间有可能存在依赖关系，为了保证不同指令队列间的指令按照正确的逻辑关系执行，Scalar计算单元也会给对应单元下发同步指令。各单元之间的同步过程可以参考图1中的绿色箭头所示的同步信号流。
AI Core内部数据处理的基本过程：DMA搬入单元把数据搬运到Local Memory，Vector/Cube计算单元完成数据计算，并把计算结果写回Local Memory，DMA搬出单元把处理好的数据搬运回Global Memory。该过程可以参考图1中的红色箭头所示的数据流。
![AI Core内部并行计算架构抽象](<AI Core内部并行计算架构抽象.png>)

四个执行单元（Scalar、Vector、DMA(VECIN)、DMA(VECOUT)）并行执行，若访问同一片Local Memory，需要同步机制控制访问时序：保证先搬入Local Memory后再计算，计算完成后再搬出。

### SetFlag/WaitFlag（多流水同步）

采用**信号通知-阻塞等待**模式，源流水线完成任务后发出"就绪信号"，目标流水线收到信号前阻塞等待、收到后继续执行。
- **SetFlag**：前序指令的所有读写操作完成后，将硬件标志位设置为1，表示数据已就绪
- **WaitFlag**：执行到该指令时，若标志位为0则阻塞等待，为1则清零并继续执行

#### 硬件流水类型

**表 1** 硬件流水类型
| 流水类型 | 含义 |
|----------|------|
| **PIPE_S** | 标量流水线，使用Tensor GetValue函数时为此流水 |
| **PIPE_V** | 矢量计算流水及部分硬件架构下的L0C→UB数据搬运流水 |
| **PIPE_M** | 矩阵计算流水 |
| **PIPE_MTE1** | L1→L0A/L0B数据搬运流水 |
| **PIPE_MTE2** | GM→L1、GM→UB等数据搬运流水 |
| **PIPE_MTE3** | UB→GM等数据搬运流水 |
| **PIPE_FIX** | L0C→GM、L0C→L1等数据搬运流水 |

#### 常用同步类型

**表 2** 常用同步类型
| 同步类型 | 描述 | 使用场景 |
|----------|------|----------|
| **HardEvent::MTE2_V** | MTE2 → Vector | DataCopy（GM→UB）完成后执行Add |
| **HardEvent::V_MTE3** | Vector → MTE3 | Add完成后执行DataCopy（UB→GM） |
| **HardEvent::MTE2_MTE1** | MTE2 → MTE1 | DataCopy（GM→L1）完成后执行LoadData |
| **HardEvent::MTE1_M** | MTE1 → Cube | LoadData完成后执行Mmad |
| **HardEvent::M_MTE3** | Cube → MTE3 | Mmad完成后执行DataCopy（L0C→GM） |

#### 适用场景
同一核内不同流水之间的同步处理，具有数据依赖的不同流水指令之间需要插此同步。
```cpp
AscendC::GlobalTensor<half> dstGlobal;
AscendC::LocalTensor<half> dstLocal;
dstLocal.SetValue(0, 0);
uint32_t dataSize = 512;
// 基于TPipe和TQue编程场景中，eventID需要通过AllocEventID或FetchEventID获取
int32_t eventIDSToMTE3 = static_cast<int32_t>(GetTPipePtr()->FetchEventID(AscendC::HardEvent::S_MTE3));
AscendC::SetFlag<AscendC::HardEvent::S_MTE3>(eventIDSToMTE3);
AscendC::WaitFlag<AscendC::HardEvent::S_MTE3>(eventIDSToMTE3);
AscendC::DataCopy(dstGlobal, dstLocal, dataSize);
```

### Mutex（共享资源访问保护, Ascend 950PR/950DT引入）

Mutex用于核内异步流水指令之间的同步处理，其功能类似于传统CPU中的锁机制。通过锁定指定流水线再释放流水线来完成流水线间的同步。每个锁有固定的一个MutexID，该ID可通过用户自定义（范围为0-27）或者通过AllocMutexID/ReleaseMutexID进行申请释放。
- **Lock**：根据MutexID获取Mutex，并阻塞当前流水指令队列，直到对应的MutexID被Unlock。
- **Unlock**：等待当前流水线的指令全部执行完毕后，根据MutexID释放对应Mutex。

> 💡 **类比理解**：Mutex像"会议室门锁"——多人共享一个会议室（多条流水线共享同一资源），进入会议室后需要先锁门（Lock），确保独占使用，其他人必须等待（阻塞）。使用完毕后开门离开（Unlock），其他人才能进入使用。同一时刻仅允许一人持有钥匙并使用会议室（互斥性）。

#### 使用场景
```cpp
// 锁定 MTE2 流水线互斥锁，确保当前线程独占 MTE2 资源进行数据搬运
AscendC::Mutex::Lock<PIPE_MTE2>(mutexId);
AscendC::DataCopy(xLocal, src0Global[TILE_LENGTH * progress], TILE_LENGTH);
AscendC::DataCopy(yLocal, src1Global[TILE_LENGTH * progress], TILE_LENGTH);
// 解锁 MTE2 流水线，允许其他线程使用 MTE2
AscendC::Mutex::Unlock<PIPE_MTE2>(mutexId);

// 锁定 Vector 流水线互斥锁，确保当前线程独占向量计算资源
AscendC::Mutex::Lock<PIPE_V>(mutexId);
AscendC::Add(zLocal, xLocal, yLocal, TILE_LENGTH);
// 解锁 Vector 流水线，释放计算资源供其他线程使用
AscendC::Mutex::Unlock<PIPE_V>(mutexId);
```

### PipeBarrier（单流水同步）

采用**阻塞等待**模式，保证前序指令中所有数据的读写工作全部完成，后序指令才能执行。用于在同一流水线内部约束执行顺序。

#### 适用场景

相同流水线内，前序指令输出是后续指令输入时，需要插入PipeBarrier。

```cpp
Add(dst0, src0, src1, 512);    // Add输出是Mul输入
PipeBarrier<PIPE_V>();         // Vector流水线内同步
Mul(dst1, dst0, src2, 512);    // Mul依赖Add输出
```

## 二、核间同步

### CrossCoreSetFlag/WaitFlag（多核协作同步）
核间同步采用**计数器递增/递减**模式，通过flag_id对应的计数器协调多核执行进度。每个flag_id对应一个初始值为0的计数器，arrive指令递增计数器表示"当前核到达同步点"，wait指令检测计数器大于0则递减并继续执行、等于0则阻塞等待。这种机制实现了"多核到达同步点后才继续执行"的协调效果，适用于跨核数据交换、多核矩阵乘等协作场景。

> 💡 **类比理解**：多核协作像"团队开会约定"——每个人各自从不同地方出发前往会议室（各核独立执行算子逻辑），到达会议室后在签到表上签到（arrive递增计数器），等待所有人都签到后会议才开始（wait检测计数器大于0后继续执行）。若签到人数不够，则等待（计数器为0时阻塞）。

#### 适用场景
多核协作算子（跨核数据交换、多核矩阵乘），各核在关键节点等待其他核完成后再继续。
```cpp
// 使用模式0的方式同步所有的AIV核
if (g_coreType == AscendC::AIV) {
    AscendC::CrossCoreSetFlag<0x0, PIPE_MTE3>(0x8);
    AscendC::CrossCoreWaitFlag(0x8);
}

// 使用模式1的方式同步当前AICore内的所有AIV子核
if (g_coreType == AscendC::AIV) {
    AscendC::CrossCoreSetFlag<0x1, PIPE_MTE3>(0x8);
    AscendC::CrossCoreWaitFlag(0x8);
}

// 注意：如果调用高阶API,无需开发者处理AIC和AIV的同步
// 以Matmul为例：AIC侧做完Matmul计算后通知AIV进行后处理
if (g_coreType == AscendC::AIC) {
    // Matmul处理
    AscendC::CrossCoreSetFlag<0x2, PIPE_FIX>(0x8);
}

// AIV侧等待AIC Set消息, 进行Vector后处理
if (g_coreType == AscendC::AIV) {
    AscendC::CrossCoreWaitFlag(0x8);
    // Vector后处理
}
```

## 小结

同步机制协调流水线协作，确保数据依赖关系正确处理。核内同步包括SetFlag/WaitFlag（多流水同步）和PipeBarrier（单流水同步）。核间同步采用计数器机制协调多核执行进度。

# 抽象硬件架构<a name="ZH-CN_TOPIC_0000001861989988"></a>

AI Core 是 AI 处理器的计算核心，一个处理器内部包含多个 AI Core。本章节介绍 AI Core 的并行计算架构抽象，该抽象屏蔽了不同硬件（如达芬奇架构的 2002、2201、3510 等 NPU 型号）之间的差异，让你只需理解一套统一的编程模型即可完成算子开发。想要了解真实硬件与抽象模型的对应关系，可参考[硬件实现](../../硬件实现/基本架构.md)。

AI Core 中包含**计算单元、存储单元、搬运单元**三大类核心组件。

### 计算单元

AI Core 内部有三个计算单元，分工如下：

| 单元 | 职责 |
|---|---|
| Scalar | 地址计算、循环控制、指令分派 |
| Vector | 向量运算（SIMD 逐元素操作） |
| Cube | 矩阵运算（高密度矩阵乘法） |

**Scalar 计算单元** — 负责执行地址计算、循环控制等标量计算工作，同时将向量计算、矩阵计算、数据搬运和同步指令**分派**到对应单元的指令队列。在代码中，Scalar 的工作通常是隐式的——你编写的循环、地址偏移计算都由它完成。一个典型的使用场景是循环分块（Tiling）时的地址生成。

**Vector 计算单元** — 负责执行向量运算（SIMD 范式），对一个数组中的所有元素同时执行相同的操作。在 AscendC 中，像 `Add`、`Mul`、`Max` 这类逐元素运算都由 Vector 单元完成：

```cpp
// Vector 计算：对 ubX 和 ubY 中每个元素执行加法
Add(ubZ, ubX, ubY, CALC_NUM);
```

> Tiling: 将大块数据分割成小块（Tile），以便能放入有限的片上内存（UB）中进行处理。这是 AscendC 性能优化的核心技术之一，初次接触时不必深究其全部细节。

**Cube 计算单元** — 专门处理矩阵乘法等高密度运算，在涉及深度学习全连接层、卷积等计算时，Cube 单元的吞吐量远高于 Vector。它在代码中通常通过 `MatMul` 等高层 API 调用。

这三个计算单元的具体接口定义可以在 [`asc-devkit/include/basic_api/kernel_operator.h`](../../../../../../asc-devkit/include/basic_api/kernel_operator.h) 中找到，包含 Vector 和 Cube 计算 API 的完整声明。完整的算子示例请参考 [`asc-devkit/examples/01_simd_cpp_api/`](../../../../../../asc-devkit/examples/01_simd_cpp_api) 目录下的 Add、MatMul 等项目。

### 存储单元

一个核函数在运行过程中，数据在两个存储层级之间流动：

- **Global Memory（全局内存/GM）** — 对应 `GlobalTensor` 数据类型。所有 AI Core 都能访问的全局存储空间，容量大但访问延迟高。

- **Local Memory（本地内存/LM）** — 对应 `LocalTensor` 数据类型。每个 AI Core 私有的片上存储空间，容量有限但访问速度快。其中最主要的部分是 Unified Buffer（UB），Vector 计算时数据暂存在 UB 中。

```cpp
// GlobalTensor：指向全局内存中的数据
GlobalTensor<float> gmTensor;
// LocalTensor：在本地内存上分配一块空间
LocalTensor<float> ubTensor = AllocTensor<float>(queue, BUFFER_SIZE);
```

这两个 Tensor 类型的具体定义和操作方法，可以在 [`asc-devkit/include/basic_api/kernel_tensor.h`](../../../../../../asc-devkit/include/basic_api/kernel_tensor.h) 中查看。

### 搬运单元

**DMA（Direct Memory Access）搬运单元** — 负责在 Global Memory 和 Local Memory 之间搬运数据，以及在不同层级的 Local Memory 之间搬运。DMA 搬运数据不需要计算单元参与，可以与计算**异步并行**进行。

```cpp
// DMA 将数据从 Global Memory 搬运到 Unified Buffer
DataCopy(ubTensor, gmTensor, COPY_LEN);
```

`DataCopy` 接口在 [`asc-devkit/include/basic_api/kernel_operator.h`](../../../../../../asc-devkit/include/basic_api/kernel_operator.h) 中有多个重载版本，支持不同内存层级间的数据搬运。

### 三条核心数据流

理解上述组件后，你需要重点关注 AI Core 内部的**三个过程**，它们分别用[图1](#fig1095152043812)中蓝、绿、红三种箭头标注：

1. **异步指令流（蓝色箭头）**：Scalar 计算单元读取指令序列，将向量计算、矩阵计算、数据搬运等指令发射到对应单元的**独立指令队列**中。Vector、Cube、DMA 三个单元各自维护自己的队列，**异步并行**地执行接收到的指令。这是 AI Core 高性能的来源——DMA 搬运数据的同时，Vector 可以继续执行上一批数据的计算。

2. **同步信号流（绿色箭头）**：由于各单元异步执行，指令之间可能存在数据依赖——例如 Vector 必须等 DMA 将数据搬运到 Local Memory 后才能读取。Scalar 单元会在依赖点插入**同步指令（Pipe Barrier）**，等待某条流水线上所有已发射的指令执行完毕后，再允许依赖方继续执行。详见本章[内存层级间的同步机制](#内存层级间的同步机制)。

3. **计算数据流（红色箭头）**：数据在 AI Core 内部的基本处理路径为 DMA 搬入 → Vector/Cube 计算 → DMA 搬出：
   - DMA 将数据从 Global Memory 搬运到 Local Memory（UB）
   - Vector/Cube 单元从 UB 读取数据并执行计算，结果写回 UB
   - DMA 将处理结果从 UB 搬运回 Global Memory

要查看以上三个过程在完整核函数中的具体编排方式，可以参考 [`asc-devkit/examples/01_simd_cpp_api/02_features/00_compilation/custom_op/op_kernel/add_custom/add_custom_kernel.cpp`](../../../../../../asc-devkit/examples/01_simd_cpp_api/02_features/00_compilation/custom_op/op_kernel/add_custom/add_custom_kernel.cpp) 中的 `KernelAdd` 类，它清晰地展示了 DMA 搬入、Vector 计算、DMA 搬出的三阶段循环。

### 内存层级间的同步机制

在理解同步机制之前，需要先明确一个关键事实：AI Core 内部的**搬运单元（DMA）**、**向量计算单元（Vector）**、**矩阵计算单元（Cube）** 各自拥有独立的指令队列，由 Scalar 单元分派指令后**异步并行执行**。这意味着：

- DMA 搬运数据到 Local Memory 的同时，Vector 可能在执行上一次的计算
- 如果 Vector 在 DMA 尚未完成时就读取目标缓冲区，就会读到脏数据
- 同样，如果 DMA 在 Vector 尚未写回结果时就开始搬出，则会搬出旧值

**Pipe Barrier** 是 AscendC 用来解决上述数据一致性问题的同步原语，由 Scalar 计算单元统一管理。其工作机制是：DMA 完成数据搬运后触发 `SetFlag` 标记数据就绪，Vector 调用 `WaitFlag` 等待该标记后再读取数据；Vector 完成计算并写回结果后同样触发标记，DMA 等待后再搬出。这套 `SetFlag` / `WaitFlag` 机制确保了 DMA 搬运、Vector 计算、Cube 计算三条流水线之间按正确的顺序访问 Local Memory。

要理解同步机制，最直接的方式是看**静态 Tensor（Static Tensor）** 的用法——它不使用队列封装，每个同步点都由开发者通过 `pipe_barrier` 显式控制。下面的例子展示了三个步骤分别执行，每个步骤之间用 `pipe_barrier` 明确隔开：

```cpp
__aicore__ inline void SyncAddExample()
{
    // 1. 在 UB 上分配三块空间：输入 x、输入 y、输出 z
    LocalTensor<float> ubX = AllocTensor<float>(queue, TILE_LEN);
    LocalTensor<float> ubY = AllocTensor<float>(queue, TILE_LEN);
    LocalTensor<float> ubZ = AllocTensor<float>(queue, TILE_LEN);

    // ──── 第一步：DMA 从 GM 搬入数据到 UB ────
    DataCopy(ubX, gmX, TILE_LEN);
    DataCopy(ubY, gmY, TILE_LEN);
    // ← 显式等待 DMA 搬运完成，确保 ubX、ubY 中的数据已就绪
    pipe_barrier(PIPE_MTE2);
    
    // ──── 第二步：Vector 执行加法计算 ────
    Add(ubZ, ubX, ubY, TILE_LEN);
    // ← 显式等待 Vector 计算完成，确保 ubZ 中的结果已写回
    pipe_barrier(PIPE_V);
    
    // ──── 第三步：DMA 将结果从 UB 搬回 GM ────
    DataCopy(gmZ, ubZ, TILE_LEN);
    // ← 等待最后一次 DMA 搬出完成（确保后续操作能安全使用 gmZ）
    pipe_barrier(PIPE_MTE2);

    // 释放 UB 空间
    FreeTensor(ubX);
    FreeTensor(ubY);
    FreeTensor(ubZ);
}
```

在整个流程中，Scalar 单元通过统计每条流水线上已发射的指令数量来决定 barrier 的释放时机——只有当一条流水线的指令队列全部执行完毕后，对应的 `pipe_barrier` 才会被释放，后续依赖该流水线的单元才能继续执行。

除 `pipe_barrier` 之外，AscendC 还提供了其他内存层级间的同步机制：基于 `SetFlag`/`WaitFlag` 的事件同步接口定义在 [`asc-devkit/include/basic_api/kernel_operator_block_sync_intf.h`](../../../../../../asc-devkit/include/basic_api/kernel_operator_block_sync_intf.h) 中，`TQue` 的入队/出队自动同步实现在 [`asc-devkit/include/basic_api/kernel_tpipe.h`](../../../../../../asc-devkit/include/basic_api/kernel_tpipe.h) 中。各机制的硬件实现原理请参考 [同步机制说明](../../硬件实现/基本架构.md)。

> 以上为静态 Tensor + 显式 `pipe_barrier` 的示意代码，这是推荐的主流程编程方式，每个同步点清晰可见，便于开发者精确控制数据流。同时 AscendC 也提供了 `TQue` + `EnQue`/`DeQue` 的队列封装，它自动根据 `VECIN`、`VECOUT` 等位置信息推导依赖并插入相同的 `pipe_barrier` 指令，适合快速编写原型代码。要查看基于队列封装的可编译运行示例，请参阅 [`asc-devkit/examples/01_simd_cpp_api/02_features/00_compilation/custom_op/op_kernel/add_custom/add_custom_kernel.cpp`](../../../../../../asc-devkit/examples/01_simd_cpp_api/02_features/00_compilation/custom_op/op_kernel/add_custom/add_custom_kernel.cpp)。

# 抽象硬件架构<a name="ZH-CN_TOPIC_0000001861989988"></a>

Ascend C 的编程模型建立在对 AI Core 硬件架构的抽象之上。本章从初学者的视角介绍这套抽象架构的各个组成部分，帮助你在阅读后续的编程接口与示例之前，先建立起清晰的硬件心智模型。

> [!NOTE]
> 无论底层芯片是 Ascend 950 系列、Atlas A2/A3 系列还是其他 NPU 型号，本章描述的抽象模型都保持一致。若想了解抽象模型与具体硬件的映射关系，可参考[硬件实现](../../高级编程/硬件实现/基本架构.md)。不同芯片型号通过 [`__NPU_ARCH__` 宏](../../语言扩展层/SIMD-BuiltIn关键字.md#预定义宏)进行区分。

---

## 1. 异构计算系统<a name="heterogeneous_system"></a>

Ascend C 面向的是**异构计算系统**：Host 侧 CPU 负责任务调度与数据准备，Device 侧 NPU 负责大规模并行计算。

```
┌─────────────────────────────────────────────────┐
│  Host（CPU）                                     │
│  ├─ 准备输入数据                                  │
│  ├─ 调用 Runtime API 管理 Device 内存              │
│  ├─ 启动 Kernel <<<>>>                           │
│  └─ 等待执行完成 / 取回结果                        │
│        │  PCIe / 片间总线                          │
│        ▼                                          │
│  Device（NPU）                                    │
│  ├─ Global Memory（HBM，所有 AI Core 共享）        │
│  ├─ AI Core 0  │  AI Core 1  │  ... │  AI Core N │
│  └─ L2 Cache（所有 AI Core 共享）                  │
└─────────────────────────────────────────────────┘
```

**核心概念**：

| 概念 | 说明 |
|:---|:---|
| **Host（主机端）** | 运行 C++ 控制程序的 CPU，通过 ASCEND Runtime API 管理 Device 内存、启动 Kernel、同步任务。 |
| **Device（设备端）** | NPU 上的计算资源集合，包含多个 AI Core 和一块全局高带宽内存（HBM）。 |
| **Global Memory（GM）** | Device 侧的全局内存，Host 和所有 AI Core 均可访问。容量大但访问延迟高（百纳秒级），是整个系统的数据源头和最终出口。 |
| **Kernel** | 在 Device 上执行的函数，等价于"GPU 上的 CUDA Kernel"。用 `__global__` 声明，通过 `<<<>>>` 语法从 Host 侧启动。 |
| **Kernel Launch** | 一次 `<<<blockNum, l2Ctrl, stream>>>(args...)` 调用可以向多个 AI Core 同时下发同一个 Kernel 函数，每个 AI Core 处理一部分数据——这正是数据并行的核心机制。 |

**典型执行流程**：

1. Host 侧申请 GM 空间（`aclrtMalloc`），将输入数据从 Host 内存拷贝到 GM（`aclrtMemcpy`）。
2. Host 侧启动 Kernel（`kernel_name<<<N, nullptr, stream>>>(args...)`），N 个 AI Core 并行执行。
3. 每个 AI Core 从 GM 加载自己的那部分数据到片上内存，完成计算后将结果写回 GM。
4. Host 侧同步（`aclrtSynchronizeStream`），等待所有 AI Core 完成。
5. Host 侧将结果从 GM 拷贝回 Host 内存。

## 2. AI Core 抽象架构<a name="aicore_abstract_arch"></a>

一个 AI Core 内部包含**计算单元、存储单元、搬运单元**三大类核心组件，由 **Scalar 调度单元**统一协调各单元的并行执行：

**图 1** AI Core 抽象架构<a name="fig1095152043812"></a>
![](../../../figures/抽象硬件架构.png "抽象硬件架构")

图中用三种箭头标注了 AI Core 内部的三条关键通路：

| 通路 | 颜色 | 含义 |
|:---|:---|:---|
| **指令流** | 蓝色 | Scalar 单元从指令缓存读取指令，将其中的 Vector/Cube/搬运指令分派到对应单元的独立指令队列 |
| **数据流** | 红色 | 数据在 GM → 片上 Buffer → 计算单元之间流转 |
| **同步流** | 绿色 | Scalar 在管线间插入同步指令，确保数据依赖关系正确 |

AI Core 高性能的秘密在于三条通路可以**异步并行**——在 DMA 搬运下一批数据的同时，Vector/Cube 可以继续执行上一批数据的计算。

## 3. 计算单元<a name="compute_units"></a>

AI Core 内部有三个计算单元，分别负责不同类型的计算任务。每个单元都拥有独立的指令队列，由 Scalar 统一分派指令后异步执行。

### 3.1 Scalar 计算单元

Scalar 是整个 AI Core 的**控制中枢**。它的职责不是做海量数据计算，而是：

- **指令分派**：从指令缓存读取指令序列，将 Vector 指令、Cube 指令、搬运指令分别发射到对应单元的指令队列。
- **地址计算**：为数据搬运和计算生成正确的内存地址（例如循环分块时的地址偏移）。
- **流程控制**：执行循环计数、分支判断等标量逻辑。
- **同步协调**：在流水线之间插入 `SetFlag`/`WaitFlag`/`PipeBarrier` 等同步原语（详见[同步机制](#sync)）。

> [!TIP]
> Scalar 的计算能力相对有限。在实际开发中应尽量减少 Scalar 侧的重度运算（如复杂分支、大量变量计算），将计算密集任务交给 Vector 或 Cube。

### 3.2 Vector 计算单元

Vector 负责执行**向量运算**——对一组连续数据同时执行相同的操作，即我们常说的 SIMD（Single Instruction, Multiple Data）。

| 属性 | 说明 |
|:---|:---|
| **类比** | 相当于 GPU 中的 CUDA Core 集合，或者 CPU 中的 SIMD 扩展（如 AVX/NEON） |
| **数据来源** | 所有输入和输出数据均位于 **Unified Buffer（UB）** 中 |
| **典型操作** | 逐元素加减乘除、指数/对数、比较、类型转换、归约求和/求最大值等 |
| **对齐要求** | 通常要求 32B 对齐（具体以各 API 的约束描述为准） |

Vector 每次指令可处理多个操作数，显著减少了指令发射开销。例如，一个 `AscendC::Add(z, x, y, 1024)` 调用可在一次发射中完成 1024 个元素的加法。

数据流转路径：

```
GM ──(MTE2)──▶ UB ──(Vector)──▶ UB ──(MTE3)──▶ GM
```

### 3.3 Cube 计算单元

Cube 是 AI Core 的**矩阵加速引擎**，专门处理高密度的矩阵乘法运算。

| 属性 | 说明 |
|:---|:---|
| **类比** | 相当于 GPU 中的 Tensor Core |
| **典型操作** | 矩阵乘法（Mmad）、卷积运算的数据加载（LoadData） |
| **数据来源** | 左矩阵从 L0A Buffer 读取，右矩阵从 L0B Buffer 读取，结果写入 L0C Buffer |
| **吞吐量** | 以 float16 为例，一次 Mmad 可完成两个 16×16 矩阵的乘法，远超 Vector 的同精度计算吞吐 |

数据流转路径：

```
GM ──(MTE2)──▶ L1 ──(MTE1)──▶ L0A/L0B ──(Cube)──▶ L0C ──(FixPipe)──▶ GM
```

> [!NOTE]
> Cube 和 Vector 的计算通路是独立的，互不阻塞。在分离模式的硬件架构下，两者甚至可以位于不同的物理核（AIC 与 AIV）。详见[硬件实现](../../高级编程/硬件实现/基本架构.md#AI Core的工作模式)。

## 4. 存储单元与搬运单元<a name="memory_and_transfer"></a>

计算单元的算力再强，如果数据不能及时到达也是枉然。本节介绍 AI Core 的多级存储层次以及负责数据搬家的搬运单元。

### 4.1 存储层次总览

AI Core 的存储系统分为多个层级，离计算单元越近的存储器速度越快、容量越小：

```
容量大、延迟高                             容量小、延迟低
   GM ──── L2 Cache ──── L1 Buffer ──── L0 Buffer / UB
  (HBM)    (核外)         (核内中转)       (计算直连)
```

| 层级 | 存储单元 | 位置 | 访问范围 | 承载内容 |
|:---|:---|:---|:---|:---|
| **全局** | Global Memory（GM） | Device 侧 HBM | Host + 所有 AI Core | 原始输入数据、最终输出结果 |
| **核外缓存** | L2 Cache | 所有 AI Core 共享 | 所有 AI Core | 自动缓存 GM 访问，以 Cache Line 为单位（128/256/512B 不等） |
| **核内矩阵** | L1 Buffer | AI Core 内部 | 本 AI Core | Cube 输入数据的中转站，可存放反复使用的矩阵块 |
| **核内矩阵** | L0A / L0B Buffer | Cube 单元直连 | Cube | 矩阵乘法的左/右输入矩阵 |
| **核内矩阵** | L0C Buffer | Cube 单元直连 | Cube / FixPipe | 矩阵乘法的结果与累加中间值 |
| **核内向量** | Unified Buffer（UB） | Vector/Scalar 直连 | Vector / Scalar | 向量/标量计算的输入和输出 |

> [!NOTE]
> 不同芯片型号的各级存储容量不同。开发者可通过 `GetCoreMemSize` 接口查询当前芯片的存储规格，避免硬编码容量值——这是保证[跨代兼容性](../../跨代迁移兼容性指南/概述.md)的关键实践之一。

### 4.2 存储单元详解

**表 1** 存储单元<a name="table1692510612218"></a>

| 存储单元 | 功能描述 |
|:---|:---|
| **Global Memory（GM）** | 设备侧全局内存（HBM），是算子数据的起点和终点。Host 通过 Runtime API 读写，AI Core 通过搬运单元读写。 |
| **L2 Cache** | 核外高速缓存，所有 AI Core 共享。搬运单元对 GM 的读写默认经过 L2 Cache。对一次性读取的数据可设置 Cache Bypass 来减少不必要缓存。 |
| **L1 Buffer** | 核内通用缓冲，是 Cube 数据通路的中转枢纽。GM 到 L0A/L0B 的数据通常先经过 L1，L0C 的结果也可经 FixPipe 写回 L1。 |
| **L0A Buffer** | Cube 左矩阵输入。数据由 MTE1 从 L1 搬运而来。 |
| **L0B Buffer** | Cube 右矩阵输入。数据由 MTE1 从 L1 搬运而来。 |
| **L0C Buffer** | Cube 结果输出（同时也是累加输入）。数据由 FixPipe 搬运到 GM 或 L1。 |
| **Unified Buffer（UB）** | 向量计算的核心工作区。Vector 的所有源操作数和目标操作数必须位于 UB。Scalar 也可通过 UB 与 Vector 交换数据。 |
| **BiasTable Buffer（BT Buffer）** | 存放矩阵乘法中的 Bias 数据。 |
| **Fixpipe Buffer（FP Buffer）** | 存放 FixPipe 搬运过程中的量化参数、ReLU 参数等。 |

### 4.3 搬运单元

搬运单元（MTE，Memory Transfer Engine）负责在各级存储之间异步搬运数据，搬运过程**不需要计算单元参与**，可与计算**并行执行**。

| 搬运单元 | 负责通路 | 说明 |
|:---|:---|:---|
| **MTE1** | L1 → L0A / L0B，L1 → BT Buffer | 将矩阵数据从 L1 中转站喂入 Cube 计算所需的 L0 缓充。 |
| **MTE2** | GM → L1 / L0A / L0B，GM → UB | 将数据从全局内存搬入核内。按 Cache Line 大小对齐时性能最优。 |
| **MTE3** | UB → GM | 将计算结果从 Unified Buffer 写回全局内存。 |
| **FixPipe** | L0C → GM / L1，L1 → FP Buffer | Cube 结果的搬出通路，搬运过程中可完成随路数据格式/类型转换（如量化、ReLU 激活）。 |

> [!NOTE]
> 不同架构版本的搬运通路存在差异。例如 3510 架构删除了 L1→GM 通路、GM→L0A/L0B 通路等。编写跨代兼容算子时请参考[跨代迁移兼容性指南](../../跨代迁移兼容性指南/概述.md)。

### 4.4 完整数据流<a name="data_flow"></a>

理解了存储层次和搬运单元之后，下面给出两条最典型的数据通路，它们串联起了存储单元、搬运单元和计算单元的协作。

#### Vector 计算数据流

```
GM ──(MTE2)──▶ UB ──(Vector)──▶ UB ──(MTE3)──▶ GM
```

这是最简单的数据通路：输入数据从 GM 搬入 UB，Vector 单元在 UB 上完成计算，结果通过 MTE3 搬回 GM。**初学阶段建议先掌握这条通路**，它包含了 Ascend C 编程的全部基本要素。

#### Cube 计算数据流

```
GM ──(MTE2)──▶ L1 ──(MTE1)──▶ L0A/L0B ──(Cube)──▶ L0C ──(FixPipe)──▶ GM
                                    ▲
                                    │
                              L1 ──(MTE1)──▶ BT Buffer（可选 Bias）
```

这条通路较复杂，但性能更高：数据从 GM 先进入 L1（中转站），再从 L1 分发到 L0A/L0B，Cube 完成矩阵乘法后将结果写入 L0C，最后通过 FixPipe 搬回 GM。L1 充当了"数据蓄水池"——当矩阵数据需要被反复使用时，可避免重复从 GM 加载。

## 5. 同步机制<a name="sync"></a>

由于 AI Core 内部的搬运单元、Vector、Cube 各自独立异步执行，当它们之间存在数据依赖时（例如 Vector 必须等 DMA 搬运完成才能开始计算），需要通过同步机制来保证数据正确性。

Ascend C 提供两种同步原语：

| 同步原语 | 作用范围 | 使用场景 |
|:---|:---|:---|
| **PipeBarrier** | 单条指令流水线内部 | 确保前序指令的所有读写操作完成后，后续指令才开始执行 |
| **SetFlag / WaitFlag** | 两条不同指令流水线之间 | SetFlag 标记"数据已就绪"，WaitFlag 等待该标记后才继续执行——即生产者-消费者模型 |

> [!TIP]
> 在初学者的典型开发流程中，使用 [TPipe/TQue 编程框架](../基于TPipe-TQue框架编程/TPipe-TQue框架编程原理.md) 时，框架会自动完成同步管理，开发者**无需手动插入同步指令**。只有当采用[静态Tensor编程](../基于Tensor的C++编程/静态Tensor编程.md)方式追求极致性能时，才需要手动管理同步事件。

同步机制的详细原理与代码示例请参考后续章节：[TPipe-TQue框架的同步机制](../基于TPipe-TQue框架编程/TPipe-TQue框架编程原理.md#数据依赖与同步机制双api的协同工作) 和 [同步控制 API](../../../../api/SIMD-API/基础API/同步控制/核内同步/同步控制简介.md)。

> 想要从硬件层面理解同步的工作机制？请参考[硬件实现 - 典型的指令流](../../高级编程/硬件实现/基本架构.md#典型的指令流)。

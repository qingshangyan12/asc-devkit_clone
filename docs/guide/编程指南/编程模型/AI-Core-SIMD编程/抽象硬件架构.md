# 抽象硬件架构<a name="ZH-CN_TOPIC_0000001861989988"></a>

AI Core 是 AI 处理器的计算核心，一个处理器内部包含多个 AI Core。本章节介绍 AI Core 的并行计算架构抽象，该抽象屏蔽了不同硬件（如达芬奇架构的 2002、2201、3510 等 NPU 型号）之间的差异，让你只需理解一套统一的编程模型即可完成算子开发。

可以把一个 AI Core 想象成一个**微型工厂**，里面有不同的车间（计算单元）、仓储区（存储单元）和物流通道（搬运单元）。不同车间异步并行工作，Scalar 单元充当"厂长"统一调度，保证生产流程不出错。想要了解真实硬件与抽象模型的对应关系？可参考[硬件实现](../../硬件实现/基本架构.md)。

AI Core 中包含**计算单元、存储单元、搬运单元**三大类核心组件。

### 计算单元：三个各司其职的"车间"

AI Core 内部有三个计算单元，每个负责不同类型的计算任务：

**Scalar 计算单元** — 可以把它看作工厂里的**厂长/总指挥**。它负责执行地址计算、循环控制等标量运算，同时把向量计算、矩阵计算、数据搬运和同步指令**分派**给对应单元的指令队列。在代码中，Scalar 单元的工作通常是隐式的——你编写的循环、地址偏移计算都由它完成。一个典型的使用场景是循环分块（Tiling）时的地址生成。

**Vector 计算单元** — 可以看作工厂里的**装配流水线**。它擅长对一个数组中的所有元素同时执行相同的运算（SIMD 范式）。在 AscendC 中，像 `Add`、`Mul`、`Max` 这类逐元素运算都由 Vector 单元完成：

```cpp
// Vector 计算单元：对 ubX 和 ubY 中每个元素执行加法
Add(ubZ, ubX, ubY, CALC_NUM);
```

> Tiling: 将大块数据分割成小块（Tile），以便能放入有限的片上内存（UB）中进行处理。这是 AscendC 性能优化的核心技术之一，初次接触时不必深究其全部细节。

**Cube 计算单元** — 可以看作工厂里的**专用焊接机器人**，专门处理矩阵乘法这类高密度运算。在涉及深度学习中全连接层、卷积等计算时，Cube 单元能提供远高于 Vector 的吞吐量。它在代码中通常通过 `MatMul` 等高级 API 调用。

这三个计算单元的具体接口定义可以在 `asc-devkit/include/basic_api/kernel_operator.h` 中找到，其中包含了 Vector 和 Cube 计算 API 的完整声明。完整的算子示例请参考 `asc-devkit/examples/01_simd_cpp_api/` 目录下的 Add、MatMul 等项目。

### 存储单元：仓库与工作台

一个核函数在运行过程中，数据在两个存储层级之间流动：

- **Global Memory（全局内存/GM）** — 对应 `GlobalTensor` 数据类型。可以想象成工厂的**中心仓库**，容量大但离车间较远，访问延迟高。所有 AI Core 都能访问同一个 Global Memory 空间。

- **Local Memory（本地内存/LM）** — 对应 `LocalTensor` 数据类型。可以想象成每个车间里的**工作台**，容量小但离加工设备极近，访问速度快。其中最主要的部分是 Unified Buffer（UB），是 Vector 计算时数据暂存的地方。Local Memory 是每个 AI Core 私有的。

```cpp
// GlobalTensor：指向仓库中的数据
GlobalTensor<float> gmTensor;
// LocalTensor：在工作台上分配一块空间
LocalTensor<float> ubTensor = AllocTensor<float>(queue, BUFFER_SIZE);
```

这两个 Tensor 类型的具体定义和操作方法，可以在 `asc-devkit/include/basic_api/kernel_tensor.h` 中查看。

### 搬运单元：自动化物流通道

**DMA（Direct Memory Access）搬运单元** — 可以看作工厂里的**自动叉车/传送带**。它负责在仓库（Global Memory）和工作台（Local Memory）之间搬运数据，以及在不同本地内存层级之间搬运。最关键的特性是：DMA 搬运数据**不需要计算单元参与**，可以和计算**异步并行**进行。

```cpp
// DMA 将数据从 Global Memory 搬运到 Unified Buffer
DataCopy(ubTensor, gmTensor, COPY_LEN);
```

这个 `DataCopy` 接口在 `asc-devkit/include/basic_api/kernel_operator.h` 中有多个重载版本，支持不同内存层级间的搬运。

### 三条核心数据流

理解上述组件后，你需要重点关注 AI Core 内部的**三个过程**。它们分别用[图1](#fig1095152043812)中蓝、绿、红三种箭头标注：

1. **异步指令流（蓝色箭头）**：Scalar 计算单元读取指令序列，将向量计算、矩阵计算、数据搬运等指令发射到对应单元的**独立指令队列**中。Vector、Cube、DMA 三个单元各自维护自己的队列，**异步并行**地执行接收到的指令。这正是 AI Core 高性能的来源——在 DMA 搬运数据的同时，Vector 可以继续算上一批数据。

2. **同步信号流（绿色箭头）**：因为各单元异步执行，指令之间可能存在数据依赖——比如 Vector 必须等 DMA 把数据搬完才能开始计算。Scalar 单元会在此类依赖点插入**同步指令（Pipe Barrier）**，等待某条流水线上所有已发射的指令执行完毕，再允许依赖方继续。这部分在本章[内存层级间的同步机制](#内存层级间的同步机制)中有详细说明。

3. **计算数据流（红色箭头）**：数据在 AI Core 内部的基本处理路径是：DMA 搬入 → Vector/Cube 计算 → DMA 搬出。具体来说：
   - DMA 将数据从 Global Memory 搬运到 Local Memory（UB）
   - Vector/Cube 单元从 UB 读取数据并执行计算，结果写回 UB
   - DMA 将处理好的结果从 UB 搬运回 Global Memory

要查看以上三个过程在完整核函数中的具体编排方式，可以参考 `asc-devkit/examples/01_simd_cpp_api/02_features/00_compilation/custom_op/op_kernel/add_custom/add_custom_kernel.cpp` 中的 `KernelAdd` 类，它清晰地展示了 DMA 搬入、Vector 计算、DMA 搬出的三阶段循环。

### 内存层级间的同步机制

在理解同步机制之前，需要先明确一个关键事实：AI Core 内部的**搬运单元（DMA）**、**向量计算单元（Vector）**、**矩阵计算单元（Cube）** 各自拥有独立的指令队列，它们由 Scalar 单元分派指令后**异步并行执行**。这意味着：

- DMA 搬运数据到 Local Memory 的同时，Vector 可能在执行上一次的计算
- 如果 Vector 在 DMA 尚未完成时就读取目标缓冲区，就会读到脏数据
- 同样，如果 DMA 在 Vector 尚未写回结果时就开始搬出，则会搬出旧值

**Pipe Barrier（管道屏障）** 是 AscendC 用来解决上述数据一致性问题的同步原语，由 Scalar 计算单元统一管理。你可以把它想象成车间里的**传递窗口**：DMA 把工件（数据）放进窗口时打一个信号灯（`SetFlag`），Vector 看到信号灯亮起后才能取走工件（`WaitFlag`）；Vector 加工完成后放回窗口再打一次信号灯，DMA 看到后才能取走搬出。这套机制确保了 DMA 搬运、Vector 计算、Cube 计算三个流水线之间按正确的顺序访问 Local Memory。

要理解同步机制，最直接的方式是看**静态 Tensor（Static Tensor）** 的用法——它不使用队列封装，每个同步点都由开发者通过 `pipe_barrier` 显式控制。下面的例子展示了三个步骤分别执行，每个步骤之间用 `pipe_barrier` 明确隔开：

```cpp
__aicore__ inline void SyncAddExample()
{
    // 1. 在 UB 上分配三块空间：输入 x、输入 y、输出 z
    LocalTensor<float> ubX = AllocTensor<float>(queue, TILE_LEN);
    LocalTensor<float> ubY = AllocTensor<float>(queue, TILE_LEN);
    LocalTensor<float> ubZ = AllocTensor<float>(queue, TILE_LEN);

    // ──── 第一步：DMA 从 GM 搬入数据到 UB ────
    DataCopy(ubX, gmX, TILE_LEN);
    DataCopy(ubY, gmY, TILE_LEN);
    // ← 显式等待 DMA 搬运完成，确保 ubX、ubY 中的数据已就绪
    pipe_barrier(PIPE_MTE2);
    
    // ──── 第二步：Vector 执行加法计算 ────
    Add(ubZ, ubX, ubY, TILE_LEN);
    // ← 显式等待 Vector 计算完成，确保 ubZ 中的结果已写回
    pipe_barrier(PIPE_V);
    
    // ──── 第三步：DMA 将结果从 UB 搬回 GM ────
    DataCopy(gmZ, ubZ, TILE_LEN);
    // ← 等待最后一次 DMA 搬出完成（确保后续操作能安全使用 gmZ）
    pipe_barrier(PIPE_MTE2);

    // 释放 UB 空间
    FreeTensor(ubX);
    FreeTensor(ubY);
    FreeTensor(ubZ);
}
```

上面这段代码中的**每一行 `pipe_barrier` 都是一个明确的同步锚点**，对应着硬件上 Scalar 单元插入的一条同步指令：

| 代码行 | 同步信号含义 |
|---|---|
| `pipe_barrier(PIPE_MTE2)` ① | 告诉 Vector："等 DMA（MTE2）全部搬完，你再往后走" |
| `pipe_barrier(PIPE_V)` ② | 告诉 DMA："等 Vector 全部算完，你再往后走" |
| `pipe_barrier(PIPE_MTE2)` ③ | 确保最后一次 DMA 搬出完成（实际编程中可按需添加） |

在整个流程中，Scalar 单元承担着"交通警察"的角色——它统计每条流水线上发射的指令数量，只有当队列中所有已发射的指令都执行完毕后，才释放对应的 `pipe_barrier`，允许依赖方继续执行。

> 以上为静态 Tensor + 显式 `pipe_barrier` 的示意代码，重点展示同步信号在代码层面的位置和作用。在实际项目中，更常见的是使用 `TQue` + `EnQue`/`DeQue` 的队列管理模式，由编译器自动根据 `VECIN`、`VECOUT` 等位置信息推导依赖并插入相同的 `pipe_barrier` 指令。要查看基于队列管理且可编译运行的完整示例，请参阅 `asc-devkit/examples/01_simd_cpp_api/02_features/00_compilation/custom_op/op_kernel/add_custom/add_custom_kernel.cpp`。

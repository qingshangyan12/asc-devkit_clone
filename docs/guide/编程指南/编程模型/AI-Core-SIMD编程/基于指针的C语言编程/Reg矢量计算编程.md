# Reg矢量计算编程<a name="ZH-CN_TOPIC_0000002509863891"></a>

> 📌 **提示**：Reg矢量计算编程仅在Ascend 950PR/Ascend 950DT 进行SIMD编程时支持

本文介绍如何在AscendC中使用Reg矢量计算API编写寄存器级**向量计算代码**，该能力面向已经熟悉基础AscendC编程模型的开发者。Reg矢量计算提供更贴近硬件的向量寄存器编程方式。

## 适用场景<a name="section1825793122916"></a>

Reg矢量计算并不是替代Memory矢量计算，而是面向不同开发层次需求。Reg矢量编程适用于需要进一步减少UB读写、压缩关键路径访存开销、并愿意显式管理寄存器Load/Store流程的高性能场景。 

| 维度 | Memory矢量计算 | Reg矢量计算 |
| --- | --- | --- |
| 数据位置 | UB | SIMD Registers |
| 中间结果 | 必须回写UB | 可保留在寄存器中连续消费（需要在VF内） |
| 使用成本 | 较低 | 较高（需要理解寄存器、掩码等） |
| 适用目标 | 快速实现、不追求极致性能 | 愿意用高复杂度编程追求性能 |

通常在以下条件同时满足时，建议考虑使用Reg矢量计算编程：

1. 核心耗时集中在连续向量计算。
2. 中间结果在UB中存在明显的反复读写。
3. 追求极致性能收益，可接受更高的代码复杂度。

> 📌 **提示**：Reg矢量计算编程更适合作为热点片段的精细化优化手段。

## Regbase编程模型<a name="section1977234218287"></a>

Reg矢量计算编程必须基于寄存器（Regbase）的编程模型：
1. 开发者需要编写使用`__simd_vf__`标记Vector Function（VF, 向量函数）。
2. 开发者需要在VF函数内显示调用Reg矢量搬运API完成UB <-> Registers的数据搬运。
3. 开发者需要在VF函数内显示调用Reg矢量计算API完成计算功能。
4. 在`__aicore__` 标记的函数中调用VF函数时，需要使用asc_vf_call。

> 📌 **提示**：VF函数内只能调用Reg矢量接口和标量计算。
> 📌 **提示**：Reg矢量接口只能在VF函数内被调用。

### 内存层级

SIMD架构不支持从全局内存GM直接加载数据到Reg矢量计算寄存器。数据必须先从GM搬运至UB，再通过显式的Reg矢量搬运API在UB和寄存器之间实现数据移动。

```text
Global Memory (GM)            
        ^
        |
        | DataCopy
        v
Unified Buffer (UB)           
        ^
        |
        | Reg矢量搬运API
        v
 Registers 
```

### 执行关系

Reg矢量计算编程架构中，矢量计算执行单元从Registers读取数据，完成计算后将结果写回Regsiters；矢量搬运单元负责在Registers和UB之间搬运数据。虽然矢量计算单元和矢量搬运单元在不同的硬件执行单元，但均属于PIPE.V流水。所以在使用Reg矢量计算API和Reg矢量搬运API之间存在数据依赖时，无需用户显示管理数据依赖关系，由硬件保证。在使用asc_vf_call调用VF函数后，用户无需关注PIPE.V的Barrier，在VF函数退出时，所有此VF函数内部的Reg矢量指令均已执行完成。

### 调用层级<a name="section61258392540"></a>

在Reg矢量编程体系中，VF函数既可以被算子实现直接调用，也可以作为基础API或高阶API的内部实现手段；Reg矢量计算API本身直接调用编译器BuiltIn API。

![](../../../../figures/API-调用-regbase.png)

Reg矢量计算通过函数标签区分不同执行域，用于在编译期限制调用关系，避免将只能在某个执行域使用的API放到错误位置。例如：在`__aicore__`修饰的函数中直接调用Reg矢量相关API。所有Reg矢量相关API，均使用`__simd_callee__`修饰，表明此API只能在VF内使用。

| 标签 | 角色 | 调用方 | 可调用对象 |
| --- | --- | --- | --- |
| `__aicore__` | Device侧普通函数 | 核函数或其他`__aicore__`函数 | `__aicore__`函数，或通过`asc_vf_call`调用VF函数 |
| `__simd_vf__` | VF函数| `__aicore__`函数通过`asc_vf_call`调用 | `__simd_callee__` |
| `__simd_callee__` | VF内部子函数 | `__simd_vf__`或其他`__simd_callee__` | `__simd_callee__`|

完整调用关系图如下：

![](../../../../figures/reg_calculation_call_hierarchy.png)


这种隔离有三个目的：

- **编译期校验**：错误的跨域调用可以在编译阶段暴露，例如在`__simd_vf__`中误调用`__aicore__`函数。
- **职责清晰**：`__aicore__`负责UB、队列、地址获取等外层逻辑；`__simd_vf__`专注寄存器级计算。
- **优化边界明确**：编译器可以针对VF函数做独立优化，例如多个VF函数融合，且不影响外层算子结构。

典型调用形式如下：

```cpp
template <typename T>
__aicore__ inline void Compute()
{
    // 1. 准备输入/输出UB物理地址。
    // ...

    // 2. 通过asc_vf_call进入寄存器级VF函数域: __simd_vf__ inline void add_vf(...)
    asc_vf_call<add_vf<T>>(dst_addr, src0_addr, src1_addr,
                           count, one_repeat_size, repeat_times);

    // 3. 收尾工作。
    // ...
}
```

## Reg矢量计算寄存器<a name="section1910719438134"></a>

Reg矢量计算API操作的基础对象是寄存器。它们在代码中表现为变量，编译后映射到硬件寄存器或相关控制资源。

### 矢量数据寄存器
矢量数据寄存器是长度为VL Bytes，用于保存一个参与计算矢量的数据寄存器。例如：在Ascend 950PR/Ascend 950DT版本中，VL为256Bytes，可保存64个float元素或者128个half元素。寄存器变量作为整体使用，无法使用索引或者偏移等手段访问其中的某个元素。Reg矢量计算API的源和目的参数、Reg矢量搬入API的目的参数以及Reg矢量搬出API的源参数均为此类寄存器。


### 掩码寄存器
掩码寄存器是长度为VL Bits（VL/8 Bytes），常用于控制对应矢量数据寄存器中哪些元素参与本轮计算的寄存器。最小对应关系为掩码寄存器1bit对应矢量数据寄存器的1Byte. 例如：在在Ascend 950PR/Ascend 950DT版本中，其宽度为32Bytes(256bits) 。在数据位宽大于1Byte时，由矢量数据寄存器每个元素对应掩码寄存器位置的MSB bit生效。
此外，掩码寄存器还可承载比较类运算的结果，也可作为进位等输入与矢量数据寄存器协同参与Reg矢量运算；还可用作移位、逻辑（与、或、非）、交织等操作的源和目的参数，以及Reg矢量搬入API的目的参数和Reg矢量搬出API的源参数。

### 地址寄存器
地址寄存器用于在VF循环中保存UB访问的地址偏移量，适合存在固定stride、多维索引或重复寻址表达式的场景。其宽度为 8Bytes。它将原本需要在循环体内反复执行的地址偏移标量计算转化为寄存器化的地址管理，从而减少每轮循环中的标量指令开销。地址寄存器在每层循环中根据所设置的stride自动自增，支持最多四维偏移量叠加，具体使用规则可以参考Reg矢量计算API中搬运相关接口描述。

### 搬入非对齐寄存器
搬入非对齐寄存器是长度为32Bytes的临时缓存寄存器，用于优化从UB地址非对齐地址连续搬入时的开销。当搬入源地址不满足对齐要求时，搬入非对齐寄存器充当中间缓存，跨源地址非对齐边界的数据暂存于其中，使整个连续搬入保持高效流水。在使用非对齐搬入时，搬入非对齐寄存器必须以源地址为输入进行初始化；并在循环体内调用非对齐搬入接口时，它同时作为输入和输出参数，用于在不同循环轮次时，保留对齐边界处的数据。

### 搬出非对齐寄存器
搬出非对齐寄存器是长度为32Bytes的临时缓存寄存器，用于优化连续搬出到非对齐UB地址的开销。当搬出目的地址不满足对齐要求时，搬出非对齐寄存器充当中间缓存，跨目的地址非对齐边界的数据暂存于其中，使整个连续搬出保持高效流水。在使用非对齐搬出时，循环结束后，必须将搬出非对齐寄存器中残余的尾部数据刷回UB；完成整个非对齐写出过程。在配合`Squeeze`接口使用时，搬出非对齐寄存器还可以与AR特殊寄存器协作，以有效元素的总字节数作为存储偏移量，实现条件压缩搬出。


> 📌 **提示**：在Reg矢量编程代码中，寄存器表现为变量，此类变量由编译器自动完成映射到硬件寄存器，用户无法控制。

在VF函数内，使用实际使用寄存器变量进行编程，寄存器对应的变量如下：
| 寄存器类型 | 寄存器变量 | 
| --- | --- | --- |
|矢量数据寄存器| `RegTensor` | 
|掩码寄存器| `MaskReg` |
|地址寄存器| `AddrReg` | 
|搬入非对齐寄存器| `UnalignRegForLoad` | 
|搬出非对齐寄存器| `UnalignRegForStore` | 

## Reg矢量计算<a name="section1227863453815"></a>

一个Regbase实现在`__simd_vf__`修饰的VF函数内，由`__aicore__`修饰的函数使用`asc_vf_call`调用。

`__simd_vf__`函数VF-Compute通常遵循以下骨架：

```text
for (i = 0; i < repeatTimes; ++i) {
    1. 计算本轮UB地址偏移。
    2  从UB Load到寄存器。
    3. 在寄存器上执行计算。
    4. 将结果Store回UB。
}
```
GM和UB的数据搬入CopyIn、数据搬出CopyOut均由`__aicore__`修饰的函数实现。
![](../../../../figures/微指令编程流程图.png)

语言扩展CAPI`asc_add`接口原型如下：

```cpp
__simd_callee__ inline void asc_add(vector_float& dst, vector_float src0, vector_float src1, vector_bool mask)
```

## 特性描述<a name="features_list"></a>
在Reg矢量编程体系中，根据不同场景存在不同的特性，在实际开发中需要了解如下特性：

| 场景 | 特性名称 |
| --- | --- |
| 搬运类 | 通用搬运 |
| 搬运类 | 对齐搬运 |
| 搬运类 | 非对齐搬运 |
| 同步类 | 流水线同步控制 |
| VF函数 | VF融合 |


### 通用搬运<a name="section_capi_normal_move"></a>

通用搬运`asc_load` / `asc_store`是不区分UB地址是否32B对齐的通用搬运接口, 用于将连续的VL数据在UB和矢量数据寄存器之间搬运，或者将不超过一个VL的元素数据从矢量数据寄存器搬出到UB，元素数的取值范围为`[1, VL / sizeof(dst_data_type)]`。它们适合需要统一处理UB地址对齐和非对齐地址的场景；如果已知地址满足对齐要求，并且追求更高性能，优先选择对齐搬运接口。

> 📌 **提示**：此接口为软件封装的接口, 实现调用了非对齐搬运的相关接口和寄存器。

### 对齐搬运

对齐搬运`asc_load_align` / `asc_store_align`是在UB地址满足对齐要求时，矢量数据寄存器和UB之间数据搬运的首选接口。与通用搬运相比，性能开销更低。

### 非对齐搬运

非对齐搬运用于UB地址不满足对齐要求时，但仍需要在UB和寄存器之间连续读写数据的场景。通过搬入非对齐寄存器或者搬出非对齐寄存器作为临时缓存，保存跨对齐边界的数据，从而降低连续非对齐访问的额外开销。

非对齐搬入一般由搬入非对齐寄存器初始化接口和非对齐搬入组合完成：先初始化非对齐寄存器，再连续搬入数据。

非对齐搬出一般由非对齐搬出接口和非对齐寄存器后处理接口组合完成：循环中连续写出，循环结束后调用一次后处理接口，将缓存中尚未写出的尾部数据刷回UB。

> 📌 **提示**：推荐写法是把初始化和后处理放在循环外，只在循环体内保留连续搬运和计算。

### 流水线同步控制<a name="section1633824511379"></a>

在SIMD VF函数中，执行单元和搬运单元可以并行工作。因此，某些UB访问顺序需要显式同步。判断重点不是代码书写顺序，而是硬件流水之间是否已经建立必要的数据依赖。

| 场景                                   | 是否需要同步      | 原因                                   |
| -------------------------------------- | ----------------- | -------------------------------------- |
| 同一寄存器内的写后读                   | 不需要        | 寄存器依赖由硬件按指令顺序保证         |
| 不同寄存器访问同一UB地址，且存在写后读 | 需要 | 搬运和计算执行单元之间没有自动顺序约束 |
| 不同寄存器访问同一UB地址，且存在写后写 | 需要 | 需要保证写入顺序                       |
| 地址无重叠、寄存器无依赖               | 不需要        | 不存在数据竞争                         |

![](../../../../figures/同步流水.png)


语言扩展CAPI函数原型：
```cpp
__simd_callee__ inline void asc_mem_bar(MEM_TYPE mem_type)
```

经验上，只要出现以下情况，就应主动检查是否需要同步：

- 源地址和目标地址可能重叠。
- 同一段UB数据在循环内先写后读。
- 不同寄存器对象围绕同一UB区域交替Load/Store。

### VF融合

VF融合指把一段连续计算链路写在同一个`__simd_vf__`函数和同一个循环中，使中间结果保留在寄存器中继续被后续指令消费，减少写回UB再读回寄存器的开销。融合后可以减少VF启动开销，并有机会消除多个VF之间冗余的搬运和同步开销。

VF融合不是融合范围越大越好，在融合时需要控制寄存器数量。融合粒度过大可能增加寄存器数量，导致寄存器压力升高。当超出寄存器规格时，导致寄存器溢出反而性能变差。

AI Core采用多条流水线异步并行架构，数据搬入、计算、数据搬出分别由MTE2、Vector/Cube、MTE3流水线承载。流水线异步执行带来天然并行优势，但也引入数据依赖风险。同步机制是协调流水线协作、确保数据依赖关系得到满足的关键技术。本章旨在帮助开发者建立对C指针编程同步机制的核心认知。全文遵循「问题背景—芯片原理—CAPI接口定义—同步实现」的递进逻辑展开。

## 为什么需要同步：流水线异步并行的性能收益与数据依赖代价

AI Core内部包含多条独立流水线：MTE2/MTE3搬运、Vector计算、Cube计算等。异步并行计算时，Scalar计算单元读取指令序列，将向量计算、矩阵计算、数据搬运指令发射至对应单元的指令队列，各单元异步并行执行。不同指令间可能存在依赖关系，Scalar计算单元通过下发同步指令确保各指令队列按正确逻辑关系执行。

![AI Core内部并行计算架构抽象](<../../../../figures/AI Core内部并行计算架构抽象.png>)

综上，AI Core采用多条独立流水线异步并行执行，各流水线独立推进、互不等待，**带来显著性能收益**。但流水线异步执行缺乏自动协调，计算可能在搬运完成前启动而读取未就绪数据，需通过同步机制**确保数据依赖关系**满足。

> 📌 **提示**：同步的核心目的是在数据依赖节点插入等待，确保数据搬运完成后再让数据计算开始执行。

## 同步机制及接口定义

C指针编程同步机制按**同步范围**分为三大类：**核内同步**、**核间同步**、**核间Block内同步**。核内同步解决单个AI Core内部的流水线协作与资源保护问题。核间同步解决多AI Core协作场景的执行进度协调问题。核间Block内同步解决Block内部Vector Core与Cube Core协作问题（Ascend 950PR/950DT专用）。

---

### 核内同步

核内同步机制面向单个AI Core内部，解决流水线间的数据依赖同步、共享资源访问保护、内存访问顺序控制三类问题。

#### Mutex（共享资源访问保护）

> 📌 **提示**：Mutex机制仅**Ascend 950PR/Ascend 950DT**芯片支持，用于核内多流水线共享资源场景。

Mutex互斥锁采用**获取锁→访问资源→释放锁**模式，通过互斥访问确保共享资源的正确性。当一条流水线获取锁后访问资源时，其他流水线必须等待锁释放后才能访问同一资源，避免并发访问导致的数据不一致或覆盖损坏。Mutex的核心在于"互斥性"：同一时刻仅允许一条流水线持有锁并访问资源，其他流水线处于阻塞等待状态。

该同步主要适用于当核内多条流水线需要访问同一共享资源时（如共享UB区域），存在并发冲突风险：Vector流水线正在写入共享缓冲区时MTE3流水线同时读取可能导致数据不一致，多条流水线并发修改同一内存区域可能产生数据覆盖或损坏。Mutex互斥锁通过互斥访问机制确保共享资源的安全性，保障并发场景下的数据完整性。

#### 接口说明

- **asc_lock(pipe, mutex_id)**  ：根据mutex_id获取mutex，并阻塞当前流水指令队列，直到对应的mutex_id被unlock。
- **asc_unlock(pipe, mutex_id)**: 直到前置当前流水指令退出后，根据mutex_id释放对应mutex。

```c
uint8_t mutex_id = 1;
asc_lock(PIPE_S, mutex_id);               // 获取锁
asc_add(shared_buffer, x_local, y_local); // 访问共享资源
asc_unlock(PIPE_S, mutex_id);             // 释放锁
```

### Notify/Wait（流水线间数据依赖同步）

Notify/Wait采用**信号通知-阻塞等待**模式，通过流水线间的主动通知与被动等待实现执行顺序的严格约束。源流水线完成任务后主动发出"就绪信号"，告知目标流水线数据已准备好；目标流水线在收到信号前保持阻塞状态、暂停执行，收到信号后解除阻塞继续推进。这种机制确保了数据依赖关系的严格满足：生产者流水线（如MTE2搬运）完成数据准备后发出通知，消费者流水线（如Vector计算）等待通知后再开始消费数据，避免异步并行执行中的错误执行顺序。

该同步主要适用于同一核内不同流水之间的同步指令。具有数据依赖的不同流水指令之间需要插此同步。

#### 接口说明

Notify/Wait机制提供三类接口：**手动同步接口**、**简化同步接口**、**自动同步接口**。

**手动同步接口** ：手动同步接口需要开发者显式调用notify/wait配对，适用于需要精确控制流水线间同步时序的复杂场景。开发者可指定源流水线、目标流水线和事件ID，实现灵活的流水线协作控制。

- **asc_sync_notify** : 发送同步信号, 源流水线通知目标流水线数据已就绪
- **asc_sync_wait**   : 等待同步信号, 目标流水线等待源流水线的通知
```cpp
asc_copy_gm2ub((__ubuf__ void*)src0, (__gm__ void*)src0_gm, total_length * sizeof(float));
asc_copy_gm2ub((__ubuf__ void*)src1, (__gm__ void*)src1_gm, total_length * sizeof(float));
asc_sync_notify(PIPE_MTE2, PIPE_V, EVENT_ID0);
asc_sync_wait(PIPE_MTE2, PIPE_V, EVENT_ID0);
asc_add(dst, src1, src0, total_length);
```

**简化同步接口** ：简化同步接口封装了notify/wait的配对调用，开发者无需手动指定源流水线和目标流水线，只需指定需要等待的流水线即可。适用于单一流水线同步场景，代码更简洁、易用性更高。

- **asc_sync** ： 等待所有流水线操作完成
- **asc_sync_pipe(pipe)** : 等待指定流水线操作完成
- **asc_sync_mte2(id)** : 针对PIPE_MTE2流水线执行同步操作
- **asc_sync_mte3(id)** : 针对PIPE_MTE3流水线执行同步操作
- **asc_sync_vec** : 针对所有流水线执行同步操作
```c
asc_copy_gm2ub((__ubuf__ void*)src0, (__gm__ void*)src0_gm, total_length * sizeof(float));
asc_copy_gm2ub((__ubuf__ void*)src1, (__gm__ void*)src1_gm, total_length * sizeof(float));
asc_copy_mte2(EVENT_ID0);
asc_add(dst, src1, src0, total_length);
```

**自动同步接口**：自动同步接口在数据搬运计算接口名后添加_sync后缀，接口内部自动等待搬运完成后再返回，无需开发者显式调用同步接口。适用于不需要精细控制同步时序的场景，简化编程复杂度，但牺牲了一定的流水线并行优化空间。

- **asc_copy_gm2ub_sync(dst, src, size)** : 将数据从Global Memory搬运至Unified Buffer，接口内部自动等待搬运完成后再返回。
- **asc_add_sync(dst, src0, src1, count)**: 执行向量加法运算 dst = src0 + src1，接口内部自动等待计算完成后再返回。
```c
asc_copy_gm2ub_sync((__ubuf__ void*)src0, (__gm__ void*)src0_gm, total_length * sizeof(float));
asc_copy_gm2ub_sync((__ubuf__ void*)src1, (__gm__ void*)src1_gm, total_length * sizeof(float));
asc_add(dst, src1, src0, total_length);
```

### 数据屏障（内存访问顺序控制）

数据屏障采用**阻塞等待**模式，通过强制等待确保前置内存访问指令执行完毕后再继续执行后续指令。在异步并行架构中，后续指令可能在流水线中先于前序指令执行，导致"写操作未完成时读操作已执行"的顺序混乱。数据屏障插入一个强制等待点，确保内存访问的严格顺序，避免异步执行导致的数据错误。

数据屏障用于阻塞后续指令执行，直到所有之前的内存访问指令（需要等待的内存位置可通过参数控制）执行结束。开发者可根据需要选择等待的内存范围：全局内存（GM）、局部内存（UB）或全部内存，灵活控制同步粒度。

#### 接口说明
- **asc_sync_data_barrier(arg)**: 阻塞后续指令，直到之前的内存访问指令执行完毕
```c
asc_sync_data_barrier(mem_dsb_t::DSB_ALL);  // 等待所有内存访问完成
```

## 核间同步

核间同步机制面向多AI Core协作场景，协调多个AI Core之间的执行进度，确保多核场景下的数据正确性与协作有序性。

### 核间同步（多AI Core协作）

核间同步（多AI Core协作）采用**计数器递增/递减**模式，通过flag_id对应的计数器协调多核执行进度。每个flag_id对应一个初始值为0的计数器，arrive指令递增计数器表示"当前核到达同步点"，wait指令检测计数器大于0则递减并继续执行、等于0则阻塞等待。这种机制实现了"多核到达同步点后才继续执行"的协调效果，适用于跨核数据交换、多核矩阵乘等协作场景。

该同步主要应用于多AI Core协作场景（如跨核数据交换、多核矩阵乘），需要核间同步协调执行进度。各核独立执行算子逻辑，但在关键节点需要等待其他核完成后再继续，避免"部分核数据已准备好、部分核仍在计算"的不一致状态。

#### 接口说明

- **asc_sync_block_arrive(pipe, flag_id)**: 和asc_sync_block_wait配合使用（通过flagID关联），用于向核间同步寄存器发送同步信号，标识当前pipeline已到达flagID对应的同步点。每个flagID对应一个初始值为0的计数器，执行asc_sync_block_arrive后flagID对应的计数器增加1；执行asc_sync_block_wait时如果对应的计数器数值为0则阻塞不执行；如果对应的计数器大于0，则计数器减一，同时后续指令开始执行。
- **asc_sync_block_wait(pipe, flag_id)**: 和asc_sync_block_arrive配合使用（通过flagID关联），用于等待所有同步对象到达flagID对应的同步点。如果flagID所对应的计数器数值为0则阻塞不执行；如果对应的计数器大于0，则计数器减一，同时后续指令开始执行。
```c
// Atlas A2/A3系列：需设置核间同步基地址
uint64_t config = *(__gm__ uint64_t*)ffts_addr;
asc_set_ffts_base_addr(config);
int64_t flag_id = 1;
asc_sync_block_arrive(PIPE_S, flag_id);
asc_sync_block_wait(PIPE_S, flag_id);

// Ascend 950PR/950DT：无需设置基地址
int64_t flag_id = 1;
asc_sync_block_arrive(PIPE_S, flag_id);
asc_sync_block_wait(PIPE_S, flag_id);
```

### 核间Block内同步（Ascend 950PR/950DT专用）

> 📌 **提示**：Block内同步仅**Ascend 950PR/Ascend 950DT**芯片支持，用于Block内Vector Core与Cube Core间的流水线同步。

Block内同步采用**ID映射机制**，通过映射后的sync_id实现Vector Core与Cube Core间的信号传递与等待。Block内包含两个Vector Core与一个Cube Core，各Core通过映射后的ID向其他Core发送同步信号或等待其他Core的信号。每个sync_id对应Vector Core与Cube Core中的一个初始值为0的计数器，arrive指令后其他Core对应的计数器递增，wait指令检测计数器大于0则递减并继续、等于0则阻塞。

Block内同步主要用于Vector Core 与Cube Core之间的流水线同步，用于协调Block内不同Core的执行进度。典型场景包括：Vector Core完成数据预处理后通知Cube Core开始矩阵计算，Cube Core完成矩阵计算后通知Vector Core进行后处理。

#### 接口说明
- **asc_sync_intra_arrive(pipe, sync_id)** : 向其他Core发送同步信号，计数器递增 
- **asc_sync_intra_wait(pipe, sync_id)** : 等待其他Core同步信号，计数器大于0则递减继续 
```c
int64_t sync_id = 1;
asc_sync_intra_arrive(PIPE_S, sync_id);
asc_sync_intra_wait(PIPE_S, sync_id);
```

本章阐述了C指针编程同步机制，按同步范围分为核内同步、核间同步、Block内同步三大类。核内同步包括Notify/Wait（流水线间数据依赖同步）、Mutex（共享资源访问保护，950PR/950DT专用）、数据屏障（内存访问顺序控制）。核间同步采用计数器机制协调多AI Core执行进度。Block内同步采用ID映射机制协调Vector Core与Cube Core协作（950PR/950DT专用）。标准同步模式遵循「搬入→同步→计算→同步→搬出」流程。

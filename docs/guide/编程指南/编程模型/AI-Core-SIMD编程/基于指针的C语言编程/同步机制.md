AI Core采用多条流水线异步并行架构，数据搬入、计算、数据搬出分别由MTE2、Vector/Cube、MTE3流水线承载。流水线异步执行带来天然并行优势，但也引入数据依赖风险。同步机制是协调流水线协作、确保数据依赖关系得到满足的关键技术。本章旨在帮助开发者建立对C指针编程同步机制的核心认知。全文遵循「问题背景—芯片原理—CAPI接口定义—同步实现」的递进逻辑展开。

## 为什么需要同步：异步执行带来的数据依赖风险

### 流水线异步执行的好处与风险

**表 1**  AI Core流水线分类

| 流水线 | 功能 | 典型指令 |
|--------|------|----------|
| **MTE2** | 数据搬入（GM→Local Memory） | `asc_copy_gm2ub`、`asc_copy_gm2l1` |
| **MTE3** | 数据搬出（Local Memory→GM） | `asc_copy_ub2gm`、`asc_copy_l0c2gm` |
| **Vector** | 向量计算 | `asc_add`、`asc_mul` |
| **Cube** | 矩阵计算 | `asc_mmad` |

AI Core包含多条独立流水线（MTE2/MTE3搬运、Vector计算、Cube计算），异步并行执行，各自独立推进，无需等待其他流水线。
- **并行优势**：数据搬入与计算可同时进行，MTE2搬运下一块数据时Vector正在处理上一块，流水线重叠使吞吐率大幅提升。
- **潜在风险**：流水线缺乏自动协调，若计算在搬运完成前启动，会读取未就绪数据导致错误。需开发者通过显式同步指令控制执行顺序，确保数据搬运与计算的严格时序。

### 数据依赖关系：同步的本质需求

流水线之间存在明确的数据依赖关系：
- **MTE2 → Vector/Cube**：计算依赖搬入的数据，数据未就绪时计算会出错
- **Vector/Cube → MTE3**：搬出依赖计算的结果，计算未完成时搬出会输出错误数据

```c
// 错误示例：缺少同步
asc_copy_gm2ub(x_local, x_gm, 256);   // MTE2开始搬运
asc_add(z_local, x_local, y_local);   // Vector立即开始计算（可能读取未就绪数据）
asc_copy_ub2gm(z_gm, z_local, 256);   // MTE3立即搬出（可能输出错误结果）
```

> 📌 **提示**：同步的核心目的是在数据依赖节点插入等待，确保"生产者"完成后再让"消费者"开始。

## 同步机制概述

C指针编程同步机制按**同步范围**分为三大类：**核内同步**、**核间同步**、**Block内同步**。核内同步解决单个AI Core内部的流水线协作与资源保护问题。核间同步解决多AI Core协作场景的执行进度协调问题。Block内同步解决Block内部Vector Core与Cube Core协作问题（Ascend 950PR/950DT专用）。

---

## 一、核内同步机制

核内同步机制面向单个AI Core内部，解决流水线间的数据依赖同步、共享资源访问保护、内存访问顺序控制三类问题。

### 机制一：Notify/Wait（流水线间数据依赖同步）

#### 同步原理

Notify/Wait采用**信号通知-阻塞等待**模式，通过流水线间的主动通知与被动等待实现执行顺序的严格约束。源流水线完成任务后主动发出"就绪信号"，告知目标流水线数据已准备好；目标流水线在收到信号前保持阻塞状态、暂停执行，收到信号后解除阻塞继续推进。这种机制确保了数据依赖关系的严格满足：生产者流水线（如MTE2搬运）完成数据准备后发出通知，消费者流水线（如Vector计算）等待通知后再开始消费数据，避免异步并行执行中的错误执行顺序。

> 💡 **类比理解**：传统串行程序中洗菜→切菜→炒菜依次进行，自动等待前一步完成；异步并行程序中洗菜人、切菜人、炒菜人各自独立工作；同步机制则像"洗菜人洗完后喊'菜洗好了'，切菜人听到后才开始切"，通过明确的信号传递协调各环节的执行时机。

#### 接口分类

Notify/Wait机制提供三类接口：**手动同步接口**、**简化同步接口**、**自动同步接口**。

**手动同步接口**（精细控制流水线间同步）：

| 接口 | 功能 |
|------|------|
| `asc_sync_notify(pipe, tpipe, id)` | 发送同步信号：源流水线通知目标流水线数据已就绪 |
| `asc_sync_wait(pipe, tpipe, id)` | 等待同步信号：目标流水线等待源流水线的通知 |

**简化同步接口**（等待指定流水线完成）：

| 接口 | 功能 |
|------|------|
| `asc_sync()` | 等待所有流水线操作完成 |
| `asc_sync_pipe(pipe)` | 等待指定流水线操作完成 |
| `asc_sync_mte2(id)` | 针对PIPE_MTE2流水线执行同步操作 |
| `asc_sync_mte3(id)` | 针对PIPE_MTE3流水线执行同步操作 |
| `asc_sync_vec()` | 针对所有流水线执行同步操作 |

**自动同步接口**（数据搬运接口的自动同步版本）：

数据搬运接口提供`_sync`后缀版本，接口内部自动等待搬运完成：

```c
// ===== 自动同步版本：内部自动等待 =====
asc_copy_gm2ub_sync(x_local, x_gm, 256);

// ===== 手动同步版本：需显式调用同步接口 =====
asc_copy_gm2ub(x_local, x_gm, 256);  // 搬入数据
asc_sync_notify(PIPE_MTE2, PIPE_V, EVENT_ID0);  // MTE2通知V：数据就绪
asc_sync_wait(PIPE_MTE2, PIPE_V, EVENT_ID0);    // V等待MTE2
```

### 机制二：Mutex（共享资源访问保护）

> 📌 **提示**：Mutex机制仅**Ascend 950PR/Ascend 950DT**芯片支持，用于核内多流水线共享资源场景。

#### 同步原理

Mutex互斥锁采用**获取锁→访问资源→释放锁**模式，通过互斥访问确保共享资源的正确性。当一条流水线获取锁后访问资源时，其他流水线必须等待锁释放后才能访问同一资源，避免并发访问导致的数据不一致或覆盖损坏。Mutex的核心在于"互斥性"：同一时刻仅允许一条流水线持有锁并访问资源，其他流水线处于阻塞等待状态。

#### 适用场景

当核内多条流水线需要访问同一共享资源时（如共享UB区域），存在并发冲突风险：Vector流水线正在写入共享缓冲区时MTE3流水线同时读取可能导致数据不一致，多条流水线并发修改同一内存区域可能产生数据覆盖或损坏。Mutex互斥锁通过互斥访问机制确保共享资源的安全性，保障并发场景下的数据完整性。

#### 接口定义

| 接口 | 功能 |
|------|------|
| `asc_lock(pipe, mutex_id, mode)` | 获取共享资源访问权 |
| `asc_unlock(pipe, mutex_id, mode)` | 释放共享资源访问权 |

```c
uint8_t mutex_id = 1;
asc_lock(PIPE_S, mutex_id);             // 获取锁
asc_add(shared_buffer, x_local, y_local); // 访问共享资源
asc_unlock(PIPE_S, mutex_id);           // 释放锁
```

### 机制三：数据屏障（内存访问顺序控制）

#### 同步原理

数据屏障采用**阻塞等待**模式，通过强制等待确保前置内存访问指令执行完毕后再继续执行后续指令。在异步并行架构中，后续指令可能在流水线中先于前序指令执行，导致"写操作未完成时读操作已执行"的顺序混乱。数据屏障插入一个强制等待点，确保内存访问的严格顺序，避免异步执行导致的数据错误。

#### 功能说明

数据屏障用于阻塞后续指令执行，直到所有之前的内存访问指令（需要等待的内存位置可通过参数控制）执行结束。开发者可根据需要选择等待的内存范围：全局内存（GM）、局部内存（UB）或全部内存，灵活控制同步粒度。

#### 接口定义

| 接口 | 功能 |
|------|------|
| `asc_sync_data_barrier(arg)` | 阻塞后续指令，直到之前的内存访问指令执行完毕 |

```c
asc_sync_data_barrier(mem_dsb_t::DSB_ALL);  // 等待所有内存访问完成
```

## 二、核间同步机制

核间同步机制面向多AI Core协作场景，协调多个AI Core之间的执行进度，确保多核场景下的数据正确性与协作有序性。

### 机制四：核间同步（多AI Core协作）

#### 同步原理

核间同步采用**计数器递增/递减**模式，通过flag_id对应的计数器协调多核执行进度。每个flag_id对应一个初始值为0的计数器，arrive指令递增计数器表示"当前核到达同步点"，wait指令检测计数器大于0则递减并继续执行、等于0则阻塞等待。这种机制实现了"多核到达同步点后才继续执行"的协调效果，适用于跨核数据交换、多核矩阵乘等协作场景。

#### 适用场景

多AI Core协作场景（如跨核数据交换、多核矩阵乘），需要核间同步协调执行进度。各核独立执行算子逻辑，但在关键节点需要等待其他核完成后再继续，避免"部分核数据已准备好、部分核仍在计算"的不一致状态。

#### 接口定义

| 接口 | 功能 |
|------|------|
| `asc_sync_block_arrive(pipe, flag_id)` | 当前核到达同步点，计数器递增 |
| `asc_sync_block_wait(pipe, flag_id)` | 等待其他核到达同步点，计数器大于0则递减继续 |
| `asc_sync_inter_wait(pipe, flag_id)` | 核间同步寄存器同步指令 |

```c
// Atlas A2/A3系列：需设置核间同步基地址
uint64_t config = *(__gm__ uint64_t*)ffts_addr;
asc_set_ffts_base_addr(config);
int64_t flag_id = 1;
asc_sync_block_arrive(PIPE_S, flag_id);
asc_sync_block_wait(PIPE_S, flag_id);

// Ascend 950PR/950DT：无需设置基地址
int64_t flag_id = 1;
asc_sync_block_arrive(PIPE_S, flag_id);
asc_sync_block_wait(PIPE_S, flag_id);
```

### 机制五：CV核间同步（Ascend 950PR/950DT专用）

> 📌 **提示**：Block内同步仅**Ascend 950PR/Ascend 950DT**芯片支持，用于Block内Vector Core与Cube Core间的流水线同步。

#### 同步原理

Block内同步采用**ID映射机制**，通过映射后的sync_id实现Vector Core与Cube Core间的信号传递与等待。Block内包含两个Vector Core（VECCORE0/VECCORE1）与一个Cube Core（CUBECORE），各Core通过映射后的ID向其他Core发送同步信号或等待其他Core的信号。每个sync_id对应Vector Core与Cube Core中的一个初始值为0的计数器，arrive指令后其他Core对应的计数器递增，wait指令检测计数器大于0则递减并继续、等于0则阻塞。

#### 适用场景

Block内Vector Core（VECCORE0/VECCORE1）与Cube Core（CUBECORE）之间的流水线同步，用于协调Block内不同Core的执行进度。典型场景包括：Vector Core完成数据预处理后通知Cube Core开始矩阵计算，Cube Core完成矩阵计算后通知Vector Core进行后处理。

#### 接口定义

| 接口 | 功能 |
|------|------|
| `asc_sync_intra_arrive(pipe, sync_id)` | 向其他Core发送同步信号，计数器递增 |
| `asc_sync_intra_wait(pipe, sync_id)` | 等待其他Core同步信号，计数器大于0则递减继续 |

```c
int64_t sync_id = 1;
asc_sync_intra_arrive(PIPE_S, sync_id);
asc_sync_intra_wait(PIPE_S, sync_id);
```

## 标准同步模式：Vector算子实践

### 同步流程五步骤

Vector算子的标准同步模式遵循「搬入 → 同步 → 计算 → 同步 → 搬出」流程，通过两个同步节点确保数据依赖关系正确处理：
```c
// ===== 第一步：数据搬入 =====
asc_copy_gm2ub(x_local, x_gm, 256);  // MTE2搬运数据

// ===== 第二步：搬入同步 =====
asc_sync_notify(PIPE_MTE2, PIPE_V, EVENT_ID0);  // MTE2通知V：数据就绪
asc_sync_wait(PIPE_MTE2, PIPE_V, EVENT_ID0);    // V等待MTE2

// ===== 第三步：计算执行 =====
asc_add(z_local, x_local, y_local);  // Vector计算

// ===== 第四步：计算同步 =====
asc_sync_notify(PIPE_V, PIPE_MTE3, EVENT_ID0);  // V通知MTE3：计算完成
asc_sync_wait(PIPE_V, PIPE_MTE3, EVENT_ID0);    // MTE3等待V

// ===== 第五步：数据搬出 =====
asc_copy_ub2gm(z_gm, z_local, 256);  // MTE3搬出结果
```

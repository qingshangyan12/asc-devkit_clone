# 内存一致性

本文介绍 NPU 编程中常见的内存一致性问题，重点说明 GM、L2 Cache、DCache、ICache、UB 以及原子操作之间的数据可见性关系。

## 1. 概念体系

### 1.1 Overlap

Overlap（地址重叠）指两个内存访问范围在字节地址区间上存在交集。例如，源操作数覆盖`[addr, addr + 128)`，目的操作数覆盖`[addr + 64, addr + 192)`，则两者地址重叠。相关约束见[通用地址重叠约束](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/通用说明和约束.md#section668772811100)。

如果同一流水中的前后指令访问同一段地址，且后一条指令依赖前一条指令的结果，需要插入同步指令，保证前序指令完成后再执行后续指令。同步能力说明见[系统同步能力概述](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/同步控制/系统同步能力概述.md)。

### 1.2 Alias

Alias（别名）描述两个不同的名字指向同一段物理内存。类似于浅拷贝，两个对象指向同一个地址，修改其中一个对象的值会影响另一个对象的值。Alias本身不一定错误，但在并发访问、缓存访问或原子更新场景中，需要明确哪一个执行单元先写、哪一个执行单元后读。

### 1.3 Cache Line

Cache Line是Cache加载、失效、写回的最小操作粒度。资料中将Cache Line定义为缓存（DCache、ICache、L2 Cache）中的最小数据单位；缓存控制接口也以Cache Line为基本处理对象。相关说明见[术语表](https://gitcode.com/cann/asc-devkit/blob/master/docs/guide/技术附录/概念原理和术语/术语表.md)和[系统缓存概述](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/系统缓存概述.md)。

Cache Line会影响一致性判断。例如多个核分别修改GM上同一条DCache Cache Line长度内的不同字段时，经过DCache写回GM可能以整条Cache Line为粒度回写，导致随机覆盖。相关示例见[DataCacheCleanAndInvalid调用示例3](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md#example3_multi_core)。

### 1.4 一致性

一致性指多个执行单元或多个核对同一数据并发读写时，各执行单元看到的数据是否符合程序预期。本文将一致性分成两个层面：内存一致性和Cache一致性。

**内存一致性**是指生产者已经写了数据，消费者什么时候、以什么顺序能看到这些写入，即关注读写操作的顺序和可见性。例如，考虑两个核同时访问GM中的两个变量：

```text
初始状态：A == 1, B == 2

Core 0                         Core 1
===========================    ===========================
A = 3;                         x = B;
B = 4;                         y = A;
```

如果没有额外同步，内存系统中间看到的访问顺序可能不等同于代码书写顺序。例如下面几种顺序都可能对应不同的观察结果：

```text
STORE A = 3, STORE B = 4, x = LOAD B -> 4, y = LOAD A -> 3
STORE A = 3, x = LOAD B -> 2, STORE B = 4, y = LOAD A -> 3
x = LOAD B -> 2, y = LOAD A -> 1, STORE A = 3, STORE B = 4
x = LOAD B -> 2, STORE A = 3, y = LOAD A -> 3, STORE B = 4
```

因此，Core 1最终可能看到不同的读值组合：

```text
x == 2, y == 1
x == 2, y == 3
x == 4, y == 1
x == 4, y == 3
```

内存一致性关注的是“写入以什么顺序被其他执行者观察到”。如果程序要求Core 1看到`B == 4`时一定也能看到`A == 3`，就需要在写数据和读数据之间建立同步关系，而不能只依赖代码中的书写顺序。

默认情况下，NPU上核内不同执行单元、不同核、不同SIMT线程之间的内存访问顺序和可见性不能只靠代码书写顺序推断，当存在数据依赖或通信关系时，需要开发者自行使用对应同步接口和缓存控制接口建立可见性。

**缓存一致性（cache一致性）**是指某个地址的数据被某个核的Cache修改后，GM或其他核看到的是新值还是旧值，即关注同一地址或同一Cache Line在不同缓存副本之间的值是否一致。

以DCache为例，`A`和`B`位于GM上同一条64B DCache Cache Line内：

```text
初始状态：GM Cache Line [A, B, ...] == [0, 0, ...]

Core 0                         Core 1
===========================    ===========================
LOAD A;                         LOAD B;
// Core 0 DCache缓存整条Line     // Core 1 DCache缓存整条Line
// [A=0, B=0, ...]              // [A=0, B=0, ...]

STORE A = 1;                    STORE B = 2;
// Core 0 DCache变成             // Core 1 DCache变成
// [A=1, B=0, ...]              // [A=0, B=2, ...]
```

两个核虽然修改的是不同字段，但各自DCache里保存的是整条Cache Line的副本。后续写回GM时，如果以整条Cache Line为单位写回，就可能出现不同结果：

```text
Core 0先写回，Core 1后写回：
GM Cache Line == [A=0, B=2, ...]   // Core 1旧副本覆盖了Core 0对A的修改

Core 1先写回，Core 0后写回：
GM Cache Line == [A=1, B=0, ...]   // Core 0旧副本覆盖了Core 1对B的修改

```

因为每个核都有自己的缓存数据，各个核都是在自己的缓存的旧值上进行修改，这个例子因为缓存一致性没有获得期望的[A=1, B=2, ...]。

## 2. 内存一致性

本章借用形式化内存模型的写法，把一次NPU内存访问先抽象成一个事件，再讨论事件之间如何建立可见性。这里不做完整数学定义，但会固定几个概念，便于后续描述。

- **执行者**：发起访问的单元或线程，例如Scalar、MTE2、MTE3、FixPipe、Vector、SIMT线程。
- **操作**：读、写、原子读改写、Clean、Invalid、Preload、Prefetch等。
- **位置**：事件访问的地址范围。两个事件访问范围重叠时，才需要讨论同一份数据的可见性。
- **路径**：访问经过的存储层级，例如`GM -> L2 Cache -> DCache -> Scalar`、`GM -> L2 Cache -> UB`、`UB -> GM`。
- **作用域**：事件希望影响的范围，例如单流水、单AI Core、单Device内多个AI Core，或跨Device通信。

在这个抽象下，一致性问题通常来自两类关系：第一，写事件产生的新值是否已经沿访问路径到达读事件能看到的位置；第二，生产者和消费者之间是否建立了顺序关系。对NPU编程来说，缓存控制接口负责处理“值在哪里”，同步接口负责处理“什么时候能看见”。

### 2.1 GM与L2 Cache的一致性

NPU上各储存单元的硬件架构图见[3510架构图](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)，内存层级图如下：

 ![](../../../figures/内存层级.png "内存层级")

GM（Global Memory）是全局内存。L2 Cache位于搬运单元、Scalar单元和GM之间，用于缓存频繁访问的数据和指令。可以把L2 Cache看成靠近多个AI Core的一层共享缓存：如果数据在L2 Cache中命中，就不必每次都访问更远的GM。

#### 2.1.1 硬件一致性

对GM与L2 Cache，可以把读写事件分开看。

写事件经过L2 Cache时，资料以NPU架构版本2201为例说明，L2 Cache采用直写（Write-Through）策略。直写表示数据被写入Cache的同时也写入GM。因此，一个写事件不会只更新L2 Cache而长时间不更新GM，L2 Cache中也不会形成类似Dirty DCache Line那样等待未来写回的状态。

读事件经过L2 Cache时，如果命中，则直接返回L2 Cache中的数据；如果未命中，则从GM加载数据并更新到L2 Cache。也就是说，L2 Cache中的缓存数据来自GM，写入L2 Cache的数据也会同步写入GM。

因此，在资料覆盖的路径中，GM与L2 Cache不是两份需要开发者手动维护的独立副本。开发者在这一层更关注的是是否启用L2 Cache、是否命中L2 Cache，以及缓存替换是否影响性能。

#### 2.1.2 跳过L2 Cache访问

默认情况下，GlobalTensor启用L2 Cache，读写GM的数据会进入L2 Cache。这个默认策略适合数据会被复用的场景，但并不适合所有访问。L2 Cache容量有限，当进入L2 Cache的数据超过容量时，会触发数据替换；如果大量只访问一次的数据也进入L2 Cache，就可能挤出后续仍需要复用的数据，导致真正有复用价值的数据命中率下降。

对于只访问一次的GlobalTensor，可以设置[cache mode](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/数据结构/LocalTensor和GlobalTensor定义/GlobalTensor/SetL2CacheHint.md#参数说明)为`CACHE_MODE_DISABLE`，让这类数据不进入L2 Cache，直接把GM上的数据搬运到UB或者L1 Buffer中。对这种路径来说，L2 Cache中没有对应的数据副本，因此也不存在这份数据在GM与L2 Cache之间不一致的问题。

### 2.2 DCache与GM的一致性

DCache与GM的一致性是NPU内存一致性中最容易出错的一类问题。它的关键差异在于：DCache不是多核共享缓存，而是每个核内Scalar访问GM数据时使用的本地Data Cache。

把Scalar对GM的访问建模为事件时，可以分成读事件和写事件：

- Scalar读GM时，硬件优先从本核DCache读取；DCache未命中时，再从L2 Cache读取；L2 Cache也未命中时，再从GM加载数据并更新到L2 Cache和DCache。
- Scalar写GM时，资料说明会先修改本核DCache中的Cache Line，并把该Cache Line标记为Dirty，GM上的数据不会立刻更新。

Dirty Cache Line后续写回GM有两个来源：一是硬件替换该Cache Line时写回，二是开发者显式执行Clean操作。由于写回时机可能晚于程序中写语句出现的位置，另一个核或另一个访问路径直接读取GM时，可能还看不到本核Scalar写入的新值。

#### 2.2.1 Scalar访问GM带来的一致性

Scalar普通读写GM时，可以把一致性风险拆成三种事件关系。

第一种是“本核缓存命中”。执行`GlobalTensor::GetValue`后，相邻数据会进入Data Cache；后续读取如果命中DCache，就直接使用DCache中的Cache Line。若该GM地址已经被外部修改，本核仍可能读到旧的DCache副本。因此，资料要求：如果`GetValue`访问的Global Memory地址内容存在被外部改写的可能，需要先调用[DataCacheCleanAndInvalid](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)。

第二种是“写停留在本核DCache”。执行`GlobalTensor::SetValue`后，首先改写的是每个AI Core内部的DCache，不会立刻写出到GM。如果希望该写入立刻对GM或其他核可见，需要在写之后调用`DataCacheCleanAndInvalid`。其中Clean负责把Dirty数据写回GM，Invalid负责使对应Cache Line失效，避免后续继续使用可能过期的缓存数据。

第三种是“Cache Line粒度写回”。`SetValue`后续写出时以64B Cache Line为单位。多个核即使写的是同一条Cache Line中的不同字段，也可能在各自写回整条Cache Line时覆盖对方结果。资料中的`DataCacheCleanAndInvalid`示例3专门说明了多核操作同一条Cache Line时的随机覆盖问题。此类场景可以通过让不同核操作的地址至少相隔Cache Line大小，或使用绕过DCache的读写接口降低风险。

因此，Scalar路径建立可见性的基本原则是：

- 生产者通过Scalar写GM后，如果消费者需要从GM或其他路径读取该数据，生产者需要执行`DataCacheCleanAndInvalid`把Dirty数据写回GM。
- 消费者如果担心本核DCache中有旧副本，读取前需要执行`DataCacheCleanAndInvalid`使旧副本失效。
- 如果算法本身不需要DCache缓存，可以使用[ReadGmByPassDCache](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md)和[WriteGmByPassDCache](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md)直接读写GM。

#### 2.2.2 ATOM访问导致的DCache一致性

Scalar原子操作可以看成对某个GM地址执行的读-改-写事件。以`AtomicAdd`为例，该接口在指定GM地址上执行原子加操作，并返回GM地址上做原子操作前的数据。原子操作保证的是这一次读-改-写不会被其他原子更新打断，但它不会自动清理同一地址在DCache中的旧副本或Dirty副本。

因此，如果同一GM地址此前被普通Scalar路径访问过，就需要把原子事件和DCache事件放在同一个一致性图里分析：

- 若普通Scalar写先发生，数据可能仍停留在DCache中。后续原子操作如果依赖这个写入，需要先把相关DCache Line写回GM。
- 若原子操作先发生，本核DCache中可能仍保留旧副本。后续再用普通Scalar读同一地址时，需要先使旧副本失效，避免读到原子操作之前的值。
- 若原子操作与MTE2/MTE3搬运单元读写GM之间存在数据依赖，资料要求开发者根据实际情况插入同步。

在Ascend 950PR/Ascend 950DT上，`DataCacheCleanAndInvalid`提供`DcciDst::CACHELINE_ATOMIC`，用于原子操作过程中保证DCache和GM的一致性。C API中的[asc_sync_data_barrier](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/C-API/同步控制/asc_sync_data_barrier.md)可用于阻塞后续指令，直到之前的内存访问指令执行结束。把二者组合起来理解，DCCI处理“缓存内容是否写回或失效”，DSB处理“前序内存访问是否完成”。具体使用顺序需要按访问路径和数据依赖决定。

### 2.3 ICache与GM一致性

ICache用于缓存Scalar单元最近使用或频繁使用的指令。Scalar读取GM指令时，优先从ICache读取；ICache未命中时，再从L2 Cache读取；L2 Cache也未命中时，再从GM加载指令并更新到L2 Cache和ICache。相关说明见[系统缓存概述](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/系统缓存概述.md)。

从一致性角度看，ICache的事件比较特殊：它缓存的是指令而不是普通数据，资料中将ICache描述为只读Cache。因此，本文不把ICache建模为多个核之间需要互相写回的数据副本。开发者主要关注取指效率，可以使用[ICachePreLoad](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/ICachePreLoad(ISASI).md)从指令所在GM地址预加载指令到ICache中，并通过[GetICachePreloadStatus](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/GetICachePreloadStatus(ISASI).md)查询预加载状态。

如果某个场景涉及运行时修改代码段，再让Scalar取指执行，当前公开资料没有把它描述为普通算子编程模型中的使用方式，本文不把这类场景纳入通用一致性规则。

### 2.4 SIMT DCache与GM一致性

[适用版本：NPU架构版本3510/Ascend 950PR/Ascend 950DT] SIMT路径需要单独讨论，因为SIMT线程的并发访问行为更接近GPU弱内存模型。资料说明，SIMT访问GM需要经过SIMT DCache中转；SIMT支持最大128KB Data Cache，Data Cache直接复用UB作为cacheline，SIMT所有对外访存都是以128B为粒度。相关说明见[NPU架构版本3510](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)。

SIMT文档中的哈希表案例直接给出了弱内存模型示例：一个核先写`A`再写`flag`，另一个核看到`flag=1`后再读`A`，如果没有内存屏障，读端不一定能按程序书写顺序看到`A=1`。该案例使用`asc_threadfence()`在写入数据和写入状态标志之间建立顺序，确保状态标志对外可见时，前面的数据写入已经完成。

因此，SIMT路径中需要同时考虑两类关系：

- **顺序关系**：线程或核之间通过标志位通信时，需要使用`asc_threadfence`等内存栅栏避免写数据和写标志被其他线程观察成错误顺序。
- **缓存关系**：资料说明Data Cache与Global Memory之间不保证一致性。如果一个核写GM后另一个核读取同一地址，而读端DCache命中旧值，就可能不会从L2 Cache或GM获取新值。哈希表案例中使用`volatile`保证每次读取都从Global Memory获取，而不是使用DCache旧值。

SIMT还提供不同访存函数来表达缓存意图：[DCache访问优化](../../../算子实践参考/SIMT算子性能优化/内存访问/DCache访问优化.md)中建议，对只遍历一次的数据使用`asc_ldcg`减少对DCache空间的占用；对热点数据使用`asc_ldca`优先从DCache加载；对写入后不需要驻留DCache的输出数据使用`asc_stcg`直接写入Global Memory，不经过DCache缓存。

### 2.5 UB与DCache的一致性

UB（Unified Buffer）通常作为Vector计算和MTE搬运的核内数据缓冲区。资料说明，DMA搬运单元通过DataCopy等接口在UB等Local Memory和GM之间交互，没有Cache一致性问题；Scalar访问GM时才会首先访问每个核内的Data Cache，因此存在Data Cache与GM的Cache一致性问题。相关说明见[DataCacheCleanAndInvalid](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)。

从事件路径看，普通`GM <-> UB`的DataCopy和Scalar普通读写GM不是同一条路径。前者通过搬运单元在GM和Local Memory之间移动数据，后者通过DCache访问GM。如果同一份数据先通过Scalar写GM，再由MTE2从GM搬入UB，那么MTE2能否拿到新值取决于Scalar写入是否已经从DCache写回GM。反过来，如果UB侧数据已经搬回GM，而Scalar侧本核DCache里仍保留旧副本，Scalar读也可能看不到新值。

`DataCacheCleanAndInvalid`提供了`GlobalTensor`版本和`LocalTensor`版本，并支持通过`DcciDst`选择一致性目标：`CACHELINE_OUT`用于DCache与GM，`CACHELINE_UB`用于DCache与UB。实际编程时，应先判断数据当前在哪个存储层级，再选择对应的DCCI目标。

可以采用如下原则：

- 普通DataCopy本身不需要为DCache一致性额外处理。
- 只要同一地址或同一数据语义同时被Scalar DCache路径和UB/DataCopy路径访问，就需要显式确认写回、失效和同步顺序。
- 若后续消费者通过GM读取，优先保证DCache与GM一致；若后续消费者直接读取UB或LocalTensor，则按接口参数选择DCache与Local Memory一致性。

### 2.6 Prefetch与Preload

Prefetch和Preload都是性能相关事件，它们改变的是数据或指令提前进入Cache的时机，不应被当成生产者-消费者同步。资料中区分如下：

- Prefetch：硬件根据访问模式自动将预期访问的数据提前加载到缓存。
- Preload：软件通过显式指令将指定数据主动加载到缓存。

相关说明见[系统缓存概述](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/系统缓存概述.md)。

#### 2.6.1 GM数据与L2 Cache

GM数据是否进入L2 Cache主要通过`SetL2CacheHint`设置。默认情况下GlobalTensor启用L2 Cache；对只访问一次的数据可以考虑`CACHE_MODE_DISABLE`，避免一次性数据进入L2 Cache并替换热点数据。这里的事件不建立新的同步顺序，只是改变后续访问命中L2 Cache的可能性。相关说明见[SetL2CacheHint](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/数据结构/LocalTensor和GlobalTensor定义/GlobalTensor/SetL2CacheHint.md)和[设置合理的L2 CacheMode](../../../算子实践参考/SIMD算子性能优化/内存访问/设置合理的L2-CacheMode.md)。

#### 2.6.2 DCache Preload

[DataCachePreload](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/DataCachePreload.md)用于从源地址所在的特定GM地址预加载数据到DCache中，每次调用只能预加载一个Cache Line大小的数据。它可以提前构造“GM数据进入DCache”的缓存事件，但不等价于Clean、Invalid或同步。如果对应GM数据可能被其他核修改，仍需按DCache与GM一致性规则处理。

资料提醒，频繁调用该接口可能导致保留站拥塞；在此情况下，该指令将被视为NOP指令并阻塞Scalar流水线，因此建议连续调用次数不要超过4次。

#### 2.6.3 ICache PreLoad

[ICachePreLoad](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/缓存控制/ICachePreLoad(ISASI).md)用于从指令所在GM地址预加载指令到ICache中。`preFetchLen`表示预取长度；在Ascend 950PR/Ascend 950DT、Atlas A3、Atlas A2产品上，该参数单位为2KB，取值应小于ICache大小/2KB。

和DCache Preload类似，ICache PreLoad主要影响取指性能，不建立普通数据读写之间的可见性关系。

## 3. 原子操作与一致性

原子操作用于多个执行单元或多个线程并发更新同一地址时，将读-改-写过程作为一个不可分割的更新。原子操作可以避免单次更新被其他更新打断，但不等价于整个程序顺序确定；当原子操作与普通读写、DataCopy或跨核同步混用时，仍需处理同步顺序和Cache可见性。

### 3.1 数据搬运随路原子操作

数据搬运随路原子操作通过`SetAtomicAdd`、`SetAtomicMax`、`SetAtomicMin`等接口配置后续目的地址为GM的数据搬运。资料说明，`SetAtomicAdd`会对后续目的地址为GM的数据搬运开启原子累加：将待拷贝内容和GM已有内容求和，然后把求和结果写入GM。使用完成后建议通过`DisableDmaAtomic`关闭原子累加，以免影响后续相关指令功能；执行前不会自动清零GM数据。相关说明见[原子操作概述](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/原子操作/原子操作概述.md)和[SetAtomicAdd](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/原子操作/SetAtomicAdd.md)。

从数据通路看，`SetAtomicAdd`资料列出的支持路径包括：

| 产品 | 支持的数据通路 |
| --- | --- |
| Ascend 950PR/Ascend 950DT | UB/L0C Buffer -> GM |
| Atlas A3训练/推理系列产品 | UB/L0C Buffer/L1 Buffer -> GM |
| Atlas A2训练/推理系列产品 | UB/L0C Buffer/L1 Buffer -> GM |
| Atlas 200I/500 A2推理产品 | UB/L0C Buffer/L1 Buffer -> GM |
| Atlas推理系列产品AI Core | UB -> GM |
| Atlas训练系列产品 | UB -> GM |

这类原子操作写入的是GM。若同一GM地址还被Scalar普通读写访问，需要同时考虑DCache中是否存在旧副本或Dirty副本，并按2.2节处理DCache与GM一致性。

### 3.2 Scalar原子操作

Scalar原子接口包括`AtomicAdd`、`AtomicCas`、`AtomicExch`等。以`AtomicAdd`为例，资料说明该接口在指定GM地址上执行原子加操作，并返回GM地址上做原子操作前的数据。若标量计算单元和MTE2/MTE3搬运单元在读写GM时存在数据依赖，开发者需要根据实际情况插入同步。相关说明见[AtomicAdd](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/原子操作/AtomicAdd.md)。

Scalar原子操作需要关注两类一致性：

- 与DCache的关系：如果同一GM地址之前通过普通Scalar路径访问过，DCache中可能存在旧副本或Dirty副本。需要在原子操作前后根据读写关系使用`DataCacheCleanAndInvalid`处理。
- 与MTE搬运的关系：如果原子操作后马上由MTE2从GM搬入UB，或MTE3/FixPipe写GM后马上做Scalar原子，需要插入核内同步，保证前序写入完成后再启动后续访问。

### 3.3 MTE3上的原子操作

MTE3负责将UB等核内数据搬出到GM。数据搬运随路原子操作配置后，会影响后续目的地址为GM的数据搬运，因此MTE3的`UB -> GM`路径是常见的随路原子使用场景。处理原则是：

- 开启原子前确认GM目标区域的初值是否已经按算法要求初始化。
- 开启原子后，只让需要原子语义的搬运受影响；完成后调用`DisableDmaAtomic`关闭原子状态。
- 如果前后存在MTE2/MTE3或Scalar数据依赖，插入对应同步。

### 3.4 FixPipe上的原子操作

FixPipe常用于`L0C Buffer -> GM`或相关矩阵搬出路径。`SetAtomicAdd`资料明确列出多种产品支持`L0C Buffer -> GM`随路原子，因此FixPipe写GM时可以成为随路原子操作的数据来源之一。其一致性关注点与MTE3类似：目标是GM，若同一GM地址还通过DCache路径访问，需要处理DCache与GM一致性；若与其他搬运或计算存在依赖，需要插入同步。

### 3.5 SIMT原子操作

SIMT原子接口如`asc_atomic_add`可对Unified Buffer或Global Memory中的数据执行原子加操作。资料说明，`int32_t`、`uint32_t`、`float`、`half`、`bfloat16_t`、`half2`、`bfloat16x2_t`支持Unified Buffer和Global Memory，`int64_t`、`uint64_t`支持Global Memory。相关说明见[asc_atomic_add](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMT-API/原子操作/asc_atomic_add.md)。

SIMT原子操作需要区分目标地址：

- 目标是UB时，主要关注同一Thread Block内线程之间的共享数据可见性，可结合`asc_threadfence_block`或同步接口处理。
- 目标是GM时，需要关注SIMT DCache与GM访问路径，以及与SIMD/Scalar路径混用时的可见性。若同一GM地址还通过Scalar普通DCache路径访问，应结合2.2节处理DCache与GM一致性。

## 4. 总结

NPU内存一致性问题通常来自两类原因：一是不同流水、不同线程、不同核之间没有自动建立预期的读写顺序；二是同一份数据可能同时存在于GM、L2 Cache、DCache、ICache、UB等不同位置。编写算子时，应先确认访问路径，再决定是否需要同步、是否需要绕过Cache、是否需要调用`DataCacheCleanAndInvalid`或SIMT内存栅栏接口。资料未明确说明的硬件模式或内部流程，不应直接写成通用编程规则。

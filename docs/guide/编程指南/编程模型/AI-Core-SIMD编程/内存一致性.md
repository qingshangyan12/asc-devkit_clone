# 内存一致性

本文介绍 NPU 编程中常见的内存一致性问题，重点说明 GM、L2 Cache、DCache、ICache、UB 以及原子操作之间的数据可见性关系。

## 1. 概念体系

### 1.1 Overlap

Overlap（地址重叠）指两个内存访问范围在字节地址区间上存在交集。例如，源操作数覆盖`[addr, addr + 128)`，目的操作数覆盖`[addr + 64, addr + 192)`，则两者地址重叠。相关约束见[通用地址重叠约束](../../../../api/SIMD-API/通用说明和约束.md#section668772811100)。

如果不同流水访问重叠地址且存在读写依赖时，需要用户使用核内同步建立先后顺序。同步能力说明见[系统同步能力概述](../../../../api/SIMD-API/基础API/同步控制/系统同步能力概述.md)。

### 1.2 Alias

Alias（别名）描述两个不同的名字指向同一段物理内存。类似于浅拷贝，两个对象指向同一个地址，修改其中一个对象的值会影响另一个对象的值。Alias本身不一定错误，但在并发访问、缓存访问或原子更新场景中，需要明确哪一个执行单元先写、哪一个执行单元后读。

### 1.3 Cache Line

Cache Line是Cache加载、失效、写回的最小操作粒度。例如访问GM内存时，会将GM里一个Cache Line长度内相邻的数据加载到L2 Cache缓存，利用空间局部性提高访问效率。Cache Line是硬件真正搬入、标记、替换和写回缓存数据的最小粒度，直接影响性能和一致性。NPU架构版本3510支持L2 Cache、DCache、ICache、SIMT DCache、NDDMA Cache；NPU架构版本2201（对应Atlas A2/A3训练系列产品和推理系列产品）支持L2 Cache、DCache和ICache。本文讨论的通用Cache单元信息如下：
 	 
| 存储单元 | 位置 | 数据一致性说明 | 3510 Cache Line大小 | 2201 Cache Line大小 |
| --- | --- | --- | --- | --- |
| L2 Cache | 核外共享缓存 | 多个核共享，不考虑多个核之间的Cache副本不一致问题 | 128B/256B/512B | 256B |
| ICache | Scalar取指缓存 | 只读，不考虑多个核之间的数据不一致问题 | 2KB | 2KB |
| DCache | Scalar数据缓存 | 每个核独立缓存，需要考虑多个核之间的数据一致性问题 | 64B | 64B |

### 1.4 一致性

一致性指多个执行单元或多个核对同一数据并发读写时，各执行单元看到的数据是否符合程序预期。本文将一致性分成两个层面：内存一致性和缓存一致性。

**内存一致性**是指生产者已经写了数据，消费者什么时候、以什么顺序能看到这些写入，即关注读写操作的顺序和可见性。例如，考虑两个核同时访问GM中的两个变量：

```text
初始状态：A == 1, B == 2

Core 0                         Core 1
===========================    ===========================
A = 3;                         x = B;
B = 4;                         y = A;
```

如果没有额外同步，Core 1观察到两个写入的时机和顺序不一定等同于Core 0的代码书写顺序，会存在以下4种可见性顺序：

```text
Case 1: x = LOAD B -> 2, y = LOAD A -> 1, STORE A = 3, STORE B = 4
Case 2: STORE A = 3, x = LOAD B -> 2, y = LOAD A -> 3, STORE B = 4
Case 3: STORE B = 4, x = LOAD B -> 4, y = LOAD A -> 1, STORE A = 3
Case 4: STORE A = 3, STORE B = 4, x = LOAD B -> 4, y = LOAD A -> 3
```

因此，Core 1最终可能看到不同的读值组合：

```text
Case 1：x == 2, y == 1
Case 2：x == 2, y == 3
Case 3：x == 4, y == 1
Case 4：x == 4, y == 3
```

内存一致性关注的是"写入以什么顺序被其他执行者观察到"。如果程序要求Core 1看到`B == 4`时一定也能看到`A == 3`，就需要在写数据和读数据之间建立同步关系，而不能只依赖代码中的书写顺序。

默认情况下，NPU上核内不同执行单元、不同核、不同SIMT线程之间的内存访问顺序和可见性不能只靠代码书写顺序推断，当存在数据依赖或通信关系时，需要开发者自行使用对应同步接口和缓存控制接口建立可见性。

**缓存一致性**（cache一致性）是指某个地址的数据被某个核的Cache修改后，GM或其他核看到的是新值还是旧值，即关注同一地址或同一Cache Line在不同缓存副本之间的值是否一致。

以DCache为例，`A`和`B`位于GM上同一条64B DCache Cache Line内：

```text
初始状态：GM Cache Line [A, B, ...] == [0, 0, ...]

Core 0                         Core 1
===========================    ===========================
LOAD A;                         LOAD B;
// Core 0 DCache缓存整条Line     // Core 1 DCache缓存整条Line
// [A=0, B=0, ...]              // [A=0, B=0, ...]

STORE A = 1;                    STORE B = 2;
// Core 0 DCache变成             // Core 1 DCache变成
// [A=1, B=0, ...]              // [A=0, B=2, ...]
```

两个核虽然修改的是不同字段，但各自DCache里保存的是整条Cache Line的副本。后续写回GM时，如果以整条Cache Line为单位写回，就可能出现不同结果：

```text
Case 1：Core 0先写回，Core 1后写回
GM Cache Line == [A=0, B=2, ...]   // Core 1旧副本覆盖了Core 0对A的修改

Case 2：Core 1先写回，Core 0后写回
GM Cache Line == [A=1, B=0, ...]   // Core 0旧副本覆盖了Core 1对B的修改

```

因为每个核都有自己的缓存数据，各个核都是在自己的缓存的旧值上进行修改，这个例子因为缓存一致性没有获得期望的[A=1, B=2, ...]。

## 2. 内存一致性

本章按具体访问路径说明一致性问题。每一类问题都先看数据可能停留在哪个存储位置，再看生产者写入后消费者从哪里读取，最后确定是否需要[DCCI](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)（Data Cache Clean and Invalid）、[DSB](../../../../api/SIMD-API/C-API/同步控制/asc_sync_data_barrier.md)（Data Sync Barrier）、同步接口或绕过DCache的访问接口。

### 2.1 DCache与GM的一致性

DCache与GM的一致性是NPU内存一致性中最常见的一致性问题。Scalar读写GM时会经过当前核内的Data Cache，而每个AIC/AIV核内都有独立的Data Cache用于缓存GM里的数据，如果某个核修改了GM数据，不会主动通知其他核该数据已被修改，导致其他核都以为自己DCache里缓存的数据是最新的正确数据。

因此多个核通过各自DCache访问同一段GM数据，如果没有做好通信时，通常会出现DCache与GM的一致性问题。

把Scalar对GM的访问拆成读和写，可以得到两个基本规则：

- Scalar读GM后，数据会进入Data Cache；后续读取同一条Cache Line内的数据时，可能直接从DCache读取，不再访问GM。
- Scalar写GM时，只会修改DCache中的Cache Line，并把该Cache Line标记为Dirty。Dirty表示DCache中的Cache Line数据与GM中的数据不一致，但是并不会立刻将Dirty数据写回GM，而是需要用户手动刷新或者该数据段被替换时才会写回GM。

所以，生产侧要关心Dirty数据是否已经写回GM；消费侧要关心本核DCache里是否还保留旧副本。DCCI负责处理"副本是否写回或失效"，同步指令负责处理"后续访问是否等到前序内存访问完成"。

#### 2.1.1 Scalar访问GM带来的一致性

Scalar普通读写GM时，“Scalar已经执行了写语句”不等于“GM已经被改写”。下面用两个核访问同一GM地址`A`说明生产侧的问题，示例中用直接GM地址读写表示普通Scalar访问。

```text
初始状态：
GM[A] == 0
Core 0 DCache中没有A
Core 1 DCache中没有A

Core 0                                  Core 1
====================================    ====================================
*A = 1;                                 r = *A;
// Core 0 DCache[A] == 1, Dirty
// GM[A] 仍可能是 0
```

如果Core 0写入后没有执行DCCI，Core 1从GM或自己的DCache路径读取时，可能仍然看到旧值：

```text
Core 0 *A = 1                // 新值进入Core 0 DCache，GM[A]仍可能是0
Core 1 *A -> 0               // Core 1从GM加载，看到旧值
Core 0 DCCI                  // 发起Dirty Cache Line写回GM
Core 0 DSB                   // 等待DCCI触发的GM写回完成，GM[A]变为1
Core 1 *A -> 1               // 后续读取才可能看到新值
```

如果读端本核DCache中已经缓存过同一地址，还需要考虑旧副本。下面示例中，消费侧使用[`asc_dcci_single`](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)在读取数据前刷新指定GM地址所在Cache Line：

```text
初始状态：GM[A] == 0

Core 1 *A -> 0               // Core 1 DCache缓存A所在Cache Line
Core 0 *A = 1
Core 0 DCCI                  // Core 0发起新值写回GM
Core 0 DSB                   // 等待DCCI触发的GM写回完成，GM[A]变为1
Core 1 *A -> 0               // 如果Core 1仍命中旧DCache副本，可能继续看到旧值
Core 1 asc_dcci_single(A)
Core 1 *A -> 1               // 旧副本失效后重新从GM获取
```

这个例子里，Core 0是生产者，Core 1是消费者。生产者写入后，如果新值还停留在Core 0 DCache中，消费者从GM或自己的DCache路径读取时，就可能看不到这个新值。

消费侧还有另一种常见问题：读端本核DCache中已经缓存过同一地址，即使GM后来被其他核更新，读端也可能继续命中旧副本。

基于上面的生产侧和消费侧问题，Scalar路径建立可见性的基本原则是：

- 生产者通过Scalar写GM后，如果消费者需要从GM或其他路径读取该数据，生产者需要执行DCCI（例如`asc_dcci_single`）把Dirty数据写回GM。
- 消费者如果担心本核DCache中有旧副本，读取前需要执行DCCI使旧副本失效。
- 如果算法本身不需要DCache缓存，可以使用[ReadGmByPassDCache](../../../../api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md)和[WriteGmByPassDCache](../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md)直接读写GM。

还有一类问题来自Cache Line粒度。普通Scalar写后续写出时以64B Cache Line为单位。多个核即使写的是同一条Cache Line中的不同字段，也可能在各自写回整条Cache Line时覆盖对方结果。此类场景可以通过让不同核操作的地址至少相隔Cache Line大小，或使用绕过DCache的读写接口降低风险。

#### 2.1.2 ATOM访问导致的DCache一致性

Scalar原子操作可以看成对某个GM地址执行的读-改-写事件。以原子加操作[asc_atomic_add](/data/hxj/code/2/asc-devkit_0616/docs/api/SIMT-API/原子操作/asc_atomic_add.md)为例，该接口在指定GM地址上执行原子加操作，并返回GM地址上做原子操作前的数据。原子操作保证的是这一次读-改-写不会被其他原子更新打断，但它不会自动清理同一地址在DCache中的旧副本或Dirty副本。

因此，如果同一GM地址此前被普通Scalar路径访问过，就需要分析原子事件和DCache事件的一致性问题：

- 若普通Scalar写先发生，数据可能仍停留在DCache中。后续原子操作如果依赖这个写入，需要先把相关DCache Line写回GM。
- 若原子操作先发生，本核DCache中可能仍保留旧副本。后续再用普通Scalar读同一地址时，需要先使旧副本失效，避免读到原子操作之前的值。

下面用一个地址`A`说明ATOM与DCache混用时的问题：

```text
初始状态：GM[A] == 0

Core 0
====================================
*A = 1;
// Core 0 DCache[A] == 1, Dirty
// GM[A] 仍可能是 0

asc_atomic_add(A, 1);
// 如果原子操作从GM上的旧值0开始累加，结果可能变成1，而不是期望的2
```

上面的关键不是`asc_atomic_add`本身不原子，而是原子操作看到的GM值没有包含此前停留在DCache中的普通Scalar写入。反过来，如果`asc_atomic_add(A, 1)`已经把GM更新为1，而本核DCache里还保留`A == 0`的旧副本，后续普通Scalar读也可能继续读到旧副本。

#### 2.1.3 DCCI、DSB处理ATOM访问一致性

如果ATOM访问需要避免DCache一致性问题，需要开发者根据实际情况插入DCCI和DSB同步：

- **DCCI**：通常指Data Cache Clean and Invalid。Clean将DCache中的Dirty数据写回GM，Invalid让对应Cache Line失效，避免后续继续使用旧副本。可使用`asc_dcci_single`刷新指定GM地址所在的单个Cache Line，使用[`asc_dcci_entire_out`](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)刷新面向GM的一致性目标；原子相关目标按产品支持情况选择[`asc_dcci_entire_atomic`](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)等接口。
- **DSB**：Data Sync Barrier。可以使用[`asc_sync_data_barrier`](../../../../api/SIMD-API/C-API/同步控制/asc_sync_data_barrier.md)用于阻塞后续指令执行，直到之前的内存访问指令执行结束；参数可选择`DSB_ALL`、`DSB_DDR`或`DSB_UB`。

因此，ATOM访问标准处理流程可以写成：

```text
asc_dcci_single(A) -> asc_sync_data_barrier(DSB_DDR) -> asc_atomic_add(A, val) -> asc_sync_data_barrier(DSB_DDR)
```

含义如下：

```text
asc_dcci_single(A)：把原子操作前可能停留在DCache中的Dirty数据写回GM，并使旧副本失效。
asc_sync_data_barrier(DSB_DDR)：等待前序DCCI触发的GM写回完成，避免原子操作过早开始。如果前序还混有UB等其他内存访问，可以使用更保守的DSB_ALL。
asc_atomic_add(A, val)：对GM地址执行原子读-改-写。
asc_sync_data_barrier(DSB_DDR)：等待原子访问产生的GM访问完成，确保后续依赖该结果的读写不会提前执行。
```
这样操作可以保证生产者原子操作完成后，GM里的数据按照预期被正确修改，用户之后再添加消费者读写操作就不会使用错误数据。

#### 2.1.4 Scalar写GM后的读取同步组合

Scalar写GM可以分为两类：
- 普通Scalar写通过DCache修改GM，例如直接写`__gm__`地址；
- `WriteGmByPassDCache`不经过DCache，直接向GM发起写操作。

本节目的是描述：生产者完成写指令之后、消费者真正读取之前，生产者和消费者需要按顺序执行哪些操作，才能让消费者读到生产者写入的数据。判断时需要同时看两个条件：生产者写出的数据是否已经到达消费者会访问的存储位置，消费者所在路径是否可能继续命中旧的Cache副本。

下表先列出同一AI Core内的组合，并假设生产者和消费者访问同一地址、不存在并发写入，也不存在不同写入落在同一条DCache Cache Line内的交叉覆盖。每个单元格都是从写后处理到读前处理的完整操作序列。

表中的`VF_SIMT`表示SIMT Vector Function，即使用`__simt_vf__`标记、由Scalar侧启动的一段SIMT线程函数。`VF_SIMT（no cache）`表示VF内使用不占用或绕过SIMT Data Cache的GM访问路径。

| 读取方式<br>╲<br>写入方式 | Scalar | Scalar（no cache） | VF_SIMT | VF_SIMT（no cache） | MTE2 | MTE2（no cache） |
| --- | --- | --- | --- | --- | --- | --- |
| Scalar 经 DCache <br>回写 GM | 无需同步 | Scalar.DCCI<br>Scalar.DSB | Scalar.DCCI<br>Scalar.DSB<br>sync S→V/VF<br>SIMT.DCCI| Scalar.DCCI<br>Scalar.DSB<br>sync S→V/VF | Scalar.DCCI<br>Scalar.DSB<br>sync S→MTE2<br>MTE2.DCCI | Scalar.DCCI <br> Scalar.DSB <br> sync S -> MTE2 |
| Scalar 不经 DCache <br>写 GM | Scalar.DCCI<br>Scalar.DSB | Scalar.DSB| Scalar.DSB<br>sync S→V/VF<br>SIMT.DCCI| Scalar.DSB<br>sync S→V/VF | Scalar.DSB<br>sync S→MTE2<br>MTE2.DCCI | Scalar.DSB<br>sync S→MTE2 |

表中命令按"生产者写后处理 -> 消费者读前处理"的顺序排列。`DCCI`用于把Dirty数据写回GM，或使读端路径中可能存在的旧Cache副本失效；`DSB`用于等待前序GM访问完成；`sync S→X`用于同一AI Core内建立Scalar到读取流水的执行顺序。两种写入方式的含义如下：

- **Scalar 经 DCache 回写 GM**（例如直接写`__gm__`地址）：普通Scalar写会先把数据放进生产者本核DCache并标记为Dirty，GM不一定立即变化。除同核Scalar直接读取这个DCache新副本的场景外，消费者要读到正确值，需要先由生产者执行`Scalar.DCCI -> Scalar.DSB`，把Dirty数据写回GM并等待写回完成；随后再按读端路径执行流水同步和读端Cache失效操作。
- **Scalar 不经 DCache 写 GM**（例如`WriteGmByPassDCache`）：写操作绕过DCache直接发往GM，不会在生产者DCache中留下Dirty副本，但该GM写入仍需要通过`Scalar.DSB`等待完成。同时，绕过DCache写不会自动更新或失效消费者路径中已有的旧Cache副本；如果消费者通过带Cache路径读取，需要按表在读前执行对应的DCCI。例如后续普通Scalar读需要执行`Scalar.DCCI -> Scalar.DSB`，后续VF_SIMT或MTE2带Cache读还需要执行对应的流水同步和读端DCCI。

表中的`DSB`只负责等待前序GM访问完成，不能替代流水间或核间同步；`S -> V/VF`和`S -> MTE2`只用于同一AI Core内建立流水顺序。如果生产者和消费者位于不同AI Core，表中的核内流水同步不能跨核生效，还需要按以下顺序建立核间可见性：

```text
生产核：完成生产者侧Cache处理 -> DSB -> 发送核间通知
消费核：等待核间通知 -> 处理消费者侧可能存在的旧Cache副本 -> 读取数据
```

跨核场景中，生产核上的DCCI只能处理生产核自己的DCache；如果消费核的Scalar DCache或SIMT Data Cache中已有旧副本，仍需由消费核在读取前使其失效。

### 2.2 ICache与GM一致性

ICache用于缓存Scalar单元最近使用或频繁使用的指令。Scalar读取GM指令时，优先从ICache读取；ICache未命中时，再从L2 Cache读取；L2 Cache也未命中时，再从GM加载指令并更新到L2 Cache和ICache。相关说明见[系统缓存概述](../../../../api/SIMD-API/基础API/缓存控制/系统缓存概述.md)。

从一致性角度看，ICache缓存的是指令而不是普通数据，并且是只读Cache，因此ICache和GM之间没有一致性问题。

### 2.3 SIMT DCache与GM一致性

#### 2.3.1 SIMT DCache访问路径

NPU架构版本3510新增SIMT相关硬件单元。普通/默认SIMT访存会涉及SIMT DCache：SIMT DCache复用UB中的一部分空间，用于缓存SIMT线程访问GM时的数据。SIMT Data Cache空间可配置范围为32KB到128KB，实际大小由UB总大小扣除静态内存、动态内存和预留空间后确定，若剩余空间超过128KB，Data Cache大小固定为128KB。SIMT也提供[`asc_ldcg`](../../../../api/SIMT-API/访存函数/asc_ldcg.md)、[`asc_stcg`](../../../../api/SIMT-API/访存函数/asc_stcg.md)等接口表达不占用或绕过SIMT Data Cache的访问意图，因此本节按带Cache路径和no cache路径分别分析。

默认SIMT读GM的底层实现：先从SIMT Data Cache读取，未命中再访问L2 Cache或GM，并把数据缓存到L2 Cache和SIMT Data Cache中。L2 Cache与GM之间的数据一致性由硬件保证，但SIMT Data Cache与GM之间不保证一致性。因此，如果同一GM地址已经被其他线程、其他核、Scalar路径或MTE路径更新，而当前SIMT Data Cache中仍有旧副本，后续默认SIMT读可能继续命中旧值。

判断SIMT写GM后消费者能否读到新值，可以按两步看：

- **先看生产者写完后新值是否已经到达GM**：write-through写入时，底层会把新值写出到GM；no cache写入不经过SIMT Data Cache，也不留下需要写回的新副本；两者仍需要通过`SIMT.DSB`等待GM写入完成。write-back写入先停留在SIMT Data Cache中，如果其他路径要读这个新值，需要先执行`SIMT.DCCI -> SIMT.DSB`。
- **再看消费者从哪里读**：如果消费者通过Scalar或MTE2等其他路径读取，读端路径中可能已有旧副本，需要在读前按表执行对应的DCCI；如果消费者本来就走no cache读取路径，则不需要处理SIMT Data Cache中的旧副本。

如果线程或核之间还通过GM上的标志位通信，需要额外处理写入顺序关系：使用[`asc_threadfence`](../../../../api/SIMT-API/同步与内存栅栏/内存栅栏接口/asc_threadfence.md)等内存栅栏，避免"先写数据、再写标志"被其他线程观察成错误顺序。内存栅栏只约束调用线程前后内存操作的可见性顺序，不等价于等待消费者，也不会自动刷新消费者侧Cache。

#### 2.3.2 VF_SIMT写GM后的读取同步组合

下表描述的是核内VF_SIMT作为生产者写GM之后、消费者真正读取之前，生产者和消费者需要按顺序执行哪些操作，才能保证消费者读取到生产者写入的数据。

表中的三类写入方式含义如下：

- **VF_SIMT（write-through）**：写入经过SIMT Data Cache，但底层会确保数据写出到GM，因此生产者侧不需要执行`SIMT.DCCI`推出Dirty数据；后续其他流水读取前仍需等待GM写完成，并处理读端可能存在的旧副本。
- **VF_SIMT（write-back）**：写入先停留在SIMT Data Cache中，其他路径读取前需要由生产者侧执行`SIMT.DCCI -> SIMT.DSB`，把新值写回到GM并等待完成。
- **VF_SIMT（no cache）**：写GM不经过SIMT Data Cache，不留下需要写回的新副本，其他流水读取前仍需通过`SIMT.DSB`等待GM写完成，并按读端路径处理旧副本。

表中的`SIMT.DSB`用于等待SIMT侧前序GM访问或DCCI触发的写回完成，`SIMT.DCCI`用于处理SIMT Data Cache中的写回或失效，`sync V/VF->X`用于同一AI Core内建立Vector/VF流水到后续读取流水的执行顺序，`Scalar.DCCI`和`MTE2.DCCI`表示消费者侧在读取前处理本路径可能存在的旧Cache副本。

| 读取方式<br>╲<br>写入方式 | Scalar | Scalar（no cache） | VF_SIMT | VF_SIMT（no cache） | MTE2 | MTE2（no cache） |
| --- | --- | --- | --- | --- | --- | --- |
| VF_SIMT（write-through） | SIMT.DSB<br>sync V/VF->S<br> Scalar.DCCI| SIMT.DSB<br>sync V/VF->S | 无需同步| 无需同步 | SIMT.DSB<br>sync V/VF->MTE2<br> MTE2.DCCI | SIMT.DSB<br>sync V/VF->MTE2 |
| VF_SIMT（write-back） | SIMT.DCCI<br>SIMT.DSB<br>sync V/VF->S<br> Scalar.DCCI| SIMT.DCCI<br>SIMT.DSB<br>sync V/VF->S| 无需同步 | 无需同步 | SIMT.DCCI<br>SIMT.DSB<br>sync V/VF->MTE2<br> MTE2.DCCI | SIMT.DCCI<br>SIMT.DSB<br>sync V/VF->MTE2 |
| VF_SIMT（no cache） | SIMT.DSB<br>sync V/VF->S<br> Scalar.DCCI | SIMT.DSB<br>sync V/VF->S| 无需同步| 无需同步 | SIMT.DSB<br>sync V/VF->MTE2<br> MTE2.DCCI| SIMT.DSB<br>sync V/VF->MTE2 |

表格的阅读方式是先定位生产者写入路径所在的行，再定位消费者读取路径所在的列，单元格中的操作按从上到下的顺序执行。例如，生产者是`VF_SIMT（write-back）`，消费者通过普通`Scalar`读取时，需要执行：

```text
SIMT.DCCI -> SIMT.DSB -> sync V/VF->S -> Scalar.DCCI -> Scalar读
```

含义是：SIMT write-back写入可能还停留在SIMT Data Cache中，生产者侧先执行`SIMT.DCCI`把相关Cache Line写回GM或使其失效；随后执行`SIMT.DSB`等待写回或前序GM访问完成。消费者读前再通过`sync V/VF->S`保证同一AI Core内Scalar读取发生在VF_SIMT写入之后，并执行`Scalar.DCCI`避免Scalar DCache中已有旧副本；之后Scalar读取才能从正确位置获得新值。

如果核内消费者仍通过`VF_SIMT`或`VF_SIMT（no cache）`读取，表中给出"无需同步"，只表示在表格假设范围内不需要额外跨流水同步或其他路径的Cache处理，不表示不同线程、不同核或不同VF调用阶段之间天然有同步关系。如果程序通过GM上的标志位在不同线程块、不同核或不同执行阶段之间通信，仍需要结合`asc_threadfence`、原子操作、轮询协议以及必要的DCCI/绕过Cache读取来建立完整同步关系。若生产者和消费者位于不同AI Core，表中的`sync V/VF->S`和`sync V/VF->MTE2`不能跨核生效，应先在生产核完成生产者侧Cache处理和`DSB`，再发送核间通知；消费核收到通知后，再处理本核读端可能存在的旧Cache副本。

### 2.4 UB与DCache的一致性

UB与DCache的一致性问题主要出现在Scalar开启Data Cache模式读取UB的场景：Scalar访问UB路径时可以`CTRL[49]`控制Scalar读取UB时是否通过Data Cache读取；当`CTRL[49] = 1'b1`时，Scalar读UB会从Data Cache中读取。相关说明见[DataCacheCleanAndInvalid](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)和[asc_dcci](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)。

#### 2.4.1 Scalar以Data Cache模式访问UB带来的一致性

Scalar以Data Cache模式读UB后，数据可能进入Data Cache；后续Scalar再次读取同一段UB地址时，可能继续命中DCache副本，而不是直接读取UB。下面用同一核内的一个UB地址`A`说明旧副本问题。

```text
初始状态：
UB[A] == 0
Scalar DCache中没有A
CTRL[49] = 1'b1    // Scalar读UB时从Data Cache读取

Scalar GetValue(A) -> 0        // Scalar DCache缓存A所在Cache Line
Vector写UB[A] = 1              // UB中已经是新值
Scalar GetValue(A) -> 0        // 如果仍命中旧DCache副本，可能继续看到旧值
```

如果Vector写UB后没有建立流水顺序，Scalar读取还可能早于Vector写完成；如果Scalar DCache中已经缓存过旧值，即使Vector写完成，Scalar也可能继续命中旧副本。因此，消费者通过Scalar Data Cache模式读取UB前，需要同时处理流水顺序和DCache旧副本：

```text
Vector写UB[A] = 1
sync V->S
DataCacheCleanAndInvalid<..., DcciDst::CACHELINE_UB>(localTensorA)
Scalar GetValue(A) -> 1
```

其中，`sync V->S`用于保证同一AI Core内Scalar读取发生在Vector写UB之后；`CACHELINE_UB`用于保证DCache与UB的一致性，使Scalar后续读取不再使用旧DCache副本。若生产者是MTE2把GM数据搬入UB，也需要先建立`MTE2 -> S`的流水顺序，再处理Scalar DCache中的旧UB副本。

#### 2.4.2 一致性原则

`DataCacheCleanAndInvalid`支持通过`DcciDst`选择一致性目标：`CACHELINE_UB`表示通过该接口保证DCache与UB的一致性。C API中也提供了[`asc_ub_dcci_single`](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)、[`asc_dcci_entire_ub`](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)等面向UB地址空间的DCCI接口。

实际编程时，应先判断消费者从哪里读取，再选择对应的一致性目标：

- 如果后续消费者以Scalar Data Cache模式直接读取UB，关注的是DCache与UB的一致性，应使用`CACHELINE_UB`，并在读取前建立生产流水到Scalar流水的同步。
- 如果Scalar读取UB时没有开启Data Cache模式，即`CTRL[49] = 1'b0`，Scalar直接从UB读取，此时通常只需要处理Scalar流水与Vector/MTE流水之间的执行顺序，不需要通过`CACHELINE_UB`处理旧DCache副本。


## 3. 原子操作与一致性

原子操作用于多个执行单元、多个线程或多个核并发更新同一地址时，将一次读-改-写过程作为不可被其他更新打断的事件。原子操作可以避免同一地址上的更新丢失，但不等价于Cache一致性处理，也不等价于同步屏障。判断atomic操作下的Cache一致性，需要同时看两个问题：atomic操作实际更新的是GM还是UB，以及同一地址是否还被普通DCache、SIMT DCache或DataCopy等其他路径访问。

下面按atomic事件发起路径分四类说明：Scalar原子、MTE3随路原子、FixPipe随路原子和SIMT原子。本节只说明这些atomic事件放入一致性分析时需要关注的Cache行为，接口细节可参考对应API文档。

### 3.1 Scalar原子操作与DCache一致性

Scalar原子操作直接对GM地址执行原子读-改-写。它和普通Scalar读写GM最大的区别是：Scalar原子操作会绕过DCache，需要调用DCCI确保GM与DCache的一致性。接口说明可参考[AtomicAdd](../../../../api/SIMD-API/基础API/原子操作/AtomicAdd.md)和[asc_dcci](../../../../api/SIMD-API/C-API/缓存控制/asc_dcci.md)。

因此，Scalar原子操作和普通Scalar读写GM混用时，需要按DCache与GM的一致性来分析：

- 如果普通Scalar写GM在前，数据可能还停留在DCache中，并未写回GM。后续Scalar原子操作绕过DCache访问GM时，可能看不到这个Dirty副本。此时需要先执行`asc_dcci_single`和`asc_sync_data_barrier`，把Dirty数据写回GM并等待完成，再执行原子操作。

- 如果Scalar原子操作在前，它更新的是GM，不会自动失效本核或其他核DCache中的旧副本。后续普通Scalar读同一GM地址前，需要在读端执行DCCI，避免继续命中旧DCache副本。

- 如果Scalar原子操作前后还存在MTE2/MTE3搬运同一GM地址，需要额外插入核内同步，保证前序GM访问完成后再启动后续访问。原子操作只保证单次读-改-写不可分割，不负责建立MTE流水与Scalar流水之间的执行顺序。

### 3.2 MTE3随路原子操作与DCache一致性

随路原子操作不是单独读取某个地址的Scalar事件，而是改变后续目的地址为GM的数据搬运行为。MTE3负责将UB等核内数据搬出到GM，因此`UB -> GM`是常见的随路原子使用路径。接口说明可参考C API [asc_set_atomic_add](../../../../api/SIMD-API/C-API/原子操作/asc_set_atomic_add.md)和[asc_set_atomic_none](../../../../api/SIMD-API/C-API/原子操作/asc_set_atomic_none.md)。

从一致性角度看，MTE3随路原子的目标是GM，不会自动处理Scalar DCache中已有的副本，因此需要关注以下关系：

- 开启随路原子前，如果GM目标地址此前被普通Scalar写过，需要先确保Scalar DCache中的Dirty数据已经写回GM，否则原子操作读取到的"GM已有内容"可能不是程序期望的初值。

- 随路原子完成后，如果后续通过普通Scalar读取同一GM地址，需要处理读端DCache旧副本，并等待MTE3写GM完成。


### 3.3 FixPipe随路原子操作与DCache一致性

FixPipe常用于`L0C Buffer -> GM`或相关矩阵搬出路径。对一致性分析来说，FixPipe随路原子可以看成另一类"向GM写入的随路原子事件"：数据来源不同于MTE3，但最终更新的仍是GM目标地址。

因此，FixPipe随路原子的Cache一致性行为与MTE3随路原子类似：它不会自动清理Scalar DCache旧副本，也不会自动把此前停留在DCache中的Dirty数据合入GM。

- 如果GM目标地址的初值来自普通Scalar写GM，需要先按2.1节把DCache中的Dirty数据写回GM，再执行FixPipe随路原子。
- 如果FixPipe随路原子后，消费者通过Scalar普通路径读取GM，需要等待FixPipe写GM完成，并在读端处理DCache旧副本。
- 如果多个流水或多个核都对同一GM地址做随路原子，原子操作只保证每次GM读-改-写不被打断；不同流水、不同核之间的启动顺序仍应由同步或算法协议保证。

### 3.4 SIMT原子操作与Cache一致性

SIMT原子操作可能作用于UB，也可能作用于GM；接口例子可参考[asc_atomic_add](../../../../api/SIMT-API/原子操作/asc_atomic_add.md)。它保证的是同一地址上这一次读-改-写具有原子性，不保证多个线程之间的执行顺序。

分析Cache一致性时，需要先区分目标地址：

- 目标是UB时，主要关注同一Thread Block内线程之间对共享UB数据的可见性和执行顺序；如果同一段UB数据还被Scalar以Data Cache模式读取，需要结合2.4节处理DCache与UB的一致性。
- 目标是GM时，需要把SIMT原子更新GM、SIMT普通读写GM、Scalar普通读写GM、MTE搬运GM放在同一张可见性图里分析。原子操作本身不能替代SIMT DCache或Scalar DCache的旧副本处理；若后续通过默认SIMT读或Scalar普通读读取同一GM地址，仍需要按2.3节或2.1节处理读端可能存在的旧Cache副本。
- 如果不同Thread Block或不同AI Core通过GM标志位配合SIMT原子操作通信，仍需要结合内存栅栏、原子操作、轮询协议以及必要的Cache处理建立完整同步关系，不能只依赖原子操作本身。

## 4. 预取

预取用于提前把后续可能访问的数据或指令放入Cache，目的是降低访问延迟。相关说明见[系统缓存概述](../../../../api/SIMD-API/基础API/缓存控制/系统缓存概述.md)。从一致性角度看，预取会改变数据或指令进入Cache的时机，可能会导致一致性问题。

#### 4.1 L2 Cache预取

L2 Cache和GM之间没有一致性问题，因此L2 Cache的预取不会导致多核间数据不一致问题。但这不表示L2 Cache预取获得的数据就是期望的：如果生产者写入的新值还停留在DCache中、MTE3写GM尚未完成，或者消费者读取顺序早于生产者写入完成，那么L2 Cache中提前加载到的仍可能是GM可见的旧值。此时仍应回到对应章节处理生产者写回、访问完成等待和读端旧副本失效。

#### 4.2 DCache预取

[DataCachePreload](../../../../api/SIMD-API/基础API/缓存控制/DataCachePreload.md)用于从指定GM地址预加载数据到DCache中，每次调用只能预加载一个Cache Line大小的数据。它的作用是让后续Scalar读取更可能命中DCache，而不是建立新的同步或一致性关系。

DCache是每个核内独立的缓存，因此DCache预取会在当前核DCache中提前形成GM数据副本。如果预取之后，同一GM地址被其他核、MTE、原子操作或SIMT路径更新，当前核后续普通Scalar读可能继续命中预取形成的旧副本。需要读取最新GM数据时，仍要按2.1节执行DCCI失效旧副本，或使用绕过DCache的读接口。

#### 4.3 ICache预取

[ICachePreLoad](../../../../api/SIMD-API/基础API/缓存控制/ICachePreLoad(ISASI).md)用于从指令所在GM地址预加载指令到ICache中。ICache预取主要影响取指性能，不参与普通数据的生产者-消费者可见性判断，也没有一致性问题。

## 5. 总结

NPU内存一致性问题通常来自两类原因：一是不同流水、不同线程、不同核之间没有自动建立预期的读写顺序；二是同一份数据可能同时存在于GM、L2 Cache、DCache、ICache、UB等不同位置。编写算子时，应先确认访问路径，再决定是否需要同步、是否需要绕过Cache、是否需要调用DCCI或SIMT内存栅栏接口。

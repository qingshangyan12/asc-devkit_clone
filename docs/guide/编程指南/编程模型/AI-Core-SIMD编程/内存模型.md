# 内存模型

本文的主要目的是介绍NPU的内存层级、数据在不同层级之间的搬运行为及注意事项。后续内容先定义Overlap、Alias、一致性、Cache Line、内存对齐等基础概念，再结合NPU架构版本2201说明GM、L2 Cache和核内存储单元之间的数据流向及编程约束。

## 1. 概念体系

本节定义后续讨论中使用的核心概念。

### 1.1 Overlap

Overlap（地址重叠）描述两个内存访问范围在字节地址区间上存在交集。例如，源操作数覆盖`[addr, addr + 128)`，目的操作数覆盖`[addr + 64, addr + 192)`，则两者部分重叠。

地址重叠会影响正确性，因为一次计算或搬运可能在读取源数据之前改写目的区域，导致后续读取到已经被覆盖的数据。Ascend C API对地址重叠有通用约束：

- 对于基础API的Tensor高维切分计算接口，单次迭代内源操作数与目的操作数如果重叠，通常必须100%完全重叠，不支持部分重叠。
- 多次迭代间通常不支持前序迭代的目的操作数与后序迭代的源操作数重叠。
- 具体API如果声明了额外约束，应以具体API说明为准。
- API文档未描述地址重叠约束时，应按“不支持地址重叠”处理。

相关约束见[通用地址重叠约束](../../../../api/SIMD-API/通用说明和约束.md#section668772811100)。

### 1.2 Alias

Alias（别名）描述两个程序对象或两个Tensor视图可能指向同一段物理内存。Alias关注的是“两个名字是否可能访问同一存储对象”，Overlap关注的是“两个具体访问区间是否相交”。

例如，两个`LocalTensor`由同一块UB分配切分而来，或者源Tensor和目的Tensor通过不同接口传入但底层GM地址相同，都可能形成Alias。Alias本身不一定错误，但它会降低编译器和开发者对读写顺序的判断确定性。涉及Alias时需要明确：

- 两个对象是否指向同一内存空间，例如GM、UB、L1或Register。
- 两个对象的有效访问区间是否Overlap。
- 读写是否发生在同一流水、不同流水或不同核之间。
- 是否已经通过同步、Cache控制或API约束建立正确顺序。

在接口允许原地计算时，完全重叠的Alias可能是合法优化；在接口不允许地址重叠时，Alias可能导致结果不满足预期。

### 1.3 Cache Line

Cache Line是Cache加载、失效、写回的最小操作粒度。例如访问GM内存时，会将相邻数据作为一个Cache Line加载到L2 Cache缓存，利用空间局部性提高访问效率。Cache Line不是简单的“推荐对齐值”，而是硬件真正搬入、标记、替换和写回缓存数据时使用的粒度，因此同时影响性能和一致性。

| 存储单元 | 位置|数据一致性说明 |  Cache Line大小 |
| --- | --- | --- |--- |
| L2 Cache | 核外共享缓存|多核间共享，不考虑多核间数据不一致性 |256B |
| ICache | Scalar取指缓存|只读，不考虑多核间数据不一致性 |  2KB |
| DCache | Scalar数据缓存|多核独立缓存，需要考虑多核间数据一致性问题 | 64B |

Cache Line带来的典型风险是“同一条Cache Line内的不同字段并不总是完全独立”。例如，多个核分别写同一条64B DCache Line中的不同`uint64_t`字段，如果写入经过DCache，最终写回GM时可能以整条Cache Line为单位覆盖其他核写入的字段。此类场景可考虑让不同核写入地址至少相隔一个Cache Line，或使用绕过DCache的读写接口。

### 1.4 一致性

一致性用于描述多个执行单元、多个核或多个缓存层级围绕同一批数据读写时，读者看到的数据是否符合程序期望。本文将一致性分成两个层面：内存一致性和Cache一致性。

**内存一致性**关注读写操作的顺序和可见性。换句话说，它回答的是“生产者已经写了数据，消费者什么时候、以什么顺序能看到这些写入”。在NPU SIMD编程中，常见例子包括：

- MTE2把GM数据搬入UB后，Vector必须等搬入完成后再读取UB，否则可能读到未完成搬运的数据。
- Vector写UB后，MTE3必须等计算完成后再把UB搬回GM，否则可能搬出旧数据或部分结果。
- AIC将L0C结果通过FixPipe搬到GM后，AIV如果要从GM读取这批结果，需要先通过核间同步确认写入已经完成。

这类问题通常通过自动同步、`SetFlag/WaitFlag`、`PipeBarrier`或核间同步接口处理。核内同步的详细说明见[核内同步能力概述](../../../../api/SIMD-API/基础API/同步控制/核内同步/核内同步能力概述.md)。

**Cache一致性**关注同一地址或同一Cache Line在不同缓存副本之间的值是否一致。它回答的是“某个地址的数据被某个核的Cache修改了，GM或其他核看到的是新值还是旧值”。在NPU SIMD编程中，最典型的例子是DCache：

- Scalar通过`GlobalTensor::SetValue`写GM时，数据会先写入本核DCache，GM不会立刻更新；其他核直接读GM时可能读到旧值。
- 多个核通过DCache写同一条64B Cache Line中的不同字段时，后续写回GM的粒度仍然是Cache Line，可能出现随机覆盖。例如两个核的DCache单元都缓存了GM 的同一条 64B Cache Line：[0x1000, 0x1040)，核0 修改 0x1000 处，核1 修改 0x1008 处，后续核0 先写回整条 64B，核1 后写回整条 64B，最终 GM 里可能只保留核1的修改，核0对 0x1000 的修改被核1那条旧副本覆盖掉。

这类问题通常通过`DataCacheCleanAndInvalid`把脏数据写回并失效，或通过`ReadGmByPassDCache`/`WriteGmByPassDCache`绕过DCache处理。缓存行为和接口汇总见[系统缓存概述](../../../../api/SIMD-API/基础API/缓存控制/系统缓存概述.md)。

## 2. 硬件架构与内存层级

### 2.1 硬件结构图与内存层级

[NPU架构版本3510](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)中，AI Core分为AIC和AIV两个独立的核，分别用于矩阵计算和向量计算。AIC核与AIV核配比为1：2。每个核都有自己的Scalar单元，能独立加载自己的代码段。

![](../../../figures/硬件架构.png)

3510架构中的存储层级可以按"片外GM、共享L2 Cache、核内显式管理存储、寄存器层级、Scalar私有Cache、SIMT访存Cache、SSBuffer通信空间"理解。各个存储单元的作用和对齐要求如下：

| 存储单元 | 主要作用 | 对齐/粒度 |
| --- | --- | --- |
| GM/HBM | Kernel输入、输出、Workspace、Tiling以及跨核、跨AIC/AIV交换数据的全局存储。 | 接口级通常无强制对齐要求；搬运性能上尽量512B对齐。 |
| L2 Cache | 缓存频繁访问的GM数据和指令，降低GM访问延迟并提升带宽。 | Cache Line大小256B |
| UB（Unified Buffer） | AIV侧Local Memory，用于Vector/SIMT相关数据暂存，也是GM与Register之间的重要中转空间。3510中新增UB与L1 Buffer之间的硬通道。 | 32B对齐，搬入UB的数据大小通常按DataBlock对齐。 |
| SIMD Register File | Reg矢量计算的数据源和中间结果存储层级。3510中Vector计算单元处理的数据来源于Register，部分中间结果可以不写回UB，直接继续在Register中计算。 | RegTensor位宽为VL，VL为256B。 |
| SIMT Register File | SIMT应用程序使用的寄存器空间，为SIMT线程提供通用寄存器资源。 | 总容量128KB；每个Thread可用寄存器数与Thread数量相关。 |
| L1 Buffer | AIC侧Local Memory，用于暂存Cube计算需要复用的数据。3510中支持与UB之间的数据通路。 | 32B对齐，推荐使用FRACTAL_NZ等适合矩阵计算的数据排布。 |
| L0A/L0B Buffer | Cube计算单元的输入缓冲区，L0A存储左矩阵，L0B存储右矩阵。3510中不再支持GM直接搬入L0A/L0B，通常需要先经L1 Buffer。 | 512B对齐。 |
| L0C Buffer | Cube计算单元的输出缓冲区，累加计算时也作为输入参与计算。3510中新增L0C Buffer到UB的数据通路。 | 64B对齐。 |
| BiasTable Buffer | 存放矩阵计算中的Bias数据。 | 64B对齐。 |
| Fixpipe Buffer | 存放FixPipe随路量化、激活等参数。 | 64B对齐。 |
| DCache | Scalar访问GM数据时使用的私有数据Cache。 | Cache Line为64B。 |
| ICache | Scalar执行代码段时使用的指令Cache。 | 以2KB为单位预加载指令。 |
| SIMT DCache | SIMT访问GM时的中转Cache，Data Cache直接复用UB作为Cache Line。 | SIMT所有对外访存以128B为粒度；最大128KB Data Cache。 |
| SSBuffer | AIC和AIV之间的轻量级共享通信空间，用于核间通信和参数传递。 | 每个Core对应1KB；AIC:AIV=1:2的Mix模式下共享3KB空间。 |

内存层级图如下：

<img src="../../../figures/SIMD-Reg矢量计算内存层级_内存模型.png" alt="SIMD-Reg矢量计算内存层级" width="520px">

典型数据流如下：

- Reg矢量计算路径：`GM -> L2 Cache -> UB -> SIMD Register File -> Vector -> SIMD Register File -> UB -> L2 Cache -> GM`。
- Cube路径：`GM -> L2 Cache -> L1 -> L0A/L0B -> Cube -> L0C -> FixPipe -> GM/L1`；需要回到AIV侧继续处理的数据，也可以经新增的`L0C Buffer -> UB`或`L1 Buffer <-> UB`通路进入UB。
- SIMT访存路径：`GM -> L2 Cache -> SIMT DCache -> SIMT Register File/通用寄存器`；SIMT对外访存以128B为粒度，SIMT DCache复用UB作为Cache Line。
- Scalar数据路径：`GM -> L2 Cache -> DCache -> Scalar`，Scalar写GM时为`Scalar -> DCache -> L2 Cache -> GM`。
- Scalar指令路径：`GM -> L2 Cache -> ICache -> Scalar`。
- AIC与AIV之间的核间通信可以通过SSBuffer完成；大块数据仍需要按具体搬运接口在GM、L1、UB、L0C等存储层级之间显式搬运，并结合核内同步或核间同步保证先写后读。


### 2.2 GM

GM（Global Memory）是AI Core外部的全局内存空间，用于承载Kernel输入、输出、Workspace、Tiling等数据，也是AIC、AIV以及不同核之间交换数据的基础位置。AI Core内部的计算单元通常不会直接在GM上完成向量或矩阵计算：Vector计算的源数据和目的数据位于UB，Cube计算的数据主要经过L1、L0A/L0B、L0C等片上存储流动；GM中的数据需要通过MTE或FixPipe等搬运单元进入片上存储，计算结果也需要再搬回GM。

GM的接口级对齐要求通常较宽松，[通用说明和约束](../../../../api/SIMD-API/通用说明和约束.md)中将Global Memory描述为“无对齐要求”。但从性能角度看，GM地址对齐仍然很重要：

- 从GM向Local Memory搬运数据时，GM地址尽量保持512B对齐，可以更有效发挥带宽，相关说明见[GM地址尽量512B对齐](../../../算子实践参考/SIMD算子性能优化/内存访问/GM地址尽量512B对齐.md)。
- MTE2、MTE3、Scalar等单元访问GM时，地址请求会按照512B粒度对齐后处理。多个核或多个请求同时访问同一个连续512B范围内的GM地址时，由于一致性要求，相关请求可能被串行处理，降低搬运效率。相关说明见[避免同地址访问](../../../算子实践参考/SIMD算子性能优化/内存访问/避免同地址访问.md)。
- 当前算子执行机制保证用户Kernel入参地址512B对齐，Workspace和Tiling也包含在内。实际编写算子时，还需要关注各Tensor在GM基址上的偏移，避免偏移后落入不利于带宽或容易产生同地址访问冲突的位置。

### 2.3 L2 Cache

L2 Cache位于搬运单元、Scalar单元和GM之间，用于缓存频繁访问的数据和指令，减少对GM的直接读写。

- 通过MTE2读取GM时，硬件优先从L2 Cache读取；L2 Cache未命中时，再从GM加载并更新到L2 Cache。
- 通过Scalar读取GM数据时，访问路径通常是优先从DCache读取，DCache未命中时再读取L2 Cache，L2 Cache未命中时，再从GM加载并更新到L2 Cache。
- 通过Scalar读取GM指令时，访问路径通常是优先从ICache读取，ICache未命中时再读取L2 Cache，L2 Cache未命中时，再从GM加载并更新到L2 Cache。

**访问模式**

Ascend C通过GlobalTensor的`SetL2CacheHint`接口设置L2 Cache模式。若不调用该接口，默认使用`CACHE_MODE_NORMAL`。

| 模式 | 枚举 | 行为说明 | 典型使用场景 |
| --- | --- | --- | --- |
| Normal | `CACHE_MODE_NORMAL` | 启用L2 Cache。GM数据进入L2后，如果后续再次访问同一数据，命中L2可减少GM读写。L2容量耗尽时，已缓存数据可能被替换。 | 默认模式；适合输入会被重复读取、输出后续可能被复用的场景。 |
| No-alloc/Disable | `CACHE_MODE_DISABLE` | 不启用L2 Cache，对应GlobalTensor不会写入L2 Cache，可减少一次性数据对L2空间和GM写回带宽的占用。 | 只读取一次的大输入、流式搬运数据，或启用L2后实测性能下降的GlobalTensor。 |
| Persistent | `CACHE_MODE_PERSISTENT` | 启用L2 Cache驻留模式，用于提示特定GlobalTensor数据尽量保留在L2 Cache中。当前资料说明该驻留模式仍在开发中，暂不支持。 | 后续平台支持后，可用于需要长期驻留L2的热点数据。 |

相关接口说明见[SetL2CacheHint](../../../../api/SIMD-API/基础API/数据结构/LocalTensor和GlobalTensor定义/GlobalTensor/SetL2CacheHint.md)，CacheMode优化方法见[设置合理的L2 CacheMode](../../../算子实践参考/SIMD算子性能优化/内存访问/设置合理的L2-CacheMode.md)。

**内存对齐**

L2 Cache以Cache Line为单位加载数据，Cache Line大小为256B。MTE2执行GM到L1、L0A/L0B或UB的搬运时，满足Cache Line大小对齐通常有更好的搬运性能。这里的Cache Line对齐是访问路径上的缓存粒度要求，不等同于UB 32B、L1 32B、L0A/L0B 512B等片上存储单元自身的最小访问粒度。

**一致性**

在NPU架构版本2201中，L2 Cache是多核共享Cache，因此不会像DCache那样因为“每个核各自保存一份私有副本”而产生多核副本不一致。但L2仍然会因为缓存替换、GM写回和访问粒度带来一致性相关的性能和可见性问题：

- 当访问总量超过L2容量时，硬件会替换L2中的旧数据。由于Cache一致性要求，被替换的旧数据需要先写回GM，旧数据写回后，新数据才能进入L2。这个过程会占用GM带宽；如果大量只访问一次的数据进入L2，就可能挤出后续还会复用的数据。
- MTE2、MTE3、Scalar等单元访问GM时，需要先写入L2 Cache，再写入GM，如果多个核同时访问同一个连续512B范围内的GM地址时，硬件可能为保证一致性而串行处理请求，导致带宽下降。
- Scalar访问GM还会经过每核私有DCache。即使L2是共享的，DCache中的脏数据或旧数据仍然可能导致其他核看到的GM值不符合预期。

规避方法包括：对只访问一次的大流量数据使用`CACHE_MODE_DISABLE`，避免其进入L2并替换热点数据；调整多核访问顺序，避免多个核同时访问连续512B范围内的GM地址；涉及Scalar跨核读写GM时，使用`DataCacheCleanAndInvalid`或绕过DCache读写接口，并配合核间同步建立读写先后关系。

### 2.4 核内内存层级

AI Core内部包含显式管理的片上存储和Scalar使用的私有Cache。需要区分两类一致性：UB、L1、L0这类Local Memory不会自动与GM保持一致，需要通过显式搬运和同步保证数据顺序；DCache、ICache属于Cache层级，需要关注Cache Line、写策略和失效/写回行为。

#### 2.4.1 UB

UB（Unified Buffer）是Vector计算的输入、输出缓冲区，典型数据流是：

```text
读取：GM -> L2 Cache -> UB 
写出：UB -> L2 Cache -> GM
```
UB本身不是自动缓存GM的Cache。GM中的数据搬到UB后，如果GM随后被其他核改写，UB中的旧副本不会自动更新；反过来，Vector或Scalar写UB后，其他核也不能通过GM看到这份数据，只有通过MTE3把UB结果搬回GM后，GM侧才具备被其他核读取的基础。

UB一致性风险主要来自核内流水并行和地址重叠。例如MTE2尚未完成`GM -> UB`搬运时，Vector提前读取UB会读到未就绪数据；Vector尚未完成写UB时，MTE3提前搬出会把旧数据写回GM；多个MTE2指令写入重叠UB地址时，如果没有同步，后续数据顺序不可靠。通常优先使用TPipe/TQue或编译器自动同步；需要手动控制时，可参考[核内同步能力概述](../../../../api/SIMD-API/基础API/同步控制/核内同步/核内同步能力概述.md)和[PipeBarrier](<../../../../api/SIMD-API/基础API/同步控制/核内同步/PipeBarrier(ISASI).md>)。

#### 2.4.2 L1 Buffer

L1 Buffer是AIC内部较大的数据中转区，用于暂存Cube计算需要复用的数据。

典型Cube数据流是：

```text
GM -> L2 Cache -> L1 -> L0A/L0B -> Cube -> L0C -> FixPipe -> GM/L1
```

L1 Buffer的一致性问题主要来自显式搬运顺序。比如MTE2将GM数据搬到L1，MTE1再把L1数据搬到L0A/L0B供Cube计算；如果MTE1读取L1时MTE2尚未完成，Cube可能使用未就绪的数据。又如多个DataCopy写入重叠L1地址时，硬件不会主动报告重叠写入，也不保证重叠数据的写入顺序。处理方式是避免重叠写入，或在存在依赖时插入同流水`PipeBarrier`、跨流水`SetFlag/WaitFlag`等同步。矩阵数据搬入和重叠写同步可参考GM到L1、UB到L1等DataCopy接口约束。

#### 2.4.3 DCache

DCache是Scalar访问GM数据时使用的每核私有数据Cache。Scalar读取GM时，通常先查本核DCache；未命中时再经过L2 Cache访问GM。Scalar写出GM时，数据首先修改本核DCache，并将Cache Line标记为Dirty，GM不会立刻更新，而是该Cache Line被替换时，数据才会被写回GM。

典型数据流是：

```text
读取：GM -> L2 Cache -> DCache -> Scalar
写出：Scalar -> DCache -> L2 Cache -> GM
```

因为每个核都有自己的DCache单元用于缓存GM里的数据，DCache一致性风险最突出：
- 如果一个核通过Scalar写GM后，没有清理DCache，其他核从GM或自己的DCache读取时可能看到旧值；
- 多个核写同一条64B Cache Line中的不同字段时，经过DCache写回可能发生随机覆盖。

处理方式包括：

- 写后需要立刻对GM可见时，调用[DataCacheCleanAndInvalid](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)执行Clean和Invalid。
- 多核读写同一GM数据、且不希望经过DCache时，使用[ReadGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md>)或[WriteGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md>)。
- 多核写GM时，尽量让不同核写入地址至少相隔一个64B Cache Line，并结合核间同步保证先写后读。

#### 2.4.4 ICache

ICache是Scalar执行指令时使用的指令Cache。Scalar指令路径通常是：

```text
GM -> L2 Cache -> ICache -> Scalar
```

ICache缓存的是代码段，资料中将其归为只读Cache，因此通常不需要考虑多个核之间的数据一致性问题。它的主要注意点是指令加载效率：Scalar执行代码时优先从ICache取指，未命中时再经过L2 Cache和GM加载。开发者可以在需要时通过[ICachePreLoad](<../../../../api/SIMD-API/基础API/缓存控制/ICachePreLoad(ISASI).md>)预加载指令，降低后续取指开销。

#### 2.4.5 SSBuffer

SSBuffer（Scalar Shared Buffer）是AI Core内部的物理存储单元，用于同一AI Core内AIC/AIV之间的轻量级数据共享和参数传递。分离模式下，Cube Core和Vector Core按1:2通信时，可以选择使用SSBuffer在Cube Core和Vector Core的Scalar单元之间通信。SSBUF相关信息如下：

- 每个Core 为 1K SSBuf;
- 在MixCore 1:2 时，因为3个Core, 则占用3K SSBUF （地址范围： 0~3K-1； 地址空间在3个Core内可见)；
- 在MixCore 1:1 时，不支持 SSBUF
- 在AivOnly, AicOnly 时，每个Core 占用1K SSBUF （地址范围： 0~1K-1)
- SSBUF 支持 b64 / b32 读写。 不支持 atomic 读写； 不支持 mte 读写；

以UB到L1 Buffer搬运为例，Ascend 950PR/Ascend 950DT上可以通过ENABLE_CV_COMM_VIA_SSBUF选择搬运通路：配置为true时，使用SSBuffer进行通信，数据通过UB到L1 Buffer之间的硬件通道搬运；配置为false时，数据搬运到L1 Buffer需要经过GM，相关约束见[UBToL1连续数据搬运](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/矩阵计算（ISASI）/矩阵计算的搬入/矩阵数据搬入至L1-Buffer/UBToL1连续数据搬运（DataCopy）.md)。

### 2.5 内存访问和原子操作

原子操作用于解决多个执行单元或多个核并发更新同一GM地址时的读-改-写冲突。例如多个Scalar核同时对同一个GM计数器执行加1操作时，可能都读到同一个旧值，最终只写回一次累加结果。而原子操作会把读取旧值、计算新值、写回GM作为不可分割的更新过程，从而避免这类数据竞争。
```cpp
问题场景: 多个 Scalar 核同时修改同一 GM 地址

Core 0: LD X0, [counter]    → X0 = 100
Core 1: LD X0, [counter]    → X0 = 100  (都读到了 100)
Core 0: ADD X0, X0, #1      → X0 = 101
Core 1: ADD X0, X0, #1      → X0 = 101  (各自加 1)
Core 0: ST X0, [counter]    → [counter] = 101
Core 1: ST X0, [counter]    → [counter] = 101  (应该是 102!)

两次 +1, 但结果只 +1 了 → 数据竞争 (Race Condition)

原子操作解决:
Core 0: ATOM.add.u32 Xm, [counter], Xt  → [counter] = 101 (原子完成)
Core 1: ATOM.add.u32 Xm, [counter], Xt  → [counter] = 102 (原子完成)
```

NPU SIMD编程中常见的原子相关访问可以分为以下几类，数据搬运随路原子操作接口见[原子操作概述](../../../../api/SIMD-API/基础API/原子操作/原子操作概述.md)，Scalar原子操作接口见[AtomicAdd](../../../../api/SIMD-API/基础API/原子操作/AtomicAdd.md)、[AtomicCas](../../../../api/SIMD-API/基础API/原子操作/AtomicCas.md)、[AtomicExch](../../../../api/SIMD-API/基础API/原子操作/AtomicExch.md)等接口说明。

| 类型 | 典型接口 | 作用位置 | 主要用途 |
| --- | --- | --- | --- |
| 数据搬运随路原子操作 | `SetAtomicAdd`、`SetAtomicMax`、`SetAtomicMin`、`DisableDmaAtomic` | UB/L0C Buffer/L1 Buffer等搬运到GM的写出阶段 | 多核或多次搬运向同一GM区域累加、取最大值或取最小值。 |
| Scalar ATOM原子操作 | `AtomicAdd`、`AtomicCas`、`AtomicExch`等 | Scalar直接访问指定GM地址，返回旧值 | 计数器、自旋锁、需要根据旧值判断是否成功的同步原语。 |
| Scalar RED归约操作 | `AtomicAdd`、`AtomicMax`、`AtomicMin`等不返回旧值的归约形式 | Scalar直接访问指定GM地址，不返回旧值 | 不需要旧值的整数或浮点归约，减少返回值相关开销。 |

数据搬运随路原子操作的典型流程如下，其中`SetAtomicAdd`用于对后续目的地址为GM的数据搬运开启原子累加，`DisableDmaAtomic`用于关闭数据搬运随路原子操作功能，相关约束见[SetAtomicAdd](../../../../api/SIMD-API/基础API/原子操作/SetAtomicAdd.md)和[DisableDmaAtomic](../../../../api/SIMD-API/基础API/原子操作/DisableDmaAtomic.md)。

```text
1. 先将GM上的目标区域初始化为期望初值。
2. 调用SetAtomicAdd/SetAtomicMax/SetAtomicMin开启后续写GM搬运的原子操作。
3. 执行UB/L0C Buffer/L1 Buffer到GM的数据搬运。
4. 搬运完成后调用DisableDmaAtomic关闭原子状态，避免影响后续搬运。
```

原子操作只保证单个原子更新本身不会被其他更新打断，并不等价于“整个程序顺序确定”。这里的“单个原子更新”是指一次读-改-写过程不会被拆开，例如两个核同时对同一GM地址做原子加时，不会出现两个核都读到旧值、最终只保留一次加法结果的覆盖问题。但是，多个核、多个搬运指令或多个流水之间谁先到达GM，仍可能受实际调度和流水执行顺序影响；因此原子操作只能避免单次更新被打断，不能自动保证初始化、累加、读取结果等整个程序阶段都按源码顺序完成。确定性计算相关问题和同步方案见[关键特性说明](../../../../api/SIMD-API/基础API/原子操作/关键特性说明.md)。

使用原子操作需要特别注意以下几点一致性的问题：

- 开启原子操作前，GM目标区域不会自动清零。若原子累加依赖初值，开发者需要先初始化GM，并通过同步保证初始化写入已经完成，见[SetAtomicAdd](../../../../api/SIMD-API/基础API/原子操作/SetAtomicAdd.md)和[关键特性说明](../../../../api/SIMD-API/基础API/原子操作/关键特性说明.md)。
- `SetAtomicAdd`等接口会影响后续目的地址为GM的数据搬运，使用完成后应关闭原子状态，避免影响后续普通写GM搬运，见[DisableDmaAtomic](../../../../api/SIMD-API/基础API/原子操作/DisableDmaAtomic.md)。
- Scalar原子操作直接作用于GM地址，`AtomicAdd`、`AtomicCas`、`AtomicExch`等接口参数均使用`__gm__`指针，见[AtomicAdd](../../../../api/SIMD-API/基础API/原子操作/AtomicAdd.md)、[AtomicCas](../../../../api/SIMD-API/基础API/原子操作/AtomicCas.md)和[AtomicExch](../../../../api/SIMD-API/基础API/原子操作/AtomicExch.md)。SSBuffer不支持atomic读写，见[GetSsbufBaseAddr](../../../../api/SIMD-API/基础API/工具接口/系统资源与变量/GetSsbufBaseAddr.md)。
- Scalar访问GM时需要考虑DCache一致性。若通过Scalar访问的GM数据可能被其他核修改，或希望Scalar写GM后立刻对外可见，可以使用`DataCacheCleanAndInvalid`；若希望绕过DCache访问GM，可以使用`ReadGmByPassDCache`或`WriteGmByPassDCache`，见[系统缓存概述](../../../../api/SIMD-API/基础API/缓存控制/系统缓存概述.md)和[DataCacheCleanAndInvalid](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)。
- 浮点原子累加可能产生非确定性结果。原因是多条原子搬运的实际执行顺序可能变化，而浮点加法不满足结合律。需要确定性结果时，应在相关搬运之间插入核内同步或核间同步，保证执行顺序符合预期，见[关键特性说明](../../../../api/SIMD-API/基础API/原子操作/关键特性说明.md)。
- Scalar原子操作与MTE2/MTE3等搬运单元读写GM存在数据依赖时，需要按实际依赖插入同步。例如Scalar原子写GM后，后续MTE2从GM搬入UB，应确保Scalar操作完成后再启动搬运，见[AtomicAdd](../../../../api/SIMD-API/基础API/原子操作/AtomicAdd.md)。
- 如果用GM信号量做核间同步，且通过Scalar普通读写GM实现，需要同时考虑DCache一致性；可以使用`DataCacheCleanAndInvalid`，或使用绕过DCache的读写接口，见[关键特性说明](../../../../api/SIMD-API/基础API/原子操作/关键特性说明.md)。
- 原子操作和同步都会影响流水执行与访存路径。对性能敏感的场景，应优先减少不必要的原子操作和全量DCache刷新；`DataCacheCleanAndInvalid`的整DCache刷新模式耗时较大，性能敏感场景需慎用，见[DataCacheCleanAndInvalid](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)。

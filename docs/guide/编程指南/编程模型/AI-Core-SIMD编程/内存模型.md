# 内存模型

本文的主要目的是介绍NPU的内存层级、数据在不同层级之间的搬运行为及注意事项。后续内容先定义Overlap、一致性、Cache Line、内存对齐等基础概念，再结合[NPU架构版本3510](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)说明Global Memory（GM）、L2 Cache和核内存储单元之间的数据流向及编程约束。

## 1. 概念体系

本节定义后续讨论中使用的核心概念。

### 1.1 Overlap

Overlap（地址重叠）描述两个内存访问范围在字节地址区间上存在交集。例如，源操作数覆盖`[addr, addr + 128)`，目的操作数覆盖`[addr + 64, addr + 192)`，则两者部分重叠。

地址重叠会影响正确性，因为一次计算或搬运可能在读取源数据之前改写目的区域，导致后续读取到已经被覆盖的数据。Ascend C API对地址重叠有通用约束：

- 对于基础API的Tensor高维切分计算接口，单次迭代内源操作数与目的操作数如果重叠，通常必须100%完全重叠，不支持部分重叠。
- 多次迭代间通常不支持前序迭代的目的操作数与后序迭代的源操作数重叠。
- 具体API如果声明了额外约束，应以具体API说明为准。
- API文档未描述地址重叠约束时，应按“不支持地址重叠”处理。

相关约束见[通用地址重叠约束](../../../../api/SIMD-API/通用说明和约束.md#section668772811100)。

### 1.2 Cache Line

Cache Line是Cache操作的基本粒度。[系统缓存概述](../../../../api/SIMD-API/基础API/缓存控制/系统缓存概述.md)中说明，Invalid操作会将指定地址范围的Cache Line标记为无效，Clean操作会将缓存中被修改过的数据写回GM。[基本架构](../../高级编程/硬件实现/基本架构.md)中说明，DCache以Cache Line（64Byte）为单位加载，核外L2 Cache以Cache Line为单位加载，且Cache Line大小与硬件规格相关。

| Cache类型 | 资料中的粒度说明 | 数据一致性说明 |
| --- | --- | --- |
| L2 Cache | 以Cache Line为单位加载，大小随硬件规格不同可能为128/256/512Byte等 | 用于缓存频繁访问的数据和指令，减少对GM的读写。 |
| ICache | 用于缓存Scalar单元最近使用或频繁使用的指令；[基本架构](../../高级编程/硬件实现/基本架构.md)中说明其以2K为单位加载 | 资料中将ICache归为只读Cache。 |
| DCache | 以Cache Line（64Byte）为单位加载 | DCache为多核独立缓存，需要考虑多核间数据一致性。 |

Cache Line带来的典型风险来自DCache的读写粒度。[DataCacheCleanAndInvalid调用示例3](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md#example3_multi_core)说明，多核操作虽然不在同一个地址，但在同一个Cache Line时会出现数据随机覆盖；[WriteGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md>)和[ReadGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md>)也说明，当多个核写入的数据落在同一条Cache Line内时，经过DCache的读写会以64B为粒度，可能引发多核数据随机覆盖问题。

### 1.3 一致性

本文围绕资料中明确涉及的两类一致性相关问题展开：核内流水访问顺序和Cache一致性。

**核内流水访问顺序**关注不同执行单元访问同一片Local Memory时的先后关系。[核内同步能力概述](../../../../api/SIMD-API/基础API/同步控制/核内同步/核内同步能力概述.md)说明，AI Core内部执行单元（如MTE2搬运单元、Vector计算单元等）以异步并行方式运行，若访问同一片Local Memory，需要同步机制控制访问时序。常见例子包括：

- MTE2把GM数据搬入UB后，Vector必须等搬入完成后再读取UB，否则可能读到未完成搬运的数据。
- Vector写UB后，MTE3必须等计算完成后再把UB搬回GM，否则可能搬出旧数据或部分结果。
这类问题通常通过自动同步、`SetFlag/WaitFlag`或`PipeBarrier`处理。

**Cache一致性**是指某个地址的数据被某个核的Cache修改了，GM或其他核看到的是新值还是旧值。关注同一地址或同一Cache Line在不同缓存副本之间的值是否一致。在NPU SIMD编程中，最典型的例子是DCache：

- Scalar通过`GlobalTensor::SetValue`写GM时，数据会先写入本核DCache，GM不会立刻更新；如果需要立即写出到Global Memory，需要在调用该接口后再调用`DataCacheCleanAndInvalid`。
- 多个核通过DCache写同一条64B Cache Line时，可能出现随机覆盖。相关示例见[DataCacheCleanAndInvalid调用示例3](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md#example3_multi_core)。

此类场景可考虑让不同的核写入地址至少相隔一个Cache Line，或使用绕过DCache的读写接口，相关示例见[DataCacheCleanAndInvalid调用示例3](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md#example3_multi_core)，绕过DCache接口见[ReadGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md>)和[WriteGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md>)。

### 1.4 内存对齐

内存对齐描述访问起始地址、数据长度或数据块跨度是否满足硬件粒度要求。对齐要求来自两类约束：一类是存储单元自身的最小访问粒度，另一类是数据搬运路径为了获得更好带宽而推荐的访问粒度。下表以[NPU架构版本3510](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)中的最小访问粒度和通用对齐说明为准。

| 存储单元 | 对齐要求 | 不满足时的影响 | 处理建议 |
| --- | --- | --- | --- |
| GM | 无对齐要求；性能推荐[GM地址尽量512B对齐](../../../算子实践参考/SIMD算子性能优化/内存访问/GM地址尽量512B对齐.md) | 多个请求落入同一个连续512B范围时，会因数据一致性要求被串行处理，影响数据搬运效率。 | Tensor基址和偏移尽量保持512B对齐；具体API有额外约束时，以具体API说明为准。 |
| L2 Cache | 以Cache Line为单位加载，Cache Line大小与硬件规格相关 | 访问总量超出L2 Cache容量时，会触发数据替换。 | 重复读取的数据尽量缓存在L2 Cache；只访问一次的数据可结合`SetL2CacheHint`设置合适的CacheMode。 |
| UB | 32Byte对齐；搬运到UB的数据大小需要按DataBlock对齐 | 搬运到Unified Buffer的数据大小需要按照DataBlock对齐。 | 单个数据块长度不是32B对齐时，可使用Loop模式中的Padding或Compact模式，具体约束以DataCopyPad等接口说明为准。 |
| L1 Buffer | 32Byte对齐；搬运到后续矩阵计算单元时还需要满足分形要求 | 其他存储单元的数据搬运必须按分形要求进行；从L1 Buffer搬运到L0A Buffer时，如果L1 Buffer剩余大小不足1个分形，则硬件执行中会出现异常。 | L1 Buffer缓存推荐使用FRACTAL_NZ格式；涉及重叠写入时，在相关DataCopy之间插入`PipeBarrier`。 |
| L0A/L0B Buffer | 512Byte对齐 | 数据搬运必须按分形要求进行。 | 按矩阵计算接口要求准备FRACTAL_NZ/FRACTAL_ZN等格式，并保证搬运大小按分形对齐。 |
| L0C Buffer | 64Byte对齐 | 具体搬出接口可能有目标地址、格式、搬运大小等约束。 | 按L0C到GM、L0C到UB、L0C到L1等具体搬出接口要求设置。 |
| BiasTable Buffer | 64Byte对齐 | 具体矩阵计算或FixPipe接口可能有额外约束。 | 按具体接口要求准备Bias数据。 |
| Fixpipe Buffer | 64Byte对齐 | 具体FixPipe搬出接口可能有额外约束。 | 按FixPipe搬出接口要求设置地址、格式、量化参数和同步关系。 |

## 2. 硬件架构与内存层级

### 2.1 内存层级与数据流

[NPU架构版本3510](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)中，AI Core分为AIC和AIV两个独立的核，分别用于矩阵计算和向量计算。AIC核与AIV核配比为1：2。每个核都有自己的Scalar单元，能独立加载自己的代码段。该架构增加了`L0C Buffer -> Unified Buffer`、`Unified Buffer <-> L1 Buffer`的数据通路，新增SIMD Register File、SIMT相关硬件单元和用于AIC/AIV核间通信的SSBuffer。内存层级图如下：

<img src="../../../figures/SIMD-Reg矢量计算内存层级_内存模型.png" alt="SIMD-Reg矢量计算内存层级" width="600px">

结合架构资料和缓存资料，本文后续重点讨论以下数据通路：

- Reg矢量计算相关路径：数据从Unified Buffer搬运到SIMD Register File进行计算，中间结果可以保留在寄存器中继续计算。
- Cube相关路径：Cube计算单元可访问L0A Buffer、L0B Buffer和L0C Buffer；3510架构增加了`L0C Buffer -> Unified Buffer`、`Unified Buffer <-> L1 Buffer`的数据通路。
- SIMT访存路径：SIMT访问GM需要经过SIMT DCache中转，SIMT对外访存以128B为粒度，SIMT DCache复用UB作为Cache Line。
- Scalar读GM数据路径：通过Scalar单元读取GM时，资料说明优先从DCache读取；DCache未命中时再读取L2 Cache，L2 Cache未命中时再从GM加载。
- Scalar读GM指令路径：通过Scalar单元读取GM指令时，资料说明优先从ICache读取；ICache未命中时再读取L2 Cache，L2 Cache未命中时再从GM加载。
- AIC与AIV之间的核间通信可以通过SSBuffer完成。

### 2.2 GM

GM是AI Core外部的全局内存空间，用于承载Kernel输入、输出、Workspace、Tiling等数据，也是不同核之间交换数据的基础位置。向量计算通常围绕UB组织输入和输出数据，Cube计算的数据主要经过L1、L0A/L0B、L0C等核内存储流动；GM中的数据需要通过MTE或FixPipe等搬运单元进入或离开相关存储单元。

GM的接口级对齐要求通常较宽松，[通用说明和约束](../../../../api/SIMD-API/通用说明和约束.md)中将GM描述为“无对齐要求”。但从性能角度看，GM地址对齐仍然很重要：

- 从GM向核内存储搬运数据时，GM地址尽量保持512B对齐，可以更有效发挥带宽，相关说明见[GM地址尽量512B对齐](../../../算子实践参考/SIMD算子性能优化/内存访问/GM地址尽量512B对齐.md)。
- MTE2、MTE3、Scalar等单元访问GM时，地址请求会按照512B粒度对齐后处理。多个核或多个请求同时访问同一个连续512B范围内的GM地址时，由于一致性要求，相关请求可能被串行处理，降低搬运效率。相关说明见[避免同地址访问](../../../算子实践参考/SIMD算子性能优化/内存访问/避免同地址访问.md)。

### 2.3 L2 Cache

L2 Cache位于搬运单元、Scalar单元和GM之间，用于缓存频繁访问的数据和指令，减少对GM的直接读写。

- 通过MTE2读取GM时，硬件优先从L2 Cache读取；L2 Cache未命中时，再从GM加载并更新到L2 Cache。
- 通过Scalar读取GM数据时，访问路径通常是优先从DCache读取，DCache未命中时再读取L2 Cache，L2 Cache未命中时，再从GM加载并更新到L2 Cache。
- 通过Scalar读取GM指令时，访问路径通常是优先从ICache读取，ICache未命中时再读取L2 Cache，L2 Cache未命中时，再从GM加载并更新到L2 Cache。

**访问模式**

Ascend C通过GlobalTensor的`SetL2CacheHint`接口设置L2 Cache模式。若不调用该接口，默认使用`CACHE_MODE_NORMAL`。

| 模式 | 枚举 | 行为说明 | 典型使用场景 |
| --- | --- | --- | --- |
| Normal | `CACHE_MODE_NORMAL` | 启用L2 Cache。资料说明通常情况下L2 Cache可采用该模式运行；当L2 Cache容量耗尽时，会触发数据置换机制。 | 默认模式；适合需要缓存到L2 Cache的数据。 |
| Disable | `CACHE_MODE_DISABLE` | 不启用L2 Cache，对应GlobalTensor不会写入L2 Cache。 | 特定GlobalTensor启用L2 Cache后实测性能下降，或该GlobalTensor仅执行单次读取操作时，可考虑关闭。 |
| Persistent | `CACHE_MODE_PERSISTENT` | 启用L2 Cache驻留模式。当前资料说明该驻留模式仍在开发中，暂不支持，计划于Ascend 950PR/Ascend 950DT产品上提供支持。 | 后续平台支持后，可用于需要保留在L2 Cache中的数据。 |

相关接口说明见[SetL2CacheHint](../../../../api/SIMD-API/基础API/数据结构/LocalTensor和GlobalTensor定义/GlobalTensor/SetL2CacheHint.md)，CacheMode优化方法见[设置合理的L2 CacheMode](../../../算子实践参考/SIMD算子性能优化/内存访问/设置合理的L2-CacheMode.md)。

**内存对齐**

L2 Cache以Cache Line为单位加载数据，Cache Line大小与硬件规格相关。[基本架构](../../高级编程/硬件实现/基本架构.md)中说明，GM到L1、L0A/L0B通路满足Cache Line大小对齐时性能更优，GM到UB通路基于Cache Line大小搬运性能更优。这里的Cache Line对齐是访问路径上的缓存粒度要求，不等同于UB 32B、L1 32B、L0A/L0B 512B等核内存储单元自身的最小访问粒度。

**一致性**

L2 Cache相关注意事项主要来自缓存替换和GM访问粒度：

- 当访问总量超过L2容量时，AI Core会对L2 Cache进行数据替换。资料说明，由于Cache一致性要求，替换过程中旧数据需要先写回GM，旧数据写回后新的数据才能进入L2 Cache，该过程会占用GM带宽。
- MTE2、MTE3、Scalar等单元访问GM时，地址请求会按照512字节粒度对齐后处理；当同时访问的GM地址处于连续512字节范围内时，多个请求会因数据一致性原因被串行处理，影响数据搬运效率。
- Scalar访问GM数据还会经过DCache。涉及Scalar跨核读写GM时，需要同时考虑DCache一致性。

规避方法包括：对只访问一次的大流量数据使用`CACHE_MODE_DISABLE`，避免其进入L2并替换热点数据；调整多个核的访问顺序，避免多个核同时访问连续512B范围内的GM地址；涉及Scalar跨核读写GM时，使用`DataCacheCleanAndInvalid`或绕过DCache读写接口，并配合核间同步建立读写先后关系。

### 2.4 核内内存层级

AI Core内部包含显式管理的核内存储和Scalar使用的Cache。UB、L1、L0这类核内存储主要通过显式搬运和同步控制数据顺序；DCache、ICache属于Cache层级，需要关注Cache Line、写策略和失效/写回行为。

#### 2.4.1 UB

UB（Unified Buffer）是Vector计算的输入、输出缓冲区，UB逻辑架构和内存结构可参考[Vector逻辑架构](../../../../api/SIMD-API/基础API/Memory矢量计算/Vector逻辑架构/Vector逻辑架构.md)。典型数据流是：

```text
读取：GM -> L2 Cache -> UB
写出：UB -> L2 Cache -> GM
```
UB相关一致性问题主要来自核内流水并行和地址重叠。例如MTE2尚未完成`GM -> UB`搬运时，Vector提前读取UB会读到未就绪数据；Vector尚未完成写UB时，MTE3提前搬出会把旧数据写回GM。多个DataCopy指令目的地址存在重叠时，需要通过`PipeBarrier`插入同步指令，保证多个DataCopy指令串行化，防止出现异常数据。通常优先使用TPipe/TQue或编译器自动同步；需要手动控制时，可参考[核内同步能力概述](../../../../api/SIMD-API/基础API/同步控制/核内同步/核内同步能力概述.md)和[PipeBarrier](<../../../../api/SIMD-API/基础API/同步控制/核内同步/PipeBarrier(ISASI).md>)。

#### 2.4.2 L1 Buffer

L1 Buffer是AIC内部较大的数据中转区，用于暂存Cube计算需要复用的数据。L1 Buffer以及L0A/L0B Buffer的内存结构可参考[L1 Buffer内存结构介绍](../../../../api/SIMD-API/基础API/矩阵计算（ISASI）/矩阵计算的搬入/L1-L0A-B内存结构介绍.md)。

典型Cube数据流是：

```text
GM -> L2 Cache -> L1 -> L0A/L0B -> Cube -> L0C -> FixPipe -> GM/L1
```

L1 Buffer的一致性问题主要来自显式搬运顺序。比如MTE2将GM数据搬到L1，MTE1再把L1数据搬到L0A/L0B供Cube计算；如果MTE1读取L1时MTE2尚未完成，Cube可能使用未就绪的数据。又如多个DataCopy写入重叠L1地址时，硬件不会主动报告重叠写入，也不保证重叠数据的写入顺序。处理方式是避免重叠写入，或在存在依赖时插入同流水`PipeBarrier`、跨流水`SetFlag/WaitFlag`等同步。矩阵数据搬入和重叠写同步可参考GM到L1、UB到L1等DataCopy接口约束。

#### 2.4.3 DCache

DCache是Scalar访问GM数据时使用的每核私有数据Cache。Scalar读取GM时，通常先查本核DCache；未命中时再经过L2 Cache访问GM。通过`GlobalTensor::SetValue`写GM时，资料说明该操作首先改写每个AI Core内部的DCache，不会立刻写出到Global Memory，后续写出时以Cache Line（64B）为单位。

典型数据流是：

```text
读取：GM -> L2 Cache -> DCache -> Scalar
SetValue写GM：先改写DCache，后续按64B Cache Line写出到Global Memory
```

因为每个核都有自己的DCache单元用于缓存GM里的数据，DCache一致性风险最突出：
- 如果一个核通过Scalar写GM后，没有清理DCache，其他核从GM或自己的DCache读取时可能看到旧值；
- 多个核写同一条64B Cache Line中的不同字段时，经过DCache写回可能发生随机覆盖。

处理方式包括：

- 写后需要立刻对GM可见时，调用[DataCacheCleanAndInvalid](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)执行Clean和Invalid。
- 多个核读写同一GM数据、且不希望经过DCache时，使用[ReadGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md>)或[WriteGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md>)。
- 多个核写GM时，尽量让不同的核写入地址至少相隔一个64B Cache Line，并结合核间同步保证先写后读。

#### 2.4.4 ICache

ICache是Scalar执行指令时使用的指令Cache。Scalar指令路径通常是：

```text
GM -> L2 Cache -> ICache -> Scalar
```

ICache缓存的是代码段，资料中将其归为只读Cache，因此通常不需要考虑多个核之间的数据一致性问题。它的主要注意点是指令加载效率：Scalar执行代码时优先从ICache取指，未命中时再经过L2 Cache和GM加载。开发者可以在需要时通过[ICachePreLoad](<../../../../api/SIMD-API/基础API/缓存控制/ICachePreLoad(ISASI).md>)预加载指令，降低后续取指开销。

#### 2.4.5 SSBuffer

SSBuffer（Scalar Shared Buffer）是AI Core内部的物理存储单元，用于AIC和AIV的核间通信。`GetSsbufBaseAddr`接口用于获取SSBuffer基地址。资料说明，目前SSBuffer的大小为3KB；每个核在非MIX模式下运行时，可以独立占用1KB空间（AIC、AIV0、AIV1各占据1KB），在MIX模式下运行时共享整个3KB空间（AIC:AIV = 1:2）。访问SSBuffer时需要注意：

- SSBuffer中存在脏数据，读取时数据不保证全为0。
- AIC和AIV启动不同任务时，不能访问SSBuffer。
- 访问超过最末端的地址存在异常。
- SSBuffer只支持通过读写指令32字节的对齐访问。

以UB到L1 Buffer搬运为例，[适用版本：Ascend 950PR/Ascend 950DT] 可以通过`ENABLE_CV_COMM_VIA_SSBUF`选择搬运通路：配置为`true`时，使用SSBuffer进行通信，数据通过UB到L1 Buffer之间的硬件通道搬运；配置为`false`时，数据搬运到L1 Buffer需要经过GM，相关约束见[UBToL1连续数据搬运](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/矩阵计算（ISASI）/矩阵计算的搬入/矩阵数据搬入至L1-Buffer/UBToL1连续数据搬运（DataCopy）.md)。

### 2.5 内存访问和原子操作

原子操作用于在GM地址上执行带原子语义的更新。NPU SIMD编程中常见的原子相关访问可以分为数据搬运随路原子操作和Scalar原子操作。数据搬运随路原子操作接口见[原子操作概述](../../../../api/SIMD-API/基础API/原子操作/原子操作概述.md)，Scalar原子操作接口见[AtomicAdd](../../../../api/SIMD-API/基础API/原子操作/AtomicAdd.md)、[AtomicCas](../../../../api/SIMD-API/基础API/原子操作/AtomicCas.md)、[AtomicExch](../../../../api/SIMD-API/基础API/原子操作/AtomicExch.md)等接口说明。

| 类型 | 典型接口 | 作用位置 | 主要用途 |
| --- | --- | --- | --- |
| 数据搬运随路原子操作 | `SetAtomicAdd`、`SetAtomicMax`、`SetAtomicMin`、`DisableDmaAtomic` | 后续目的地址为GM的数据搬运 | 将待拷贝内容与GM已有内容做求和、取最大值或取最小值后写入GM；使用完成后通过`DisableDmaAtomic`关闭原子状态。 |
| Scalar原子操作 | `AtomicAdd`、`AtomicCas`、`AtomicExch`等 | Scalar直接访问指定GM地址 | 在指定GM地址上执行原子加、原子比较交换、原子交换等操作，接口返回GM地址上做原子操作前的数据。 |

## 3. 总结

本文主要介绍了NPU的内存单元、各单元上不同操作对内存一致性的影响、以及如何保证NPU上的“内存正确性”，使用者需要选择合适的存储层级、明确的数据搬运路径、满足约束的地址和粒度、必要的同步控制以及Cache一致性处理共同保证内存正确。

# 内存模型

本文主要介绍 NPU 的内存层级、数据在不同层级间的搬运方式及注意事项。文中先定义 Overlap、Alias、一致性、Cache Line、内存对齐等基础概念，然后结合[NPU架构版本3510](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)说明Global Memory（GM）、L2 Cache和核内存储单元之间的数据流向及编程约束。

## 1. 概念体系

### 1.1 Overlap

Overlap（地址重叠）指两个内存访问范围在字节地址区间上存在交集。例如，源操作数覆盖`[addr, addr + 128)`，目的操作数覆盖`[addr + 64, addr + 192)`，则两者地址重叠。

地址重叠会影响正确性，因为一次计算或搬运可能改写目的区域，导致后续读取源数据读取到已经被覆盖的数据。Ascend C API对地址重叠有通用约束：

- 对于基础API的Tensor高维切分计算接口，单次迭代内源操作数与目的操作数如果重叠，通常必须100%完全重叠，不支持部分重叠。
- 多次迭代间通常不支持前序迭代的目的操作数与后序迭代的源操作数重叠。
- 具体API如果声明了额外约束，应以具体API说明为准。
- API文档未描述地址重叠约束时，应按"不支持地址重叠"处理。

相关约束见[通用地址重叠约束](../../../../api/SIMD-API/通用说明和约束.md#section668772811100)。

### 1.2 Alias

Alias（别名）描述两个不同的名字指向同一段物理内存。类似于浅拷贝，两个对象指向同一个地址，修改其中一个对象的值会影响另一个对象的值。Alias本身不一定错误，但开发者使用时需要谨慎。

### 1.3 Cache Line

Cache Line是Cache加载、失效、写回的最小操作粒度。例如访问GM内存时，会将GM里一个Cache Line长度内相邻的数据加载到L2 Cache缓存，利用空间局部性提高访问效率。Cache Line是硬件真正搬入、标记、替换和写回缓存数据的最小粒度，直接影响性能和一致性。NPU架构版本3510上Cache单元信息如下：

| 存储单元 | 位置 | 数据一致性说明 | Cache Line大小 |
| --- | --- | --- | --- |
| L2 Cache | 核外共享缓存 | 多个核共享，不考虑多个核之间的Cache副本不一致问题 | 根据硬件规格不同，Cache Line大小不同（3510版本Cache Line支持128/256/512B，2201版本Cache Line支持256B）|
| ICache | Scalar取指缓存 | 只读，不考虑多个核之间的数据不一致问题 | 2KB |
| DCache | Scalar数据缓存 | 每个核独立缓存，需要考虑多个核之间的数据一致性问题 | 64B |

Cache Line带来的典型风险是：加载和写回时通常以整条Cache Line为粒度，因此当多个核操作不同地址但恰好落在同一条Cache Line内时，可能出现数据随机覆盖。例如，DCache的Cache Line为64B，读写操作以64B为单位。假设GM上有一批数据，实际存储地址落在同一段64B范围内，多个核分别将这段数据读取到各自的DCache中，各自修改不同的地址，写回GM时以64B为粒度，就会把当前核修改的数据与旧副本一并写回GM，从而覆盖其他核已更新的数据。

### 1.4 一致性

一致性指多个执行单元或多个核对同一数据并发读写时，各执行单元看到的数据是否符合程序预期。本文将一致性分成两个层面：内存一致性和Cache一致性。

**内存一致性**是指生产者已经写了数据，消费者什么时候、以什么顺序能看到这些写入，即关注读写操作的顺序和可见性。在NPU SIMD编程中，常见例子包括：

- MTE2把GM数据搬入UB后，Vector必须等搬入完成后再读取UB，否则可能读到未完成搬运的数据。
- Vector写UB后，MTE3必须等计算完成后再把UB搬回GM，否则可能搬出旧数据或部分结果。
- AIC将L0C结果通过FixPipe搬到GM后，AIV如果要从GM读取这批结果，需要先通过核间同步确认写入已经完成。

这类问题通常通过自动同步、`SetFlag/WaitFlag`、`PipeBarrier`或核间同步接口处理。核内同步的详细说明见[核内同步能力概述](../../../../api/SIMD-API/基础API/同步控制/核内同步/核内同步能力概述.md)。

**Cache一致性**是指某个地址的数据被某个核的Cache修改后，GM或其他核看到的是新值还是旧值，即关注同一地址或同一Cache Line在不同缓存副本之间的值是否一致。在NPU SIMD编程中，最典型的例子是DCache：

- Scalar通过`GlobalTensor::SetValue`写GM时，数据会先写入本核DCache，GM不会立刻更新；其他核直接读GM时可能读到旧值。
- 多个核通过DCache写同一条64B Cache Line中的不同字段时，后续写回GM的粒度仍然是Cache Line，可能出现随机覆盖。例如两个核的DCache单元都缓存了GM的同一条64B Cache Line：[0x1000, 0x1040)，核0修改0x1000处，核1修改0x1008处；后续核0先写回整条64B，核1后写回整条64B，最终GM里可能只保留核1的修改，核0对0x1000的修改被核1那条旧副本覆盖。

此类场景可考虑让不同核的写入地址至少相隔一个Cache Line，或使用绕过DCache的读写接口，相关示例见[DataCacheCleanAndInvalid调用示例3](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md#example3_multi_core)，绕过DCache接口见[ReadGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md>)和[WriteGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md>)。

### 1.5 内存对齐

内存对齐描述访问起始地址、数据长度或数据块跨度是否与硬件访问粒度匹配。NPU中的数据搬运和计算通常按DataBlock、Cache Line或矩阵分形块等固定粒度处理数据。保持对齐能避免硬件对不对齐数据做额外拆分或补齐，减少无效搬运。下表给出常见存储单元的对齐要求。

| 存储单元 | 粒度或对齐说明 |
| --- | --- | 
| GM | 通用说明中GM无强制地址对齐要求；性能优化中建议GM地址尽量512B对齐。 |
| UB | UB/LocalTensor起始地址通常要求32Byte对齐；搬运到UB的数据大小需要按DataBlock（32Byte）对齐。 | 
| L1 Buffer | L1 Buffer通常要求32Byte对齐；作为矩阵计算输入时，还需要满足数据分形和搬运接口的格式约束。 | 
| L0A/L0B Buffer | L0A/L0B Buffer通常要求512Byte对齐。 | 
| L0C Buffer | L0C Buffer通常要求64Byte对齐。 | 
| BiasTable Buffer | BiasTable Buffer通常要求64Byte对齐。 | 
| Fixpipe Buffer | Fixpipe Buffer通常要求64Byte对齐。 | 

## 2. 硬件架构与内存层级

### 2.1 内存层级与数据流

[NPU架构版本3510](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)中，AI Core分为AIC和AIV两种独立的核，分别用于矩阵计算和向量计算。AIC核与AIV核配比为1:2。每个核都有自己的Scalar单元，能独立加载自己的代码段。3510架构的内存层级包括GM、共享L2 Cache、核内存储、寄存器层级、Scalar私有Cache、SIMT寄存器和SSBuffer通信空间。内存层级图如下：

<img src="../../../figures/SIMD-Reg矢量计算内存层级_内存模型.png" alt="SIMD-Reg矢量计算内存层级" width="600px">

NPU上各储存单元的硬件架构图见[3510架构图](../../高级编程/硬件实现/架构规格/NPU架构版本3510.md)，各个内存层级典型的数据流如下：

- Reg矢量计算路径：`GM -> L2 Cache -> UB -> SIMD Register File -> Vector -> SIMD Register File -> UB -> L2 Cache -> GM`。
- Cube路径：`GM -> L2 Cache -> L1 -> L0A/L0B -> Cube -> L0C -> FixPipe -> GM/L1`；3510架构里需要回到AIV侧继续处理的数据，也可以经新增的`L0C Buffer -> UB`或`L1 Buffer <-> UB`通路进入UB。
- SIMT访存路径：`GM -> L2 Cache -> SIMT DCache -> SIMT Register File/通用寄存器`，SIMT DCache复用UB作为存储空间。
- Scalar数据路径：`GM -> L2 Cache -> DCache -> Scalar`，Scalar写GM时为`Scalar -> DCache -> L2 Cache -> GM`。
- Scalar指令路径：`GM -> L2 Cache -> ICache -> Scalar`。
- AIC与AIV之间的核间通信可以通过SSBuffer或者GM完成。

### 2.2 GM

GM是AI Core外部的全局内存空间，用于承载Kernel输入、输出等数据，也是AIC、AIV以及不同AI Core之间交换数据的基础位置。AI Core内部的计算单元通常不会直接在GM上完成向量或矩阵计算，GM中的数据需要通过MTE搬运单元进入核内存储单元，计算单元完成计算之后再把计算结果从核内存储单元搬回GM。

GM的接口级对齐要求通常较宽松，[通用说明和约束](../../../../api/SIMD-API/通用说明和约束.md)中记录GM"无对齐要求"。但从性能角度看，GM地址对齐仍然很重要：

- 从GM向核内存储搬运数据时，GM地址尽量保持512B对齐，可以更有效发挥带宽，相关说明见[GM地址尽量512B对齐](../../../算子实践参考/SIMD算子性能优化/内存访问/GM地址尽量512B对齐.md)。
- MTE2、MTE3、Scalar等单元访问GM时，地址请求会按照512B粒度对齐后处理。多个核或多个请求同时访问同一个连续512B范围内的GM地址时，由于一致性要求，相关请求可能被串行处理，降低搬运效率。相关说明见[避免同地址访问](../../../算子实践参考/SIMD算子性能优化/内存访问/避免同地址访问.md)。

### 2.3 L2 Cache

L2 Cache位于核内内存和GM之间，用于缓存频繁访问的数据和指令，减少对GM的直接读写。

- 通过MTE2读取GM时，硬件优先从L2 Cache读取；L2 Cache未命中时，再从GM加载并更新到L2 Cache。
- 通过Scalar读取GM数据时，访问路径通常是优先从DCache读取，DCache未命中时再读取L2 Cache，L2 Cache未命中时，再从GM加载并更新到L2 Cache。
- 通过Scalar读取GM指令时，访问路径通常是优先从ICache读取，ICache未命中时再读取L2 Cache，L2 Cache未命中时，再从GM加载并更新到L2 Cache。

**访问模式**

SetL2CacheHint 接口设置 GlobalTensor 的 L2 Cache 模式；不调用时默认为 CACHE_MODE_NORMAL，即启用 L2 Cache。

| 模式 | 枚举 | 行为说明 | 典型使用场景 |
| --- | --- | --- | --- |
| Normal | `CACHE_MODE_NORMAL` | 启用L2 Cache。把GlobalTensor缓存到L2，如果后续再次访问同一数据，命中L2可减少GM读写。但当L2容量被用完时，会替换之前已缓存的数据。 | 默认模式；适合输入会被重复读取、输出后续可能被复用的场景。 |
| No-alloc/Disable | `CACHE_MODE_DISABLE` | 不启用L2 Cache，对应GlobalTensor不会写入L2 Cache，可减少一次性数据对L2空间和GM写回带宽的占用。 | 只读取一次的大输入、流式搬运数据，或启用L2后实测性能下降的GlobalTensor。 |
| Persistent | `CACHE_MODE_PERSISTENT` | 启用L2 Cache驻留模式，用于提示特定GlobalTensor数据尽量保留在L2 Cache中。该驻留模式仍在开发中，暂不支持。 | 预研中，可用于需要长期驻留L2的热点数据。 |

相关接口说明见[SetL2CacheHint](../../../../api/SIMD-API/基础API/数据结构/LocalTensor和GlobalTensor定义/GlobalTensor/SetL2CacheHint.md)，CacheMode优化方法见[设置合理的L2 CacheMode](../../../算子实践参考/SIMD算子性能优化/内存访问/设置合理的L2-CacheMode.md)。

**内存对齐**

L2 Cache以Cache Line为单位加载数据。从GM上搬运数据时，会将相邻的数据作为一个Cache Line加载到L2 Cache，GM上待搬运的数据满足Cache Line大小对齐通常有更好的搬运性能，如果数据跨两个Cache Line，会触发多次缓存访问。

**一致性**

L2 Cache会因为缓存替换、直写GM和访问粒度方面带来一致性问题：

- 当访问总量超过L2容量时，硬件会替换L2中的旧数据。由于Cache一致性要求，被替换的旧数据需要先写入GM，旧数据写入后，新数据才能进入L2。这个过程会占用GM带宽；如果大量只访问一次的数据进入L2，就可能挤出后续还会复用的数据。
- MTE2、MTE3、Scalar等单元访问GM时，需要先写入L2 Cache，再写入GM，如果多个核同时访问同一个连续512B范围内的GM地址时，硬件可能为保证一致性而串行处理请求，导致带宽下降。
- Scalar访问GM还会经过每核私有DCache。即使L2是共享的，DCache中的脏数据或旧数据仍然可能导致其他核看到的GM值不符合预期。

规避方法包括：对只访问一次的大流量数据使用`CACHE_MODE_DISABLE`，避免其进入L2并替换热点数据；调整多个核的访问顺序，避免多个核同时访问连续512B范围内的GM地址；涉及Scalar跨核读写GM时，使用`DataCacheCleanAndInvalid`或绕过DCache读写接口，并配合核间同步建立读写先后关系。

### 2.4 核内内存层级

AI Core内部包含核内存储UB、L1、L0等和Scalar使用的Cache。需要区分两类一致性：UB、L1、L0这类核内存储不会自动与GM保持一致，需要通过显式搬运和同步保证数据顺序；DCache、ICache属于Cache层级，需要关注Cache Line、写策略和失效/写回行为。

#### 2.4.1 UB

UB（Unified Buffer）是Vector计算的输入、输出缓冲区，UB内存结构和bank可参考[UB内存架构](../../../../api/SIMD-API/基础API/Memory矢量计算/Vector逻辑架构/Vector逻辑架构.md#unified-buffer介绍)。典型数据流是：

```text
读取：GM -> L2 Cache -> UB
写出：UB -> L2 Cache -> GM
```
GM中的数据搬到UB后，如果GM随后被其他核改写，UB中的旧副本不会自动更新；反过来，Vector或Scalar写UB后，其他核也不能通过GM看到这份数据，只有通过MTE3把UB结果搬回GM后，GM侧才具备被其他核读取的基础。

 UB相关一致性问题主要来自核内流水并行和地址重叠。例如MTE2尚未完成`GM -> UB`搬运时，Vector提前读取UB会读到未就绪数据；Vector尚未完成写UB时，MTE3提前搬出会把旧数据写回GM。多个DataCopy指令目的地址存在重叠时，需要通过`PipeBarrier`插入同步指令，保证多个DataCopy指令串行化，防止出现异常数据。通常优先使用TPipe/TQue或编译器自动同步；需要手动控制时，可参考[核内同步能力概述](../../../../api/SIMD-API/基础API/同步控制/核内同步/核内同步能力概述.md)和[PipeBarrier](<../../../../api/SIMD-API/基础API/同步控制/核内同步/PipeBarrier(ISASI).md>)。

#### 2.4.2 L1 Buffer

L1 Buffer是AIC内部较大的数据中转区，用于暂存Cube计算需要复用的数据。L1 Buffer的内存结构和bank可参考[L1 Buffer内存结构介绍](../../../../api/SIMD-API/基础API/矩阵计算（ISASI）/矩阵计算的搬入/L1-L0A-B内存结构介绍.md)。

典型Cube数据流是：

```text
GM -> L2 Cache -> L1 -> L0A/L0B -> Cube -> L0C -> FixPipe -> GM/L1
```

 L1 Buffer的一致性问题主要来自显式搬运顺序。例如MTE2将GM数据搬到L1，MTE1再把L1数据搬到L0A/L0B供Cube计算；如果MTE1读取L1时MTE2尚未完成，Cube可能使用未就绪的数据。多个DataCopy写入重叠L1地址时，硬件不会主动报告重叠写入，也不保证重叠数据的写入顺序。处理方式是避免重叠写入，或在存在依赖时插入同流水`PipeBarrier`、跨流水`SetFlag/WaitFlag`等同步。矩阵数据搬入和重叠写同步可参考[矩阵数据搬入至L1-Buffer](<../../../../api/SIMD-API/基础API/矩阵计算（ISASI）/矩阵计算的搬入/矩阵数据搬入至L1-Buffer/矩阵数据搬入至L1-Buffer.md>)中的GM到L1、UB到L1等DataCopy接口约束。

#### 2.4.3 DCache

DCache是Scalar访问GM数据时使用的每核私有数据Cache。Scalar读取GM时，通常先查本核DCache；未命中时再经过L2 Cache访问GM。Scalar写出GM时，数据首先修改本核DCache，并将Cache Line标记为Dirty，GM不会立刻更新，而是该Cache Line被替换时，以Cache Line（64B）为单位把数据写回GM。

典型数据流是：

```text
读取：GM -> L2 Cache -> DCache -> Scalar
写出：Scalar -> DCache -> L2 Cache -> GM
```

因为每个核都有自己的DCache单元用于缓存GM里的数据，DCache一致性风险最突出：
- 如果某个核通过Scalar写GM后，没有对相关DCache Line执行写回/失效操作，写入值可能仍停留在该核私有DCache中，GM或其他核的DCache中仍可能保留旧值。
- 多个核写同一条64B Cache Line中的不同字段时，经过DCache写回可能发生随机覆盖。

处理方式包括：

- 写后需要立刻对GM可见时，调用[DataCacheCleanAndInvalid](../../../../api/SIMD-API/基础API/缓存控制/DataCacheCleanAndInvalid.md)执行Clean和Invalid。
- 多个核读写同一GM数据、且不希望经过DCache时，使用[ReadGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/ReadGmByPassDCache(ISASI).md>)或[WriteGmByPassDCache](<../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache(ISASI).md>)。
- 多个核写GM时，尽量让不同的核写入地址至少相隔一个64B Cache Line，并结合核间同步保证先写后读。

#### 2.4.4 ICache

ICache是Scalar执行指令时使用的指令Cache。Scalar指令路径通常是：

```text
GM -> L2 Cache -> ICache -> Scalar
```

ICache缓存的是代码段，是只读Cache，因此通常不需要考虑多个核之间的数据一致性问题。它的主要注意点是指令加载效率：Scalar执行代码时优先从ICache取指，未命中时再经过L2 Cache和GM加载。开发者可以在需要时通过[ICachePreLoad](<../../../../api/SIMD-API/基础API/缓存控制/ICachePreLoad(ISASI).md>)预加载指令，降低后续取指开销。

#### 2.4.5 SSBuffer

SSBuffer（Scalar Shared Buffer）是AI Core内部的物理存储单元，用于同一AI Core内AIC/AIV之间的轻量级数据共享和参数传递。3510版本SSBuffer的大小为3KB，每个核在非MIX模式下运行时，可以独立占用1KB的空间（AIC、AIV0、AIV1各占1KB）；在MIX模式下运行时，共享整个3KB的空间（AIC:AIV = 1:2）。SSBuffer支持b64/b32读写，不支持atomic读写，不支持MTE读写。

以UB到L1 Buffer搬运为例，[适用版本：Ascend 950PR/Ascend 950DT] 可以通过`ENABLE_CV_COMM_VIA_SSBUF`选择搬运通路：配置为`true`时，使用SSBuffer进行通信，数据通过UB到L1 Buffer之间的硬件通道搬运；配置为`false`时，数据搬运到L1 Buffer需要经过GM，相关约束见[UBToL1连续数据搬运](https://gitcode.com/cann/asc-devkit/blob/master/docs/api/SIMD-API/基础API/矩阵计算（ISASI）/矩阵计算的搬入/矩阵数据搬入至L1-Buffer/UBToL1连续数据搬运（DataCopy）.md)。

### 2.5 内存访问和原子操作

原子操作用于解决多个执行单元或多个核并发更新同一GM地址时的读-改-写冲突。例如多个Scalar核同时对同一个GM计数器执行加1操作时，可能都读到同一个旧值，最终只写回一次累加结果。而原子操作会把读取旧值、计算新值、写回GM作为不可分割的更新过程，从而避免这类数据竞争。
```cpp
问题场景: 多个 Scalar 核同时修改同一 GM 地址

Core 0: LD X0, [counter]    → X0 = 100
Core 1: LD X0, [counter]    → X0 = 100  (都读到了 100)
Core 0: ADD X0, X0, #1      → X0 = 101
Core 1: ADD X0, X0, #1      → X0 = 101  (各自加 1)
Core 0: ST X0, [counter]    → [counter] = 101
Core 1: ST X0, [counter]    → [counter] = 101  (应该是 102!)

两次 +1, 但结果只 +1 了 → 数据竞争 (Race Condition)

原子操作解决:
Core 0: ATOM.add.u32 Xm, [counter], Xt  → [counter] = 101 (原子完成)
Core 1: ATOM.add.u32 Xm, [counter], Xt  → [counter] = 102 (原子完成)
```

NPU SIMD编程中常见的原子相关访问可以分为以下几类，数据搬运随路原子操作接口见[原子操作概述](../../../../api/SIMD-API/基础API/原子操作/原子操作概述.md)，Scalar原子操作接口见[AtomicAdd](../../../../api/SIMD-API/基础API/原子操作/AtomicAdd.md)、[AtomicCas](../../../../api/SIMD-API/基础API/原子操作/AtomicCas.md)、[AtomicExch](../../../../api/SIMD-API/基础API/原子操作/AtomicExch.md)等接口说明。

| 类型 | 典型接口 | 作用位置 | 主要用途 |
| --- | --- | --- | --- |
| 数据搬运随路原子操作 | `SetAtomicAdd`、`SetAtomicMax`、`SetAtomicMin`、`DisableDmaAtomic` | 后续目的地址为GM的数据搬运 | 将待拷贝内容与GM已有内容做求和、取最大值或取最小值后写入GM；使用完成后通过`DisableDmaAtomic`关闭原子状态。 |
| Scalar ATOM原子操作 | `AtomicAdd`、`AtomicCas`、`AtomicExch`等 | Scalar直接访问指定GM地址，返回旧值 | 计数器、自旋锁、需要根据旧值判断是否成功的同步原语。 |
| Scalar RED归约操作 | `AtomicAdd`、`AtomicMax`、`AtomicMin`等不返回旧值的归约形式 | Scalar直接访问指定GM地址，不返回旧值 | 不需要旧值的整数或浮点归约，减少返回值相关开销。 |

## 3. 总结

本文介绍了NPU的内存单元、内存操作对一致性的影响及相关约束。编写算子时，应根据需求选择存储层级、规划搬运路径，必要时加入同步控制或Cache一致性处理保证计算正确性。

# 算子功能设计

> 类型：基础

本文以快速入门中的 AddCustom 算子（`z = x + y`）为贯穿示例，演示如何从数学公式出发，完成算子设计的主要步骤：

1. **转换输入、输出和属性** → 得出 OpDef 的 Input/Output 骨架
2. **确定支持范围** → 完善 OpDef 的 dtype/format/芯片配置
3. **编写算子实现** → 不区分场景，使用统一的 TilingData、Tiling 函数和 Kernel
4. **针对不同场景扩展** → 按数据类型、shape 大小或运行时配置拆分不同的 kernel 实现

## 从数学公式转换输入、输出和属性

### 数学公式

AddCustom 的计算语义是逐元素加法：

```
z[i] = x[i] + y[i]
```

从这个公式可以识别：
- **两个输入张量** x 和 y，shape 相同
- **一个输出张量** z，shape 与输入相同
- **无额外参数**——公式中只有输入张量，没有标量参数

> 如果公式是 `z = x + α · y`，则 `α` 就是属性。属性识别和传递的完整示例请参考[通过TilingData传递属性信息](./Host侧Tiling实现/通过TilingData传递属性信息.md#端到端示例addcustom-的-alpha-属性传递)。

### 得出 OpDef 骨架

根据公式，可以写出 OpDef 的 Input/Output 骨架——此时只确定 name 和 ParamType：

```cpp
class AddCustom : public OpDef {
public:
    AddCustom(const char* name) : OpDef(name)
    {
        this->Input("x")
            .ParamType(REQUIRED);
        this->Input("y")
            .ParamType(REQUIRED);
        this->Output("z")
            .ParamType(REQUIRED);
    }
};
```

> 以下代码片段省略了 `namespace ops` 包裹和 `OP_ADD(AddCustom)` 注册宏，完整写法请参考[算子原型定义](./算子原型定义.md)。

**ParamType 选择：**
- `REQUIRED`：必须提供，如 AddCustom 的 x、y、z
- `OPTIONAL`：可选，有默认值，如 BatchNorm 推理模式下的均值方差
- `DYNAMIC`：动态数量，如 AddN 的 N 个输入

此时 OpDef 还不完整——缺少 dtype/format 列表、芯片配置等信息。下一步将根据支持范围来完善。

## 确定支持范围

明确了算子做什么计算后，需要确定它在什么条件下能工作。这些决策直接写入 OpDef，完善 Input/Output 的细节和跨芯片配置。

### dtype / format

dtype 和 format 决定了原型注册、aclnn 接口和 kernel 实现的组合空间。

**AddCustom 的选择：** 支持 `{float16, float, int32}` 三种 dtype，均使用 ND 格式。将 dtype/format 列表填入 OpDef：

```cpp
this->Input("x")
    .ParamType(REQUIRED)
    .DataType({ge::DT_FLOAT16, ge::DT_FLOAT, ge::DT_INT32})  // 3 种 dtype
    .Format({ge::FORMAT_ND, ge::FORMAT_ND, ge::FORMAT_ND});   // 3 种 format，一一对应
this->Input("y")
    .ParamType(REQUIRED)
    .DataType({ge::DT_FLOAT16, ge::DT_FLOAT, ge::DT_INT32})
    .Format({ge::FORMAT_ND, ge::FORMAT_ND, ge::FORMAT_ND});
this->Output("z")
    .ParamType(REQUIRED)
    .DataType({ge::DT_FLOAT16, ge::DT_FLOAT, ge::DT_INT32})
    .Format({ge::FORMAT_ND, ge::FORMAT_ND, ge::FORMAT_ND});
```

> 以下代码片段省略了 `namespace ops` 包裹和 `OP_ADD(AddCustom)` 注册宏，完整写法请参考[算子原型定义](./算子原型定义.md)。

**填写规则：**
- **dtype 和 format 列表长度必须一致**，保持一一对应关系。上例中 3 个 dtype 对应 3 个 format，表示支持 `{float16+ND, float+ND, int32+ND}` 三种组合。
- 如果某输入/输出的 dtype/format 与所有组合通用，可用 `DataTypeList`/`FormatList` 简化，无需重复列出。详细说明请参考[算子原型定义](./算子原型定义.md)。

### 芯片范围

芯片支持范围通过 `AddConfig` 注册：

```cpp
this->AICore().AddConfig("Ascend910B");
```

**开发阶段**只需注册手头有硬件的芯片型号，先在单平台上验证功能。**产品交付**时覆盖目标用户的所有芯片型号。

如果不同芯片的算子原型有差异（如某型号支持 BF16 而其他不支持），需要用 `OpAICoreConfig` 定义差异化原型：

```cpp
OpAICoreConfig config;
config.Input("x").DataType({ge::DT_FLOAT16, ge::DT_BF16}).Format({ge::FORMAT_ND, ge::FORMAT_ND});
this->AICore().AddConfig("ascendxxx3", config);
```

`OpAICoreConfig` 中未定义的输入输出会继承 `OpDef` 的原型；已定义的会覆盖。也可以通过 `REGISTER_OP_AICORE_CONFIG` 宏在独立文件中注册差异化原型，详细用法请参考[多硬件平台注册差异化的算子原型](./算子原型定义.md#多硬件平台注册差异化的算子原型)。

### 确定性

确定性指算子在相同输入下是否产生相同输出：

- **AddCustom 是确定性算子**：`z[i] = x[i] + y[i]` 每个元素独立计算，不存在累加顺序等不确定因素
- **非确定性算子**（如归约求和）：因浮点累加顺序不同，相同输入可能产生微小差异

确定性约束会影响 kernel 设计——非确定性场景下可以放开累加顺序约束以获得更好的并行性能。

### 完善后的 OpDef

将前两步确定的 Input/Output 骨架、dtype/format 列表、芯片配置等合并，即得到完整的 OpDef 定义。完整的 OpDef 编写方法和 API 说明请参考[算子原型定义](./算子原型定义.md)。

OpDef 定义完成后，下一步是编写算子实现——TilingData、Tiling 函数和 Kernel 代码。

## 编写算子实现

在开始编写代码之前，先了解 tiling 函数和 kernel 函数在运行时执行模型中的角色和关系：

**Tiling 函数：**

- 同一 opType 共用一份 tiling 函数（不区分芯片型号）。
- 接收算子的输入、输出、属性、平台和运行时信息等，确定 kernel 函数加载时所需的信息，包括但不限于 kernel 入口标识（TilingKey 或 Kernel 模板参数实例化）、launch 配置（如逻辑 Block 数）、额外 workspace 信息等。
- 运行时通常在 launch kernel 前调用该函数。

**Kernel 函数：**

- 默认同一 opType 共用一个 kernel 入口（不区分芯片型号）。
- 通过在 CMakeLists.txt 中为不同芯片指定不同的 KERNEL_FILE，可以做到同一 opType 在不同芯片上使用不同的 kernel 实现。
- 每个 kernel 入口函数名唯一（与 opType 对应）。若需要针对不同场景拆分不同的实现分支，通过 TilingKey 或 Kernel 模板参数实例化等方式，在**同一入口函数内**用编译期常量判断来选择不同分支，编译器会为每个分支生成独立的 binary。
- 编译成独立的 `.o` 文件。运行时通常先运行 tiling 函数找到对应的 `.o` 和 kernel 入口，再按照配置 launch kernel。

**TilingData 结构体：**
- 在**动态参数传递**场景下（即大多数场景），TilingData 用于在 Tiling 函数和 Kernel 函数之间传递运行时参数（如数据量、分块数等每次调用可能不同的值）。
- 在**模板参数传递**场景下（使用 Kernel 模板时），部分 TilingData 字段可作为编译期常量，用于折叠分支、缩减代码段。

基础场景下，算子不区分场景，不使用额外 workspace 空间，统一使用一份 kernel 实现。需要编写三个部分：TilingData 结构体、Tiling 函数和 Kernel 代码。

### 编写 TilingData

数学公式决定了 kernel 需要哪些调度信息。对于 `z[i] = x[i] + y[i]`：
- 每个元素独立计算，无跨元素依赖 → kernel 只需要知道**总共有多少元素**和**如何分块**

因此 TilingData 只需要两个字段：

```cpp
// op_kernel/add_custom_tiling.h
struct AddCustomTilingData {
    uint32_t totalLength;  // 总计算数据量（从输入 shape 计算）
    uint32_t tileNum;      // 每个 Block 上的分块个数
};
```

**设计原则：TilingData 只传 kernel 需要的标量值。** kernel 不应该做"查属性表"或"重新解析 shape"的动作。关于 TilingData 的详细说明，请参考 [Host 侧 Tiling 实现](./Host侧Tiling实现/基本流程.md)。

### 编写 Tiling 函数

Tiling 函数在 Host 侧运行，负责从输入 shape 计算出 TilingData 的值。关键步骤：

1. **获取输入 shape 信息**：通过 `context->GetInputShape()` 获取算子输入的 shape
2. **填写 TilingData**：通过 `context->GetTilingData<T>()` 获取 TilingData 指针，计算并赋值成员变量
3. **设置逻辑 Block 数**：通过 `context->SetBlockDim()` 设置参与计算的 Block 数量
4. **（可选）设置 workspace**：通过 `context->GetWorkspaceSizes()` 设置额外内存空间

基础场景下所有 dtype 和 shape 走同一个 kernel，无需设置 TilingKey 和 workspace。

Tiling 函数的完整编写流程、API 用法和约束说明，请参考 [Host 侧 Tiling 实现](./Host侧Tiling实现/基本流程.md)。

### 编写 Kernel 代码

Kernel 在 AI Core 上运行，根据 TilingData 中的调度信息执行实际计算。数学公式到 kernel 代码的对应关系：

```
数学公式:  z[i] = x[i] + y[i]
                ↓
Kernel 计算: Add(zLocal, xLocal, yLocal, length)
```

Kernel 实现遵循"搬运-计算-搬运"的三段式模式：`CopyIn`（GM → UB）→ `Compute`（向量计算）→ `CopyOut`（UB → GM）。入口函数通过 `GET_TILING_DATA` 获取 TilingData 后调用计算类。

Kernel 侧的编程模式、API 和完整代码，请参考 [Kernel 侧算子实现](./Kernel侧算子实现/基本流程.md) 和 [快速入门](../快速入门.md)。

以上是最基础的实现模式——所有 dtype 和 shape 走同一个 kernel，不使用额外 workspace，不需要分支判断。

## 针对不同场景扩展 kernel 实现

当算子需要支持更多数据类型、更大 shape 范围、或运行时确定性配置时，需要在基础实现上添加分支策略，针对不同场景调用不同的 kernel 实现。分支通过 TilingKey 或 Kernel 模板参数实现，具体 API 和代码示例请参考 [多分支策略](./多分支策略.md)。以下侧重于**什么时候该分支、按什么维度分支**的设计决策。

### 按数据类型选择不同 kernel

当不同 dtype 的计算路径有明显差异时，需要按数据类型选择不同 kernel。

**示例**：假设 AddCustom 扩展到支持 float16，float16 加法需要升精度到 float32 计算以避免中间结果溢出：

```
float32:  z = x + y                       → 直接 Add
float16:  z = Cast(Add(Cast(x), Cast(y)))  → 先升精度到 float32，计算后降回 float16
```

**为什么需要升精度**：float16 最大值仅 65504，当 `x=60000, y=10000` 时直接相加会溢出为 `Inf`。升到 float32 后中间结果可正确表示，最终再降精度写回。

此时在 Tiling 函数中根据 dtype 设置不同的 TilingKey，Kernel 侧用 `TILING_KEY_IS` 区分分支。`TILING_KEY_IS` 是编译期常量判断，编译器会将未命中的分支完全移除（常量折叠），不存在运行时开销。关于 TilingKey 的 Host 侧设置和 Kernel 侧使用的完整代码，请参考 [TilingKey：数字标识分支](./多分支策略.md#tilingkey数字标识分支)。

### 按 shape 大小选择不同 kernel

当数据量差异很大时，小 shape 可以一次搬入全部数据，大 shape 需要分块循环，两者适合不同的 kernel 实现。

**示例**：AddCustom 根据总元素数选择分支——设定阈值（如 1024），小数据量 `tileNum=1` 单次处理全部数据（`SetTilingKey(1)`），大数据量 `tileNum=8` 分块循环处理（`SetTilingKey(2)`）。Kernel 侧根据 TilingKey 调用 `ProcessSmall()` 或 `ProcessLarge()`。

### 按运行时确定性配置选择不同 kernel

当算子既有确定性模式又有非确定性模式时，需要根据运行时配置选择不同分支。确定性模式要求固定累加顺序，非确定性模式可以放开以获得更好的并行性能。

**示例**：假设有一个 ReduceCustom 算子（`y = sum(x, dim=0)`），归约顺序会影响确定性——确定性模式设 `SetTilingKey(1)` 走固定累加顺序的 `ProcessDeterministic()`，非确定性模式设 `SetTilingKey(2)` 走自由累加的 `ProcessNonDeterministic()`。

### 分支策略选择总结

关于 TilingKey 和 Kernel 模板的选择准则，请参考 [多分支策略 — 如何选择](./多分支策略.md#如何选择)。

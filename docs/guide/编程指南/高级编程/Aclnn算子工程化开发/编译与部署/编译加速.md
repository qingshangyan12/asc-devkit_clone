# 编译加速
> 类型：扩展

算子工程编译耗时主要来自 kernel 侧代码的逐芯片、逐 TilingKey 编译。本章从缓存复用、选择性编译、并行度和增量构建四个维度给出加速方案。

## ccache 编译缓存

ccache 通过缓存编译结果，在源码、编译命令、编译器路径和构建目录不变时直接复用缓存，跳过实际编译。示例工程的 `custom_op/CMakeLists.txt` 已内置 `ENABLE_CCACHE` option，默认 OFF，开启后 cmake 自动将 ccache 挂接到 C/C++ 编译器 launcher。

### 单机缓存

**安装与启用**：

```bash
apt install ccache
mkdir -p build && cd build
cmake -DENABLE_CCACHE=ON .. && make -j binary package
```

cmake 检测到 ccache 后，会设置 `CMAKE_CXX_COMPILER_LAUNCHER` 和 `CMAKE_C_COMPILER_LAUNCHER` 为 ccache 路径。若 ccache 未安装但 `ENABLE_CCACHE=ON`，cmake 会发出 WARNING 并回退为普通编译。

**验证缓存命中率**：

```bash
ccache -Cz
rm -rf build && mkdir -p build && cd build
cmake -DENABLE_CCACHE=ON .. && make -j binary package
ccache --show-stats -v
```

首次构建写入缓存，二次构建后 `Local storage Hits` 应显著提升。

**清空缓存**：

```bash
ccache -z          # 仅清空统计
ccache -C          # 仅清空缓存内容
ccache -Cz         # 同时清空内容和统计
```

### 分布式缓存（ccache + Redis）

多机共享缓存场景：机器 A 编译后将结果推送至 Redis，机器 B 在相同源码、编译选项和工具链版本下可从 Redis 命中缓存，减少重复编译。ccache 以各机器本地缓存为一级缓存、Redis 为共享二级缓存。

**前置检查**：

```bash
ccache --version
# 预期：Features 中包含 redis-storage
```

**组网要求**：

- 机器 A（首次编译）、机器 B（二次编译）、机器 C（Redis 服务器）需处于同一网络
- A/B 机器都必须能访问机器 C 的 Redis 端口（6379）
- A/B 机器建议保持一致：相同源码内容、相同编译命令、相同编译器版本、一致的源码路径和构建目录路径

**机器 C：部署 Redis**：

```bash
apt install redis-server
redis-server --daemonize yes --bind 0.0.0.0 --port 6379 --requirepass <PASSWORD>
redis-cli -h <C_IP> -p 6379 -a <PASSWORD> ping
```

**机器 A/B：配置 ccache**：

```bash
apt install redis-tools
redis-cli -h <C_IP> -p 6379 -a <PASSWORD> ping
ccache --set-config=secondary_storage=redis://default:<PASSWORD>@<C_IP>:6379
ccache --set-config=compiler_check=content
```

`compiler_check=content` 按编译器内容校验而非路径，避免不同安装路径导致缓存未命中。

**机器 A/B：构建验证**：

```bash
ccache -Cz
rm -rf build && mkdir -p build && cd build
cmake -DENABLE_CCACHE=ON .. && make -j binary package
```

机器 A 构建写入本地缓存和 Redis，机器 B 本地缓存为空但可从 Redis 读取。对比两次 `ccache --show-stats -v`，机器 B 的 `Remote storage Hits` 应显著提升。

## 选择性编译

开发阶段可通过缩小编译范围显著减少耗时。下表汇总各策略：

| 策略 | 适用场景 | 配置方式 | 效果 |
|------|---------|---------|------|
| `--tiling_key=1,2` | TilingKey 编程算子，仅调试特定分支 | `npu_op_kernel_options` 的 OPTIONS 参数 | 只编译指定 TilingKey 的 kernel，跳过其余 |
| `--kernel-template-input="D_T_X=float"` | 模板编程算子，仅调试特定模板参数组合 | `npu_op_kernel_options` 的 OPTIONS 参数 | 只编译指定模板参数组合的 kernel |
| `ASCEND_COMPUTE_UNIT` 收窄 | 开发阶段只跑当前 SOC | CMakeLists.txt 中 `set(ASCEND_COMPUTE_UNIT ascend910b)` | 跳过其他芯片的 kernel 编译 |
| `ENABLE_BINARY_PACKAGE=False` | 源码发布模式，不需要二进制 | CMakeLists.txt 或 cmake 参数 | 跳过 kernel 二进制编译，仅保留源码 |

**TilingKey 选择编译**：

对于使用 TilingKey 编程的算子，开发阶段可只编译正在调试的分支：

```bash
# 在 op_kernel/CMakeLists.txt 中添加
npu_op_kernel_options(ascendc_kernels AddCustom COMPUTE_UNIT Ascend910B OPTIONS --tiling_key=1,2)
```

未指定时默认编译所有 TilingKey。多个 TilingKey 之间不能有空格。

**模板参数选择编译**：

对于多分支与模板化算子，可只编译指定的模板参数组合：

```bash
# 原生数据类型直接使用类型名
npu_op_kernel_options(ascendc_kernels AddCustomTemplate COMPUTE_UNIT Ascend910B OPTIONS --kernel-template-input="D_T_X=float;D_T_Y=float;D_T_Z=float")

# 自定义类型使用对应数字值
npu_op_kernel_options(ascendc_kernels AddCustomTemplate COMPUTE_UNIT Ascend910B OPTIONS --kernel-template-input="D_T_X=10;D_T_Y=half;D_T_Z=10")
```

相同模板参数配置多个值时用逗号分隔，不同参数之间用分号分隔，整体用引号包裹，不能有空格。

**芯片范围收窄**：

默认 `ASCEND_COMPUTE_UNIT` 包含多个芯片型号，每个芯片独立编译一轮 kernel。开发阶段可临时只编译当前运行环境的芯片：

```bash
# 在 custom_op/CMakeLists.txt 中临时修改
set(ASCEND_COMPUTE_UNIT ascend910b)
```

发布前需恢复为完整芯片列表。

**跳过二进制编译**：

源码发布模式下，kernel 侧代码不编译为二进制，保留源码文件，支持后续 ATC 模型转换或在线编译场景：

```bash
cmake -DENABLE_BINARY_PACKAGE=False .. && make -j binary package
```

此模式下跳过所有 kernel 二进制编译步骤，仅生成源码包。

## 并行度控制

`make -j` 的线程数直接影响编译的速度。线程数过多会导致系统资源争抢，反而降低效率。

**线程数选择建议**：

- 一般场景：`make -j$(nproc)`，使用全部 CPU 核心
- 内存受限场景：kernel 编译每个线程内存开销较大，可设置为 `nproc / 2` 或更低
- 自动检测：`nproc` 命令返回可用 CPU 核数

```bash
make -j$(nproc) binary package
make -j8 binary package
```

多芯片编译时，每个 `ASCEND_COMPUTE_UNIT` 会触发独立的 kernel 编译轮次，并行度需求更高。此时建议适当增加 `-j` 线程数或收窄芯片范围。

## 增量编译

每次执行 `rm -rf build` 会清空全部构建产物，导致全量重编译。在仅修改 kernel 代码或 tiling 逻辑时，可保留 build 目录进行增量编译。

**增量编译操作**：

```bash
cd build
make -j$(nproc) binary package
```

cmake 会根据文件修改时间判断是否需要重新编译，未修改的文件直接复用已有产物。

**何时增量、何时全量**：

| 场景 | 建议操作 | 原因 |
|------|---------|------|
| 仅修改 kernel 源码 | `cd build && make -j binary package` | cmake 缓存有效，make 按修改时间增量编译 |
| 仅修改 tiling 逻辑 | `cd build && make -j binary package` | cmake 缓存有效，make 按修改时间增量编译 |
| 仅修改算子原型 | `cd build && cmake .. && make -j binary package` | cmake 需重新运行 opbuild 生成 autogen 代码 |
| 修改 CMakeLists.txt 配置 | `cd build && cmake .. && make -j binary package` | cmake 变量变更需重新 configure |
| 修改 `npu_op_kernel_options` 编译选项 | `cd build && cmake .. && make -j binary package` | cmake 变量变更需重新 configure |
| 新增或删除算子文件 | `cd build && cmake .. && make -j binary package` | cmake 需重新扫描源文件列表 |
| 排查编译污染 | `rm -rf build && mkdir build && cmake .. && make -j binary package` | 全量清除确保干净构建 |
| cmake 参数大幅变更 | `rm -rf build && mkdir build && cmake .. && make -j binary package` | 缓存可能残留旧配置导致冲突 |

**增量编译 + ccache 组合**：

增量编译与 ccache 配合使用效果最佳。增量编译减少需要检查的文件数量，ccache 确保即使触发重编译也能命中缓存：

```bash
cd build
cmake -DENABLE_CCACHE=ON .. && make -j$(nproc) binary package
```

仅在 cmake 配置发生变更时才需要清空 build 目录，其余场景均可增量编译。

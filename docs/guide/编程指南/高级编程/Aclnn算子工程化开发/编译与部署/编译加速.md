# 编译加速
> 类型：扩展

算子工程编译耗时主要来自 kernel 侧代码的逐芯片、逐 TilingKey 编译。本章从缓存复用、选择性编译、并行度和增量构建四个维度给出加速方案。

## 1 ccache 编译缓存

ccache 通过缓存编译结果，在源码、编译命令和编译器等输入一致时复用缓存，减少重复编译耗时。算子工程可通过 CMake 的 `CMAKE_CXX_COMPILER_LAUNCHER` 将 C++ 编译器和毕昇编译器的启动器配置为 ccache。

**安装与启用**：

```bash
apt install ccache
```

在对应的 `CMakeLists.txt` 中配置：

```cmake
set(CMAKE_CXX_COMPILER_LAUNCHER /usr/bin/ccache)
```

如果 ccache 安装在其他路径，请将 `/usr/bin/ccache` 替换为实际路径。

**验证缓存命中率**：

```bash
ccache -Cz
cmake -S . -B build_out --preset=default
cmake --build build_out --target binary package -j$(nproc)
ccache --show-stats -v
```

首次构建写入缓存，二次构建后 `Local storage Hits` 应显著提升。

**清空缓存**：

```bash
ccache -z          # 仅清空统计
ccache -C          # 仅清空缓存内容
ccache -Cz         # 同时清空内容和统计
```

### 分布式缓存（ccache + Redis）

多机共享缓存场景下，可将 Redis 配置为 ccache 的二级缓存。机器 A 首次编译后将缓存写入本地和 Redis，机器 B 在相同源码、相同编译命令、相同编译器和相同构建目录路径下再次编译时，可从 Redis 命中缓存，减少重复编译。

**前置检查**：

```bash
ccache --version
# 预期：Features 中包含 redis-storage
```

**组网要求**：

- 机器 A：首次编译机器，将缓存写入 Redis
- 机器 B：二次编译机器，从 Redis 验证共享缓存命中
- 机器 C：Redis 服务器，保存共享缓存数据
- A、B、C 三台机器需处于同一网络，A/B 机器都必须能访问机器 C 的 Redis 端口（默认 6379）
- A/B 机器建议保持一致：相同源码内容、相同编译命令、相同编译器版本、一致的源码路径和构建目录路径

**机器 C：部署 Redis**：

```bash
apt install redis-server
redis-server --daemonize yes --bind 0.0.0.0 --port 6379 --requirepass <PASSWORD>
redis-cli -h <C_IP> -p 6379 -a <PASSWORD> ping
```

上述命令仅用于受控测试环境。共享环境或生产环境中，应根据实际安全要求配置访问控制、认证和网络隔离。

**机器 A/B：配置 ccache**：

```bash
apt install redis-tools
redis-cli -h <C_IP> -p 6379 -a <PASSWORD> ping
ccache --set-config=secondary_storage=redis://default:<PASSWORD>@<C_IP>:6379
ccache --set-config=compiler_check=content
```

`compiler_check=content` 按编译器内容校验而非路径校验，可避免 A/B 机器编译器安装路径不同但内容一致时缓存无法命中。

**机器 A/B：构建验证**：

以下命令假设工程已按前文配置 `CMAKE_CXX_COMPILER_LAUNCHER`：

```bash
ccache -Cz
cmake -S . -B build_out --preset=default
cmake --build build_out --target binary package -j$(nproc)
ccache --show-stats -v
```

机器 A 构建会写入本地缓存和 Redis；机器 B 本地缓存为空时，仍可从 Redis 读取共享缓存。对比两台机器的 `ccache --show-stats -v` 输出，机器 B 的 `Remote storage Hits` 应显著提升。

## 2 选择性编译

开发阶段可通过缩小编译范围显著减少耗时。下表汇总各策略：

| 策略 | 适用场景 | 配置方式 | 效果 |
|------|---------|---------|------|
| `--tiling_key=1,2` | TilingKey 编程算子，仅调试特定分支 | `npu_op_kernel_options` 的 OPTIONS 参数 | 只编译指定 TilingKey 的 kernel，跳过其余 |
| `--kernel-template-input="D_T_X=float"` | 模板编程算子，仅调试特定模板参数组合 | `npu_op_kernel_options` 的 OPTIONS 参数 | 只编译指定模板参数组合的 kernel |
| `ASCEND_COMPUTE_UNIT` 收窄 | 开发阶段只跑当前 SOC | CMakeLists.txt 中 `set(ASCEND_COMPUTE_UNIT ascendxxx)` | 跳过其他芯片的 kernel 编译 |
| `ENABLE_BINARY_PACKAGE=False` | 源码发布模式，不需要二进制 | CMakeLists.txt 或 cmake 参数 | 跳过 kernel 二进制编译，仅保留源码 |

**TilingKey 选择编译**：

对于使用 TilingKey 编程的算子，开发阶段可只编译正在调试的分支：

```cmake
# 在 op_kernel/CMakeLists.txt 中添加
npu_op_kernel_options(ascendc_kernels AddCustom COMPUTE_UNIT ascendxxx OPTIONS --tiling_key=1,2)
```

未指定时默认编译所有 TilingKey。多个 TilingKey 之间不能有空格。

**模板参数选择编译**：

对于多分支与模板化算子，可只编译指定的模板参数组合：

```cmake
# 原生数据类型直接使用类型名
npu_op_kernel_options(ascendc_kernels AddCustomTemplate COMPUTE_UNIT ascendxxx OPTIONS --kernel-template-input="D_T_X=float;D_T_Y=float;D_T_Z=float")

# 自定义类型使用对应数字值
npu_op_kernel_options(ascendc_kernels AddCustomTemplate COMPUTE_UNIT ascendxxx OPTIONS --kernel-template-input="D_T_X=10;D_T_Y=half;D_T_Z=10")
```

相同模板参数配置多个值时用逗号分隔，不同参数之间用分号分隔，整体用引号包裹，不能有空格。

**芯片范围收窄**：

默认 `ASCEND_COMPUTE_UNIT` 包含多个芯片型号，每个芯片独立编译一轮 kernel。开发阶段可临时只编译当前运行环境的芯片：

```cmake
# 在 custom_op/CMakeLists.txt 中临时修改
set(ASCEND_COMPUTE_UNIT ascendxxx)
```

发布前需恢复为完整芯片列表。

**跳过二进制编译**：

源码发布模式下，kernel 侧代码不编译为二进制，保留源码文件，支持后续 ATC 模型转换或在线编译场景：

```cmake
npu_op_package(${package_name}
    TYPE RUN
    CONFIG
        ENABLE_SOURCE_PACKAGE ${ENABLE_SOURCE_PACKAGE}
        ENABLE_BINARY_PACKAGE ${ENABLE_BINARY_PACKAGE}
        INSTALL_PATH ${CMAKE_BINARY_DIR}/
)
```

然后在 configure 阶段传入变量：

```bash
cmake -S . -B build_out --preset=default -DENABLE_BINARY_PACKAGE=False
cmake --build build_out --target binary package -j$(nproc)
```

此模式下跳过 kernel `.o` 二进制生成步骤，仅生成源码包和必要配置。注意：如果顶层 `CMakeLists.txt` 在 `npu_op_package(... CONFIG ...)` 中硬编码了 `ENABLE_BINARY_PACKAGE True`，命令行传入的 `-DENABLE_BINARY_PACKAGE=False` 不会生效，需先改为变量形式。

## 3 并行度控制

`cmake --build ... -j` 的线程数直接影响编译速度。线程数过多会导致系统资源争抢，反而降低效率。

**线程数选择建议**：

- 一般场景：`cmake --build build_out --target binary package -j$(nproc)`，使用全部 CPU 核心
- 内存受限场景：kernel 编译每个线程内存开销较大，可设置为 `nproc / 2` 或更低
- 自动检测：`nproc` 命令返回可用 CPU 核数

```bash
cmake --build build_out --target binary package -j$(nproc)
cmake --build build_out --target binary package -j8
```

多芯片编译时，每个 `ASCEND_COMPUTE_UNIT` 会触发独立的 kernel 编译轮次，并行度需求更高。此时建议适当增加 `-j` 线程数或收窄芯片范围。

## 4 增量编译

每次重新创建干净的 build 目录都会清空全部构建产物，导致全量重编译。在仅修改 kernel 代码或 tiling 逻辑时，可保留 build 目录进行增量编译。

**增量编译操作**：

```bash
cmake --build build_out --target binary package -j$(nproc)
```

CMake 生成的构建系统会根据文件修改时间判断是否需要重新编译，未修改的文件直接复用已有产物。

**何时增量、何时全量**：

| 场景 | 建议操作 | 原因 |
|------|---------|------|
| 仅修改 kernel 源码 | `cmake --build build_out --target binary package -j$(nproc)` | CMake 缓存有效，按修改时间增量编译 |
| 仅修改 tiling 逻辑 | `cmake --build build_out --target binary package -j$(nproc)` | CMake 缓存有效，按修改时间增量编译 |
| 仅修改算子原型 | `cmake -S . -B build_out --preset=default && cmake --build build_out --target binary package -j$(nproc)` | 需重新运行代码生成，更新 autogen 代码 |
| 修改 CMakeLists.txt 配置 | `cmake -S . -B build_out --preset=default && cmake --build build_out --target binary package -j$(nproc)` | CMake 变量变更需重新 configure |
| 修改 `npu_op_kernel_options` 编译选项 | `cmake -S . -B build_out --preset=default && cmake --build build_out --target binary package -j$(nproc)` | CMake 变量变更需重新 configure |
| 新增或删除算子文件 | `cmake -S . -B build_out --preset=default && cmake --build build_out --target binary package -j$(nproc)` | CMake 需重新扫描源文件列表 |
| 排查编译污染 | 重新创建干净的 build 目录后执行 configure 和 build | 全量清除确保干净构建 |
| cmake 参数大幅变更 | 重新创建干净的 build 目录后执行 configure 和 build | 缓存可能残留旧配置导致冲突 |

**增量编译 + ccache 组合**：

增量编译与 ccache 配合使用效果最佳。增量编译减少需要检查的文件数量，ccache 确保即使触发重编译也能命中缓存：

```bash
cmake -S . -B build_out --preset=default
cmake --build build_out --target binary package -j$(nproc)
```

仅在 cmake 配置发生变更时才需要清空 build 目录，其余场景均可增量编译。

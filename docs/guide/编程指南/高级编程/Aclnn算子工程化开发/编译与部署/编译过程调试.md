# 编译过程调试

> 类型：扩展

算子工程编译涉及代码生成、Host 侧编译、Kernel 侧编译、打包部署四个阶段。当编译出现问题时，默认输出通常不足以定位根因。本文从四个阶段分别介绍调试手段，并提供常见错误的诊断方法和排查思路。

## 生成代码调试

`npu_op_code_gen` 在 cmake configure 阶段自动生成 aclnn 调用代码和算子原型定义代码。生成产物位于 `ASCEND_AUTOGEN_PATH` 目录（默认为 `build/autogen`）。当原型定义有误或生成结果与预期不符时，需要检查这些文件。

### 生成产物目录

```
build/autogen/
├── aclnn_add_custom.cpp      // aclnn 调用代码实现
├── aclnn_add_custom.h        // aclnn 调用代码头文件
├── aclnn_matmul_custom.cpp   // 每个算子各生成一对 .cpp/.h
├── aclnn_matmul_custom.h
├── op_proto.cc               // 算子原型定义代码（入图用）
├── op_proto.h                // 算子原型定义头文件
└── fallback_*.cpp            // Tiling 相关代码（如配置了 EnableFallBack）
```

### 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| aclnn 接口参数与原型定义不匹配 | 检查 `aclnn_<op>.h` 中的函数签名，确认输入输出和属性参数是否正确映射 |
| 入图场景算子注册信息异常 | 检查 `op_proto.cc` 中的注册宏，确认 OpType、dtype/format 是否与 Host 侧定义一致 |
| 某个算子的调用代码未生成 | 检查 `npu_op_code_gen` 的 `SRC` 参数是否包含了该算子的 Host 侧源文件 |
| JOIN_OP_DEF 导致部分芯片型号缺失 | `JOIN_OP_DEF=True` 时仅编译原型注册和 CMakePresets.json 中共有的芯片型号，确认 AddConfig 是否覆盖了目标型号 |

### 强制重新生成

`ASCEND_AUTOGEN_PATH` 目录下的生成文件在每次 `cmake ..` 时会清空并重新生成。如果怀疑生成文件残留导致问题，可以手动清理后重新 configure：

```bash
rm -rf build/autogen
cmake ..
```

## Host 侧编译调试

Host 侧使用标准 cmake 构建系统，默认只输出编译目标的摘要信息，不显示实际执行的编译和链接命令。通过 VERBOSE 机制可以打印完整的命令行，用于排查头文件路径、链接库、编译选项等问题。

### 方式一：make VERBOSE=1

在 make 命令中指定 `VERBOSE=1`，打印每条编译和链接命令：

```bash
cd build
make -j VERBOSE=1 binary package
```

输出示例：

```
[ 10%] Building CXX object op_host/CMakeFiles/cust_opapi.dir/.../aclnn_add_custom.cpp.o
/usr/bin/c++ -Dcust_opapi_EXPORTS -I/usr/local/Ascend/cann/include ... -fvisibility=hidden -o aclnn_add_custom.cpp.o -c aclnn_add_custom.cpp
```

每行输出包含完整的编译器调用，可以看到：
- 实际的编译器路径（如 `/usr/bin/c++`）
- 宏定义（`-D`）和头文件搜索路径（`-I`）
- 编译选项（如 `-fvisibility=hidden`、`-g`、`-O2`）
- 链接库路径（`-L`）和链接库（`-l`）

### 方式二：cmake 配置 CMAKE_VERBOSE_MAKEFILE

在 cmake configure 阶段开启 verbose，后续所有 make 调用都会自动打印完整命令：

```bash
cmake -DCMAKE_VERBOSE_MAKEFILE=ON ..
make -j binary package
```

与方式一效果相同，区别在于设置持久化在 CMakeCache.txt 中，无需每次 make 时重复指定。

### 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| 头文件找不到 | `-I` 路径是否包含目标头文件所在目录 |
| 链接 undefined reference | `-L` 和 `-l` 是否包含缺失符号所在的库 |
| 符号不可见 | `-fvisibility=hidden` 是否意外隐藏了需要导出的符号 |
| 编译选项冲突 | 同一目标是否被多次添加矛盾的选项（如同时 `-O2` 和 `-O0`） |

## Kernel 侧编译调试

Kernel 侧由编译框架为每个算子调用毕昇编译器，默认不保留中间产物。通过 `--save-temp-files` 选项可以保留每次编译的中间文件，用于排查预处理、编译、链接各阶段的问题。

### 开启方法

在 Kernel 侧 CMakeLists.txt 中，通过 `npu_op_kernel_options` 添加 `--save-temp-files` 选项：

```cmake
# 为所有算子开启
npu_op_kernel_options(ascendc_kernels ALL OPTIONS --save-temp-files)

# 仅对特定算子开启
npu_op_kernel_options(ascendc_kernels AddCustom OPTIONS --save-temp-files)
```

也可以同时添加 `-g` 生成调试信息，配合使用：

```cmake
npu_op_kernel_options(ascendc_kernels ALL OPTIONS --save-temp-files -g)
```

### 保留的中间产物

开启后，编译框架会在 build 目录下保留每个 kernel 编译过程的中间文件：

- **预处理文件**（`.i`）：预处理后的源码，可用于确认宏展开是否正确、头文件是否被正确包含
- **汇编文件**（`.s`）：编译后的汇编输出，可用于确认编译器生成的指令是否符合预期
- **目标文件**（`.o`）：链接前的目标文件，可用于确认符号是否正确导出

### 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| 宏定义未生效 | 检查 `.i` 文件，确认宏是否被正确展开 |
| 头文件包含缺失 | 检查 `.i` 文件，确认目标头文件的内容是否被引入 |
| 编译器优化导致异常 | 对比 `.s` 文件在不同优化级别下的差异 |
| 模板实例化错误 | 检查 `.i` 文件中的模板展开结果，确认参数是否正确传递 |
| 链接符号缺失 | 检查 `.o` 文件的符号表（`nm` 命令），确认目标符号是否存在 |

### 部分芯片编译失败处理

当 `ASCEND_COMPUTE_UNIT` 配置了多个芯片型号时，kernel 编译会对每个芯片独立执行一轮。如果某个芯片的 kernel 编译失败，默认行为是终止整个构建流程。

`ASCEND_SKIP_FAILED_COMPUTE_UNIT` 选项允许跳过单个芯片的编译失败，继续编译其余芯片。适用场景：

- 算子对某些芯片型号尚不完全适配，但其他型号已可正常使用
- `npu_op_code_gen` 的 `JOIN_OP_DEF` 参数设为 False 时，可能编译更多芯片型号的算子，其中部分型号可能缺少适配

**配置方法**：在 CMakeLists.txt 中设置：

```cmake
set(ASCEND_SKIP_FAILED_COMPUTE_UNIT TRUE)
```

或在 cmake 命令行中传入：

```bash
cmake -DASCEND_SKIP_FAILED_COMPUTE_UNIT=TRUE ..
```

默认值为 FALSE。

**跳过机制的行为**：当 `ASCEND_SKIP_FAILED_COMPUTE_UNIT` 为 TRUE 时，编译框架的行为变化：

1. kernel 编译命令的输出重定向到日志文件，退出码写入 fail 日志
2. 编译结束后检查退出码，若非零则将失败信息追加到 `build/compile_error.log`
3. 失败的 kernel 不会阻塞其他芯片的编译，make 继续执行
4. 打包阶段结束后，在终端汇总所有失败的算子和芯片型号：

```
=========== Failed operators ===========
fail op-type: AddCustom, fail compute-unit: ascend910_93.
========================================
```

5. 如果所有芯片型号的编译全部失败，构建仍然会完成打包，但生成的 run 包中不含任何有效的 kernel 二进制

## 打包与部署调试

打包阶段将编译产物组织为 `.run` 安装包，部署阶段将算子包安装到目标环境。当打包或安装出现问题时，需要检查中间产物和打包命令。

### 查看打包命令

与 Host 侧调试一样，使用 VERBOSE 机制可以看到实际的打包命令：

```bash
make VERBOSE=1 package
```

输出示例：

```
[100%] Generating CPack package
/usr/bin/cpack --config ./CPackConfig.cmake
```

可以看到 cpack 调用过程，用于排查打包配置问题。

### 检查编译产物目录

在打包之前，先检查 `INSTALL_PATH`（或 `build_out`）目录下的中间产物结构，确认各库文件是否都已生成：

```
build_out/
├── lib/
│   ├── libcust_opapi.so        // Host 侧 API 库
│   ├── libcust_op_proto.so     // 原型定义库
│   └── libcust_op_tiling.so    // Tiling 库
├── kernel_meta/
│   ├── Ascend910B/             // 各芯片型号的 kernel binary
│   │   ├── add_custom.o
│   │   └── matmul_custom.o
│   └── Ascend310P/
├── include/
│   ├── aclnn_add_custom.h      // aclnn 头文件
│   └── op_proto.h              // 原型定义头文件
└── config.json                 // 算子配置信息
```

**检查要点**：
- `lib/` 目录下的三个库文件是否齐全
- `kernel_meta/` 下是否包含目标芯片型号的 kernel binary
- `include/` 下的头文件是否与 `aclnn_<op>.h` 命名一致
- 如果使用 SHARED/STATIC 模式，`ENABLE_BINARY_PACKAGE` 必须为 True

### 解压 .run 包验证内容

`.run` 文件本质是 shell 脚本 + tar 压缩包的自解压格式。可以不解包直接查看内部内容：

```bash
# 查看 .run 包内容（不安装）
./custom_op_ascend.run --noexec --list

# 解压后的内容在临时目录中，查看结构
ls -R /tmp/custom_op_*
```

解压后的目录结构应与编译产物目录一致。检查要点：
- 是否包含所有预期的库文件和 kernel binary
- 头文件是否完整
- `config.json` 中的算子列表是否正确

### 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| `make package` 失败 | `make VERBOSE=1 package` 输出中 cpack 的命令和报错信息 |
| `.run` 包安装后缺少文件 | `build_out/` 目录结构，确认 `lib/`、`kernel_meta/`、`include/` 下的文件是否齐全 |
| `.run` 包中无 kernel binary | `build_out/kernel_meta/` 下是否有目标芯片型号的子目录和 `.o` 文件 |
| SHARED/STATIC 模式下打包报错 | `npu_op_package` CONFIG 中 `ENABLE_BINARY_PACKAGE` 是否为 True |
| INSTALL_PATH 生成产物位置不对 | `npu_op_package` CONFIG 中 `INSTALL_PATH` 配置是否指向预期目录 |
| 安装后算子未被识别 | 是否执行了 `source <install_path>/vendors/<vendor_name>/bin/set_env.bash`，`config.json` 语法是否正确 |
| `.run` 包安装失败 | 使用 `--install --verbose` 查看安装过程中的文件复制和权限设置详情 |

## 编译日志存盘

默认情况下，kernel 侧编译过程中的中间日志不会保留到磁盘，编译失败时终端仅打印异常抛出信息。通过设置 `ASCENDC_BUILD_LOG_DIR` 环境变量，可将每个编译阶段的日志写入指定目录，便于事后回溯。

**开启方法**：在执行 cmake 或 build.sh 之前设置环境变量：

```bash
export ASCENDC_BUILD_LOG_DIR=/home/build_log/
```

编译框架会在其下按芯片型号创建子目录。例如编译 `ascend910b` 和 `ascend910_93` 两个芯片时，日志目录结构为：

```
/home/build_log/
├── ascend910b/
└── ascend910_93/
```

**日志命名规则**：kernel 编译过程分为多个阶段（预处理、编译、链接等），每个阶段的日志按 `kernelName_hashName.log` 格式命名：

- **编译成功**：日志文件重命名为 `kernelName_hashName_success.log`
- **编译失败**：日志文件重命名为 `kernelName_hashName_error.log`

**从日志定位错误**：日志文件中每条记录以 `[CC]`（编译阶段）或 `[LD]`（链接阶段）开头，后跟完整编译命令和编译器原始输出。定位步骤：

1. 在 `ASCENDC_BUILD_LOG_DIR` 对应芯片子目录下搜索 `_error.log` 文件，确认哪些 kernel 编译失败
2. 打开 `_error.log` 文件，查找 `[CC]` 或 `[LD]` 标记后的编译器输出段落
3. 编译器错误信息通常包含行号和错误类型，据此回到源码修正

> [!NOTE] 与部分芯片编译失败处理的配合
> 开启 `ASCEND_SKIP_FAILED_COMPUTE_UNIT` 时，建议同时开启 `ASCENDC_BUILD_LOG_DIR`，两者配合使用可以完整保留每个失败 kernel 的详细编译日志，便于逐个修复。

## 常见编译错误诊断

算子工程编译涉及多个阶段：cmake 配置、opbuild 代码生成、Host 侧库编译、Kernel 侧逐芯片编译等。本节提供常见编译错误的诊断方法和排查思路。

### 常见编译错误及解决方法

**表 1** 常见编译错误及解决方法

| 错误现象 | 可能原因 | 解决方法 |
|---------|---------|---------|
| `ASCEND_HOME_PATH environment variable is not set!` | 未执行 CANN 环境变量配置 | 执行 `source /usr/local/Ascend/cann/set_env.sh`（root 安装）或 `source $HOME/Ascend/cann/set_env.sh`（非 root 安装） |
| `ASCEND_COMPUTE_UNIT not set` | 未配置 AI 处理器型号 | 在 CMakePresets.json 中设置 `ASCEND_COMPUTE_UNIT` 为实际的 soc_version，参考 [soc_version 获取方法](../附录/soc_version获取方法.md) |
| `kernel compilation failed: unsupported soc_version` | soc_version 与实际硬件不匹配 | 使用 `npu-smi info` 命令查询正确的 soc_version |
| `undefined reference to 'aclnnXxxGetWorkspaceSize'` | 未开启二进制编译或编译产物不完整 | 确认 `ENABLE_BINARY_PACKAGE` 为 `True`，清理 build 目录后重新编译 |
| `template parameter mismatch` | `--kernel-template-input` 指定的模板参数与 kernel 入口或 host 侧定义不匹配 | 检查模板参数名称是否与 `ASCENDC_TPL_ARGS_DECL` 中的定义一致 |

### 详细错误诊断

#### ASCEND_HOME_PATH 未设置

**错误表现**：cmake 在加载 `cmake/asc/asc-config.cmake` 时立即终止，报 `FATAL_ERROR`：

```
CMake Error at cmake/asc/asc-config.cmake:11 (message):
  ASCEND_HOME_PATH environment variable is not set!
  source set_env.sh in cann install directory first.
```

**根因**：未执行 `source /usr/local/Ascend/cann/set_env.sh`，或设置了变量但路径不存在。

**排查步骤**：

1. 检查环境变量是否已设置：`echo $ASCEND_HOME_PATH`
2. 检查路径是否存在：`ls $ASCEND_HOME_PATH/compiler/tikcpp/ascendc_kernel_cmake/`
3. 若未设置，执行 `source /usr/local/Ascend/cann/set_env.sh`
4. 重新进入 build 目录执行 cmake

#### Kernel 编译失败

**错误表现**：`make` 过程中某个芯片型号的 kernel 编译目标失败，终端输出类似：

```
Kernel Compilation Error: OpType AddCustom KernelFile add_custom_kernel.cpp!
```

**根因**：kernel 源码存在语法错误、类型不匹配、API 用法错误、UB 越界等问题，或 tiling 库加载失败导致编译参数不正确。

**排查步骤**：

1. 如已开启 `ASCENDC_BUILD_LOG_DIR`，直接查看对应芯片子目录下的 `_error.log` 文件
2. 如未开启日志存盘，可通过 `npu_op_kernel_options` 添加 `--save-temp-files` 选项保留中间产物
3. 检查预处理文件（`.i`）确认宏展开和头文件包含是否正确
4. 检查汇编文件（`.s`）确认编译器生成的指令是否符合预期

详细方法参考上文"Kernel 侧编译调试"章节。

#### npu_op_code_gen 失败

**错误表现**：cmake configure 阶段报错：

```
CMake Error: opbuild run failed! <error_detail>
```

**根因**：`npu_op_code_gen` 函数在 cmake configure 阶段执行两步操作：先编译 `libascend_all_ops.so`，再调用 `opbuild` 从该库中提取算子信息并生成 aclnn 接口代码。失败通常发生在第一步。

**排查步骤**：

1. 查看 cmake configure 输出中 `compile ascend_all_ops` 相关的 error 信息
2. 检查 `op_host/CMakeLists.txt` 中 `npu_op_code_gen` 的 `SRC` 参数，确认列出的源文件都存在且路径正确
3. 检查 Host 侧源文件的算子原型注册代码，确认 `OP_PROTO` 和 `OP_TILING` 注册宏使用正确
4. 如果报错信息指向 `opbuild` 调用失败，检查 `ASCEND_HOME_PATH/tools/opbuild/op_build` 是否存在且可执行

# 运行时加载机制

> 类型：扩展

算子开发完成后，需要了解编译产物如何被加载和执行、开发时做出的设计决策如何影响运行表现。本文从算子开发者视角梳理运行时调用的基本模型和代码写法对运行行为的影响。

## 算子是如何被调用的

### 二段式接口

单算子 API 采用二段式调用：`aclnnXxxGetWorkspaceSize` 和 `aclnnXxx`。

**第一阶段：GetWorkspaceSize**

```cpp
aclnnXxxGetWorkspaceSize(input0, input1, output, &workspaceSize, &executor);
```

此阶段在 Host 侧完成所有准备工作：
1. 根据输入的 dtype/format/shape，尝试匹配已编译的 kernel binary（**快速路径**：如果输入参数的组合之前已经执行过且 binary 已缓存，则直接复用，跳过 TilingFunc 调用）
2. 未匹配时，调用开发者编写的 TilingFunc 计算当前输入对应的 TilingData、TilingKey、BlockDim
3. 根据 TilingKey 查找对应的 kernel binary（.o 文件）
4. 返回 workspaceSize（需要分配的 Device 内存大小）和 executor（承载调度上下文）

此阶段可能触发的耗时操作：
- **TilingFunc 调用**：执行 Host 侧 C++ 函数，通常在微秒级
- **Binary 查找**：在文件系统中检索 .o 文件，涉及文件 I/O

**第二阶段：Execute**

```cpp
aclnnXxx(workspace, workspaceSize, executor, stream);
```

此阶段只做一件事：将第一阶段准备好的全部信息打包提交到 stream 上执行。不调用 TilingFunc、不查找 binary、不触发编译——所有决策在第一阶段已完成。

### 为什么分两阶段

两阶段设计的核心目的是**将 workspace 内存分配与 kernel 执行解耦**：

- 用户可以在第一阶段后统一分配所有算子的 workspace，合并为一块 Device 内存池，减少 `aclrtMalloc` 调用次数和内存碎片
- 第一阶段返回的 workspaceSize 可用于内存预算——在提交任何 kernel 之前就知道总内存需求
- workspace 可以在算子执行完成后立即回收复用

### Binary 匹配机制

运行时框架通过输入参数的组合（dtype/format/shape + TilingKey）来查找预编译的 kernel binary。**相同 dtype/format/shape 的输入总是映射到同一个 kernel binary**，与输入 Tensor 中的实际数据内容无关。这是 binary 缓存和复用的基础。

Binary 查找的优先级顺序：
1. **自定义 vendor 算子包**（按 `config.ini` 中 `load_priority` 配置的顺序）
2. **CANN 内置算子库**

自定义算子包始终优先于内置算子库。多个自定义 vendor 包包含相同 OpType 时，`load_priority` 排在前面的优先匹配。

## 代码写法如何影响运行行为

开发者在编写算子代码时做出的选择，会直接影响编译产物的形态和运行时的表现。以下按影响阶段分为三类。

### 影响编译产物形态的写法

#### TilingKey / Kernel 模板的分支数量

算子有两种分支策略可选：[数字 TilingKey](../设计与实现/多分支策略.md#tilingkey数字标识分支) 或 [命名 Kernel 模板参数](../设计与实现/多分支策略.md#kernel-模板)，两者互斥。Host 侧 TilingFunc 中的分支逻辑决定了 TilingKey 的数量。每个 TilingKey 在编译时对应一个独立的 kernel binary（.o + .json）。

```
kernel 文件数 = OpType 数 × TilingKey 数 × compute_unit 数
```

| 分支策略 | 编译耗时 | Binary 覆盖率 | 适用场景 |
|---------|---------|-------------|---------|
| 单一分支（所有输入走同一 Tiling 参数） | 极快 | 仅匹配特定参数 | 简单算子、开发阶段 |
| 按 shape 分档（如 ≤64 / ≤1024 / ≤64K / >64K） | 适中 | 覆盖常见场景 | 大多数算子 |
| 按 shape × dtype 精细分档（如 64 档） | 较长 | 接近 100% | 生产部署、性能敏感 |

**开发阶段建议**：少分档，加速编译迭代。**生产部署**：确保分档覆盖所有实际输入组合——二进制发布环境不支持在线编译，未覆盖的输入组合会导致算子调用失败。

#### ASCEND_COMPUTE_UNIT 范围

每个 compute_unit 独立编译一套 kernel binary，同一份 AscendC 源码需分别编译为对应架构的机器码。

- 范围越大 → 编译时间成倍增长、RUN 包体积成倍增长
- 范围越大 → 跨芯片部署时无需重新编译
- 只在目标芯片上运行时，应收窄到该芯片型号以加速编译

#### ENABLE_BINARY_PACKAGE 开关

RUN 包形态下，编译产物包含 binary 资源注册信息，运行时可通过快速匹配直接定位 kernel binary。STATIC/SHARED 库形态不包含此注册，运行时必须走完整 Tiling 计算路径，每次调用开销更大。

绝大多数自定义算子场景应使用 RUN 包形态。当算子需要作为库集成到更大的应用中分发时，使用 STATIC/SHARED 形态。

### 影响 Host 侧运行开销的写法

#### TilingFunc 的计算复杂度

TilingFunc 在每次未命中快速路径时被调用。如果函数中包含复杂计算（如大量循环、动态内存分配、文件系统操作），会直接增加每次算子调用的 Host 侧延迟。

**建议**：TilingFunc 中只做必要的标量计算（shape 推导、分块参数计算），避免复杂逻辑。

#### TilingData 字段数量

TilingData 结构体在 Host 侧填写、序列化后传递到 Kernel 侧。字段越多，序列化开销越大。

**建议**：TilingData 只传 kernel 需要的标量值，不要传冗余信息。详细的 TilingData 设计原则请参考 [Host 侧 Tiling 实现](../设计与实现/Host侧Tiling实现/基本流程.md)。

#### SetBlockDim 设置

`context->SetBlockDim()` 设置参与计算的逻辑 Block 数，直接影响并行度。

- 设置过小 → AI Core 利用率低，计算时间增加
- 设置过大 → 超过硬件资源时无法增加实际并行度，反而增加调度开销
- 一般设置为硬件平台的逻辑 Block 数或其倍数

#### Workspace 大小设置

`context->GetWorkspaceSizes()` 设置的 workspace 大小决定了每次调用需要额外分配的 Device 内存量。workspace 越大，内存压力越大。

**建议**：精确计算所需 workspace 大小，避免预留过多冗余空间。

### 影响 Kernel 侧执行表现的写法

#### TILING_KEY_IS vs 运行时 if-else

```cpp
// 方式一：TilingKey 分支（推荐）
if (TILING_KEY_IS(1)) {
    ProcessSmall();    // 编译期常量折叠，未命中的分支被完全移除
} else if (TILING_KEY_IS(2)) {
    ProcessLarge();
}

// 方式二：运行时分支
if (tilingData.totalLength <= threshold) {
    ProcessSmall();    // 运行时条件判断，两个分支都在 binary 中
} else {
    ProcessLarge();
}
```

`TILING_KEY_IS` 是编译期常量判断，编译器将未命中的分支完全移除（常量折叠），消除运行时分支判断开销和 icache 压力。运行时 if-else 两个分支都保留在 binary 中，代码体积更大。

#### Kernel 模板参数

Kernel 模板使用命名参数（如 `D_T_X`、`TILE_NUM`）替代数字 TilingKey，同样实现编译期特化：

```cpp
template<typename D_T_X, typename D_T_Y, typename D_T_Z, int TILE_NUM>
__global__ __aicore__ void add_custom(...)
{
    // D_T_X/D_T_Y/D_T_Z 在编译期确定，类型判断在编译期完成
    // TILE_NUM 在编译期确定，循环边界等可直接展开
}
```

模板参数使编译器能够针对特定类型和常量做优化（如循环展开、常量传播），运行时零开销。

#### 数据搬运模式

Kernel 的"搬运-计算-搬运"循环中，buffer 策略影响 pipeline 利用率：

- **单 buffer**：搬运和计算串行执行，pipeline 空闲多
- **双 buffer（双缓冲）**：一组 buffer 计算时另一组搬运，pipeline 利用率高

双 buffer 需要更多 UB 内存，适合数据量较大的场景。详细编程模式请参考 [Kernel 侧算子实现](../设计与实现/Kernel侧算子实现/基本流程.md)。

#### tileNum 切分粒度

TilingData 中的 tileNum 决定每个 Block 上的分块个数：

- tileNum 过小 → 每个分块的数据量大，单次搬运耗时长，但循环次数少
- tileNum 过大 → 每个分块的数据量小，循环次数多，循环开销占比增大

需要根据 UB 内存容量和计算/搬运比例选取合适的 tileNum。

# 基本流程

本文介绍aclnn算子工程中Kernel侧算子实现的基本编写流程。Kernel侧算子实现承接[算子功能设计](../算子功能设计.md)和[Host侧Tiling实现](../Host侧Tiling实现/基本流程.md)的结论，在AICore上完成实际计算。

不同算子的Kernel实现会有不同的数据组织和计算路径。逐元素二元算子通常按连续数据段搬运和计算，归约类算子通常需要在UB内做分段归约，矩阵类算子通常围绕矩阵分块和高阶计算接口组织。本文先说明Kernel侧的通用接入流程，再用短代码片段展示典型写法。

以逐元素二元算子为例，计算语义可以表示为：

```text
z[i] = f(x[i], y[i])
```

对应到Kernel侧，核心工作可以拆成三步：

```text
GM(x, y) -> UB(xLocal, yLocal) -> AscendC::Add -> UB(zLocal) -> GM(z)
```

这里的GM表示GlobalMemory，UB表示LocalMemory。Kernel先从GM搬入一段输入数据到UB，在UB上调用对应的AscendC计算API完成计算，再把结果从UB写回GM。Host侧Tiling已经准备好的`TilingData`、`numBlocks`、workspace和`TilingKey`，会在Kernel启动和Kernel内部计算时使用。

几类常见算子的Kernel侧关注点如下：

| 算子类型 | 典型计算 | Kernel侧关注点 |
|---|---|---|
| 逐元素二元算子 | `z[i]=f(x[i],y[i])` | GM到UB搬运、向量计算API调用、结果写回 |
| 归约类算子 | `y=sum(x,axis)` | 归约轴切分、临时结果缓存、尾块处理 |
| 矩阵类算子 | `C=A*B` | 矩阵分块、L0/UB数据搬运、高阶计算API参数 |

## 1. Kernel函数格式

### 1.1命名规则

Kernel入口函数名需要和算子类型对应。算子类型通常使用大驼峰命名，Kernel入口函数使用小写下划线命名。

| 算子类型 | Kernel入口函数名 |
|---|---|
| `AddCustom` | `add_custom` |
| `MatmulCustom` | `matmul_custom` |
| `ReduceMaxCustom` | `reduce_max_custom` |

完整命名转换规则请参考[命名转换规则对照表](../../附录/命名转换规则对照表.md)。

### 1.2函数声明

基础场景通常使用C风格Kernel入口函数。入口函数使用`extern "C"`、`__global__`和`__aicore__`修饰，参数顺序固定为输入、输出、workspace、tiling。下面以二输入一输出算子为例：

```cpp
extern "C" __global__ __aicore__ void binary_elemwise(
    __gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z,
    __gm__ uint8_t* workspace, __gm__ uint8_t* tiling)
{
    // Kernel入口函数体
}
```

参数含义如下：

| 参数 | 来源 | 作用 |
|---|---|---|
| `x`、`y` | 算子原型中的输入 | 指向输入Tensor的GM地址 |
| `z` | 算子原型中的输出 | 指向输出Tensor的GM地址 |
| `workspace` | 框架追加 | 指向Host侧Tiling设置的workspace地址 |
| `tiling` | 框架追加 | 指向Host侧Tiling写入的TilingData数据 |

参数顺序需要和算子原型中的输入输出顺序保持一致，workspace和tiling由框架追加到最后。例如某算子原型先声明输入`x`、`y`，再声明输出`z`，则Kernel入口参数顺序为`x`、`y`、`z`、`workspace`、`tiling`。

> [!NOTE] 输入输出同名场景
> 如果算子原型中的输入和输出同名，msOpGen生成Kernel入口参数时会给输出参数增加`ref`后缀，用于区分输入和输出地址。

### 1.3入口函数的基本结构

Kernel入口函数通常只做启动和分发工作，不承载大量计算逻辑。二输入一输出算子的入口函数可以按下面的顺序理解：

```cpp
extern "C" __global__ __aicore__ void binary_elemwise(
    __gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z,
    __gm__ uint8_t* workspace, __gm__ uint8_t* tiling)
{
    AscendC::InitSocState();

    REGISTER_TILING_DEFAULT(ElemwiseTilingData);
    GET_TILING_DATA(tilingData, tiling);

    KernelBinaryElemwise<STATIC_TILE_LENGTH> op;
    op.Init(x, y, z, tilingData.totalLength, tilingData.tileNum);
    op.Process();

    AscendC::PipeBarrier<PIPE_ALL>();
}
```

这段代码完成以下工作：

1. 调用`AscendC::InitSocState()`初始化Kernel运行状态。
2. 通过`REGISTER_TILING_DEFAULT(ElemwiseTilingData)`注册标准C++语法定义的`TilingData`结构体。
3. 通过`GET_TILING_DATA(tilingData, tiling)`从tiling参数中解析Host侧写入的`TilingData`。
4. 创建计算类对象。
5. 调用`Init`绑定GM地址并写入Tiling参数。
6. 调用`Process`执行搬运、计算和写回。
7. 调用`AscendC::PipeBarrier<PIPE_ALL>()`完成流水同步。

## 2. TilingData处理

Kernel侧需要读取Host侧Tiling函数写入的参数。不同算子的`TilingData`字段不同，常见设计如下：

| 算子类型 | TilingData中常见字段 | Kernel侧用途 |
|---|---|---|
| 逐元素二元算子 | `totalLength`、`tileNum` | 计算每个Block处理的数据范围和循环次数 |
| 归约类算子 | `outerLength`、`axisLength`、`innerLength` | 确定归约轴位置和每个Block处理的归约范围 |
| 矩阵类算子 | `m`、`n`、`k`、分块参数 | 指导矩阵分块、搬运和计算API调用 |

以逐元素二元算子为例，`TilingData`可以只包含总元素数和Tile数量：

```cpp
struct ElemwiseTilingData {
    uint32_t totalLength;
    uint32_t tileNum;
};
```

其中`totalLength`表示本次计算的总元素数，`tileNum`表示每个Block内部继续拆分的Tile数量。Kernel侧拿到这两个值后，可以计算每个Block处理的数据范围，并控制每个Block内部的循环次数。

### 2.1注册TilingData

标准C++语法定义`TilingData`时，需要在Kernel入口函数中使用`REGISTER_TILING_DEFAULT`注册结构体类型。

```cpp
REGISTER_TILING_DEFAULT(ElemwiseTilingData);
```

该注册动作告诉框架当前Kernel入口使用的`TilingData`类型。宏定义方式和多`TilingKey`场景下的注册方式会在多分支相关章节中展开。

### 2.2获取TilingData

注册后，通过`GET_TILING_DATA`把框架传入的tiling参数解析成结构体实例。

```cpp
GET_TILING_DATA(tilingData, tiling);
```

解析完成后，Kernel侧可以直接读取字段：

```cpp
op.Init(x, y, z, tilingData.totalLength, tilingData.tileNum);
```

这里的`tilingData.totalLength`和`tilingData.tileNum`来自Host侧Tiling函数。字段含义需要和[Host侧Tiling实现](../Host侧Tiling实现/基本流程.md)中的结构体定义保持一致。

## 3. Kernel实现基本流程

Kernel实现可以按三个层次理解：

1. Kernel入口函数负责接收框架参数、解析`TilingData`并调用计算类。
2. 计算类的`Init`负责把GM地址绑定到当前Block需要处理的数据段。
3. 计算类的`Process`负责在当前Block内循环执行搬运、计算和写回。

### 3.1定义计算类

计算类用于组织Kernel侧的主要逻辑。逐元素二元算子可以把实现封装成如下结构：

```cpp
template <uint32_t tileLength>
class KernelBinaryElemwise {
public:
    __aicore__ inline KernelBinaryElemwise() {}
    __aicore__ inline void Init(
        __gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z,
        uint32_t totalLength, uint32_t tileNum);
    __aicore__ inline void Process();

private:
    AscendC::GlobalTensor<DTYPE_X> xGm;
    AscendC::GlobalTensor<DTYPE_Y> yGm;
    AscendC::GlobalTensor<DTYPE_Z> zGm;
    uint32_t blockLength;
    uint32_t tileNum;
};
```

这里的`DTYPE_X`、`DTYPE_Y`和`DTYPE_Z`由算子原型中的输入输出dtype生成，用于在Kernel侧声明对应的C++数据类型。`tileLength`是模板参数，表示每次搬运和计算的数据长度。

### 3.2在Init中绑定GM地址

`Init`阶段根据Host侧传入的`totalLength`和运行时启动的`numBlocks`计算每个Block处理的数据量，再结合`GetBlockIdx()`把GM地址移动到当前Block负责的数据段。

```cpp
__aicore__ inline void Init(
    __gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z,
    uint32_t totalLength, uint32_t tileNum)
{
    this->blockLength = totalLength / AscendC::GetBlockNum();
    this->tileNum = tileNum;

    xGm.SetGlobalBuffer((__gm__ DTYPE_X*)x + this->blockLength * AscendC::GetBlockIdx(), this->blockLength);
    yGm.SetGlobalBuffer((__gm__ DTYPE_Y*)y + this->blockLength * AscendC::GetBlockIdx(), this->blockLength);
    zGm.SetGlobalBuffer((__gm__ DTYPE_Z*)z + this->blockLength * AscendC::GetBlockIdx(), this->blockLength);
}
```

这段代码中的关键点如下：

- `AscendC::GetBlockNum()`获取本次Kernel启动的`numBlocks`。
- `AscendC::GetBlockIdx()`获取当前Block编号。
- `blockLength`表示当前Block需要处理的元素数量。
- `SetGlobalBuffer`把原始GM地址包装成`GlobalTensor`，并把起始位置偏移到当前Block对应的数据段。

### 3.3在Process中执行搬运、计算和写回

`Process`阶段在当前Block内部循环处理数据。逐元素二元算子的基本处理逻辑如下：

```cpp
__aicore__ inline void Process()
{
    int32_t loopCount = this->tileNum * BUFFER_NUM;

    AscendC::LocalMemAllocator<AscendC::Hardware::UB> ubAllocator;
    AscendC::LocalTensor<DTYPE_X> xLocal = ubAllocator.Alloc<DTYPE_X, tileLength>();
    AscendC::LocalTensor<DTYPE_Y> yLocal = ubAllocator.Alloc<DTYPE_Y, tileLength>();
    AscendC::LocalTensor<DTYPE_Z> zLocal = ubAllocator.Alloc<DTYPE_Z, tileLength>();

    for (int32_t i = 0; i < loopCount; i++) {
        AscendC::DataCopy(xLocal, xGm[i * tileLength], tileLength);
        AscendC::DataCopy(yLocal, yGm[i * tileLength], tileLength);
        AscendC::Add(zLocal, xLocal, yLocal, tileLength);
        AscendC::DataCopy(zGm[i * tileLength], zLocal, tileLength);
    }
}
```

这段代码省略了事件同步，保留最主要的数据流：

```text
DataCopy输入到UB -> Add计算 -> DataCopy结果到GM
```

真实样例中还会配合`SetFlag`、`WaitFlag`和`PipeBarrier`控制MTE2、Vector、MTE3之间的执行顺序，确保搬入、计算和写回按正确依赖关系执行。

### 3.4CopyIn、Compute和CopyOut的关系

很多Kernel样例会把`Process`中的循环拆成`CopyIn`、`Compute`和`CopyOut`三个函数。前面的逐元素二元算子代码虽然直接写在循环中，逻辑上仍然可以按三段式理解。

```text
CopyIn:  DataCopy(xLocal, xGm, length)
         DataCopy(yLocal, yGm, length)

Compute: Add(zLocal, xLocal, yLocal, length)

CopyOut: DataCopy(zGm, zLocal, length)
```

当算子逻辑变复杂时，把三段拆成独立函数可以让代码更容易维护：

- `CopyIn`只处理GM到UB的数据搬运。
- `Compute`只处理UB上的计算API调用。
- `CopyOut`只处理UB到GM的结果写回。

对于归约类算子，`Compute`通常会包含分段归约和临时结果合并；对于矩阵类算子，`CopyIn`和`Compute`通常会围绕矩阵块、L0缓存和高阶计算API组织。三段式结构不限定具体计算类型，重点是把搬运、计算和写回的职责分清。

## 4. Kernel侧信息获取

### 4.1获取输入输出dtype和format

Kernel侧可以通过框架生成的宏获取输入输出的数据类型和格式信息。宏名由输入输出名称转换成全大写形式。

| 原型名称 | Kernel参数名 | dtype宏 | 原始dtype宏 | format宏 |
|---|---|---|---|---|
| `x` | `x` | `DTYPE_X` | `ORIG_DTYPE_X` | `FORMAT_X` |
| `y` | `y` | `DTYPE_Y` | `ORIG_DTYPE_Y` | `FORMAT_Y` |
| `z` | `z` | `DTYPE_Z` | `ORIG_DTYPE_Z` | `FORMAT_Z` |

三类宏的含义如下：

- `DTYPE_<Arg>`表示Kernel侧可直接使用的C++数据类型，例如`half`、`float`和`int32_t`。
- `ORIG_DTYPE_<Arg>`表示算子原型中的dtype枚举值，例如`ge::DT_FLOAT16`和`ge::DT_FLOAT`。
- `FORMAT_<Arg>`表示算子原型中的format枚举值，例如`ge::FORMAT_ND`。

示例：

```cpp
DTYPE_X xValue;

if (ORIG_DTYPE_X == DT_FLOAT) {
    // float路径
}

if (FORMAT_X == FORMAT_ND) {
    // ND格式路径
}
```

逐元素二元算子中，`DTYPE_X`、`DTYPE_Y`和`DTYPE_Z`通常用于声明`GlobalTensor`和`LocalTensor`的数据类型。归约类或矩阵类算子也可以使用这些宏选择不同dtype下的计算路径。

### 4.2获取Block信息

Kernel侧通过Block信息确定当前AICore处理哪一段数据。

```cpp
uint32_t blockNum = AscendC::GetBlockNum();
uint32_t blockIdx = AscendC::GetBlockIdx();
uint32_t blockLength = totalLength / blockNum;
```

`GetBlockNum()`返回本次Kernel启动的`numBlocks`，`GetBlockIdx()`返回当前Block编号。Host侧Tiling设置的`numBlocks`和Kernel侧这里的分段逻辑需要配套设计。

## 5. 使用约束

### 5.1入口参数顺序保持固定

Kernel入口参数按输入、输出、workspace、tiling的顺序排列。输入输出部分和算子原型声明顺序一致，workspace和tiling位于最后。

```cpp
extern "C" __global__ __aicore__ void binary_elemwise(
    __gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z,
    __gm__ uint8_t* workspace, __gm__ uint8_t* tiling)
{
}
```

### 5.2TilingData类型保持一致

Kernel侧注册和读取的`TilingData`类型需要和Host侧写入的结构体类型一致。

```cpp
REGISTER_TILING_DEFAULT(ElemwiseTilingData);
GET_TILING_DATA(tilingData, tiling);
```

如果同一个算子需要为不同分支使用不同`TilingData`结构体，需要结合`TilingKey`注册对应关系。具体写法会在多分支策略章节展开。

### 5.3GM地址访问需要按Block偏移

多Block并行时，每个Block需要处理不同的数据段。`SetGlobalBuffer`绑定GM地址时，需要结合`GetBlockIdx()`计算当前Block的起始地址。

```cpp
xGm.SetGlobalBuffer((__gm__ DTYPE_X*)x + blockLength * AscendC::GetBlockIdx(), blockLength);
```

### 5.4UB容量和Tile长度需要配套

`tileLength`决定每轮搬入UB的数据量。实际开发中需要结合输入输出dtype、临时Tensor数量、双缓冲数量和UB容量确定，避免单轮申请的UB空间超过硬件限制。

```cpp
AscendC::LocalTensor<DTYPE_X> xLocal = ubAllocator.Alloc<DTYPE_X, tileLength>();
AscendC::LocalTensor<DTYPE_Y> yLocal = ubAllocator.Alloc<DTYPE_Y, tileLength>();
AscendC::LocalTensor<DTYPE_Z> zLocal = ubAllocator.Alloc<DTYPE_Z, tileLength>();
```

### 5.5事件同步需要覆盖数据依赖

真实Kernel中，数据搬入、向量计算和结果写回由不同硬件单元执行。使用`SetFlag`、`WaitFlag`或`PipeBarrier`时，需要保证后一阶段读取数据前，前一阶段已经完成。

```cpp
AscendC::SetFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
AscendC::WaitFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
AscendC::Add(zLocal, xLocal, yLocal, tileLength);
```

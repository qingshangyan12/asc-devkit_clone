# 概述<a name="ZH-CN_TOPIC_0000002535192325"></a>

Ascend C的核心设计目标之一是实现跨代兼容。然而，每一代芯片在微架构上都存在独特的硬件特性，因此无法保证所有接口仅通过重编译就能达成完全的跨代兼容。基于这一前提，本手册旨在为Ascend C算子开发者提供系统化指导，帮助将算子Kernel代码从当前芯片平滑移植到目标代际芯片上运行，实现高效、可控的迁移。

如[SIMD-BuiltIn关键字](../编程指南/语言扩展层/SIMD-BuiltIn关键字.md) 中所述，\_\_NPU\_ARCH\_\_是Device侧AI Core代码中的一个预处理宏，用于标识AI处理器的架构版本。例如，Ascend 950PR/Ascend 950DT的\_\_NPU\_ARCH\_\_为3510，而Atlas A3 训练系列产品/Atlas A3 推理系列产品的\_\_NPU\_ARCH\_\_则为2201。因此，后续章节将以\_\_NPU\_ARCH\_\_为主线，重点介绍相邻代际芯片间的平滑迁移方法。

> [!NOTE]
> 为保证兼容性，建议开发者在开发过程中尽量避免使用以下接口或编程方式，否则需自行保证兼容性：
> - 非 Ascend C 公开接口、结构体，例如 `impl` 目录下的接口、结构体等；
> - 对芯片规格进行硬编码，例如：
>   ```cpp
>   constexpr uint32_t MAX_UB_SIZE = 256 * 1024;  
>   // 建议获取方式：
>   // ascendcPlatform.GetCoreMemSize(platform_ascendc::CoreMemType::UB, MAX_UB_SIZE);
>   ...
>   ```
> - 编译器内置 API（BuiltIn API），例如：
>   ```cpp
>   copy_gm_to_ubuf(input_1_local_UB, input_1, 0, 1, 8, 0, 0);
>   ```

建议开发者采用以下实践：
- 使用兼容的 API 接口。
- 若涉及特定领域的扩展特性，应在 Device 侧通过 [`__NPU_ARCH__` 编译宏](../编程指南/语言扩展层/SIMD-BuiltIn关键字.md)进行隔离，在 Host 侧通过 `SocVersion` 进行隔离。
- 使用 `<<<>>>` 直调或 [Tiling 模板编程](../编程指南/高级编程/高级特性/Aclnn算子工程化开发/Host侧Tiling实现/Tiling模板编程.md)。

## 推荐的编程范式<a name="ZH-CN_TOPIC_0000003021458967"></a>

为了提升算子跨代迁移的稳定性和性能，建议开发者采用以下现代化的编程范式。

### 使用 `__vector__` / `__cube__` 声明核函数类型

在声明核函数（Kernel Function）时，建议显式使用 [`__vector__` 或 `__cube__` 属性](../编程指南/语言扩展层/SIMD-BuiltIn关键字.md)来标识核函数的执行单元，而不是仅依赖 `__aicore__` 或通过宏间接判断。这样可以：

- 让编译器在编译期进行更精准的代码生成和优化。
- 使算子代码更具可读性和可维护性，核函数的执行单元一目了然。

**推荐写法**：

```cpp
// 矢量计算核函数
__vector__ __global__ void add_custom(__gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z)
{
    AscendC::InitSocState();
    // ... 计算逻辑 ...
    AscendC::PipeBarrier<PIPE_ALL>();
}

// 矩阵计算核函数
__global__ __cube__ void fill(__gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z)
{
    AscendC::InitSocState();
    // ... 计算逻辑 ...
    AscendC::PipeBarrier<PIPE_ALL>();
}
```

> [!NOTE]
> 详细说明请参考 [SIMD BuiltIn关键字 - 函数执行空间限定符](../编程指南/语言扩展层/SIMD-BuiltIn关键字.md#函数执行空间限定符)。在耦合模式的硬件架构上，`__vector__`/`__cube__` 修饰符不生效。

### 推荐使用静态Tensor编程

相比基于 `TPipe`/`TQue` 的传统编程方式，[静态Tensor编程](../编程指南/编程模型/AI-Core-SIMD编程/基于Tensor的C++编程/静态Tensor编程.md)避免了 TPipe 内存管理初始化过程（约数百纳秒的运行时开销），并通过直接构造指定地址和存储位置的 `LocalTensor` 提供更高的灵活性。

**传统 Pipe 方式**：

```cpp
__aicore__ inline void Compute(GM_ADDR dst, GM_ADDR src, uint32_t count)
{
    AscendC::TPipe pipe;
    AscendC::TQue<AscendC::TPosition::VECIN, 1> inQueue;
    AscendC::TQue<AscendC::TPosition::VECOUT, 1> outQueue;
    pipe.InitBuffer(inQueue, 1, count * sizeof(T));
    pipe.InitBuffer(outQueue, 1, count * sizeof(T));
    AscendC::LocalTensor<T> srcLocal = inQueue.AllocTensor<T>();
    AscendC::LocalTensor<T> dstLocal = outQueue.AllocTensor<T>();
    AscendC::DataCopy(srcLocal, srcGlobal, count);
    inQueue.EnQue(srcLocal);
    outQueue.DeQue(srcLocal);
    // ... 计算 ...
    outQueue.EnQue(dstLocal);
    inQueue.DeQue(dstLocal);
    AscendC::DataCopy(dstGlobal, dstLocal, count);
    inQueue.FreeTensor(srcLocal);
    outQueue.FreeTensor(dstLocal);
}
```

**推荐的静态Tensor方式**：

```cpp
__vector__ __global__ void add_custom(__gm__ uint8_t* x, __gm__ uint8_t* y, __gm__ uint8_t* z)
{
    AscendC::InitSocState();
    // 直接构造指定地址和存储位置的 LocalTensor
    AscendC::LocalTensor<half> xLocal(AscendC::TPosition::VECCALC, xAddr, MAX_DATA_COPY_LEN);
    AscendC::LocalTensor<half> yLocal(AscendC::TPosition::VECCALC, yAddr, MAX_DATA_COPY_LEN);
    AscendC::LocalTensor<half> zLocal(AscendC::TPosition::VECCALC, zAddr, MAX_DATA_COPY_LEN);

    AscendC::DataCopy(xLocal, xGm[startElement], curLen);
    AscendC::DataCopy(yLocal, yGm[startElement], curLen);
    AscendC::SetFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);
    AscendC::WaitFlag<AscendC::HardEvent::MTE2_V>(EVENT_ID0);

    AscendC::Add(zLocal, xLocal, yLocal, curLen);

    AscendC::SetFlag<AscendC::HardEvent::V_MTE3>(EVENT_ID0);
    AscendC::WaitFlag<AscendC::HardEvent::V_MTE3>(EVENT_ID0);
    AscendC::DataCopy(zGm[startElement], zLocal, curLen);

    AscendC::PipeBarrier<PIPE_ALL>();
}
```

> [!WARNING]
> 静态Tensor编程方式使用 `SetFlag`/`WaitFlag`/`PipeBarrier` 等 ISASI 底层同步接口，因此**无法保证跨硬件版本兼容**（与 `TPipe`/`TQue` 框架的目标恰好相反）。开发者需要在「性能收益」和「跨代兼容性」之间做出权衡：
> - 如果算子不需要跨代迁移，或性能要求极高，推荐使用静态Tensor编程。
> - 如果算子需要在多个架构版本间保持代码一致性和兼容性，建议使用 `TPipe`/`TQue` 框架编程。
>
> 更多使用约束和限制请参考 [静态Tensor编程 - 使用约束和限制](../编程指南/编程模型/AI-Core-SIMD编程/基于Tensor的C++编程/静态Tensor编程.md#使用约束和限制)。

### 两种方式的对比

| 维度 | 静态Tensor（新） | TPipe/TQue（传统） |
|:---|:---|:---|
| 内存分配 | `LocalTensor(TPosition::VECCALC, addr, size)` | `pipe.InitBuffer()` + `AllocTensor()` |
| 同步管理 | 手动 `SetFlag`/`WaitFlag`/`PipeBarrier` | 框架自动管理（`EnQue`/`DeQue`） |
| 初始化要求 | 必须显式调用 `InitSocState()` | 由 TPipe 自动完成 |
| 跨版本兼容 | 不保证（ISASI接口） | 框架保证 |
| 运行时开销 | 低（避免 TPipe 初始化开销） | 较高（约数百纳秒初始化开销） |
| 灵活性 | 高（完全自主管理内存和同步） | 中（框架封装约束） |

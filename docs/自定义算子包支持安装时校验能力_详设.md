# 自定义算子包支持安装时校验能力

## 一、需求描述

【需求概述】  
为自定义算子 run 包增加安装前共享库校验能力。默认情况下执行校验，校验失败时拦截安装；当用户显式指定 `--force` 时，允许跳过本次新增校验逻辑并继续安装。

本次校验范围仅覆盖 3 个核心 so：

- `opmaster`
- `opsproto`
- `opapi`

校验逻辑分为两类场景：

1. 环境变量 `ASCEND_HOME_PATH` 存在时，执行 `dlopen` 校验。
2. 环境变量 `ASCEND_HOME_PATH` 不存在时，执行 `arch + glibc` 校验。

此外，为避免安装脚本中 so 名称硬编码与真实产物名称不一致，本方案在构建期从 target 的 `OUTPUT_NAME` 读取真实 so 名称，并注入到 `install.sh` 中。

【资料变更】  
涉及安装脚本帮助信息更新，新增 `--force` 参数说明：

- `--force Skip shared library validation and continue installation`

【DFX】  
本次需求新增安装前拦截能力，主要用于提升错误安装场景下的问题前移发现能力与可维护性，具体如下：

1. 支持跨架构安装场景的安装前拦截。
2. 支持运行环境 `glibc` 版本过低场景的安装前拦截。
3. 支持在已有 CANN 环境下，通过 `dlopen` 提前验证共享库可加载性。

【验收标准】  
1. 默认执行安装前共享库校验。  
2. 校验失败时默认拦截安装。  
3. `--force` 可跳过本次新增校验逻辑。  
4. `ASCEND_HOME_PATH` 存在时进入 `dlopen` 校验分支。  
5. `ASCEND_HOME_PATH` 不存在时进入 `arch + glibc` 校验分支。  
6. so 名称从 target `OUTPUT_NAME` 注入，安装脚本不依赖固定产物名。  

## 二、方案详述

### 2.1 总体方案

在 `cmake/asc/fwk_modules/scripts/install.sh` 中新增统一入口 `validate_shared_libraries`，并在所有 `upgrade` 安装动作执行前调用。整体处理流程如下：

1. 解析安装参数，新增 `--force` 支持。
2. 根据构建期注入的 so 名称，解析待校验共享库路径。
3. 若 `FORCE_INSTALL="y"`，则直接跳过校验。
4. 若 `ASCEND_HOME_PATH` 存在，则执行 `dlopen` 校验。
5. 若 `ASCEND_HOME_PATH` 不存在，则执行 `arch` 与 `glibc` 校验。
6. 任一 so 校验失败，则直接退出安装流程。
7. 全部校验通过后，继续执行原有 `upgrade framework/op_proto/op_impl/op_api` 逻辑。

### 2.2 构建期 so 名称注入方案

在 `install.sh` 中增加 3 个占位变量：

- `opmaster_so_name=libcust_opmaster_rt2.0.so`
- `opsproto_so_name=libcust_opsproto_rt2.0.so`
- `opapi_so_name=libcust_opapi.so`

上述值仅作为模板占位值，不作为最终生效名称。

在 `cmake/asc/fwk_modules/func.cmake` 中，通过以下方式获取真实名称：

1. 使用 `get_target_property(... OUTPUT_NAME)` 获取 target 的 `OUTPUT_NAME`。
2. 通过独立的 `add_custom_target(... ALL ...)` 调用 `sed -i`。
3. 将构建目录下 `scripts/install.sh` 中的占位值替换为真实 so 名称。

对应注入对象如下：

1. `opmaster_so_name`
2. `opsproto_so_name`
3. `opapi_so_name`

该方案可保证：

1. 安装脚本使用真实产物名。
2. 若后续 cmake 中 target 的 `OUTPUT_NAME` 变化，无需同步修改脚本中的固定字符串。

### 2.3 安装参数设计

在 `install.sh` 中新增变量：

- `FORCE_INSTALL="n"`

参数解析增加：

- `--force`：将 `FORCE_INSTALL` 设置为 `y`

帮助信息文件 `help.info` 中同步增加 `--force` 描述。

### 2.4 共享库路径解析方案

新增 `resolve_so_paths`，仅处理本次定义的 3 个目标 so。

路径规则如下：

1. `opmaster`
   - 目录：`packages/vendors/<vendor>/op_impl/ai_core/tbe/op_tiling/lib/linux`
2. `opsproto`
   - 目录：`packages/vendors/<vendor>/op_proto/lib/linux`
3. `opapi`
   - 目录：`packages/vendors/<vendor>/op_api/lib`

对于 `opmaster` 与 `opsproto`，优先检查以下架构子目录：

- `aarch64`
- `x86_64`
- `x86`

处理规则如下：

1. 若上述架构目录存在，则该目录下对应 so 必须存在，并纳入校验。
2. 若多个架构目录同时存在，则每个存在目录下的目标 so 均需逐个校验。
3. 若上述架构目录均不存在，则回退到 `linux` 基础目录下直接查找同名 so。

对 `opapi`，直接按固定路径查找单个 so，不参与多架构目录遍历。

### 2.5 `ASCEND_HOME_PATH` 分支方案

当环境变量 `ASCEND_HOME_PATH` 存在时，仅执行 `dlopen` 校验，不执行 `arch/glibc` 校验。

处理方式如下：

1. 获取当前待校验 so 的绝对路径。
2. 获取该 so 所在目录 `so_dir`。
3. 构造本次校验使用的 `LD_LIBRARY_PATH`：
   - `${so_dir}`
   - `${sourcedir}/${vendordir}/op_api/lib`
4. 使用 `python3 + ctypes.CDLL(path, mode=os.RTLD_NOW)` 尝试加载目标 so。
5. 若加载失败，则打印错误并返回失败。

说明如下：

1. `ctypes.CDLL` 使用的是目标 so 的绝对路径，因此不会将主 so 加载为其他目录下的同名文件。
2. 如果存在多个架构目录，则按路径逐个独立校验；每次校验的 `LD_LIBRARY_PATH` 均以当前 so 所在目录为优先路径。
3. `ASCEND_HOME_PATH` 在该分支中仅用于判定用户已进入 CANN 环境，不额外推导并补充 CANN 安装目录下的库路径，相关依赖由用户现有环境变量提供。

失败日志格式如下：

`Failed to load libxxx.so wish env ASCEND_HOME_PATH(/path/to/xxx),error message is xxxxx.`

### 2.6 `ASCEND_HOME_PATH` 不存在分支方案

当环境变量 `ASCEND_HOME_PATH` 不存在时，执行 `arch + glibc` 双重校验。

#### 2.6.1 arch 校验

新增 `validate_so_arch`，处理流程如下：

1. 使用 `readelf -h` 提取 so 的 `Machine` 字段。
2. 使用 `map_arch` 将 `Machine` 映射为脚本内部统一架构值。
3. 使用 `uname -m` 获取当前运行环境架构。
4. 若 so 架构与环境架构不一致，则报错并返回失败。

当前映射关系如下：

- `Advanced Micro Devices X86-64` / `X86_64` / `x86_64` -> `x86_64`
- `AArch64` / `aarch64` -> `aarch64`

失败日志格式如下：

`The architecture of the shared library 'libxxx.so' (AArch64) is incompatible with the current running environment (x86_64).`

#### 2.6.2 glibc 校验

新增 `validate_so_glibc`，处理流程如下：

1. 从 so 中提取所有 `GLIBC_x.y` 符号。
2. 取产物依赖的最高 `glibc` 版本。
3. 使用 `ldd --version` 提取当前运行环境最高 `glibc` 版本。
4. 若 so 需求版本高于环境版本，则报错并返回失败。

失败日志格式如下：

`The shared library 'liba.so' was linked against a newer version of the GNU C Library (glibc). The current runtime enviroment has an older version of glibs, which does not provide the required symbols.`

### 2.7 `--force` 处理方案

若用户显式指定 `--force`，处理方式如下：

1. `validate_shared_libraries` 直接返回成功。
2. 打印警告日志：
   - `--force is enabled, skip shared library validation.`
3. 继续执行原有安装逻辑。

说明如下：

- `--force` 仅跳过本次新增的共享库校验逻辑。
- 原有安装参数与升级逻辑不受影响。

### 2.8 安装流程集成位置

在安装脚本中，完成安装目录准备后、执行如下动作前插入校验：

- `upgrade framework`
- `upgrade op_proto`
- `upgrade op_impl`
- `upgrade op_api`

插入逻辑如下：

1. 打印 `validate shared libraries before installation`
2. 调用 `validate_shared_libraries`
3. 若返回失败，则 `exit 1`

该设计可保证共享库兼容性问题在实际安装动作执行前被拦截。

## 三、新增接口

无

## 四、约束条件

1. 本次校验范围仅覆盖 `opmaster`、`opsproto`、`opapi` 三个 so。  
2. `ASCEND_HOME_PATH` 存在时，仅执行 `dlopen` 分支，不再执行 `arch/glibc` 校验。  
3. `opmaster` 与 `opsproto` 默认按架构目录优先处理，支持 `aarch64`、`x86_64`、`x86` 目录。  
4. `opapi` 维持固定路径查找，不按多架构目录扩展。  
5. glibc 校验依赖 `strings` 与 `ldd` 命令可用。  
6. arch 校验依赖 `readelf` 命令可用。  
7. 构建期 so 名称注入依赖 target 已正确设置 `OUTPUT_NAME`。  

## 五、兼容性分析

1. 本次为安装流程新增前置校验能力，属于功能增强。  
2. 原有 `--install-path`、`--install-for-all` 参数行为保持不变。  
3. 原有 upgrade、覆盖安装、卸载逻辑保持不变。  
4. 对单架构 run 包兼容。  
5. 对未来可能存在的多架构目录布局兼容。  
6. 通过构建期注入真实 so 名称，降低脚本固定名称与实际产物名称不一致带来的兼容性风险。  

## 六、维测分析

运行时维测分析如下：

1. 对共享库缺失场景进行安装前拦截。  
2. 对 `ASCEND_HOME_PATH` 存在时的 so 加载失败场景进行安装前拦截。  
3. 对共享库架构与当前环境不匹配场景进行安装前拦截。  
4. 对共享库依赖的 `glibc` 版本高于当前环境版本场景进行安装前拦截。  
5. 对用户显式指定 `--force` 的场景打印告警，并跳过本次新增校验。  

可观测性主要依赖安装脚本日志：

1. 校验入口日志。  
2. `--force` 跳过告警日志。  
3. `dlopen` 失败日志。  
4. `arch` 失败日志。  
5. `glibc` 失败日志。  

## 七、测试用例

### 7.1 参数行为测试

1. `./pkg.run`
   - 默认执行共享库校验
   - 校验失败时应拦截安装

2. `./pkg.run --force`
   - 跳过本次新增校验
   - 后续安装流程继续执行

### 7.2 `ASCEND_HOME_PATH` 分支测试

1. 设置 `ASCEND_HOME_PATH`。
2. 构造 so 可正常加载场景：
   - 校验通过，继续安装。
3. 构造 so 加载失败场景：
   - 输出标准错误日志。
   - 安装被拦截。

### 7.3 无 `ASCEND_HOME_PATH` 分支测试

1. `aarch64` 包安装到 `x86_64`：
   - 触发 `arch` 校验失败。
   - 安装被拦截。

2. `x86_64` 包安装到 `aarch64`：
   - 触发 `arch` 校验失败。
   - 安装被拦截。

3. so 依赖高版本 `glibc`，目标环境版本较低：
   - 触发 `glibc` 校验失败。
   - 安装被拦截。

### 7.4 多架构目录测试

1. `linux/aarch64` 目录存在：
   - 对应 so 必须被校验。

2. `linux/x86_64` 目录存在：
   - 对应 so 必须被校验。

3. `linux/x86` 目录存在：
   - 对应 so 必须被校验。

4. 多个架构目录同时存在：
   - 各目录下对应 so 均应纳入校验。

### 7.5 回归测试

1. `--install-path` 正常生效。  
2. `--install-for-all` 正常生效。  
3. 原有安装升级流程不变。  
4. 原有卸载流程不变。

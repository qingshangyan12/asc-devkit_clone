## 需求

在C API接口资料的Host侧调用示例中提供统一的空指针校验接口，用于替代各文档中临时定义的CHECK_NOT_NULL宏，减少重复代码并统一错误输出行为。该接口归类到docs/zh/api/Utils-API中，面向Host侧示例和算子Host侧辅助代码使用。

## 背景简述

当前asc_add.md试点中，Host侧通过aclrtMalloc申请src0_device、src1_device和dst_device后，需要手工调用CHECK_NOT_NULL进行校验。若后续批量改造C API调用示例，继续在每个文档中定义宏会导致命名、错误信息和退出策略不一致。因此需要在Utils API中新增统一接口，并在调用示例中引用该接口。

## 涉及领域

- 文档目录：docs/zh/api/Utils-API。
- 头文件目录：include/utils，建议新增Host侧校验相关头文件。
- 适用代码：Host侧示例代码、Host侧辅助代码。
- 不适用代码：Device侧__global__、__aicore__函数内部，不用于UB、GM、LocalTensor等Device侧对象校验。

## 方案详述

1. 新增接口命名

建议新增宏接口ASC_CHECK_NOT_NULL(ptr)，用于保留实参表达式名称、源文件名和行号；同时新增内部inline函数承载实际判断逻辑。

建议原型如下：

```cpp
namespace AscendC {
inline void CheckNotNull(const void* ptr, const char* ptrName, const char* file, int line)
{
    if (ptr == nullptr) {
        std::cerr << file << ":" << line << " " << ptrName << " is nullptr" << std::endl;
        std::exit(1);
    }
}
} // namespace AscendC

#define ASC_CHECK_NOT_NULL(ptr) AscendC::CheckNotNull((ptr), #ptr, __FILE__, __LINE__)
```

2. 头文件放置

建议新增头文件：

```text
include/utils/check/host_check.h
```

如项目更倾向于不新增一级目录，也可放置在：

```text
include/utils/base/host_check.h
```

该头文件仅依赖Host侧标准库头文件，例如<cstdlib>和<iostream>。不依赖Device侧AscendC头文件，避免Host工具接口与Kernel编程接口耦合。

4. 接口文档章节建议

ASC_CHECK_NOT_NULL.md按API参考页结构组织，至少包含：

- 产品支持情况：Host侧通用工具接口，随支持Host编译运行的产品系列使用。
- 功能说明：检查传入指针是否为空；为空时输出文件名、行号和指针名，并退出程序；非空时继续执行。
- 函数原型：展示宏形式ASC_CHECK_NOT_NULL(ptr)以及内部函数CheckNotNull的说明。
- 参数说明：ptr为待校验指针，ptrName、file、line由宏自动传入，用户不直接填写。
- 返回值说明：无。
- 约束说明：仅用于Host侧；不用于Device侧Kernel代码；建议在ACL内存申请、Stream/Event创建等通过输出参数返回资源地址或句柄的接口之后立即调用。
- 调用示例：展示aclrtMalloc后对device指针调用ASC_CHECK_NOT_NULL。

5. 调用规则

Host侧示例中，满足以下条件的指针或句柄需要调用ASC_CHECK_NOT_NULL：

- 由ACL或Runtime资源申请/创建接口通过输出参数写入，例如aclrtMalloc、aclrtMallocHost、aclrtCreateStream、aclrtCreateEvent等。
- 后续会作为aclrtMemcpy、Kernel Launch、同步、销毁或释放接口的入参继续使用。

以下对象不要求调用该接口：

- 普通栈变量、常量、标量。
- std::vector、std::string等RAII对象本身。
- std::vector::data()等临时获取的内部地址，除非代码显式保存为裸指针且后续跨步骤复用。
- Device侧LocalTensor、GlobalTensor、__ubuf__数组等Kernel内部对象。

8.领导又补充一个信息：用ICHECK的方式新增校验，并且在 c api的调用示例中使用ICHECK。我没懂这句话，把分析放在下面：

### 分析

这句话较可能表达的是：不要新增只检查空指针的`ASC_CHECK_NOT_NULL`接口，而是参考`ICHECK`的通用条件校验方式新增接口，在C API调用示例中通过条件表达式完成空指针校验，例如：

```cpp
ICHECK(src0_device != nullptr);
```

此处示例仅用于说明可能的调用形式，并非已确认的接口原型。

经当前仓库检索，`include`、`impl`、`examples`和`docs`目录中均不存在`ICHECK`的定义、头文件或调用示例。因此，当前无法确认领导所说的`ICHECK`是以下哪一种情况：

- CANN其他组件中已经存在、需要由asc-devkit直接引用的公共接口。
- 其他代码仓中使用的一种校验宏风格，需要在asc-devkit中重新实现。
- 要求新增的公共接口名称就叫`ICHECK`。

在确认前不应直接实现，因为还缺少以下接口契约：

- `ICHECK`接收的是“成立即通过”的条件，还是“成立即报错”的条件。
- 校验失败后是返回错误码、执行调用方指定的语句、抛出异常，还是终止进程。
- 错误信息是否需要包含条件表达式、文件名、行号和函数名。
- `ICHECK`所在的头文件及其所属组件，asc-devkit是否允许直接依赖该头文件。
- 该接口是仅供Host侧C++代码使用，还是还需要兼容C语言。

### 对原方案的影响

在上述信息确认前，原方案中的`ASC_CHECK_NOT_NULL`及`CheckNotNull`不应进入实现阶段。如果确认需要新增通用条件校验接口，则方案应调整为以下方向：

- 对外只提供`ICHECK(condition)`形式的通用校验接口，空指针校验由调用方传入`ptr != nullptr`条件完成。
- 文件名、行号和条件文本由宏自动传递，实际输出逻辑放入内部实现函数，内部函数不作为公共API介绍。
- 校验失败后的控制流不能默认使用`std::exit(1)`，需要按确认后的`ICHECK`既有语义处理。
- C API调用示例包含对应公共头文件，并在ACL内存申请接口返回成功后调用`ICHECK(device_ptr != nullptr)`。
- 接口文档、UT和调用示例均以最终确认的函数原型和失败行为为准。

# 同步接口标识参数类型修改问题分析

## 背景

同步接口将标识参数的数据类型统一为`uint16_t`，参数名称统一为`flag_id`。涉及以下四对接口：

- `asc_sync_inter_arrive`和`asc_sync_inter_wait`
- `asc_sync_subblock_arrive`和`asc_sync_subblock_wait`
- `asc_sync_block_arrive`和`asc_sync_block_wait`
- `asc_sync_intra_arrive`和`asc_sync_intra_wait`

正式函数原型形式如下：

```cpp
__aicore__ inline void asc_sync_xxx(pipe_t pipe, uint16_t flag_id);
```

接口文档约束`flag_id`的有效范围。对于超出范围的值，硬件使用其低4位或低5位作为实际的同步标识。为向既有`int64_t`用户提供明确的迁移指引，接口额外保留带弃用属性的`int64_t`兼容原型；该原型显式转换为`uint16_t`后调用正式接口，不存在独立的硬件实现路径。

## 问题一：既有int64_t调用如何迁移

### 问题

用户原有代码使用`const int64_t`或`constexpr int64_t`大值时，直接调用`uint16_t`正式接口会产生窄化转换告警；启用`-Werror`时，该告警会使编译失败，且无法明确提示应迁移到哪种类型。

### 分析

C++允许对函数重载进行整数转换，但本次为旧`int64_t`原型增加了带弃用属性的兼容重载：

```cpp
[[deprecated("NOTICE: int64_t flag_id overload is deprecated. Please use uint16_t flag_id instead")]]
__aicore__ inline void asc_sync_block_arrive(pipe_t pipe, int64_t flag_id)
{
    asc_sync_block_arrive(pipe, static_cast<uint16_t>(flag_id));
}
```

`int64_t`变量，包括顶层`const`或`constexpr`变量，会调用该兼容原型并得到明确的弃用提示。`uint16_t`变量仍调用正式接口。

<span style="color:red"><strong>重要限制：由于接口同时提供uint16_t正式原型和int64_t弃用兼容原型，普通整数字面量（例如1、65539）及uint64_t等其他整数类型无法确定应调用哪个原型，会在编译期报“调用歧义”错误，不能进入运行阶段。接口无法约束用户传参形式，因此必须将字面量显式转换为uint16_t。</strong></span>

具体行为和迁移写法如下：

```cpp
uint16_t id1 = 5;
asc_sync_block_arrive(PIPE_V, id1);

int64_t id2 = 5;
asc_sync_block_arrive(PIPE_V, id2); // 命中弃用原型；开启-Werror时编译失败

uint64_t id3 = 5;
asc_sync_block_arrive(PIPE_V, static_cast<uint16_t>(id3));

asc_sync_block_arrive(PIPE_V, static_cast<uint16_t>(5));

asc_sync_block_arrive(PIPE_V, 5); // 错误：uint16_t与int64_t重载歧义
asc_sync_block_arrive(PIPE_V, 5L); // 命中弃用原型；开启-Werror时编译失败
```

### 结论

正式接口为`uint16_t`。`int64_t`调用在迁移期间可继续编译，并产生“请使用`uint16_t`”的弃用告警；用户启用`-Werror`时，弃用告警会按其编译策略提升为错误。<span style="color:red"><strong>普通整数字面量和非int64_t整数实参必须由用户显式转换为uint16_t；否则会因重载歧义直接编译失败。</strong></span>

## 问题二：较大的整数转换为uint16_t后，是否改变硬件标识映射

### 问题

用户传入较大的`int64_t`数值时，兼容原型会先将其转换为`uint16_t`。其他整数类型由用户显式转换为`uint16_t`后调用。该转换是否会破坏后续按低4位或低5位建立的硬件同步标识映射？

例如：

```cpp
int64_t flag_id = 65537;
asc_sync_block_arrive(PIPE_V, flag_id);
```

### 分析

整数转换为`uint16_t`时保留低16位。硬件同步标识只使用低4位或低5位，这些位均包含在低16位中，因此转换不会丢失硬件映射所需的信息。

以低4位映射为例，新旧路径分别为：

```text
旧路径：65537 & 0xF = 1
新路径：uint16_t(65537) = 1，1 & 0xF = 1
```

对于低4位和低5位映射，以下关系成立：

```cpp
(static_cast<uint16_t>(x) & 0xF) == (x & 0xF);
(static_cast<uint16_t>(x) & 0x1F) == (x & 0x1F);
```

典型数值的映射结果如下。

**表 1**  典型数值的低位映射结果

| 用户传值 | 转换为`uint16_t`后的值 | 低4位结果 | 低5位结果 |
| ---: | ---: | ---: | ---: |
| 17 | 17 | 1 | 17 |
| 31 | 31 | 15 | 31 |
| 32 | 32 | 0 | 0 |
| 65535 | 65535 | 15 | 31 |
| 65536 | 0 | 0 | 0 |
| 65537 | 1 | 1 | 1 |

如果配对的`arrive`和`wait`接口使用相同的原始数值，两端会执行相同的`uint16_t`转换，并得到相同的硬件同步标识。例如：

```cpp
int64_t flag_id = 65537;
asc_sync_block_arrive(PIPE_V, flag_id);
asc_sync_block_wait(PIPE_V, flag_id);
```

上述两个接口最终使用的硬件同步标识均为1，配对关系不变。

### 结论

将函数形参改为`uint16_t`不会改变低4位或低5位硬件同步标识的映射关系。

## 问题三：用户传入负的int64_t数值时是否受到影响

### 问题

如果既有用户代码向`int64_t`形参传入负数，并依赖底层截取低4位或低5位后得到的同步标识，改为`uint16_t`函数原型是否会改变其运行行为？

### 运行行为分析

C++将负整数转换为`uint16_t`时，结果是该数值对65536取模。例如：

```cpp
int64_t flag_id = -1;
uint16_t converted = flag_id; // 65535，即0xFFFF
```

后续低位映射结果为：

```cpp
converted & 0xF;  // 15
converted & 0x1F; // 31
```

该结果与原实现直接使用负数的低4位或低5位一致。因此，只考虑运行行为时，负数经过`uint16_t`转换后仍能得到相同的硬件同步标识。

### 编译兼容性分析

`int64_t`实参会调用弃用兼容原型，因此不会在用户调用点产生隐式窄化转换告警，而是产生固定的弃用告警：

```cpp
int64_t flag_id = -1;
asc_sync_block_arrive(PIPE_V, flag_id);
```

如果用户工程启用`-Werror`，弃用告警会被提升为编译错误：

```bash
-Werror
```

这符合弃用接口的迁移目标：未开启`-Werror`的用户可继续构建并得到明确提示；开启`-Werror`的用户必须将`flag_id`变量调整为`uint16_t`。

如果用户代码保存了旧函数指针类型，仍应调整为正式`uint16_t`函数指针类型：

```cpp
using SyncFunc = void (*)(pipe_t, uint16_t);
SyncFunc func = &asc_sync_block_arrive;
```

### 最终约束

本次需求确认`int64_t`类型的用户输入一定为非负数，因此不将负数调用作为需要兼容和验证的用户场景。

## 总体结论

- 四对同步接口的正式函数原型均为`uint16_t flag_id`。
- `int64_t`兼容原型带弃用属性，并显式转换为`uint16_t`后转发到正式接口。
- 普通整数字面量和其他整数类型应显式转换为`uint16_t`后调用正式接口，避免与`int64_t`兼容原型产生重载歧义。
- `uint16_t`保留低16位，不会改变硬件使用的低4位或低5位同步标识。
- 配对的`arrive`和`wait`接口对相同输入执行相同转换，配对映射关系保持不变。
- `int64_t`用户输入保证为非负数，负数不纳入本次兼容范围。
- `int64_t`调用会产生包含迁移建议的弃用告警；启用`-Werror`时，该告警会提升为编译错误。
- 使用函数指针的用户应将类型调整为正式`uint16_t`原型。

## 建议验证范围

UT和NPU用例建议覆盖以下非负边界值：

- 有效范围边界：0、15和31。
- 低位截断边界：16、17、32和33。
- `uint16_t`边界：65535、65536和65537。
- 使用相同的大数值分别调用`arrive`和`wait`，验证两端映射到相同的硬件同步标识。
- 使用`int64_t`变量调用公开接口，验证弃用告警和低16位转发行为。
- 使用`uint16_t`变量调用公开接口，验证正式原型。
- 使用精确函数指针和类型断言，确认正式`uint16_t`接口和`int64_t`弃用兼容原型均符合预期。

## 适用范围

本文介绍[基础API](basic_api/basic_api.md)、[高阶API](adv_api/adv_api.md)、[C API](c_api/c_api.md)和[Tensor API](tensor_api/tensor_api.md)共同适用的说明和约束。

## 通用约束

### 地址对齐要求

硬件指令通常以固定大小的数据块、矩阵分形或向量访问粒度读写存储空间。地址满足对齐要求，才能保证指令按预期访问数据；地址未对齐时，可能在编译期被接口拒绝，也可能导致运行时异常或结果错误。当数据长度允许非对齐时，起始地址和步长仍可能不支持非对齐。

四类API都需要分别检查源地址、目的地址、临时空间地址、数据长度和步长。经过地址偏移、切片或分块后，实际传入接口的地址仍须满足对应存储位置和指令的对齐要求。常见存储位置的默认地址对齐要求如下，具体接口有更严格要求时，以接口说明为准：

| 存储位置 | 常见对齐要求 | 需要重点检查的API场景 |
| --- | --- | --- |
| Global Memory | 由具体指令和接口确定，不能仅依据存储位置判断。 | GM与UB、L1 Buffer或L0C Buffer之间的数据搬运，Scalar原子操作。 |
| UB | 通常为32Byte对齐。 | 基础API和高阶API的矢量计算、GM与UB之间的数据搬运、C API的UB指针接口。 |
| L1 Buffer | 通常为32Byte对齐。 | GM与L1 Buffer之间的搬运、L1 Buffer到L0A Buffer或L0B Buffer的搬运。 |
| L0A Buffer、L0B Buffer | 通常为512Byte对齐。 | 矩阵输入搬运和矩阵计算输入。 |
| L0C Buffer | 通常为64Byte对齐。 | 矩阵计算输出、L0C Buffer到GM或UB的结果搬运。 |
| BiasTable Buffer、Fixpipe Buffer | 通常为64Byte对齐。 | 量化、偏置和Fixpipe相关接口。 |
基础API和高阶API通常通过`LocalTensor`、`GlobalTensor`或Layout描述位置和范围，调用者仍须保证底层地址满足硬件要求；C API直接通过`__gm__`、`__ubuf__`、`__cbuf__`、`__ca__`、`__cb__`和`__cc__`等地址空间限定符表达位置；Tensor API则由Tensor的`location`、Layout和搬运原子对象共同确定访问粒度。三种描述方式不能互相替代。

应依据具体接口、存储位置、数据类型和目标产品确定对齐要求。[分类补充说明](#分类补充说明)中的默认对齐数值仅适用于采用该规则的接口。

### 原子操作

原子操作用于多个执行单元或多个AI Core并发访问同一Global Memory位置的场景。普通写入可能发生读改写覆盖：多个执行单元先后读取相同旧值，再分别写回结果，后写入的结果会覆盖先写入的结果。原子操作把指定位置的读改写写过程作为一个不可分割的操作，避免并发更新相互覆盖。

原子操作包括以下两种类型：

- 数据搬运随路原子操作：作用于后续写入Global Memory的数据搬运。
- Scalar原子操作：直接对指定Global Memory地址执行加、减、最大值、最小值、交换或比较交换。

四类API在涉及并发更新Global Memory数据时，可使用的原子操作接口及其描述如下。

| API类别 | 原子操作接口和使用方式 |
| --- | --- |
| 基础API | 数据搬运随路原子操作使用[SetAtomicAdd](basic_api/atomic_operations/SetAtomicAdd.md)、[SetAtomicMax](basic_api/atomic_operations/SetAtomicMax_ISASI.md)、[SetAtomicMin](basic_api/atomic_operations/SetAtomicMin_ISASI.md)配置后续搬运；使用[DisableDmaAtomic](basic_api/atomic_operations/DisableDmaAtomic.md)关闭。Scalar原子操作使用[AtomicAdd](basic_api/atomic_operations/AtomicAdd.md)、[AtomicMin](basic_api/atomic_operations/AtomicMin.md)、[AtomicMax](basic_api/atomic_operations/AtomicMax.md)、[AtomicExch](basic_api/atomic_operations/AtomicExch.md)和[AtomicCas](basic_api/atomic_operations/AtomicCas.md)。 |
| 高阶API | 高阶接口中涉及原子写入时，按接口说明配置对应的基础API原子能力；不要因为高阶接口使用Tensor或封装了数据搬运，就假定目的Global Memory自动具备原子更新语义。 |
| C API | 数据搬运随路原子操作使用[asc_set_atomic_add](c_api/atomic/datamove_atomic/asc_set_atomic_add.md)、[asc_set_atomic_max](c_api/atomic/datamove_atomic/asc_set_atomic_max.md)、[asc_set_atomic_min](c_api/atomic/datamove_atomic/asc_set_atomic_min.md)和[asc_disable_dma_atomic](c_api/atomic/datamove_atomic/asc_disable_dma_atomic.md)；Scalar原子操作使用[asc_atomic_add](c_api/atomic/scalar_atomic/asc_atomic_add.md)、[asc_atomic_min](c_api/atomic/scalar_atomic/asc_atomic_min.md)、[asc_atomic_max](c_api/atomic/scalar_atomic/asc_atomic_max.md)、[asc_atomic_exch](c_api/atomic/scalar_atomic/asc_atomic_exch.md)和[asc_atomic_cas](c_api/atomic/scalar_atomic/asc_atomic_cas.md)。 |
| Tensor API | Tensor API的同步控制、原子操作等底层控制能力由C API提供。需要原子更新时，使用对应的C API原子接口，并同时满足Tensor API的Layout、访问范围和同步要求。 |
使用原子累加时，初始值写入和后续原子更新必须建立明确的执行顺序，避免普通写入覆盖尚未完成的原子更新。原子操作保证单次更新的不可分割性，不保证多个原子更新按源码顺序完成；浮点累加还可能因执行顺序不同而产生数值差异。需要确定执行顺序时，仍需使用适用的核内或核间同步接口。
确定性计算的具体要求请参考基础API的[原子操作特性说明](basic_api/atomic_operations/key_features.md)和C API的[原子操作特性说明](c_api/atomic/key_features.md)。

### 数据依赖与同步

四类API在使用过程中都需要根据实际的数据依赖和执行关系考虑同步问题，具体同步方式以各类API及接口的说明为准。

- 存在数据依赖时，保证生产者完成数据写入后，消费者再读取；覆盖或复用存储空间前，保证此前相关读写已完成。
- 对异步执行的搬运和计算，不能仅以源码中的调用顺序或函数返回判断操作已经完成。
- 根据执行流水、核内或核间的依赖关系，采用接口要求的同步机制。核内同步不能替代核间同步。
- 区分API内部已处理的同步与调用者需要保证的外部依赖。是否需要显式同步及使用哪种接口，以相应API说明为准，不要求每次调用后统一增加全流水同步。

AI Core中的数据搬运、矢量计算和矩阵计算由不同的硬件流水线执行，同一核内的各流水线以及不同核之间的指令都可能异步执行。例如，从GM搬入UB的数据通常由MTE2流水线写入，后续矢量计算由Vector流水线读取；不同核之间也可能通过Global Memory或片上存储交换数据。即使相关接口在源码中按先后顺序调用，后续操作也可能在前序数据写入完成前开始执行。因此，存在同一AI Core内不同流水线之间的数据依赖时，需要通过核内同步建立执行先后关系；存在不同A核之间的数据依赖时，需要通过核间同步建立执行先后关系。

以同一个核内的“GM搬入UB、矢量计算、UB搬出到GM”过程为例，需要在计算读取输入前等待搬入完成，在搬出读取结果前等待计算完成；循环复用UB缓冲区时，还需要等待上一轮读取完成后，才能向该缓冲区写入下一轮数据。同步应覆盖实际存在依赖的流水线，使没有依赖的搬运和计算仍能并行执行。

四类API在核内流水依赖场景下可使用的同步接口如下：

| API类别 | 不同流水线之间的同步 | 同一流水线内的同步 |
| --- | --- | --- |
| 基础API | 使用[SetFlag/WaitFlag](basic_api/sync_control/intra_core_sync/SetFlag_WaitFlag_ISASI.md)设置和等待流水事件，或使用[TQueSync](basic_api/sync_control/intra_core_sync/TQueSync.md)类的同名成员函数管理同步。Ascend 950系列产品还可使用[Mutex](basic_api/sync_control/intra_core_sync/Mutex_ISASI.md)的[Lock](basic_api/sync_control/intra_core_sync/Lock.md)/[Unlock](basic_api/sync_control/intra_core_sync/Unlock.md)。 | 使用[PipeBarrier](basic_api/sync_control/intra_core_sync/PipeBarrier_ISASI.md)等待指定流水线的前序指令完成。 |
| 高阶API | 高阶API的部分接口会提供明确的同步模式或配套等待接口。例如，Matmul接口通过`sync`参数区分同步、异步模式，异步模式需要调用配套的等待接口；[Fill](adv_api/tensor_transform/Fill.md)文档明确要求调用者在特定流水依赖场景下插入同步。需要调用者处理的跨流水依赖，使用接口文档规定的基础API同步接口。 | 对需要由调用者处理的单流水依赖，使用[PipeBarrier](basic_api/sync_control/intra_core_sync/PipeBarrier_ISASI.md)。 |
| C API | 使用[asc_sync_notify](c_api/sync/intra_core_sync/asc_sync_notify.md)/[asc_sync_wait](c_api/sync/intra_core_sync/asc_sync_wait.md)设置和等待流水事件；Ascend 950系列产品还可使用[asc_lock](c_api/sync/intra_core_sync/asc_lock.md)/[asc_unlock](c_api/sync/intra_core_sync/asc_unlock.md)。 | 使用[asc_sync_pipe](c_api/sync/intra_core_sync/asc_sync_pipe.md)等待指定流水线的前序指令完成。 |
| Tensor API | 配合C API的[asc_sync_notify](c_api/sync/intra_core_sync/asc_sync_notify.md)/[asc_sync_wait](c_api/sync/intra_core_sync/asc_sync_wait.md)或适用的[asc_lock](c_api/sync/intra_core_sync/asc_lock.md)/[asc_unlock](c_api/sync/intra_core_sync/asc_unlock.md)处理流水间依赖。 | 配合C API的[asc_sync_pipe](c_api/sync/intra_core_sync/asc_sync_pipe.md)处理单流水依赖。 |

不同AI Core之间存在执行顺序要求时，需要使用核间同步接口。四类API的核间同步接口如下：

| API类别 | 核间同步接口 |
| --- | --- |
| 基础API | 硬件核间同步使用[CrossCoreSetFlag](basic_api/sync_control/inter_core_sync/CrossCoreSetFlag_ISASI.md)/[CrossCoreWaitFlag](basic_api/sync_control/inter_core_sync/CrossCoreWaitFlag_ISASI.md)、[SyncAll](basic_api/sync_control/inter_core_sync/SyncAll.md)、[NotifyNextBlock](basic_api/sync_control/inter_core_sync/NotifyNextBlock.md)和[WaitPreBlock](basic_api/sync_control/inter_core_sync/WaitPreBlock.md)；软仿核间同步使用[IBSet](basic_api/sync_control/inter_core_sync/IBSet.md)/[IBWait](basic_api/sync_control/inter_core_sync/IBWait.md)。 |
| 高阶API | 高阶API的核间同步由具体接口场景决定。例如，Matmul内部可能使用[CrossCoreSetFlag](basic_api/sync_control/inter_core_sync/CrossCoreSetFlag_ISASI.md)/[CrossCoreWaitFlag](basic_api/sync_control/inter_core_sync/CrossCoreWaitFlag_ISASI.md)，使用Matmul对象时需避免flagId冲突；HCCL接口的跨核依赖按其接口说明使用[SyncAll](basic_api/sync_control/inter_core_sync/SyncAll.md)或其他核间同步接口。 |
| C API | 使用四类核间同步接口：`asc_sync_block_arrive`/`asc_sync_block_wait`、`asc_sync_inter_arrive`/`asc_sync_inter_wait`、`asc_sync_intra_arrive`/`asc_sync_intra_wait`、`asc_sync_subblock_arrive`/`asc_sync_subblock_wait`。 |
| Tensor API | Tensor API的核间同步能力由C API提供，使用适用的C API核间同步接口完成跨核依赖。 |

核内流水同步不能替代核间同步。
同一流水线的指令按顺序发射，也可能存在前后指令执行时间重叠的情况；当具体接口要求对同流水的数据依赖插入屏障时，应使用表中的单流水同步接口。上述接口的产品支持范围、可同步的流水组合及事件或Mutex资源的使用限制，见各接口说明。

### 控制状态与调用顺序

- 接口要求初始化、参数配置或资源准备时，应先完成相应步骤，再执行依赖这些状态的操作。
- 修改掩码、原子操作模式等会影响后续执行的控制状态时，应遵循接口规定的有效范围和恢复要求，确保后续操作使用预期状态。
- 混合使用不同类别的API时，检查共享控制状态和资源的影响；不能假定切换API类别会自动初始化或恢复硬件状态。

## 分类补充说明

以下内容保留基础API和高阶API使用的具体规则，各节分别说明适用范围。C API和Tensor API的存储描述、对齐和重叠限制以各自接口文档为准。

### 数据存储位置的描述方式

本节分别说明四类API对数据存储位置的描述方式：

- 基础API和部分高阶API的`GlobalTensor`、`LocalTensor`使用逻辑位置（[TPosition](basic_api/aux_data_structures/TPosition.md)）表达存储位置，从而隐藏硬件架构差异。
- Tensor API不使用`TPosition`，而是通过`location`和`PtrPattern`描述物理存储位置。
- C API使用带地址空间限定符的指针类型描述存储位置。
- 不同描述方式不能直接互换，具体接口仍以自身文档为准。

| `location::bias` | BiasTable Buffer | 偏置存储，AI Core内部物理存储单元，通常用于存储矩阵计算所需的Bias（偏置）数据，与逻辑内存AscendC::TPosition::C2相对应。 |
| `location::fixbuf` | Fixpipe Buffer | AI Core内部物理存储单元，通常用于存储Fixpipe搬运过程中所需的量化参数等数据，与逻辑内存AscendC::TPosition::C2PIPE2GM相对应。 |

Tensor API中的`location`表示物理位置类别，`PtrPattern`用于将该位置类型与指针或迭代器绑定。创建Tensor或内存指针时，位置标记必须与实际存储位置一致。

#### C API：地址空间限定符

C API通常直接使用带地址空间限定符的指针表达操作数所在的存储位置。限定符不等同于`TPosition`，也不等同于Tensor API的`location`类型。

**表4**  C API常用地址空间限定符

| 地址空间限定符 | 物理存储位置 | 说明 |
| --- | --- | --- |
| `__gm__` | Global Memory | 设备端的主内存，AI Core的外部存储，用于存储大规模数据，但需要优化访问模式以提升性能。 |
| `__ubuf__` | Unified Buffer（UB） | AI Core内部存储单元，主要用于矢量计算，与逻辑内存AscendC::TPosition::VECIN、AscendC::TPosition::VECOUT、AscendC::TPosition::VECCALC相对应。 |
| `__cbuf__` | L1 Buffer | AI Core内部物理存储单元，空间相对较大，通常用于缓存矩阵计算的输入数据。矩阵计算的输入一般需要从GM搬运到L1 Buffer，然后分别搬运到L0A Buffer和L0B Buffer。L1 Buffer与逻辑内存AscendC::TPosition::A1、AscendC::TPosition::B1相对应。 |
| `__ca__` | L0A Buffer | AI Core内部物理存储单元，通常用于存储矩阵计算的左矩阵，与逻辑内存AscendC::TPosition::A2相对应。 |
| `__cb__` | L0B Buffer | AI Core内部物理存储单元，通常用于存储矩阵计算的右矩阵，与逻辑内存AscendC::TPosition::B2相对应。 |
| `__cc__` | L0C Buffer | AI Core内部物理存储单元，通常用于存储矩阵计算的结果，与逻辑内存AscendC::TPosition::CO1相对应。 |
| `__fbuf__` | Fixpipe Buffer | AI Core内部物理存储单元，通常用于存储Fixpipe搬运过程中所需的量化参数等数据，与逻辑内存AscendC::TPosition::C2PIPE2GM相对应。 |

### 通用地址重叠约束<a name="section668772811100"></a>

本节仅适用于基础API中引用本节的Tensor高维切分计算接口，不适用于四类API的所有计算接口。在具体接口允许源操作数与目的操作数地址重叠时，使用同一存储空间需满足以下约束：

-   单次迭代内：源操作数与目的操作数必须100%完全重叠，不支持部分重叠。
-   多次迭代间：不支持前序迭代的目的操作数与后序迭代的源操作数重叠。例如，第N次迭代的目的操作数是第N+1次的源操作数（如下图所示）。在这种情况下，第N次迭代可能会改写覆盖源操作数的数值，导致无法得到预期结果。特别地，对于部分双目计算类的API（Add、Sub、Mul、Max、Min、AddRelu、SubRelu），当数据类型为half、int32\_t、float时，支持前序迭代的目的操作数与后序迭代的源操作数重叠：仅针对目的操作数和第二个源操作数重叠的情况，且src1RepStride或者dstRepStride必须为0。
-   多次迭代间：不支持前序迭代的目的操作数与后序迭代的目的操作数重叠。例如，第一轮循环写入的DataBlock编号为0、2、4、6、8、10、12、14，第二轮循环写入的编号为8、10、12、14、16、18、20、22，即第二轮迭代会覆盖第一轮迭代写入的后4个DataBlock，导致无法得到预期的结果。

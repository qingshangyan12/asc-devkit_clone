# Regbase API迁移指导

本节介绍3510到9201的Regbase计算接口适配方法。硬件指令变化可能由接口内的软件仿真吸收，但仍需检查编译资源、参数边界和精度。

**表1** Regbase API兼容性问题索引

| 功能分类 | 涉及接口 | 兼容性影响 | 迁移指导 |
|----------|----------|------------|----------|
| 归约 | Reduce、ReduceDataBlock、PairReduceElem | 原接口软仿可能额外使用一个寄存器 | [归约接口](#reduce-migration)、[寄存器压力](#register-pressure-migration) |
| 数据重排 | Interleave、DeInterleave的MaskReg及RegTensor重载 | 原接口软仿可能额外使用一个寄存器 | [交织与去交织](#interleave-migration) |
| 向量移位 | ShiftLeft、ShiftRight | 负移位不支持；b64软仿可能额外使用两个寄存器 | [非负移位](#shift-migration) |
| 标量移位 | ShiftLefts、ShiftRights | b8范围兼容处理可能增加Scalar开销；b64存在软仿资源开销 | [b8标量移位](#b8-scalar-shift-migration) |
| 指数计算 | Exp | 部分fp16输入与3510结果相差1 ULP | [Exp精度](#exp-precision-migration) |

## 归约接口<a id="reduce-migration"></a>

**说明**：9201删除原SUM、MAX、MIN相关归约硬件指令，并增加新版本指令。Reduce、ReduceDataBlock和PairReduceElem的原接口通过软仿兼容时，可能额外使用一个寄存器，其中PairReduceElem需重点检查SUM场景。

**兼容方案**：

- 使用目标SDK公开的归约接口，保留原mask、累加类型、结果布局及索引语义。需要适配旧封装名时，应先确认其返回内容，不能只替换接口名称。
- 例如，需要将旧封装中的ReduceMax归一到Regbase Reduce接口时，可使用`AscendC::Reg::Reduce<AscendC::Reg::ReduceType::MAX>(dstReg, srcReg, mask)`。这并不表示所有层级名为ReduceMax的接口均可机械替换。
- 如果配套SDK公开了新的归约版本，可在核对语义后采用。硬件指令的v2后缀不代表存在同名`ReduceV2`或`asc_reduce_*_v2`公开API，不应直接调用编译器BuiltIn替代公开接口。
- 对接近寄存器上限的内核，按[寄存器压力适配](#register-pressure-migration)缩短活跃区间或调整分块。

**迁移示例**：`dstReg`、`srcReg`和`mask`为已经初始化且类型匹配的Regbase变量，以下展示公开的归约求最大值调用。

```cpp
AscendC::Reg::Reduce<AscendC::Reg::ReduceType::MAX>(dstReg, srcReg, mask);
```

MAX/MIN同时涉及值和索引时，应按[Reduce](../../../../api/SIMD-API/basic_api/reg_vector_compute/reduction_compute/Reduce.md)约束解释结果，验证相同最值的索引选择、全mask关闭、NaN及正负零。SUM应核对累加顺序和精度，不要将“保持求和功能”等同于任意重写都逐位一致。

## 交织与去交织<a id="interleave-migration"></a>

**说明**：Interleave、DeInterleave的MaskReg和RegTensor重载都需要检查。原硬件指令删除后，兼容实现可能通过新版本指令及额外寄存器保留两份输出的语义。

**兼容方案**：

1. 核对元素位宽、交织粒度、两个目的寄存器的顺序及后续消费位置。MaskReg上的b8/b16/b32表示掩码组织粒度，不能直接等同于RegTensor的数据类型。
2. 保留必要的两份输出；若希望采用目标SDK公开的单份输出接口，须核对输出选择和布局，不能将双输出接口简单改成单输出接口。
3. 如果两份输出仅有一份实际使用，检查优化后是否已消除无用结果，再评估改写收益。
4. 对大规模展开或长流水内核，检查额外临时寄存器是否与原有输入、输出同时存活。

**验证建议**：用通道编号作为输入验证交织/去交织后的位置，分别覆盖MaskReg和RegTensor、每种位宽及两份输出，避免只比较最终统计值而漏掉布局错误。

## 移位<a id="shift-migration"></a>

### 删除负移位能力

**说明**：9201移位硬件不再支持负移位量。对于VSHL/VSHR，硬件的移位量类型由s8/s16/s32变为u8/u16/u32。公开API是否保留有符号参数、是否提供无符号重载，应以配套SDK为准。接口原型接受有符号类型不代表允许负值。

**兼容方案**：

- 对ShiftLeft、ShiftRight、ShiftLefts、ShiftRights，沿参数来源检查字面常量、模板参数、Tiling、标量运算以及向量每个有效通道，确认移位量非负。
- 如果算法使用正负号表达两个移位方向，应显式选择左移或右移，将非负的幅度传入对应接口。处理最小负数的绝对值时应避免有符号溢出。
- 不要直接把负值转换成无符号类型。这样的转换不能保留原算法意图。
- 核对大于或等于数据位宽时的填充行为：算术右移按符号位填充，逻辑右移和左移按零填充。测试应基于接口语义，不能直接使用C++中超位宽移位的未定义行为作为参考结果。

例如，`16 - pageBits`只有在`pageBits <= 16`时才能保证非负；应在Tiling或模板约束处保证输入范围，而不是依赖调用时强制转换。

### b8标量移位<a id="b8-scalar-shift-migration"></a>

**说明**：b8表示被移位数据为8位，例如RegTensor中的int8_t/uint8_t或C API的vector_int8_t/vector_uint8_t；它与移位量的类型是两个独立维度。3510的标量移位量为s16，9201硬件的b8标量移位量为u8。

如果旧的合法非负移位量超过255，直接转换为u8会发生回绕。例如，256窄化后为0，会把原本的超位宽移位变成不移位。按兼容方案，应先将超范围移位量饱和到255，再进行窄化。

**迁移示例（范围转换逻辑）**：以下仅展示已保证非负的s16移位量转为u8的逻辑，不代表所有公开API都接受u8实参。

```cpp
// 前提：shift >= 0；负数应在进入本逻辑前按算法要求处理。
uint8_t shift8 = shift > 255 ? uint8_t{255} : static_cast<uint8_t>(shift);
```

**表2** b8标量移位场景与处理方式

| 移位量来源 | 兼容性分析 | 建议 |
|------------|------------|------|
| 字面常量2、4等，位于[0, 255] | 范围判断可在内联和常量传播后折叠，不需要执行超范围分支。 | 保留清晰的常量表达，检查优化后的目标代码。不能仅因使用b8就认定有Scalar分支开销。 |
| 模板常量或可证明范围的表达式 | 优化器可能折叠判断或证明分支不可达。 | 用模板约束或范围约束表达前提，确认优化结果。 |
| 运行时s16值，保证非负 | SDK可能需要比较、饱和及窄化，存在额外开销。 | 若配套SDK公开了u8标量重载且业务保证[0, 255]，可使用该重载；否则保留兼容处理。 |
| 非负值可能超过255 | 直接窄化会改变语义。 | 使用已提供兼容处理的SDK，或在算子中按接口要求显式处理范围。 |
| 值可能为负 | 不满足移位接口约束。 | 先按算法意图拆分移位方向和幅度。 |

常量参数是否最终编码为机器指令的立即数字段，取决于指令形式和编译器；即使先装入标量寄存器，范围判断仍可被折叠。移位量为常量也不表示整个向量移位可以删除，被移位数据通常仍在运行时产生。

> [!NOTE]
> 部分SDK的ShiftLefts/ShiftRights公开实现仍要求ScalarT为int16_t，C API的b8标量重载也可能接受uint16_t。不能仅把实参强制转换为uint8_t，就认定选择了专用u8重载或绕过兼容逻辑。采用新增重载前，应先核对配套SDK的公开类型约束；相关C API适配见[C API移位迁移](./c_api_migration.md#c-api-shift-migration)。

### b64移位

**说明**：64位移位的兼容实现可能额外使用两个寄存器。其风险与b8的标量范围判断不同，应独立评估。

**兼容方案**：确认确实使用int64_t/uint64_t重载后，再检查寄存器峰值、循环展开及溢出空间。不要将所有ShiftLeft/ShiftRight调用都按b64额外开销统计。

## 寄存器压力适配<a id="register-pressure-migration"></a>

**说明**：原归约、交织/去交织接口的兼容实现可能额外使用一个寄存器，b64移位可能额外使用两个寄存器。如果内核因此超过硬件寄存器限制，编译器会使用UB保存溢出的寄存器数据，可能使性能下降。按本次迁移约束，超过6KB的UB溢出空间限制可能导致编译失败；该限制针对寄存器溢出空间，不能用UB总容量384KB替代。

**兼容方案**：

1. 在实际启用的编译优化配置下检查资源报告和诊断信息，定位寄存器峰值及溢出，不能简单按API调用次数累加额外寄存器数量。
2. 缩短临时变量活跃区间，及时消费归约或交织结果，减少同时保留的输入、输出和中间寄存器。
3. 必要时降低循环展开程度、减少流水并行级数或缩小tile，并重新评估搬运重叠和总耗时。
4. 如果配套SDK提供新的公开接口，核对语义后再替换；不要依赖内部BuiltIn规避资源问题。
5. 核对SDK及编译器建议的寄存器优化配置。不要假设某个未确认的编译开关在所有版本上存在或默认开启。

**验证建议**：同时比较优化后指令、寄存器使用、溢出UB空间和算子端到端耗时。编译通过仅表示满足编译约束，不表示资源开销和性能没有变化。

## Exp精度<a id="exp-precision-migration"></a>

**说明**：9201的exp硬件指令变化，使部分fp16输入的计算结果与3510相比存在1 ULP差异。本项涉及Regbase Exp、基于LocalTensor的基础Exp、asc_exp以及使用相应fp16计算路径的高阶激活接口，不应推广为所有数据类型或所有输入均有误差。

**兼容方案**：

- 对逐位比较3510输出的用例，区分架构间结果差异与相对数学参考值的精度要求，按算子的误差标准进行判定。
- 对精度敏感场景，将输入转换为fp32，在fp32中计算Exp，再按输出类型和舍入要求转换。该方案可避开fp16 Exp指令的差异，但不承诺所有计算在两代芯片上逐位一致。
- 如果算子已经在fp32计算Exp，不应仅因输入或输出为fp16就认定受此项变更影响。

**迁移示例**：以下为LocalTensor基础API的计算片段，`srcLocal`和`dstLocal`为half类型，`srcFp32`和`dstFp32`为已分配的float临时张量，长度均不小于`count`。按实际数据依赖补全流水同步。

```cpp
AscendC::Cast(srcFp32, srcLocal, AscendC::RoundMode::CAST_NONE, count);
AscendC::Exp(dstFp32, srcFp32, count);
AscendC::Cast(dstLocal, dstFp32, AscendC::RoundMode::CAST_RINT, count);
```

改用fp32会增加临时存储及搬运/转换开销，需要同步调整UB预算。验证应覆盖常见值、下溢和上溢附近输入、极值，以及接口支持的特殊值，分别记录ULP、绝对误差和相对误差。

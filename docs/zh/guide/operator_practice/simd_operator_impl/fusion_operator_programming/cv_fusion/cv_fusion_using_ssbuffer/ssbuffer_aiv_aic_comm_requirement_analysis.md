# 基于SSBuffer的AIC/AIV通信需求分析

## 需求

面向Ascend 950PR/Ascend 950DT，在一个`__mix__(1, 2)`任务中建立一条简单、可复用的AIV到AIC通信路径。两个AIV各自发送少量控制消息，AIC负责接收和处理。消息直接放在AI Core内部的SSBuffer中，不需要为了传递这些控制信息绕行GM。

本需求要解决的不是大块数据搬运，而是下面这类“小消息”通信：

- 数据准备完成通知。
- 计算任务消息或状态信息。
- 地址、长度、序号等描述信息。

通信过程需要满足以下要求：

1. AIC和两个AIV必须运行在同一个Mix任务中，共享同一片SSBuffer。
2. 每个AIV使用自己的队列，互不覆盖，也不需要争抢同一个写入位置。
3. 发送方写完消息后，通过核间同步接口发送消息准备完成通知；接收方收到通知后才能读取消息。
4. AIC处理完消息后清除消息头，并通过核间同步接口返回ACK。只有收到ACK后，AIV才能复用对应的消息空间。
5. SSBuffer中的初始内容不能假定为0。每次任务启动时，由AIC统一清理消息头，再通知两个AIV开始发送。
6. 队列需要支持回绕。即使发送消息数超过队列深度，也不能覆盖尚未消费的消息。
7. Host侧需要检查发送方、序号、消息数据和校验值，确认整个通信过程没有丢消息、消息进入错误队列或读到旧消息。

这套方案只负责自定义控制消息的传递，不替代GM、UB或L1 Buffer，也不负责UB到L1 Buffer的数据搬运。

## 背景简述

本说明主要依据以下两份材料整理：

- [SSBuffer基础知识](./basics.md)，用于确认SSBuffer的用途、容量、访问限制和推荐的通信顺序。
- [SSBuffer AIV/AIC通信C API样例](../../../../../../../../examples/02_simd_c_api/03_c_api/05_sync_control/ssbuf_aiv_aic_comm/ssbuf_aiv_aic_comm.asc)，用于还原一套可以落地的消息布局、收发流程和Host侧校验方法。

SSBuffer是AI Core内部的物理存储单元。在`__mix__(1, 2)`模式下，一个AIC和两个AIV共享3KB空间。它离AIC和AIV都很近，适合放控制消息，但容量不大，因此需要先划好区域，再约定谁写、谁读、什么时候可以复用。

当前样例把SSBuffer前2KB分成两条消息队列：AIV0和AIV1各使用一条，每条队列深度为8，每条消息占128B。每个AIV发送12条消息，特意让队列发生一次回绕，用来验证消息空间复用是否可靠。剩余1KB没有使用，也不能默认交给其他协议；同一个任务中如果还要使用内部KFC路径、Matmul高阶API或其他SSBuffer方案，需要先统一规划整片空间。

本次分析使用的环境和支持范围如下：

| 项目 | 取值 |
| --- | --- |
| Devkit | 当前asc-devkit仓库 |
| CANN | CANN 9.2.0，以环境变量配置的安装路径为准 |
| 支持产品 | Ascend 950PR、Ascend 950DT |
| NPU架构 | `dav-3510` |
| 运行模式 | NPU、仿真 |
| Kernel形态 | `__global__ __mix__(1, 2)` |

C API当前没有与`AscendC::GetSsbufBaseAddr()`同名的接口。在`dav-3510` NPU上，`__ssbuf__`地址空间的零地址就是SSBuffer基址，因此样例使用`reinterpret_cast<__ssbuf__ SsbufWorkspace*>(0)`取得工作区。这里的0不是普通的空指针，后续指针也必须一直保留`__ssbuf__`限定，不能转成GM地址使用。

在本样例使用的`dav-3510`编译环境中，不支持直接声明带`__ssbuf__`限定的数组，也不支持让`__ssbuf__`修饰指向数组类型的指针。样例把二维数组声明为`SsbufWorkspace`的成员，再通过`__ssbuf__ SsbufWorkspace*`把结构体布局映射到SSBuffer基地址。也可以在Local Memory中声明一个由`__ssbuf__ CommMessage*`组成的指针数组，但需要自行计算消息队列偏移。具体写法和限制请参见[基础知识](./basics.md#c-api下获取ssbuffer地址)。

显式读写SSBuffer不需要设置`ENABLE_CV_COMM_VIA_SSBUF`。该编译选项用于框架管理的内部KFC路径或UB到L1 Buffer硬通道，不是这套自定义消息协议的开关。公开的KFC资源分组接口使用GM上的`KfcWorkspace`，也不能当作获取SSBuffer基地址的接口。

## 涉及领域

| 领域 | 本需求关注点 |
| --- | --- |
| CV融合与Mix任务 | 一个AIC和两个AIV随同一个任务启动，并在任务内完成通信。 |
| SSBuffer空间规划 | 在3KB范围内划分两条互不重叠的消息队列，固定单条消息占用空间并保证对齐。 |
| C API系统接口 | 使用`asc_init`初始化NPU控制状态，使用`asc_get_sub_block_id`区分AIV0和AIV1。 |
| 核间同步 | 使用模式4的`asc_sync_intra_arrive`和`asc_sync_intra_wait`传递启动、消息准备完成和ACK通知。 |
| 消息状态管理 | 使用`valid`位检查消息状态，使用清零消息头和ACK通知释放消息空间。 |
| Host运行与校验 | 申请输出内存、启动一个Mix block、回读24条结果并逐条检查。 |
| 编译与运行 | 通过CMake指定`dav-3510`，支持`npu`和`sim`运行模式。 |

## 方案详述

### 1. 总体流程

整个过程并不复杂：AIC先把共享区域清理干净，再让两个AIV开始发送消息。

```text
AIC：清理消息头 -> 发送启动通知 -> 等待消息通知 -> 读取并校验 -> 返回ACK
                           |                 ^                         |
                           v                 |                         v
AIV0/AIV1：          等待启动通知 -> 写消息并发送通知 ---------> 等待ACK后复用消息空间
```

启动通知保证AIV不会过早访问未清理的消息队列。进入收发阶段后，每条消息都需要一组消息准备完成通知和ACK通知；`valid`位用于检查消息状态是否符合协议，不能用一次启动同步代替整段收发流程。

### 2. SSBuffer布局

每条消息占用128B，结构如下：

| 字段 | 作用 |
| --- | --- |
| `head` | 保存功能号、`valid`位和发送方编号，是消息是否可读的判断入口。 |
| `reserved0` | 与`head`一起占据前8B，AIC返回ACK时一并清零。 |
| `sequence` | 消息序号，用来识别队列回绕后读到的是不是当前期待的消息。 |
| `value` | 本次要传递的示例数据。实际使用时可换成地址、长度或其他短控制信息。 |
| `checksum` | 根据发送方、序号和消息数据计算，用来发现消息内容不完整或进入错误队列。 |
| `reserved` | 补齐单条消息占用空间，为后续扩展预留空间。 |

`head`按下面的方式组织：高16位存放固定功能号`0x5A01`，bit 15为`valid`位，低8位保存发送方编号。AIV0和AIV1分别使用编号0和1。

空间分配为：

```text
SSBuffer [0, 1024)       AIV0队列：8 x 128B
SSBuffer [1024, 2048)    AIV1队列：8 x 128B
SSBuffer [2048, 3072)    当前方案不使用
```

实现中需要保留`alignas(128)`，消息结构和工作区的大小由类型定义确定。跨核读写的字段使用`volatile`，SSBuffer访问还要遵守资料中的32B对齐要求。以后如果调整字段、单条消息大小或队列深度，需要重新检查结构布局、访问地址和总容量，不能只修改常量后直接沿用。

2KB、队列深度8和每条消息128B都是本样例选定的协议参数，并不是SSBuffer的固定规格。真正不能改变的是：总访问范围不能超过3KB，空间之间不能重叠，访问方式必须满足对齐要求。

### 3. 启动和初始化

Kernel入口先调用`asc_init()`，把当前AI Core上可能由前序算子留下的控制状态恢复到约定值。这个接口不会清零SSBuffer，所以队列仍要单独初始化。

AIC是唯一的初始化方。它遍历两条消息队列，把16条消息的消息头清零，然后分别向AIV0和AIV1发送启动通知：

```cpp
asc_sync_intra_arrive(PIPE_S, get_aic_sync_id(0, START_SYNC_ID));
asc_sync_intra_arrive(PIPE_S, get_aic_sync_id(1, START_SYNC_ID));
```

两个AIV都在下面的等待返回后再访问消息队列：

```cpp
asc_sync_intra_wait(PIPE_S, START_SYNC_ID);
```

这组接口属于核间同步，对应模式4。AIC与每个AIV单独配对：AIC侧ID 2映射到AIV0的ID 2，AIC侧ID 18映射到AIV1的ID 2。`PIPE_S`表示通知和等待都与前后的Scalar访问建立先后关系。

### 4. AIV发送消息

每个AIV通过`asc_get_sub_block_id()`取得自己的编号，并据此进入独立消息队列。发送第`sequence`条消息时，队列位置计算方式为：

```cpp
queueIndex = sequence & (QUEUE_DEPTH - 1);
```

该写法成立的前提是`QUEUE_DEPTH`为2的幂，当前取值8满足要求。如果以后把队列深度改成其他值，需要继续保持2的幂，或者改用取模计算，并补上相应检查。

队列回绕是指消息序号超过队列深度后，新的消息重新使用队列开头的存储位置。回绕不会重置消息序号。当前队列深度为8，因此序号0～7映射到位置0～7，序号8～11再次映射到位置0～3。

发送顺序必须保持为：

1. 前8条消息使用新的消息空间，可以直接写入；第9条消息开始，先等待一个ACK通知。
2. 写入`sequence`、`value`、`checksum`和`head`。
3. 调用`asc_sync_intra_arrive(PIPE_S, MESSAGE_READY_SYNC_ID)`，通知AIC消息已经准备完成。

序号0和序号8都会使用位置0，但AIV发送序号8前必须收到序号0对应的ACK。这样可以保证AIC已经读完旧消息并释放该位置，不会发生覆盖。全部12条消息发送完后，AIV还要等待剩余8个ACK，确认所有消息都已处理后才能结束。

### 5. AIC接收消息

AIC按“发送方编号、消息序号”的顺序接收。对每一条期望消息，它先等待对应AIV的消息准备完成通知，再找到队列位置，读取消息体并检查：

- 功能号是否为`0x5A01`。
- 发送方编号是否与当前队列一致。
- 消息序号是否为当前期待值。
- 校验值是否能由发送方、序号和消息数据重新计算得到。

检查结果和消息内容写入GM中的`CommResult`，供Host侧再次确认。处理完成后，AIC清零消息头前8B，并调用`asc_sync_intra_arrive(PIPE_S, MESSAGE_ACK_SYNC_ID)`返回ACK，表示该消息空间可以再次使用。

当前样例先收完AIV0的12条消息，再处理AIV1。因为两条消息队列互不重叠，AIV1最多先发布8条消息，然后等待ACK，不会挡住AIV0继续前进。不过，这种固定顺序可能让AIV1等待得更久。如果实际业务更看重两个AIV的响应时间，可以在不改变消息协议的前提下改成轮流接收两条消息队列。

样例不使用自定义编译器屏障。跨核共享字段通过`volatile`保持实际访存，消息准备完成和空间复用则通过模式4核间同步完成。`asc_sync_pipe`和`asc_sync_data_barrier`属于核内同步，前者不支持`PIPE_S`，后者只覆盖GM和UB，不能用于这段SSBuffer消息交接。

### 6. Host侧运行和结果检查

Host侧申请24条`CommResult`的输出空间，其中2表示AIV数量，12表示每个AIV发送的消息数。随后只启动一个Mix block：

```cpp
c_api_ssbuf_aiv_aic_comm<<<1, 0, stream>>>(output_device);
```

流同步完成后，将结果从Device侧GM拷回Host侧。每条结果都要检查`valid`、`sender`、`sequence`、`value`和`checksum`。全部匹配时输出`test pass!`，任意一条不匹配都要给出发送方、序号和实际结果，方便定位是哪一个队列位置或哪一次回绕出了问题。

### 7. 编译和使用约束

- CMake中的`CMAKE_ASC_ARCHITECTURES`固定为`dav-3510`，其他架构应在配置阶段直接报错。
- `CMAKE_ASC_RUN_MODE`只接受`npu`或`sim`。
- AIC和AIV必须随同一个任务启动，不能让不同任务访问同一SSBuffer。
- 不允许通过越过3KB末端的访问来探测容量，也不允许使用不满足对齐要求的地址。
- 同一任务内不能让这套消息队列与内部KFC、Matmul高阶API或其他SSBuffer协议各自占用未经协调的空间。
- 模式4核间同步计数器最多连续累加15次。队列深度和收发节奏需要保证未消费的消息通知和ACK通知不超过该上限。
- 只要消息数量、消息队列归属、同步ID映射或退出条件不一致，任务就可能一直等待。因此这些参数应由同一份协议定义，不应在AIC和AIV两侧分别维护。

### 8. 验收标准

满足以下条件，可认为需求实现完整：

1. 在Ascend 950PR或Ascend 950DT上，以`dav-3510`编译并在NPU或仿真模式运行成功。
2. 两个AIV各发送12条消息，AIC共接收24条，Host侧逐条校验全部通过。
3. 第9至第12条消息可以正确复用消息队列的前4个位置，没有覆盖尚未消费的数据。
4. 连续启动任务时，AIC每次都会先清理消息头，不会把SSBuffer中的旧内容当作新消息。
5. 两条消息队列始终位于SSBuffer前2KB，所有布局和访问满足容量及对齐约束。
6. 不依赖内部KFC头文件或接口，也不要求开启`ENABLE_CV_COMM_VIA_SSBUF`。
7. 启动、消息准备完成和ACK均使用配对的模式4核间同步接口，不使用自定义编译器屏障。
8. 配置为非`dav-3510`架构或非`npu`/`sim`模式时，构建阶段能给出清楚的错误信息。

# 编译过程调试

> 类型：扩展

算子工程编译涉及代码生成、Host 侧编译、Kernel 侧编译、打包部署四个阶段，默认输出通常不足以定位根因。下文按阶段介绍调试手段，并附常见错误的诊断方法。

## 1 生成代码调试

`npu_op_code_gen` 在 cmake configure 阶段自动生成 aclnn 调用代码和算子原型定义代码。生成产物位于 `ASCEND_AUTOGEN_PATH` 目录，默认是 `<CMAKE_BINARY_DIR>/autogen`；按本文示例使用 `build_out` 时，对应目录为 `build_out/autogen`。当原型定义有误或生成结果与预期不符时，需要检查这些文件。

### 1.1 生成产物目录

以 AddCustom 工程为例，配置完成后 `build_out/autogen/` 下会生成 aclnn 调用代码、算子原型定义代码和若干编译配置文件。多算子工程会为每个算子生成对应的 `aclnn_<op>.cpp` 和 `aclnn_<op>.h`。

```
build_out/autogen/
├── aclnn_add_custom.cpp      // aclnn 调用代码实现
├── aclnn_add_custom.h        // aclnn 调用代码头文件
├── op_proto.cc               // 算子原型定义代码（入图用）
├── op_proto.h                // 算子原型定义头文件
├── aic-<soc>-ops-info.ini    // 指定芯片型号的算子信息
├── custom_compile_options.ini
└── custom_opc_options.ini
```



### 1.2 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| aclnn 接口参数与原型定义不匹配 | 检查 `aclnn_<op>.h` 中的函数签名，确认输入输出和属性参数是否正确映射 |
| 入图场景算子注册信息异常 | 检查 `op_proto.cc` 中的注册宏，确认 OpType、dtype/format 是否与 Host 侧定义一致 |
| 某个算子的调用代码未生成 | 检查 `npu_op_code_gen` 的 `SRC` 参数是否包含了该算子的 Host 侧源文件 |
| JOIN_OP_DEF 导致部分芯片型号缺失 | `JOIN_OP_DEF=True` 时仅编译原型注册和 CMakePresets.json 中共有的芯片型号，确认 AddConfig 是否覆盖了目标型号 |

### 1.3 强制重新生成

`ASCEND_AUTOGEN_PATH` 目录下的生成文件在每次 configure 时会清空并重新生成。如果怀疑生成文件残留导致问题，可以手动清理后重新 configure：

```bash
rm -rf build_out/autogen
cmake -S . -B build_out --preset=default
```

## 2 Host 侧编译调试

Host 侧使用标准 cmake 构建系统，默认只输出编译目标的摘要信息，不显示实际执行的编译和链接命令。通过 VERBOSE 机制可以打印完整的命令行，用于排查头文件路径、链接库、编译选项等问题。

### 2.1 方式一：构建时开启 verbose

在构建命令中指定 verbose，打印每条编译和链接命令：

```bash
cmake --build build_out --target binary package --verbose -j$(nproc)
```

输出示例：

```
[ 10%] Building CXX object op_host/CMakeFiles/cust_opapi.dir/.../aclnn_add_custom.cpp.o
/usr/bin/c++ -Dcust_opapi_EXPORTS -I/usr/local/Ascend/cann/include ... -fvisibility=hidden -o aclnn_add_custom.cpp.o -c aclnn_add_custom.cpp
```

每行输出包含完整的编译器调用，可以看到：
- 实际的编译器路径（如 `/usr/bin/c++`）
- 宏定义（`-D`）和头文件搜索路径（`-I`）
- 编译选项（如 `-fvisibility=hidden`、`-g`、`-O2`）
- 链接库路径（`-L`）和链接库（`-l`）

### 2.2 方式二：cmake 配置 CMAKE_VERBOSE_MAKEFILE

在 cmake configure 阶段开启 verbose，后续所有 make 调用都会自动打印完整命令：

```bash
cmake -S . -B build_out --preset=default -DCMAKE_VERBOSE_MAKEFILE=ON
cmake --build build_out --target binary package -j$(nproc)
```

与方式一效果相同，区别在于设置持久化在 CMakeCache.txt 中，无需每次构建时重复指定。

### 2.3 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| 头文件找不到 | `-I` 路径是否包含目标头文件所在目录 |
| 链接 undefined reference | `-L` 和 `-l` 是否包含缺失符号所在的库 |
| 符号不可见 | `-fvisibility=hidden` 是否意外隐藏了需要导出的符号 |
| 编译选项冲突 | 同一目标是否被多次添加矛盾的选项（如同时 `-O2` 和 `-O0`） |

## 3 Kernel 侧编译调试

Kernel 侧由编译框架为每个算子调用毕昇编译器，默认不保留中间产物。通过 `--save-temp-files` 选项可以保留每次编译的中间文件，用于排查预处理、编译、链接各阶段的问题。

### 3.1 开启方法

在 Kernel 侧 CMakeLists.txt 中，通过 `npu_op_kernel_options` 添加 `--save-temp-files` 选项：

```cmake
# 为所有算子开启
npu_op_kernel_options(ascendc_kernels ALL OPTIONS --save-temp-files)

# 仅对特定算子开启
npu_op_kernel_options(ascendc_kernels AddCustom OPTIONS --save-temp-files)
```

也可以同时添加 `-g` 生成调试信息，配合使用：

```cmake
npu_op_kernel_options(ascendc_kernels ALL OPTIONS --save-temp-files -g)
```

### 3.2 保留的中间产物

开启后，编译框架会在构建目录下保留每个 kernel 编译过程的中间文件。例如本文在 ascend910b 上验证的 AddCustom 工程中，临时文件位于：

```
build_out/op_kernel/AddCustom_ascend910b/kernel_*/kernel_meta_<kernel_name>/kernel_meta/
```

实际目录名会随 OpType、芯片型号和 kernel 名称变化。常见文件包括：

- **预处理文件**（`.i`）：预处理后的源码，可用于确认宏展开是否正确、头文件是否被正确包含
- **目标文件**（`.o`）：链接前的目标文件，可用于确认符号是否正确导出
- **编译日志**（`.log`）：单个 kernel 的编译日志，可用于查看编译器调用和诊断信息
- **生成源码**（`*_kernel.cpp`、`*_tiling_data.h` 等）：编译框架生成的 kernel 源码和 Tiling 数据结构文件


### 3.3 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| 宏定义未生效 | 检查 `.i` 文件，确认宏是否被正确展开 |
| 头文件包含缺失 | 检查 `.i` 文件，确认目标头文件的内容是否被引入 |
| 模板实例化错误 | 检查 `.i` 文件中的模板展开结果，确认参数是否正确传递 |
| 链接符号缺失 | 检查 `.o` 文件的符号表（`nm` 命令），确认目标符号是否存在 |

### 3.4 部分芯片编译失败处理

当 `ASCEND_COMPUTE_UNIT` 配置了多个芯片型号时，kernel 编译会对每个芯片独立执行一轮。如果某个芯片的 kernel 编译失败，默认行为是终止整个构建流程。

`ASCEND_SKIP_FAILED_COMPUTE_UNIT` 选项允许跳过单个芯片的编译失败，继续编译其余芯片。适用场景：

- 算子对某些芯片型号尚不完全适配，但其他型号已可正常使用
- `npu_op_code_gen` 的 `JOIN_OP_DEF` 参数设为 False 时，可能编译更多芯片型号的算子，其中部分型号可能缺少适配

**配置方法**：在 CMakeLists.txt 中设置：

```cmake
set(ASCEND_SKIP_FAILED_COMPUTE_UNIT TRUE)
```

或在 cmake 命令行中传入：

```bash
cmake -S . -B build_out --preset=default -DASCEND_SKIP_FAILED_COMPUTE_UNIT=TRUE
```

默认值为 FALSE。

开启该选项后，部分 AI 处理器型号对应的算子编译失败时，编译流程可跳过失败项并继续编译其他型号；关闭时，遇到失败会影响其他型号的编译流程。若需要定位被跳过的失败项，建议同时配置 `ASCENDC_BUILD_LOG_DIR` 保存编译日志。

## 4 打包与部署调试

打包阶段将编译产物组织为 `.run` 安装包，部署阶段将算子包安装到目标环境。打包或安装出问题时，检查中间产物和打包命令即可定位。

### 4.1 查看打包命令

与 Host 侧调试一样，使用 VERBOSE 机制可以看到实际的打包命令：

```bash
cmake --build build_out --target package --verbose -j$(nproc)
```

输出示例：

```
[100%] Generating CPack package
/usr/bin/cpack --config ./CPackConfig.cmake
```

可以看到 cpack 调用过程，用于排查打包配置问题。

### 4.2 检查编译产物目录

在打包或安装前，先检查编译产物目录，确认单算子 API 头文件、动态库、Kernel 二进制和 Tiling 库等是否已生成。不同编译方式下目录结构会有差异。

`TYPE RUN` 模式下，原始构建目录中主要检查中间产物：

```
build_out/
├── autogen/
│   └── aclnn_add_custom.h
├── op_host/
│   ├── libcust_opapi.so
│   ├── libcust_opmaster_rt2.0.so
│   └── libcust_opsproto_rt2.0.so
└── op_kernel/ascendc_kernels/binary/
    ├── ascend910b/
    │   └── add_custom/
    ├── config/ascend910b/
    └── dynamic/
```

执行 `package` 目标后，CPack staging 目录中会出现接近安装后形态的 `vendors/<vendor_name>/` 目录，可重点检查 `op_api/`、`op_impl/`、`op_proto/`：

```
build_out/_CPack_Packages/Linux/External/custom_opp_*.run/packages/vendors/<vendor_name>/
├── op_api/
│   ├── include/aclnn_<op>.h
│   └── lib/libcust_opapi.so
├── op_impl/
│   └── ai_core/tbe/
└── op_proto/
    ├── inc/op_proto.h
    └── lib/linux/aarch64/libcust_opsproto_rt2.0.so
```

`TYPE SHARED` 或 `TYPE STATIC` 安装模式下，产物通常位于 `${CMAKE_INSTALL_PREFIX}/include` 和 `${CMAKE_INSTALL_PREFIX}/lib`。

**检查要点**：
- `build_out/autogen/` 或 staging 目录的 `op_api/include/` 下是否生成 `aclnn_<op>.h`
- `build_out/op_host/` 或 staging 目录的 `op_api/lib/` 下是否生成 `libcust_opapi.so`
- staging 目录或安装目录的 `op_impl` 下是否包含目标芯片型号的 Kernel 二进制和 Tiling 动态库
- 如果使用 SHARED/STATIC 模式，`ENABLE_BINARY_PACKAGE` 必须为 True

### 4.3 安装后验证内容

安装 `.run` 包后，可在安装目录下检查部署结果。默认安装场景检查：

```bash
ls ${INSTALL_DIR}/opp/vendors/<vendor_name>/op_api
ls ${INSTALL_DIR}/opp/vendors/<vendor_name>/op_impl
ls ${INSTALL_DIR}/opp/vendors/<vendor_name>/op_proto
```

指定目录安装场景检查：

```bash
ls <path>/vendors/<vendor_name>/op_api
ls <path>/vendors/<vendor_name>/op_impl
ls <path>/vendors/<vendor_name>/op_proto
```

### 4.4 常见排查场景

| 问题 | 查看什么 |
|------|---------|
| `package` 目标失败 | `cmake --build build_out --target package --verbose` 输出中 cpack 的命令和报错信息 |
| `.run` 包安装后缺少文件 | 安装目录下 `op_api`、`op_impl`、`op_proto` 等目录是否齐全 |
| `.run` 包中无 kernel binary | 安装目录下 `op_impl` 是否包含目标芯片型号对应的 Kernel 二进制 |
| SHARED/STATIC 模式下打包报错 | `npu_op_package` CONFIG 中 `ENABLE_BINARY_PACKAGE` 是否为 True |
| INSTALL_PATH 生成产物位置不对 | `npu_op_package` CONFIG 中 `INSTALL_PATH` 配置是否指向预期目录 |
| 安装后算子未被识别 | 指定目录安装时是否执行了 `source <path>/vendors/<vendor_name>/bin/set_env.bash`，默认安装时 `opp/vendors/config.ini` 中优先级配置是否正确 |

## 5 编译日志存盘

默认情况下，kernel 侧编译过程中的中间日志不会保留到磁盘，编译失败时终端仅打印异常抛出信息。通过设置 `ASCENDC_BUILD_LOG_DIR` 环境变量，可将每个编译阶段的日志写入指定目录，便于事后回溯。

**开启方法**：在执行 cmake 或 build.sh 之前设置环境变量：

```bash
export ASCENDC_BUILD_LOG_DIR=/home/build_log/
```

编译框架会在其下按芯片型号创建子目录。例如编译 `ascend910b` 和 `ascend910_93` 两个芯片时，日志目录结构为：

```
/home/build_log/
├── ascend910b/
└── ascend910_93/
```

**日志命名规则**：开启日志存盘后，编译框架会根据编译结果调整日志文件后缀：

- **编译成功**：对应日志文件后缀会添加 `_success`
- **编译失败**：终端会打印错误信息和对应日志文件路径，日志文件后缀会添加 `_error`

**从日志定位错误**：

1. 在终端报错中查看失败日志的具体路径，或在 `ASCENDC_BUILD_LOG_DIR` 对应芯片子目录下搜索带 `_error` 后缀的日志文件
2. 打开失败日志，查看毕昇编译器输出的错误信息
3. 根据错误中的文件名、行号或 API 提示回到源码修正

> [!NOTE] 与部分芯片编译失败处理的配合
> 开启 `ASCEND_SKIP_FAILED_COMPUTE_UNIT` 时，建议同时开启 `ASCENDC_BUILD_LOG_DIR`，两者配合使用可以完整保留每个失败 kernel 的详细编译日志，便于逐个修复。

## 6 常见编译错误诊断

算子工程编译涉及多个阶段：cmake 配置、opbuild 代码生成、Host 侧库编译、Kernel 侧逐芯片编译等。下表列出常见编译错误及解决方法。

### 6.1 常见编译错误及解决方法

**表 1** 常见编译错误及解决方法

| 错误现象 | 可能原因 | 解决方法 |
|---------|---------|---------|
| `Could not find a package configuration file provided by "ASC"` | 未执行 CANN 环境变量配置，或未设置 `ASCEND_CANN_PACKAGE_PATH` | 执行 CANN 安装目录下的 `set_env.sh`，或在 `CMakePresets.json`/cmake 命令中设置 `ASCEND_CANN_PACKAGE_PATH` |
| `ASCEND_COMPUTE_UNIT not set` | 未配置 AI 处理器型号 | 在 CMakePresets.json 中设置 `ASCEND_COMPUTE_UNIT` 为实际的 soc_version，参考 [soc_version 获取方法](../附录/soc_version获取方法.md) |
| `kernel compilation failed: unsupported soc_version` | soc_version 与实际硬件不匹配 | 使用 `npu-smi info` 命令查询正确的 soc_version |
| `undefined reference to 'aclnnXxxGetWorkspaceSize'` | 未开启二进制编译或编译产物不完整 | 确认 `ENABLE_BINARY_PACKAGE` 为 `True`，清理 build 目录后重新编译 |
| `template parameter mismatch` | `--kernel-template-input` 指定的模板参数与 kernel 入口或 host 侧定义不匹配 | 检查模板参数名称是否与 `ASCENDC_TPL_ARGS_DECL` 中的定义一致 |

### 6.2 详细错误诊断

#### 6.2.1 CANN CMake modules 未找到

**错误表现**：cmake 在执行 `find_package(ASC REQUIRED ...)` 时终止，常见报错如下：

```
Could not find a package configuration file provided by "ASC"
```

**根因**：未执行 CANN 环境变量配置，或 `ASCEND_CANN_PACKAGE_PATH` 未指向有效 CANN 安装目录。

**排查步骤**：

1. 检查环境变量是否已设置：`echo $ASCEND_HOME_PATH`、`echo $ASCEND_CANN_PACKAGE_PATH`
2. 检查路径是否存在：`ls ${ASCEND_CANN_PACKAGE_PATH}/compiler/tikcpp/ascendc_kernel_cmake/`
3. 若未设置，执行 CANN 安装目录下的 `set_env.sh`，或在 cmake 命令中传入 `-DASCEND_CANN_PACKAGE_PATH=<CANN安装路径>`
4. 重新执行 `cmake -S . -B build_out --preset=default`

#### 6.2.2 Kernel 编译失败

**错误表现**：`make` 过程中某个芯片型号的 kernel 编译目标失败，终端输出类似：

```
Kernel Compilation Error: OpType AddCustom KernelFile add_custom_kernel.cpp!
```

**根因**：kernel 源码存在语法错误、类型不匹配、API 用法错误、UB 越界等问题，或 tiling 库加载失败导致编译参数不正确。

**排查步骤**：

1. 如已开启 `ASCENDC_BUILD_LOG_DIR`，直接查看终端报错中提示的日志文件，或在对应芯片子目录下查找带 `_error` 后缀的日志
2. 如未开启日志存盘，可通过 `npu_op_kernel_options` 添加 `--save-temp-files` 选项保留中间产物
3. 检查预处理文件（`.i`）确认宏展开和头文件包含是否正确
4. 检查编译日志、生成源码和目标文件；如果实际目录中保留了汇编文件（`.s`），再结合汇编输出分析编译器生成结果

详细方法参考上文"Kernel 侧编译调试"章节。

#### 6.2.3 npu_op_code_gen 失败

**错误表现**：cmake configure 阶段报错：

```
CMake Error: opbuild run failed! <error_detail>
```

**根因**：`npu_op_code_gen` 函数在 cmake configure 阶段执行两步操作：先编译 `libascend_all_ops.so`，再调用 `opbuild` 从该库中提取算子信息并生成 aclnn 接口代码。失败通常发生在第一步。

**排查步骤**：

1. 查看 cmake configure 输出中 `compile ascend_all_ops` 相关的 error 信息
2. 检查 `op_host/CMakeLists.txt` 中 `npu_op_code_gen` 的 `SRC` 参数，确认列出的源文件都存在且路径正确
3. 检查 Host 侧源文件的算子原型注册代码，确认 `OP_PROTO` 和 `OP_TILING` 注册宏使用正确
4. 如果报错信息指向 `opbuild` 调用失败，检查 `${ASCEND_CANN_PACKAGE_PATH}/tools/opbuild/op_build` 是否存在且可执行

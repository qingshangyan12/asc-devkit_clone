# 基本流程

本文介绍Host侧Tiling在aclnn工程化算子开发方式中的基本编写流程。Host侧Tiling承接[算子功能设计](../算子功能设计.md)中的Tiling设计结论，把输入shape、属性和运行场景转换成Kernel启动前需要的参数。

## 1. Tiling概念回顾

AscendC算子在AI Core上执行时，通常无法一次性把全部输入数据搬入LocalMemory（UB）。Kernel需要先按可用AI Core数量和并行策略把总数据量分配到多个Block上（也称切核），再在单个Block内部继续切成多个Tile，每次搬入一部分数据进行计算，再把结果写回GlobalMemory，直到完成整份输入的处理。这个根据数据规模和硬件资源确定多核分配和Tile切分方式的过程，就是Tiling。

Tiling实现运行在HostCPU侧。它负责读取算子输入shape、输出shape、属性和平台信息，完成标量计算和策略选择，再把计算结果写回框架提供的`TilingContext`。这些结果会在后续Kernel启动、调度和Kernel侧计算中使用。

从数据流看，Host侧Tiling的输入和输出如下：

```text
输入：TilingContext中的输入shape、输出shape、属性、平台信息
  ↓
TilingFunc完成标量计算和策略选择
  ↓
输出：TilingData、numBlocks、workspace大小、TilingKey、调度模式等Kernel运行配置
```

`SetTiling`只负责建立算子原型与Tiling函数之间的关联。本文聚焦TilingData和Tiling函数的实现方法，aclnn两段式接口的调用方法见[单算子API调用](TBD)。

在aclnn工程化算子开发方式中，Host侧Tiling通常围绕三类动作展开：

- 读取信息：从`TilingContext`中读取shape、属性和平台信息。
- 计算参数：根据shape和属性计算总元素数、每核数据量、Tile数量和分支选择结果。
- 写回结果：把Kernel需要读取的参数写入`TilingData`，把Kernel启动需要的参数写入`numBlocks`、workspace大小、`TilingKey`和调度模式等Kernel运行配置。

## 2. 核心概念

Host侧Tiling的输出主要包括`TilingData`、`numBlocks`、workspace大小和`TilingKey`；不同运行场景还可能涉及调度模式（schedule mode）等Kernel launch配置。写代码前先理解这些输出，后面的流程会更容易对应。

### 2.1 TilingData

`TilingData`用于承载Host侧传给Kernel侧的切分参数。开发者根据Kernel实现需要自行设计字段。例如AddCustom基础样例中，Kernel侧需要知道总元素数和每个Block内部的Tile数量，因此`TilingData`只包含`totalLength`和`tileNum`两个字段。

在开始编写Tiling实现之前，首先需要定义`TilingData`结构体，用于存储切分算法相关参数。AscendC推荐使用**标准C++语法**定义Tiling结构体，这种方式更符合C++开发习惯，便于组织固定大小、可直接复制的字段，且允许不同算子使用同名结构体。字段类型、数组写法和Host/Kernel侧一致性约束见本文第4节。

> [!NOTE] 何时使用宏定义方式
> 标准C++结构体可以通过`AscendC::tiling`命名空间引用`kernel_tiling.h`中的框架预定义结构体，因此使用高阶API并不必然要求宏定义方式。具体API对Tiling结构体定义方式有特殊要求时，以对应API文档为准。维护使用`BEGIN_TILING_DATA_DEF`开发的旧项目时，也可以继续使用宏定义方式。

本文档以标准C++语法为主线介绍Tiling实现的基本流程。

### 2.2 numBlocks

`numBlocks`表示Kernel启动的逻辑Block数量。当前接口名为`context->SetBlockDim(...)`，本文把该接口设置的启动Block数量统一称为`numBlocks`。运行时会按照这个数量启动Block，Kernel侧再结合`GetBlockIdx()`和`GetBlockNum()`确定当前Block处理哪一段数据。

实际算子中，`numBlocks`通常需要结合输入总元素数、单个Block可处理的数据量、AI处理器上可用的核心数量、尾块处理方式和调度开销确定。AddCustom基础样例为了展示多Block并行写法，固定设置为8。

### 2.3 workspace大小

workspace是设备侧GlobalMemory上的临时内存，可用于保存算子计算过程中的中间结果，也可作为辅助Kernel或AscendC API在计算过程中需要的临时缓存。aclnn调用时，第一段接口会返回workspace大小，调用方据此申请workspace并传给第二段接口。

如果算子内部需要额外GlobalMemory缓存、需要为辅助Kernel准备临时空间，或调用的AscendC API需要系统workspace，需要在Tiling函数中计算workspace大小并写入`context->GetWorkspaceSizes(1)`返回的数组，设置方法如下：

```cpp
auto workspaceSizes = context->GetWorkspaceSizes(1); // 只使用1块workspace
workspaceSizes[0] = sysWorkspaceSize + usrWorkspaceSize;
```

在Kernel侧的获取和使用方法，请参考[Kernel侧算子实现](../Kernel侧算子实现/基本流程.md)。

### 2.4 TilingKey（可选）

`TilingKey`用于区分同一个算子的不同Kernel实现分支。Host侧Tiling根据shape、dtype、属性或运行场景选择一个数字标识，并通过`context->SetTilingKey(...)`写入上下文。Kernel侧和编译工具链会基于这个数字选择对应实现。

## 3. Tiling实现基本流程

AddCustom的Host侧Tiling实现可以按三个步骤理解：

1. 定义`TilingData`结构体，确定Host侧需要传给Kernel侧的字段。
2. 编写`TilingFunc`，读取shape并写入`TilingData`、`numBlocks`和workspace大小。
3. 在算子原型中通过`AICore().SetTiling(...)`关联Tiling函数。

### 3.1 定义TilingData结构体

AddCustom样例中的`TilingData`头文件位于：

```text
op_kernel/add_custom/add_custom_tiling.h
```

代码如下：

```cpp
#ifndef ADD_CUSTOM_TILING_H
#define ADD_CUSTOM_TILING_H
#include <cstdint>

struct AddCustomTilingData {
    uint32_t totalLength;
    uint32_t tileNum;
};

#endif // ADD_CUSTOM_TILING_H
```

字段含义如下：

| 字段 | 含义 | Kernel侧用途 |
|---|---|---|
| `totalLength` | 本次计算的总元素数 | 计算每个Block处理的数据范围 |
| `tileNum` | 每个Block内部的Tile数量 | 控制单个Block内部分轮搬运、计算和写回 |

结构体头文件放在`op_kernel`目录下，Host侧Tiling函数和Kernel侧实现都可以引用这个定义。

### 3.2 编写TilingFunc

AddCustom的Host侧实现文件位于：

```text
op_host/add_custom/add_custom_host.cpp
```

该文件中定义`optiling::TilingFunc`。算子原型通过`SetTiling(optiling::TilingFunc)`关联这个函数后，框架会在算子执行前调用它，并传入`gert::TilingContext* context`。

AddCustom样例代码如下：

```cpp
#include "../../op_kernel/add_custom/add_custom_tiling.h"
#include "register/op_def_registry.h"

namespace optiling {
const uint32_t NUM_BLOCKS = 8;
const uint32_t TILE_NUM = 8;

static ge::graphStatus TilingFunc(gert::TilingContext* context)
{
    AddCustomTilingData* tiling = context->GetTilingData<AddCustomTilingData>();
    uint32_t totalLength = context->GetInputShape(0)->GetOriginShape().GetShapeSize();
    context->SetBlockDim(NUM_BLOCKS);
    tiling->totalLength = totalLength;
    tiling->tileNum = TILE_NUM;
    size_t* currentWorkspace = context->GetWorkspaceSizes(1);
    currentWorkspace[0] = 0;
    return ge::GRAPH_SUCCESS;
}
} // namespace optiling
```

这段代码按以下步骤完成Tiling：

1. 通过`context->GetTilingData<AddCustomTilingData>()`获取`TilingData`指针。
2. 通过`context->GetInputShape(0)`获取第0个输入`x`的shape。
3. 通过`GetOriginShape().GetShapeSize()`计算输入`x`的总元素数。
4. 通过`context->SetBlockDim(NUM_BLOCKS)`设置Kernel启动的`numBlocks`。
5. 将`totalLength`和`tileNum`写入`TilingData`。
6. 通过`context->GetWorkspaceSizes(1)`获取workspace大小数组，并将第0块workspace设置为0。
7. 返回`ge::GRAPH_SUCCESS`表示Tiling执行成功。

标准C++结构体方式下，Host侧通过`GetTilingData<T>()`获取结构体指针并直接写字段，框架负责后续数据传递。Kernel侧读取方式会在[Kernel侧算子实现](../Kernel侧算子实现/基本流程.md)中说明。

### 3.3 关联算子原型

Tiling函数写好后，需要在算子原型定义中通过`AICore().SetTiling(...)`完成关联。AddCustom样例中的原型代码如下：

```cpp
this->AICore()
    .SetTiling(optiling::TilingFunc);
```

`SetTiling`建立算子原型和Host侧Tiling函数之间的调用关系。本文只说明`TilingFunc`内部如何准备Kernel运行参数，完整原型配置见[算子原型定义](../算子原型定义.md)。

## 4. 使用约束

使用标准C++语法定义`TilingData`结构体时，可以按代码形态检查。下面几类写法最容易影响Host侧和Kernel侧之间的数据传递。

### 4.1 避免定义成员函数

`TilingData`会同时被Host侧和Kernel侧使用。成员函数容易受到`__aicore__`修饰差异影响。

```cpp
struct AddCustomTilingData {
    uint32_t totalLength;
    uint32_t tileNum;

    __aicore__ void Init() { } // Host侧编译会受到__aicore__修饰影响
    void Reset() { }           // Kernel侧使用时缺少__aicore__修饰
};
```

### 4.2 避免使用指针和引用字段

Host侧写入`TilingData`时，写入内容需要能够被序列化并传到Kernel侧。指针和引用表达的是Host侧对象关系，传到Kernel侧后无法按原对象关系解析。

```cpp
struct AddCustomTilingData {
    uint32_t* totalLength; // 避免使用指针字段
    uint32_t& tileNum;     // 避免使用引用字段
};
```

### 4.3 字段类型保持简单

`TilingData`字段应使用大小在编译期确定、可以直接复制的类型，例如`uint32_t`、`int64_t`、`float`、`bool`和定长数组。指针、引用、动态容器以及包含虚函数或虚继承的复杂对象不适合作为`TilingData`字段。

```cpp
struct AddCustomTilingData {
    uint32_t totalLength;
    uint32_t tileNum;
    bool enableExtraPath;
    uint32_t tileSizes[8];
};
```

复杂对象和动态内存相关信息在Host侧Tiling函数中计算完成，再把Kernel侧需要的结果写成简单字段。

### 4.4 保持GetTilingData类型一致

`GetTilingData<T>()`中的类型`T`需要和实际写入的`TilingData`类型保持一致。Host侧和Kernel侧也需要引用同一个结构体定义。

```cpp
struct AddCustomTilingData {
    uint32_t totalLength;
    uint32_t tileNum;
};

struct OtherTilingData {
    uint32_t totalLength;
};

// 类型和当前算子实际使用的TilingData不一致，会导致数据解析异常
OtherTilingData* wrongTiling = context->GetTilingData<OtherTilingData>();
```

### 4.5 显式给字段赋值

`GetTilingData<T>()`获取到的结构体字段没有默认业务含义。Kernel侧后续会读取的字段，都需要在Host侧Tiling函数中显式赋值。

```cpp
AddCustomTilingData* tiling = context->GetTilingData<AddCustomTilingData>();
uint32_t totalLength = context->GetInputShape(0)->GetOriginShape().GetShapeSize();

tiling->totalLength = totalLength;
tiling->tileNum = TILE_NUM;
```

### 4.6 多模板参数使用using别名

如果`TilingData`使用多个模板参数，Kernel侧注册宏会把模板参数中的逗号识别成宏入参分隔符。此类场景先用`using`定义别名，再把别名传给注册宏。

```cpp
template<int32_t sizeA, int32_t sizeB>
struct AddCustomTilingData {
    uint32_t totalLength;
    uint32_t dataArray[sizeA][sizeB];
};

using AddCustomTiling = AddCustomTilingData<3, 5>;
REGISTER_TILING_DEFAULT(AddCustomTiling);
```

# 内存一致性

本文介绍NPU编程中的内存一致性问题，说明不同执行单元、不同AI Core、不同Stream以及Host侧和Device侧之间如何建立可预期的读写顺序。本文重点讨论“操作顺序和可见性”，缓存副本写回、失效等问题请参考[缓存一致性](缓存一致性.md)。

## 内存一致性的基本概念

### 什么是内存一致性

内存一致性关注的是多个访问者对同一片内存的读写顺序是否符合程序预期。典型内存一致性例子是：生产者先写数据再写标志，消费者看到标志后，是否一定能读取到生产者写入的数据：

```text
初始状态：
GM[data] = 0
GM[flag] = 0

时间点    生产者                                  消费者
======    ====================================    ====================================
T0        STORE data = 1
T1        STORE flag = 1
                                                T2  LOAD flag -> 1
                                                T3  LOAD data -> ?
```

用户期望内存序和代码顺序保持一致，在flag赋值之前，data已经赋值完成，期望消费者在`T2`看到`flag = 1`后，`T3`一定读取到`data = 1`。但是在NPU上，生产者和消费者可能运行在不同流水、不同AI Core、不同Stream，甚至位于Host侧和Device侧之间。不同执行域之间通常是乱序并行的，不会自动建立全局顺序，用户需要根据访问范围插入同步、内存栅栏或通信机制，自行管理内存一致性。

### 缓存一致性与内存一致性的区别

缓存一致性和内存一致性是两类不同问题：

| 类型 | 关注点 | 典型问题 | 常用处理方式 |
| --- | --- | --- | --- |
| 缓存一致性 | Cache副本和下一级存储中的值是否一致 | DCache中保留旧值，或Dirty副本尚未写回GM | DCCI |
| 内存一致性 | 多个读写操作之间的先后关系是否符合预期 | 消费者看到`flag = 1`后，是否一定能读取到生产者写入的`data` | 同步、DSB等 |

缓存一致性是“副本与最新值是否一致”，内存一致性是“指令实际执行顺序是否和代码顺序一致”。实际编程时，两类问题经常同时出现，例如生产者写入数据后通知消费者读取：

```text
初始状态：
GM[data] = 0
GM[flag] = 0
消费者DCache[data] = 0

时间点    生产者                                  消费者
======    ====================================    ====================================
T0        Scalar.STORE data = 1
T1        DCCI
T2        DSB_DDR
T3        STORE flag = 1
T4        通知消费者
                                                T5  等待通知
                                                T6  DCCI
                                                T7  Scalar.LOAD data -> 1
```

其中，DCCI用于维护缓存副本，保证缓存一致性；DSB用于等待前序内存访问完成，通知和等待用于建立生产者与消费者之间的执行顺序保证内存一致性。只做同步但不处理DCache副本，可能仍读到旧值；只做DCCI但不建立执行顺序，消费者也可能过早读取。缓存一致性或内存一致性任意一类问题没有处理好，都可能导致最终读取到的数据不符合预期。

### NPU内存序

#### 硬件执行层级与一致性边界

达芬奇架构中的执行具有多个层级的异步并行特征：
- Host侧通过Stream向Device侧异步下发任务；
- Device侧的一个Kernel可以由多个AI Core并行执行；
- 每个AI Core内部又存在多条可以异步并行执行的流水。

这些硬件层级决定了NPU编程中的内存一致性维护通常需要按访问范围分层处理：

- 同一AI Core内，不同流水访问同一地址或通过UB/GM传递数据时，需要核内同步。
- 不同AI Core之间，通过GM共享数据或传递标志时，需要核间同步。
- Host侧和Device侧之间，由于Kernel执行、异步拷贝和Stream任务下发都是异步的，需要Host-Device同步。

#### 流水间顺序

AI Core内部存在Scalar流水、MTE流水、Fixpipe流水和SIMT流水多个流水，它们负责不同类型的计算或访存任务，可以通过各自的数据通路访问GM。

不同流水之间默认显式并发，导致代码中的书写顺序不一定等于不同流水观察到的内存访问顺序。如果没有建立必要的同步关系，不同流水上的读写操作可能按照硬件调度和资源状态交错执行，导致RAW、WAW、WAR等场景下出现内存一致性问题。为了保证内存一致性，需要根据数据依赖插入同步机制：

- 跨流水存在数据依赖时，需要使用[asc_sync_notify](../../../../api/SIMD-API/C-API/sync/asc_sync_notify.md)/[asc_sync_wait](../../../../api/SIMD-API/C-API/sync/asc_sync_wait.md)、[asc_lock](../../../../api/SIMD-API/C-API/sync/asc_lock.md)/[asc_unlock](../../../../api/SIMD-API/C-API/sync/asc_unlock.md)等同步机制建立先后关系。

- 如果跨流水访问涉及Scalar或SIMT通过Cache访问GM，还需要额外考虑DCache或SIMT DCache中的旧副本、Dirty副本等[缓存一致性](缓存一致性.md)问题，必要时配合DCCI等Cache维护操作。

#### 流水内顺序

##### 单流水内的一致性保证

同一流水中的指令通常按代码书写顺序进入流水，按程序序顺序执行，这是硬件唯一提供的一致性保证。

但是这不代表后序指令开始执行时，前序指令的内存访问已经完成。如果前后指令访问同一地址或重叠地址，仍可能需要单流水同步。

##### Scalar流水

Scalar流水负责标量控制、地址计算、标量计算以及Scalar访存等操作。Scalar流水内的GM访问需要按地址和访问路径区分：

- 访问不同GM地址。不同地址之间没有天然的数据依赖，硬件不保证这些访问的完成顺序或对其他观察者的可见顺序与代码顺序一致。例如先写`data`、后写`flag`时，不能仅依赖代码顺序推断其他流水、其他AI Core或Host侧一定先看到`data`、再看到`flag`。如果后续逻辑依赖这种顺序，需要使用[asc_sync_data_barrier](../../../../api/SIMD-API/C-API/sync/asc_sync_data_barrier.md)等机制等待前序GM访问完成，并结合通知、原子或Host-Device同步建立可见性关系。
- 访问同一GM地址。普通Scalar通过DCache访问同一GM地址时，同地址访问顺序与程序序保持一致。但这不代表Dirty副本已经写回GM，也不代表其他流水或其他AI Core已经可见。如果同一地址访问中混用了不经过DCache的路径，例如[asc_store_dev](../../../../api/SIMD-API/C-API/scalar_compute/asc_store_dev.md)、[WriteGmByPassDCache](../../../../api/SIMD-API/基础API/标量计算/WriteGmByPassDCache_ISASI.md)等，硬件不保证最终执行结果一定符合代码顺序；需要在不经过DCache的写入前处理可能存在的DCache Dirty副本，并使用`asc_sync_data_barrier`等待前序操作完成。

##### MTE/Fixpipe流水

MTE/Fixpipe指令无论访问是否同地址，指令间内存访问的实际完成顺序或对外可见顺序可能与代码顺序不一致，硬件不保证内存一致性。

如果前后指令存在重叠地址或数据依赖，需要显式等待前序指令的数据读写完成。例如MTE2/MTE3搬运地址有重叠时，需要针对前序指令所在的流水进行同步：前序为MTE2搬运时使用`asc_sync_pipe(PIPE_MTE2)`，前序为MTE3搬运时使用`asc_sync_pipe(PIPE_MTE3)`，以保证前序搬运完成后再执行后序搬运；Fixpipe流水存在同类依赖时，也需要使用对应流水同步机制。

##### SIMT流水

SIMT流水用于SIMT编程模型中的线程级执行，适合复杂控制流和不规则访存场景。SIMT线程可以访问GM，也支持线程同步、内存栅栏和原子操作，相关接口请参考[SIMT编程模型](../../../../api/SIMT-API/SIMT编程简介/编程模型.md)和[SIMT同步与内存栅栏](../../../../api/SIMT-API/同步与内存栅栏/同步与内存栅栏简介.md)。

SIMT流水的顺序保证需要区分线程间和线程内：

- 线程间：不论访问是否为同一地址，不同SIMT线程之间，内存访问的实际完成顺序或对外可见顺序可能与代码顺序不一致，硬件不保证线程间内存一致性。跨线程、跨线程块或跨AI Core传递数据时，需要通过线程同步、内存栅栏、原子操作等机制建立可见性。
- 线程内：同一SIMT线程内访问不同地址时，硬件不保证不同地址访问顺序与代码顺序一致；同一SIMT线程内访问同一地址时，无论是否经过SIMT DCache，硬件保证执行结果与代码顺序一致。

### NPU内存一致性与标准一致性模型的关系

从经典并行体系结构的一致性模型看，NPU不提供全局顺序一致性，也不提供类似全存储排序的强内存序。

| 经典并行体系结构的一致性模型 | 模型特征 | NPU是否支持及NPU上的特征 |
| --- | --- | --- |
| 顺序一致性（Sequential Consistency，SC） | 所有处理单元观察到的内存访问结果，好像来自一个全局唯一顺序，且每个处理单元内部顺序与程序序一致。 | 不支持。NPU默认没有全局唯一读写顺序，不能假设所有流水、AI Core、Stream和Host侧按同一顺序观察到所有写入。 |
| 全存储排序（Total Store Order，TSO） | 写操作通常按全局存储顺序对外可见，模型强于弱一致性，弱于严格顺序一致性。 | 不支持。NPU不保证普通写操作按全局存储顺序对所有观察者可见，写入完成和对外可见需要结合DSB、同步或内存栅栏处理。 |
| 弱一致性（Weak Consistency） | 普通读写可以重排或延迟可见，只有同步、栅栏等特殊操作前后才建立明确顺序。 | 类似。NPU普通内存访问默认不建立跨执行域顺序，需要通过核内同步、核间同步、Stream/Event同步、Host-Device同步、DSB等机制显式约束访问完成顺序和可见性。 |
| Release/Acquire一致性 | 生产者用Release发布数据，消费者用Acquire获取数据；Release之前的写入在Acquire之后对消费者可见。 | 支持类似语义。NPU上通常通过[asc_sync_notify](../../../../api/SIMD-API/C-API/sync/asc_sync_notify.md)和[asc_sync_wait](../../../../api/SIMD-API/C-API/sync/asc_sync_wait.md)的组合建立Release/Acquire关系。 |

NPU更接近弱一致性模型：普通内存访问默认只具备有限的局部顺序，跨流水、跨核、跨Stream以及Host-Device之间的顺序需要用户显式建立。

### 同步、内存栅栏、Cache维护的区别

NPU编程中容易混淆同步、内存栅栏和Cache维护。三者解决的问题不同：

| 机制 | 解决的问题 | 不能替代的机制 |
| --- | --- | --- |
| 同步事件 | 建立两个执行单元之间的先后关系，例如MTE2完成后V才能计算 | 不能自动清理DCache旧副本 |
| DSB | 等待前序内存访问指令完成，例如等待GM或UB访问完成 | 不能通知其他核或其他Stream开始执行 |
| DCCI | 写回Dirty副本或失效旧副本 | 不能建立生产者和消费者之间的执行先后 |
| 原子操作 | 保证同一地址读-改-写过程不可分割 | 不保证普通数据访问的发布/获取顺序 |

因此，判断一致性问题时建议根据三个问题处理：

- 是否存在执行顺序依赖？如果存在，需要同步。
- 是否需要等待前序内存访问真正完成？如果需要，需要DSB。
- 是否涉及DCache旧副本或Dirty副本？如果涉及，需要DCCI。

## 核内内存一致性

### 核内一致性问题

本节讨论同一AI Core内，不同流水或SIMT线程之间如何建立可预期的访问顺序。这里的“核内”指生产者和消费者都在同一个AI Core内，但访问对象可以是UB、L1、L0等核内存储，也可以是由该AI Core发起访问的GM地址。

核内一致性问题通常来自两类场景：

- 不同流水之间通过同一块Buffer传递数据，例如MTE2把GM数据搬入UB后，Vector流水读取UB进行计算。
- 同一流水或SIMT线程前后访问同一地址、重叠地址，后序访问依赖前序访问真正完成。

因此，处理核内一致性时，首先要判断前序访问和后序访问分别位于哪个执行单元，再判断二者之间是RAW、WAW还是WAR依赖。若访问路径涉及DCache或SIMT DCache，还需要同时参考[缓存一致性](缓存一致性.md)处理Cache副本问题。

| 依赖类型 | 含义 | 示例 |
| --- | --- | --- |
| RAW | 先写后读，读操作必须读取前序写入的数据 | MTE2先写UB，Vector后读UB |
| WAW | 先写后写，最终结果必须以后一次写为准 | 两次MTE2搬运写入重叠UB地址 |
| WAR | 先读后写，写操作不能覆盖前序读还未使用完的数据 | Vector还在读UB，MTE2准备复用同一UB空间 |


### 跨流水内存一致性

跨流水依赖指前序访问和后序访问不在同一条流水上。不同流水默认可以并行推进，因此代码中先写的搬运或计算不代表后序流水开始时数据已经可用。需要使用[asc_sync_notify](../../../../api/SIMD-API/C-API/sync/asc_sync_notify.md)/[asc_sync_wait](../../../../api/SIMD-API/C-API/sync/asc_sync_wait.md)完成跨流水同步。

以MTE2负责把数据从GM搬入UB，Vector流水负责读取UB并计算，MTE3负责把结果从UB搬出到GM为示例，展示因为跨流水导致的内存一致性问题：

#### 正向依赖

正向依赖指本次循环内部的生产者和消费者依赖，`MTE2 -> V -> MTE3`流程如下：

```text
时间点    MTE2流水                    V流水                       MTE3流水
======    ========================    ========================    ========================
T0        MTE2.STORE_UB
          // 将GM数据搬入UB

T1                                    WAIT MTE2
                                      // 等待MTE2写UB完成

T2                                    V.LOAD_UB
                                      V.STORE_UB
                                      // 读取UB输入并写入UB结果

T3                                                                WAIT V
                                                                  // 等待Vector写UB完成

T4                                                                MTE3.LOAD_UB
                                                                  MTE3.STORE_GM
                                                                  // 读取UB结果并搬出到GM
```

上面的抽象流程对应两个同步点：

- `MTE2 -> V`：MTE2写UB完成后，Vector才能读取UB。通常通过`asc_sync_notify(PIPE_MTE2, PIPE_V, event_id)`和`asc_sync_wait(PIPE_MTE2, PIPE_V, event_id)`建立顺序。
- `V -> MTE3`：Vector写UB完成后，MTE3才能读取UB并搬出到GM。通常通过`asc_sync_notify(PIPE_V, PIPE_MTE3, event_id)`和`asc_sync_wait(PIPE_V, PIPE_MTE3, event_id)`建立顺序。

如果省略第一个同步，Vector可能读取尚未搬入完成的UB数据；如果省略第二个同步，MTE3可能把尚未计算完成的结果搬出到GM。

#### 反向依赖

反向依赖出现在多次循环复用Buffer的场景中。正向依赖约束的是“本轮后序流水等待本轮前序流水”，例如本轮Vector等待本轮MTE2搬入完成；反向依赖约束的是“后续循环重新写入某块Buffer前，必须等待前序循环中最后一个使用该Buffer的流水完成访问”。

无论使用单Buffer还是[Double Buffer](../../../技术附录/概念原理和术语/性能优化技术原理/DoubleBuffer.md)，只要后续循环会重新写入某块Buffer，就需要同步保证一致性。单Buffer和Double Buffer区别在于同一块Buffer被复用的间隔不同：

| 场景 | Buffer复用关系 | 需要等待的位置 | 说明 |
| --- | --- | --- | --- |
| 单Buffer | Loop 1复用Loop 0的`buf` | Loop 1写`buf`前，等待Loop 0最后一个使用`buf`的流水完成 | 相邻循环之间存在反向依赖 |
| Double Buffer | Loop 0使用`buffer1`，Loop 1使用`buffer2`，Loop 2重新使用`buffer1` | Loop 2写`buffer1`前，等待Loop 0最后一个使用`buffer1`的流水完成 | 反向依赖仍存在，只是同一Buffer的复用间隔变长 |

如果不处理反向依赖，后续循环的写入可能覆盖前序循环仍在读取或搬出的数据，导致内存一致性问题。下面分别用单Buffer和Double Buffer说明。

##### 单Buffer示例

单Buffer场景中，相邻循环复用同一块Buffer。Loop 1开始向`buf`搬入前，必须等待Loop 0的MTE3完成搬出，才能保证Loop 0的结果正确写回GM。

```text
时间点    Loop 0                                  Loop 1
======    ====================================    ====================================
T0        MTE2.STORE_UB(buf)
          // 搬入本轮输入

T1        V.LOAD_UB(buf)
          V.STORE_UB(buf)
          // 读取本轮输入并写入本轮结果

T2        MTE3.LOAD_UB(buf)
          MTE3.STORE_GM
          // 搬出本轮结果

T3                                                WAIT MTE3
                                                  MTE2.STORE_UB(buf)
                                                  // 上一轮搬出完成后，下一轮才能复用buf搬入
```

上例中的`WAIT MTE3`就是反向同步点。它不是本轮`MTE2 -> V -> MTE3`的正向依赖，而是用于保证Loop 1复用`buf`前，Loop 0对`buf`的使用已经结束。

##### Double Buffer示例

```text
时间点    Loop 0                                  Loop 1                                  Loop 2
======    ====================================    ====================================    ====================================
T0        MTE2.STORE_UB(buffer1)
          // 搬入Loop 0输入

T1        WAIT MTE2
          V.LOAD_UB(buffer1)
          V.STORE_UB(buffer1)                    MTE2.STORE_UB(buffer2)
          // Loop 0计算                         // 搬入Loop 1输入，与Loop 0计算并行

T2        WAIT V
          MTE3.LOAD_UB(buffer1)
          MTE3.STORE_GM                          WAIT MTE2
          // 搬出Loop 0结果                     V.LOAD_UB(buffer2)
                                                  V.STORE_UB(buffer2)
                                                  // Loop 1计算

T3                                                WAIT V
                                                  MTE3.LOAD_UB(buffer2)
                                                  MTE3.STORE_GM                          WAIT MTE3
                                                  // 搬出Loop 1结果                     // 等待Loop 0已经完成buffer1搬出

T4                                                                                        MTE2.STORE_UB(buffer1)
                                                                                          // 重新复用buffer1搬入Loop 2输入
```

上例中的`WAIT MTE3`是Double Buffer场景下的反向同步点。它不是为了建立Loop 2内部`MTE2 -> V -> MTE3`的正向依赖，而是为了保证`buffer1`在被Loop 2重新写入前，Loop 0对`buffer1`的使用已经结束。

反向依赖时，无论是单Buffer还是Double Buffer，维护内存一致性的原则不变：谁先使用Buffer，谁在使用完成后通知；谁后复用Buffer，谁在复用前等待。

### 同流水内存一致性

MTE、Fixpipe、Vector、Cube同流水依赖指前序访问和后序访问位于同一条流水。同一流水中的指令按顺序执行，但这不代表后序指令开始执行时，前序指令的数据读写已经全部完成。如果前后指令访问同一地址或重叠地址，就可能产生RAW、WAW或WAR问题。

例如，同一条MTE2流水连续向UB中存在重叠的地址区域搬入数据，期望重叠区域以后一次搬入结果为准。如果不插入同流水同步，可能出现如下问题：

```text
时间点    MTE2流水
======    ====================================
T0        MTE2.STORE_UB(region0)
          // 第一次搬入，写入UB区域region0

T1        MTE2.STORE_UB(region1)
          // 第二次搬入，region1与region0存在重叠

T2        region0和region1的重叠区域结果不确定
          // 前一次搬入的数据读写尚未全部完成，后一次搬入已经开始
          // 重叠区域不一定以后一次搬入结果为准
```

为了保证重叠区域以后一次搬入结果为准，后一次写入开始前，需要等待前一次MTE2写UB完成：

```text
时间点    MTE2流水
======    ====================================
T0        MTE2.STORE_UB(region0)
          // 第一次搬入，写入UB区域region0

T1        WAIT MTE2
          // 等待前序MTE2写UB完成

T2        MTE2.STORE_UB(region1)
          // 第二次搬入，region1与region0存在重叠
```

这里的`WAIT MTE2`是同流水同步点，用于保证后一次写入发生在前一次写入完成之后，可以通过[asc_sync_pipe](../../../../api/SIMD-API/C-API/sync/asc_sync_pipe.md)完成这类同步。

`asc_sync_pipe(PIPE_ALL)`可以等待所有流水中所有先前提交的接口完成，但会扩大同步范围并影响性能。只需要约束单条流水时，优先选择具体流水，例如`PIPE_MTE2`、`PIPE_MTE3`、`PIPE_V`、`PIPE_M`或`PIPE_FIX`。

### Scalar访问的完成顺序

Scalar流水发起的GM或UB访问需要关注“访问是否完成”。例如先由Scalar写GM，再通知其他流水或其他执行单元读取时，不能只依赖代码顺序推断后续访问一定能看到前序Scalar写入。需要使用[asc_sync_data_barrier](../../../../api/SIMD-API/C-API/sync/asc_sync_data_barrier.md)等待前序内存访问完成：

```cpp
asc_store_dev(dataGm, 1);
asc_sync_data_barrier(mem_dsb_t::DSB_DDR);
```

`asc_sync_data_barrier`按等待范围选择参数：

| 参数 | 等待范围 | 典型场景 |
| --- | --- | --- |
| `DSB_DDR` | 等待前序GM访问完成 | Scalar写GM后，后续流水或同步标志依赖该写入 |
| `DSB_UB` | 等待前序UB访问完成 | Scalar访问UB后，后续本地流水依赖该访问 |
| `DSB_ALL` | 等待前序GM和UB访问完成 | 同时涉及GM和UB，或无法精确区分等待范围 |

需要注意，DSB只等待前序内存访问完成，不负责写回或失效DCache副本。如果Scalar普通写GM经过DCache，数据可能仍停留在DCache Dirty副本中；如果后续读取路径需要从GM获取新值，还需要按[缓存一致性](缓存一致性.md)执行DCCI并配合DSB。反过来，如果后续使用[asc_store_dev](../../../../api/SIMD-API/C-API/scalar_compute/asc_store_dev.md)等不经过DCache的写GM路径，也需要先处理同地址可能存在的DCache Dirty副本，避免前序Dirty副本后续写回覆盖新写入。

### SIMT线程内与线程间同步

SIMT流水的一致性问题需要区分线程内和线程间。

同一SIMT线程内访问同一地址时，无论是否经过SIMT DCache，硬件保证执行结果与代码顺序一致；同一线程访问不同地址时，如果后续逻辑要求不同地址之间形成“先写数据、后写标志”这类发布顺序，需要使用内存栅栏建立可见性顺序。

不同SIMT线程之间，不论是否访问同一地址，硬件不自动保证线程间内存一致性。线程间存在数据依赖时，需要根据同步范围选择SIMT同步接口：

| 场景 | 处理方式 | 说明 |
| --- | --- | --- |
| Thread Block内阶段同步 | [asc_syncthreads](../../../../api/SIMT-API/同步与内存栅栏/同步接口/asc_syncthreads.md) | 等待当前Thread Block内所有Thread到达同步点，并保证同步点前的内存操作对块内线程可见 |
| 当前Thread写入需要对Thread Block内其他Thread有序可见 | [asc_threadfence_block](../../../../api/SIMT-API/同步与内存栅栏/内存栅栏接口/asc_threadfence_block.md) | 只建立Block范围内的内存操作可见性顺序，不等待其他Thread |
| 当前Thread写入需要对更大范围有序可见 | [asc_threadfence](../../../../api/SIMT-API/同步与内存栅栏/内存栅栏接口/asc_threadfence.md) | 适合通过GM发布数据或标志的场景 |
| 多个Thread并发更新同一地址 | 原子操作 | 同步屏障和内存栅栏不能替代原子读-改-写 |

典型生产者-消费者场景中，生产者线程先写数据，再通过内存栅栏约束数据写入先于标志位更新对外可见；消费者线程仍需要通过轮询、原子操作或其他同步方式等待标志，内存栅栏本身不会让消费者等待。

```cpp
data[idx] = value;
asc_threadfence();
asc_atomic_exch(ready, 1U);
```

如果SIMT访问GM时使用SIMT DCache，还需要同时结合SIMT DCache与GM的[缓存一致性](缓存一致性.md)要求处理旧副本。

### 核内同步原语选择

核内常用同步原语如下：

| 接口 | 使用场景 | 说明 |
| --- | --- | --- |
| [asc_sync_notify](../../../../api/SIMD-API/C-API/sync/asc_sync_notify.md)/[asc_sync_wait](../../../../api/SIMD-API/C-API/sync/asc_sync_wait.md) | 不同流水之间存在依赖 | 通过源流水、目标流水和事件ID配对建立顺序 |
| [asc_sync_pipe](../../../../api/SIMD-API/C-API/sync/asc_sync_pipe.md) | 同一流水内部前后操作需要隔离 | 可等待指定流水前序指令完成，避免无差别使用`PIPE_ALL` |
| [asc_sync_data_barrier](../../../../api/SIMD-API/C-API/sync/asc_sync_data_barrier.md) | Scalar内存访问需要等待完成 | `DSB_DDR`等待GM访问，`DSB_UB`等待UB访问，`DSB_ALL`等待GM和UB访问 |
| [asc_lock](../../../../api/SIMD-API/C-API/sync/asc_lock.md)/[asc_unlock](../../../../api/SIMD-API/C-API/sync/asc_unlock.md) | 需要以内聚方式管理流水互斥 | 适合复杂流水同步协议，使用时需避免嵌套同一mutex_id |

选择同步原语时，建议按依赖范围判断：

- 只需要等待同一流水中的前序操作完成，优先使用`asc_sync_pipe(PIPE_xxx)`。
- 需要让目标流水等待源流水，使用`asc_sync_notify/asc_sync_wait`。
- 需要等待Scalar发起的内存访问完成，使用`asc_sync_data_barrier`。
- Kernel结束前如果需要确保所有流水任务完成，可以使用`asc_sync_pipe(PIPE_ALL)`。

### event_id管理

`asc_sync_notify`和`asc_sync_wait`通过事件ID关联。事件ID管理错误会导致死锁、未定义行为或同步串扰。使用时需要遵循以下原则：

- `asc_sync_notify`和`asc_sync_wait`必须成对使用，源流水、目标流水和事件ID必须一致。
- 相同源流水、相同目标流水、相同事件ID下，不应连续执行多次`asc_sync_notify`而没有对应`asc_sync_wait`消费。
- Double Buffer通常为ping/pong两组Buffer分配不同事件ID，避免两组Buffer的同步信号互相干扰。
- 如果某些高阶API或框架内部会使用事件ID，手写底层同步时需要避免与内部事件ID冲突。

示例：

```cpp
constexpr event_t PING_EVENT = EVENT_ID0;
constexpr event_t PONG_EVENT = EVENT_ID1;

event_t eventId = (loopIdx & 1) == 0 ? PING_EVENT : PONG_EVENT;
asc_sync_notify(PIPE_MTE2, PIPE_V, eventId);
asc_sync_wait(PIPE_MTE2, PIPE_V, eventId);
```

## 核间内存一致性

### 多核访问GM的顺序风险

不同AI Core访问同一段GM时，硬件不会自动为用户建立“哪个核先写、哪个核后读”的全局顺序。典型风险包括：

| 场景 | 期望 | 风险 |
| --- | --- | --- |
| RAW | 后读读取前写的新值 | 消费者过早读取，或读端命中旧Cache副本 |
| WAW | 最终GM中保留后写结果 | 前序写回或后序写入顺序不确定，后写可能被覆盖 |
| WAR | 前读读取后写之前的旧值 | 后写过早发生，破坏前读期望 |

核间一致性至少需要解决两个问题：

- 建立多核之间的执行顺序，例如生产者完成后消费者再开始；
- 如果访问路径涉及DCache，还要按[缓存一致性](缓存一致性.md)维护写端Dirty副本和读端旧副本。

### 核间同步屏障

核间同步用于让不同核在某个同步点对齐。C API提供多种同步接口，例如[asc_sync_inter_arrive](../../../../api/SIMD-API/C-API/sync/asc_sync_inter_arrive.md)/[asc_sync_inter_wait](../../../../api/SIMD-API/C-API/sync/asc_sync_inter_wait.md)、[asc_sync_block_arrive](../../../../api/SIMD-API/C-API/sync/asc_sync_block_arrive.md)/[asc_sync_block_wait](../../../../api/SIMD-API/C-API/sync/asc_sync_block_wait.md)等，具体应按Kernel类型和同步范围选择。

下面是一个简化的“一个生产者写数据，一个消费者等待后读取”的逻辑示例：

```cpp
uint32_t blockIdx = asc_get_block_idx();
constexpr int64_t flagId = 1;

if (blockIdx == 0) {
    // 生产者写GM数据。
    dataGm[0] = 1;
    asc_dcci_single(reinterpret_cast<__gm__ void*>(&dataGm[0]));
    asc_sync_data_barrier(mem_dsb_t::DSB_DDR);

    // 通知消费者所在同步范围：数据已经发布。
    asc_sync_inter_arrive(PIPE_V, flagId);
} else if (blockIdx == 1) {
    // 消费者等待生产者到达同步点。
    asc_sync_inter_wait(PIPE_V, flagId);

    // 如果本核可能有旧DCache副本，读取前先处理Cache。
    asc_dcci_single(reinterpret_cast<__gm__ void*>(&dataGm[0]));
    asc_sync_data_barrier(mem_dsb_t::DSB_DDR);
    int32_t value = dataGm[0];
}
```

上例只表达顺序关系，实际使用时需要确认所选核间同步接口的Kernel类型、flag_id范围、pipe支持范围、参与核数量和并发约束。若有多个消费者等待同一生产者，需要为同步计数、等待方数量和flag_id分配设计完整协议。

### 原子操作与顺序边界

原子操作保证的是同一地址上的读-改-写过程具有原子性。例如[asc_atomic_add](../../../../api/SIMD-API/C-API/scalar_compute/asc_atomic_add.md)可以保证多个执行单元对同一GM地址累加时不会丢失更新：

```cpp
asc_atomic_add(counterGm, 1);
```

但是原子操作不等价于完整的内存序。它不能自动保证普通数据写入已经对其他核可见，也不能保证其他地址上的读写与该原子操作形成固定顺序。

错误用法：

```cpp
// 生产者
dataGm[0] = 1;
asc_atomic_add(flagGm, 1);

// 消费者
while (asc_atomic_add(flagGm, 0) == 0) {
}
int32_t value = dataGm[0];
```

上面代码使用原子操作传递标志，但如果`dataGm[0]`经普通Scalar DCache路径写入，生产者还需要在发布标志前处理Cache并等待GM访问完成：

```cpp
dataGm[0] = 1;
asc_dcci_single(reinterpret_cast<__gm__ void*>(&dataGm[0]));
asc_sync_data_barrier(mem_dsb_t::DSB_DDR);
asc_atomic_add(flagGm, 1);
```

消费者看到标志后，如果本核DCache可能有`dataGm[0]`旧副本，也需要读前DCCI。

### 同步与Cache维护的配合

核间数据传递可以按“发布”和“获取”两个动作理解：

| 阶段 | 需要处理的问题 | 典型操作 |
| --- | --- | --- |
| 发布数据 | 生产者写入的数据是否已经到达共享可见位置 | 写数据后执行DCCI和DSB_DDR |
| 发布顺序 | 消费者是否会在生产者完成后再读 | 使用核间同步或原子标志 |
| 获取顺序 | 消费者是否已等待发布动作完成 | 等待同步标志或轮询原子标志 |
| 获取数据 | 消费者本核是否存在旧Cache副本 | 读前DCCI，再读取数据 |

因此，核间一致性不要只看是否调用了同步接口。若普通Scalar DCache路径参与读写，还必须结合缓存一致性维护。

## Host-Device内存一致性

### Host/Device独立内存空间

Host侧和Device侧拥有各自的内存空间。Host侧数据要供Device侧Kernel访问，需要通过Host到Device的内存拷贝写入Device内存；Device侧计算结果要供Host侧读取，需要通过Device到Host的内存拷贝复制回Host内存。

同步拷贝接口会阻塞Host线程直到拷贝完成：

```cpp
aclrtMemcpy(devPtr, size, hostPtr, size, ACL_MEMCPY_HOST_TO_DEVICE);
myKernel<<<blockNum, nullptr, stream>>>(devPtr);
aclrtSynchronizeStream(stream);
aclrtMemcpy(hostPtr, size, devPtr, size, ACL_MEMCPY_DEVICE_TO_HOST);
```

如果使用异步拷贝或异步Kernel下发，Host侧函数返回只表示任务已经下发，不表示任务已经执行完成。

### 异步下发与同Stream保序

带Stream参数的Runtime接口通常是异步接口。任务下发到同一个Stream后，Stream内任务按下发顺序执行：

```cpp
aclrtMemcpyAsync(devIn, size, hostIn, size, ACL_MEMCPY_HOST_TO_DEVICE, stream);
myKernel<<<blockNum, nullptr, stream>>>(devIn, devOut);
aclrtMemcpyAsync(hostOut, size, devOut, size, ACL_MEMCPY_DEVICE_TO_HOST, stream);
aclrtSynchronizeStream(stream);
```

这段代码的顺序含义是：

```text
Host->Device复制完成
Kernel读取devIn并写devOut
Device->Host复制devOut
Host等待Stream完成后读取hostOut
```

如果最后缺少`aclrtSynchronizeStream(stream)`，Host线程可能在Device到Host复制完成前读取`hostOut`。

### Host阻塞同步接口

Host侧常用显式同步接口包括：

| 接口 | 等待范围 | 典型场景 |
| --- | --- | --- |
| `aclrtSynchronizeStream(stream)` | 等待指定Stream中已下发任务完成 | 单Stream任务完成后读取结果 |
| `aclrtSynchronizeDevice()` | 等待当前Device当前Context下任务完成 | 需要等待当前Device上所有相关Stream完成 |
| `aclrtSynchronizeEvent(event)` | 等待指定Event完成 | 等待某个精确时间点 |
| `aclrtMemcpy` | 同步内存拷贝 | 拷贝完成后立即使用目的内存 |

同步范围应尽量精确。只需要等待某个Stream时，不建议使用Device级同步；只需要等待某个时间点时，可以使用Event同步。

### 跨Stream Event依赖

不同Stream之间默认可并行执行，不会因为Host侧下发顺序自动建立依赖。如果`stream2`中的任务依赖`stream1`的结果，需要使用Event：

```cpp
aclrtEvent event;
aclrtCreateEventExWithFlag(&event, ACL_EVENT_SYNC);

aclrtMemcpyAsync(devA, size, hostA, size, ACL_MEMCPY_HOST_TO_DEVICE, stream1);
producerKernel<<<blockNum, nullptr, stream1>>>(devA, devB);
aclrtRecordEvent(event, stream1);

aclrtStreamWaitEvent(stream2, event);
consumerKernel<<<blockNum, nullptr, stream2>>>(devB, devC);
aclrtMemcpyAsync(hostC, size, devC, size, ACL_MEMCPY_DEVICE_TO_HOST, stream2);

aclrtSynchronizeStream(stream2);
aclrtDestroyEvent(event);
```

`aclrtRecordEvent(event, stream1)`表示在`stream1`中记录一个时间点；`aclrtStreamWaitEvent(stream2, event)`表示`stream2`后续任务等待该时间点完成。这样可以只同步必要依赖，不阻塞无关Stream。

### 内存语义同步

内存语义同步基于Device内存中的值实现等待和写入，适合Stream任务和Kernel执行过程之间建立同步关系。Runtime提供`aclrtValueWait`和`aclrtValueWrite`，分别用于在Stream上等待某个Device内存值满足条件，或向某个Device内存写入值。

Host侧示例：

```cpp
void* syncMem = nullptr;
aclrtMalloc(&syncMem, sizeof(uint64_t), ACL_MEM_MALLOC_NORMAL_ONLY);
aclrtMemset(syncMem, sizeof(uint64_t), 0, sizeof(uint64_t));

// stream1等待syncMem变为1。
aclrtValueWait(syncMem, 1, ACL_STREAM_WAIT_VALUE_EQ, stream1);
consumerKernel<<<blockNum, nullptr, stream1>>>(dataGm);

// stream2执行生产者Kernel，Kernel内部或后续ValueWrite发布syncMem。
producerKernel<<<blockNum, nullptr, stream2>>>(dataGm);
aclrtValueWrite(syncMem, 1, 0, stream2);
```

Kernel侧如果直接写同步内存，需要注意该同步内存也是Device内存；如果通过普通Scalar路径写入，应按缓存一致性要求处理写回，并通过DSB等待写入完成。

## 常见错误

| 错误类型 | 典型表现 | 处理建议 |
| --- | --- | --- |
| 跨流水少同步 | Vector计算读到未搬入完成的UB数据 | 在MTE2和V之间使用`asc_sync_notify/asc_sync_wait` |
| 结果搬出过早 | MTE3搬出旧结果或未完成结果 | 在V和MTE3之间建立同步 |
| Buffer复用过早 | 下一轮搬入覆盖上一轮还在使用的数据 | 为复用Buffer建立反向同步 |
| 无差别使用`PIPE_ALL` | 功能正确但性能下降 | 优先使用具体流水或点对点同步 |
| 核间只同步不DCCI | 消费者等到了同步点但仍读到旧值 | 写端和读端按缓存一致性维护DCache |
| 原子操作当作全局内存序 | 标志已更新但普通数据仍不可见 | 原子前后配合DCCI、DSB和同步协议 |
| Host未等待Device完成 | Host读到未更新结果 | 使用`aclrtSynchronizeStream`或同步拷贝 |
| 跨Stream缺少Event | 消费者Stream先于生产者Stream执行 | 使用`aclrtRecordEvent`和`aclrtStreamWaitEvent` |

## 快速决策参考

遇到一致性问题时，可以按下面顺序判断：

| 问题 | 判断 | 推荐动作 |
| --- | --- | --- |
| 是否在同一AI Core内？ | 是 | 判断是否跨流水；跨流水使用`asc_sync_notify/asc_sync_wait` |
| 是否只涉及同一流水？ | 是 | 使用`asc_sync_pipe(PIPE_xxx)`等待前序操作完成 |
| 是否是Scalar内存访问完成性问题？ | 是 | 使用`asc_sync_data_barrier`，按GM或UB选择`DSB_DDR`或`DSB_UB` |
| 是否跨AI Core？ | 是 | 使用核间同步或原子标志建立顺序 |
| 是否涉及DCache？ | 是 | 同步前后配合DCCI，参考[缓存一致性](缓存一致性.md) |
| 是否跨Stream？ | 是 | 使用Event或内存语义同步 |
| Host是否要读取Device结果？ | 是 | 等待对应Stream、Event或使用同步D2H拷贝 |

## 总结

NPU内存一致性的核心不是“所有操作天然按代码顺序全局可见”，而是由用户在需要的位置建立顺序。核内需要处理多流水之间的依赖，核间需要处理多AI Core之间的同步和Cache可见性，Host-Device之间需要处理异步下发和显式等待。

可以把一致性维护概括为三步：

1. 确认访问者范围：同流水、跨流水、跨核、跨Stream或Host-Device。
2. 选择同步方式：流水同步、核间同步、Event、内存语义同步或Host阻塞同步。
3. 若访问路径涉及Cache副本，再配合DCCI和DSB保证数据真正对消费者可见。

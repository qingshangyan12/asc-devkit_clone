# 通用地址对齐约束证据

本文汇总通用地址对齐约束、各NPU架构对齐要求，以及3510架构Fixpipe Buffer分场景对齐要求的仓内证据。

## 一、通用地址对齐约束

文件：`docs/zh/api/SIMD-API/general_description_and_constraints.md`

### 1. 通用约束说明

第21行要求操作数起始地址满足所在存储单元的地址对齐要求，并将具体要求指向“通用地址对齐约束”。第23行同时说明不同产品、数据类型、接口和功能场景可能存在额外约束，具体API文档优先。

证据位置：

- [第21行](zh/api/SIMD-API/general_description_and_constraints.md:21)
- [第23行](zh/api/SIMD-API/general_description_and_constraints.md:23)

### 2. 通用地址对齐表

第113行将表格描述为各类存储单元的统一对齐要求，第119～127行给出以下值：

| 存储单元 | 通用文档中的对齐要求 |
| --- | --- |
| Global Memory | 无对齐要求 |
| UB | 32Byte |
| L1 Buffer | 32Byte |
| L0A Buffer/L0B Buffer | 512Byte |
| L0C Buffer | 64Byte |
| BiasTable Buffer | 64Byte |
| Fixpipe Buffer | 64Byte |

证据位置：

- [第113行](zh/api/SIMD-API/general_description_and_constraints.md:113)

### 3. 架构硬件约束中的差异说明

3510硬件约束明确补充了场景差异：

- L0C Buffer：Mmad计算时1024B对齐，矩阵计算搬出时64B对齐。
- Fixpipe Buffer：ReLU场景64B对齐，quant场景128B对齐。

证据：[3510硬件约束第13行](zh/guide/programming_guide/advanced_programming/hardware_implementation/hardware_constraints/npu_arch_3510.md:13)。

2201硬件约束将Fixpipe Buffer写为128Byte对齐：

证据：[2201硬件约束第16行](zh/guide/programming_guide/advanced_programming/hardware_implementation/hardware_constraints/npu_arch_2201.md:16)。

因此，通用表中的固定值不能覆盖所有架构、接口和功能场景。应以架构约束和具体接口文档中的更细粒度说明为准。

## 三、3510架构Fixpipe Buffer的两个对齐值

### 1. 两个值对应两个独立参数空间

3510的Fixpipe Buffer保存随路Vector量化参数和随路ReLU参数。两类参数使用相互独立的地址空间，由目的地址`dst[19:16]`区分，`dst[15:0]`表示对应空间内的偏移。

证据：[L1到Fixpipe Buffer数据搬运第3～7行](zh/api/SIMD-API/c_api/data_move_guide/l1_fixpipe_data_move.md:3)。

### 2. 参数空间和对齐要求

| 参数空间 | 地址选择 | 目的对齐 | 容量上限 |
| --- | --- | --- | --- |
| 随路Vector量化参数 | `dst[16]=0` | 128Byte | 4KB |
| 随路ReLU参数 | `dst[16]=1` | 64Byte | 2KB |

证据：[L1到Fixpipe Buffer数据搬运第9～14行](zh/api/SIMD-API/c_api/data_move_guide/l1_fixpipe_data_move.md:9)。其中第14行还明确要求两类参数的地址偏移分别计算，不能混用两个空间的末尾地址和起始地址。

### 3. 独立的通用对齐汇总

`docs/zh/api/SIMD-API/c_api/data_move_guide/overview/overall_constraints.md`已经按参数空间分别列出：

- Fixpipe Buffer量化参数空间：128字节对齐，容量上限4KB。
- Fixpipe Buffer ReLU参数空间：64字节对齐，容量上限2KB。

证据：[第11～22行](zh/api/SIMD-API/c_api/data_move_guide/overview/overall_constraints.md:11)。该处还特别说明架构基线不等于所有原型的最终约束，具体接口可能有不同要求。

## 四、结论

1. `general_description_and_constraints.md`已经考虑了“具体API约束优先”，但其通用表仍是固定值，未直接体现架构和场景差异。
2. `hardware_implementation`目录中存在架构级对齐说明，且3510、2201的硬件约束对Fixpipe有额外或更细粒度描述。
3. 3510的Fixpipe Buffer之所以同时出现64Byte和128Byte，是因为ReLU参数空间和量化参数空间彼此独立，分别对应不同的地址空间和容量，并非同一地址需要同时满足两个对齐值。
4. 查询具体接口时，应优先使用具体接口文档和对应架构、参数空间的约束，不能只依据通用表中的Fixpipe 64Byte结论。
